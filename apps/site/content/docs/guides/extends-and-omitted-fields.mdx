---
title: "Omitted fields and `extends`"
description: "How project configuration files combine when one extends another, and what changed for omitted values"
---

When a project `extends` other files, omni combines the files in order. A field
a file leaves out keeps the value from the files below it. A single-value field
a file states, even with its default value, overrides them. A plain list
replaces the inherited list; `append`, `prepend` and `merge` combine with it. A
plain dictionary combines with the inherited entries, so an empty `env.vars`
does not clear inherited variables; use `replace` to clear them. The
`only` and `except` lists under `redact` are an exception: they are always
combined, so a child's empty `except: []` does not remove entries inherited
from a file it extends. Defaults apply once, after every file has been
combined.

This is a behavior change from earlier versions, which filled in defaults for
each file before combining. Four cases are affected.

## `cache.output.logs` is no longer reset

`cache.output.logs` defaults to `true`. Earlier versions applied that default
to every extending file, so a file that did not mention it switched it back on.

```yaml
# base.omni.yaml
name: base
base: true
cache:
    output:
        logs: false
```

```yaml
# app/project.omni.yaml
name: app
extends: ../base.omni.yaml
cache:
    key:
        env: [CI]
```

|                  | `app` effective `cache.output.logs` |
| ---------------- | ----------------------------------- |
| Earlier versions | `true`                              |
| Now              | `false`                             |

To keep the old result, state the value: `cache.output.logs: true` in `app`.

## A task's `cache` no longer resets the project's

The same applies between a project and its tasks. A task that sets only
`cache.key.env` now keeps the project's `cache.output.logs: false`; before, the
task turned it back on. Set `cache.output.logs: true` on the task to restore the
old result.

The same holds for a task that extends another task: fields the extending task
omits come from the task it extends.

## A task written two ways keeps its fields

A task can be written as a bare command (`build: cargo build`) or as a block.
Earlier versions replaced the whole task whenever the two files used different
forms, so a block that only set `env` erased the base's command. Now a task
combines field by field whatever form each file uses, with the same rules as
other fields: a plain list replaces, `append`, `prepend` and `merge` combine, a
plain dictionary combines, and a field a file leaves out is kept.

A bare command stands for its command plus a dependency on the same task in
upstream projects (`^build`). That dependency takes part in the combination
like any other list entry.

```yaml
# base.omni.yaml
tasks:
  build: cargo build

# app/project.omni.yaml
extends: ../base.omni.yaml
tasks:
  build:
    env:
      vars:
        PROFILE: release
```

Old result: `build` has no command and no dependencies, because the block
replaced the bare command. New result: `build` runs `cargo build`, depends on
`^build` and sets `PROFILE`. To drop the inherited dependency, set a plain
`dependencies` list (`dependencies: []`). Two bare commands still replace one
another, as before. A bare command over a block replaces the block's command,
adds the `^build` dependency to the block's `dependencies` list, and keeps the
other fields.

## `name` can come from an extended file

`name` is required for a finished project, not for every file. A file may leave
it out when a file it extends supplies it. A project with no name in any of its
files is rejected, and the error names the file. The published JSON schema
still lists `name` as required for every file, so an editor using it may flag
a nameless extending file even though omni accepts it.

## What did not change

- The order files are applied in, including for several `extends` entries and
  files reached through more than one path.
- `append`, `prepend`, `replace` and `merge` on lists and dictionaries.
- `base`: a file's `base: true` is not inherited by the files that extend it.
- Each side of a glob (`include`, `exclude`) combines on its own.
- `@project` paths resolve against the directory of the file that wrote them.
- The configuration schema, including `name` being required in it.
