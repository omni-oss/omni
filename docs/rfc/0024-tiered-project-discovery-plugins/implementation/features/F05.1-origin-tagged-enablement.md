# F05.1: Origin-tagged cache enablement

**Reader:** contributors implementing F05.2 (the explicit-contradiction rule) and F06.3.
**Status:** implemented, pending PR review; **Risk:** Medium (extractor and `CacheInfo`,
but no key, schema or behavior change). Slice 1 of [F05](F05-origin-aware-cache-tiers.md).

## What changed

Each task's effective `cache.enabled` is now recorded with the tier that decided it, not
just the value. `Replace<bool>` loses that once layers are merged, so the origin is
computed in `LoadedLayer::finalize_composed`, where the presence-aware layers still
distinguish "the task set it", "the project set it" and "nothing did".

- `omni_configurations::CacheEnabledSource`: `HostFallback < ActivationDefaults < Plugin <
  ProjectExplicit < TaskExplicit`, highest precedence last. `is_authored()` is true only for
  the two explicit tiers, which is the distinction F05.2's error rule needs.
- `CacheEnabled { value, source }` and `CacheEnabled::resolve(candidates, host_fallback)`:
  the highest tier that has a value wins, in any candidate order; with none, the fallback
  applies. `from_authored(task, project, fallback)` is the no-plugin case.
- `FinalizedProject::task_cache_enabled`: the result per task. Base projects record none.
- `CacheInfo::cache_enabled_source` (with `#[serde(default)]`): carried from the extractor,
  alongside the unchanged `cache_enabled`. The extractor now takes the value from the same
  resolution, so the two cannot disagree.
- The plugin tiers (`Plugin`, `ActivationDefaults`) exist and are tested through `resolve`,
  but nothing produces them yet. They are the seam, not behavior.
- The host-fallback hook is two constants: `HANDWRITTEN_TASK_FALLBACK = true` (used) and
  `INFERRED_TASK_FALLBACK = false` (unused until plugins can contribute tasks).

## What did not change

- **No cache key.** `execution_info` builds the key material from specific fields and never
  reads the source. A test asserts that every tier yields the same execution info, and that
  eligibility depends on the value alone. The existing cache, executor and collector suites
  pass unchanged (442 tests across the touched crates).
- **No effective value.** Every task's new value equals what the extractor computed before,
  checked across single files, multi-layer composition, inheritance and `extends`.
- No error is raised for contradictions; no status type changes.

## Not done (rest of F05)

- **F05.2:** the explicit-contradiction error, B04's `disabled{deciding_source}` and
  `demoted` causes, and evaluating on executable edges. This slice only supplies the data.
- The activation-level `defaults` surface stays out of scope, as F05 says.
- **Open:** F05 work item 5 says `extends`-derived tasks "have no `enabled` fallback of
  their own" (C06). A setting reached through `extends` is recorded as the task's own
  (`TaskExplicit`), and a derived task that sets nothing gets the handwritten fallback.
  Whether C06 intends something stricter is not decided here; F05.2 should settle it with
  the contradiction rule.

## Verification

- `tests/cache_enabled_origin.rs` (8): task over project, project inheritance for short and
  long form and for tasks that set other cache fields, the fallback, an explicit value equal
  to the default keeping its origin, origin across composed layers, `extends`, base projects,
  and value parity.
- Unit tests for the ordering, authored tiers, plugin-tier slotting, candidate-order
  independence, the inferred/handwritten fallbacks and the serialized form.
- Extractor test: `extract_all` carries the origin into `CacheInfo` (fails when the field is
  not populated).
- Executor tests: the source never changes the execution info, and eligibility ignores it.
  The first is a guard that fails only if `execution_info` starts reading the field, so it
  was not mutation-checked.
