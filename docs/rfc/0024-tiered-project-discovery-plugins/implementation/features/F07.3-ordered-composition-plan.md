## Decisions requested

### 1. The "proposed collection rule"

The rule: dictionaries compare at the key or nested-field boundary, additive lists concatenate in contributor order, contributions are preserved until explicit operations finish, no blanket deduplication.

| Option | Behavior | Verdict |
| --- | --- | --- |
| **A. Key-level dictionaries, ordered append, no dedup (recommended)** | `env.vars` compares per key and `meta` at the leaf boundary (nested dictionaries recurse); `dependencies`, `cache.key.env`, `cache.key.files` concatenate in contributor order; effective-field normalization stays after replay (§7.3 table). | Already the normative text in §7.3 (amended 2026-11-27). Matches what `DictConfig`/`ListConfig::merge` already do for plain dictionaries and `append`. C04 and C17 pass with no new merge code. |
| B. Whole-dictionary later-wins | A later `env.vars` replaces the earlier one. | Rejected by §7.3. One plugin could erase another's variables. |
| C. Concatenate and deduplicate | Lists are uniqued while composing. | Rejected. Breaks C17 (`[A, A]` then explicit `merge: [B]` must give `[B, A]`) and changes existing keys. |

**Recommendation: A, with these details the plan fixes** (please confirm):

1. Contributors replay with the existing `Merge`, in sequence order, before any explicit layer. No new merge algorithm. A contributor's plain dictionary merges per key; its `append` list concatenates.
2. `meta` is compared at the leaf boundary, recursing through nested `DynValue::Dict` exactly as `DynValue::merge` does: disjoint nested keys compose and record nothing; an override is recorded only where a scalar (or a type-changing value) is overwritten, at the nested key path `Meta(Vec<key>)`. `DynValue::List` values follow `ListConfig::merge` and are never compared (additive).
3. The entry point rejects, with a typed error naming the contributor and field, in `layer` and its same-key task layers: any list-valued field (`dependencies`, `cache.key.env`, task `dependencies`/`with`) that is not `append`; any `MergeGlobConfig` (`cache.key.files`, `cache.output.files`) bare pattern, plain list or non-`append` side; any dictionary `replace` on `env.vars`, `meta`, task `args` or `tasks`; any `cache.remote` (project and task); and `redact`. `env.vars`, `meta` and `redact` are checked at project and task level. The same checks apply to task-level `env`, `meta`, `cache.key` and `cache.output` forms in same-key task layers. Nested `DynValue` lists/dicts inside `meta` are not inspected here (left to P-series). P-series validation stays the primary boundary; this guard exists because the entry point must not let a later contributor erase an earlier one even if a caller skips validation ("invalid input is never hidden"). If you prefer to trust the caller and leave this to P-series, delete the collection-form checks and their tests; the rejection of `cache.enabled` inside a contributor `layer` stays, because the tier fix depends on it.
4. No deduplication anywhere in this slice.

### 2. `CacheEnabledSource::Plugin`: resolve inside the tier, or split the variant

| Option | Effect |
| --- | --- |
| **A. Keep one `Plugin` variant; resolve plugin task over plugin project, then pass one candidate (recommended)** | No change to the serialized name `plugin`, the ordering, `as_str`, F09 output, the MCP `cache_eligibility` wire, `cache_contradiction.rs` or `cache_manager.rs`. C01's "plugin task" versus "plugin project" distinction is held as data next to the decision (scope, contributor), not in the enum. |
| B. Split into `PluginTask` and `PluginProject` | Changes a wire value and every `match`; touches `omni_task_executor` and F09 snapshots (outside this slice); makes the F09 JSON a breaking change. |

**Recommendation: A.** F07.5 can add an explicit `scope` field to the inspection output without touching the enum. New helper in `cache_enabled.rs`: `resolve_plugin_tier(task: Option<Declared<bool>>, project: Option<Declared<bool>>) -> Option<(CacheScope, Declared<bool>)>`, and `FinalizedProject` gains `task_cache_enabled_scope: Map<task, CacheScope>`, present only for decisions that `Plugin` made (authored decisions already carry `TaskExplicit`/`ProjectExplicit`), task before project, each already the last contributor's value. `CacheEnabled::resolve` currently keeps the last of equal candidates (`max_by_key`), so equal-source candidates are order-dependent although its doc says "any order". The slice pins that with a test, fixes the doc comment, and never passes two candidates of one source.

## Design

New names, all inside `omni_configurations`:

- `ContributorId(Arc<str>)` and `DeclarationSource::Contributor { id: ContributorId }`. Typed, not a file path and not an anonymous `Fileless` id. `Origin::base_dir` stays the path base. Existing `File`/`Fileless` behavior and `LoadedLayer::file()` do not change.
- `Contribution { id, layer: ProjectLayer, base_dir, enabled: Vec<EnabledDecl> }`: the activation's *finished* contribution, with activation-local application already folded in (C04: one contributor's subtraction never edits another's values). "Finished" means additive forms only (lists as `append`, dictionaries as plain values or `merge`), so a folded `replace` cannot erase an earlier or later contributor; the caller (P-series application step) normalizes a folded `replace` to the resulting `append`, and the guard below rejects anything else. `layer` carries **no `cache.enabled`** (guard error if it does): `cache.enabled` is the one tiered field, so its declarations travel as typed `EnabledDecl { scope: EnabledScope, value: bool, origin: Arc<Origin> }` with `EnabledScope { Project, Task(String) }`. `Task(name)` is a canonical task name; a name that no layer declares, including an alias, is `ComposeError::UnknownTask`. (`CacheScope { Project, Task }`, unit variants, is the separate type returned by `resolve_plugin_tier` and exposed in `task_cache_enabled_scope`.) An emitted value has an origin with `DeclarationSource::Contributor` (plugin tier); a value that came from the activation's applied files has that file's `File` or `Fileless` origin (authored tier, C01 "authored means explicit or applied"). No new authored source variant is needed.
- `compose_ordered(root: OmniPath, order: &[ContributorId], contributions: Vec<Contribution>, explicit: Vec<LoadedLayer>) -> Result<Composed, ComposeError>`. The `order` slice decides precedence; the vector's arrival order and any scheduling do not. Errors: unknown, missing or duplicate id; destructive form (decision 1.3).
- `Composed { layer: LoadedLayer, overrides: Vec<FieldOverride> }`. `layer` (its `dir()` is `root` when `explicit` is empty, else the last explicit layer's, as `LoadedLayer::merge` does today) is contributors in order, then explicit layers in their given (extension-closure) order, merged with the existing `Merge`, and finalizes with the existing `finalize_composed`. With no contributors it equals today's fold.
- `FieldOverride { root, field: FieldPath, winner: ContributorId, overridden: Vec<ContributorId>, masked_by_explicit: bool }`. `FieldPath` is a structured enum with exactly these variants: `Description`, `EnvVar(String)`, `Meta(Vec<String>)`, `ProjectCacheEnabled`, `TaskCacheEnabled(String)` (the task name), `CacheKeyDefaults` (project), `OutputLogs` (project); never a joined string, and holds no values. `root` is the project root.
- Tracked set for this slice (closed, listed in one table in the code): project `description`, `env.vars.<key>`, `meta.<key>`, `cache.enabled` (project and task scope), `cache.key.defaults`, `output_logs`. Other same-key task fields compose by replay without per-field records; plugin tasks are activation-scoped, so they only meet in synthetic same-key tests. F07.4's notice counts only these fields until P12.
- `overridden` holds earlier contributors whose value differs from the winner's value. Equal values coalesce: the contributor is not listed. The comparison runs in memory with the derived `PartialEq` of the typed values (`output_logs` is compared through `to_split()` so `Uniform(All)` equals the equivalent `Split`, and its facets are not tracked separately) and keeps no value. **Interpretation modes:** no tracked field carries a literal-versus-expression tag today (`DynValue` has only `Boolean/Integer/Float/String/List/Dict`; description and env values are plain strings; `CommandOperand` modes belong to task `exec`, which is outside the tracked set). The F07 gate item "equal text with different interpretation modes" is therefore covered here by type inequality (`Integer(1)` versus `String("1")` in `meta`) and is deferred for tagged fields until they exist. **This is a deliberate narrowing of the F07.3 gate; please confirm.** If a tagged field is added to the tracked set, its test is required and `PartialEq` must distinguish the tag, else stop and ask. For `cache.enabled`, overrides compare same-scope declarations of the same tier across contributors (plugin-tier values among themselves; applied authored-tier values among themselves, recorded with the contributor ids). A plugin-tier override is `masked_by_explicit` when an authored-tier value (applied or explicit) applies to that scope; otherwise `masked_by_explicit` is true when an explicit layer declares the field, or replaces an ancestor subtree, so F07.4 can stay silent and F07.5 can still list contributors.
- `cache.enabled` tier fix (one route: typed side declarations). Today's replay folds a plugin task value over an authored project value, so C01 row 7 (authored project `false`, plugin task `true`, expected `false`) would give `true`. So contributor layers never contain `cache.enabled`; their `EnabledDecl`s are appended, in `order` position, to a new `pub(crate)` `LoadedLayer::enabled: Vec<EnabledDecl>` (`Merge for LoadedLayer` extends `self.enabled` with `other.enabled` in order; `attribute()` never touches it; `with_layer` and `update_layer` leave it alone, since these declarations were never part of `layer`). The replayed `cache` therefore holds explicit-layer values only. In `finalize_composed`, per task: (1) the replay decision is computed as today from the task and project slots (explicit layers); (2) side declarations are folded in order, last wins, into four slots: plugin task, plugin project (origin `Contributor`), applied task, applied project (any other origin); (3) authored task = replay task else applied task; authored project = replay project else applied project (explicit layers come after applied ones in ordinary layer order, so they win within a tier); (4) plugin = `resolve_plugin_tier(plugin task, plugin project)`; (5) all candidates go to `CacheEnabled::resolve`; the winning origin, file and scope are then taken from the slot that supplied the returned source (matching on it), since `resolve` returns no origin. `ProvenanceMismatch` keeps its meaning and runs only when the decision came from the replay (steps 1 and 3 replay branch): decided value versus the authored-only merge. When the decision came from a side declaration, merged may be `None` or a lower-tier value from the replay project slot (for example an applied task value beating an explicit project value leaves the explicit project value in the merged `cache`); no invariant is asserted on it, and the plan writes `Some(Replace(decided))` into that task's `task_cache` `enabled` (replacing any such lower-tier value; never for host fallback, which keeps `None`). Unmatched replay decisions are unaffected. With no side declarations (all explicit-only input) none of steps 2, 4 or the write-back run, and the code path is today's. Side task declarations apply to the named task only and are not inherited through task `extends` (plugin tasks are activation-scoped and extension of them is out of scope; one test documents this, and if inheritance turns out to be required, stop and re-plan). Tier differences (an earlier plugin's task-level value beating a later plugin's project-level value) are tier precedence, not overrides, and produce no override record.

## Risks and rollback
