  equal to hashing the concatenation (unit-tested; unused by production).

## Failing on the base, and why

The collision tests are `it.fails` (e2e) or `#[ignore]` (Rust) so the suite stays
green. `OMNI_IDENTITY_STRICT=1` (exactly the string `1`) runs the e2e ones as ordinary tests. The control
block (same fixture, distinct labels) passes on the base in both modes, so these
failures come from the collision and not from the fixture.
`cargo test -p omni_collector -- --ignored` runs the Rust one. Flip all of them
to ordinary tests in the cutover commit.

| Test                                                                         | Failure on the base                                                     | Reason                                                                                          |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `collector::tests::formerly_colliding_pairs_have_distinct_digests` (ignored) | `assert_ne!` on two equal digests                                       | both pairs hash the leaf `a#b#c`                                                                |
| e2e colliding: both pairs run with their own env, meta and logs              | expected output to contain `RUN-AB-C mark=env-ab-c`; received `RUN-AB-C mark=env-a-bc arg=default-a-bc` (the other task's env; the run log prints `Executed task 'a#b#c'` twice) | env, meta and result maps are keyed `a#b#c`; one task's data overwrites the other's. Meta-derived data was not asserted by this message |
| e2e colliding: labels and consumer dependencies                              | `a#b#c` instead of `a\#b#c` (or a pair's result missing)                | unescaped label and merged result map                                                           |
| e2e colliding: cache entries do not cross                                    | 3 distinct hashes for 4 results                                         | colliding digest                                                                                |
| e2e colliding: changing one pair re-runs only its consumer                   | `expected true to be false` (or the pair's result missing)              | shared digest and dependency inputs                                                             |
| e2e same-project logs (control names, no collision)                          | the second run replays one of `APP-X`/`APP-Y` twice and never the other | `cache_many` reads `logs_map[&result.task.project_name]`, a project-only key (read at `hybrid.rs:1211`; the map is built at `:1175-1178`) |

Observed strict-mode messages (`OMNI_IDENTITY_STRICT=1`, base `e1cdb515`):
5 of 11 e2e tests fail: `expected 'RUN-AB-C mark=env-a-bc ...' to contain
'RUN-AB-C mark=env-ab-c'`; `expected 'a#b#c' to be 'a\#b#c'`; `expected 3 to be
4` (distinct hashes); `expected true to be false` (`cache_hit` of the changed
pair); `expected '...APP-X...APP-X' to contain 'APP-Y'`. The control block
passes.

Deviation: the fixture passes `ARG` as an environment variable, not as
`args`/cache settings, so default args and `cache` settings are not yet
distinct per task in the collision proof; step 2 adds those rows in the parity
matrix.

The last row is an independent base defect that the plan already schedules for
step 2. Which sibling wins varies run to run (map order).

### Empty or NUL names reachable from configuration

All four are reachable on the base (verified with the built binary):

| Input                       | Result                                          |
| --------------------------- | ----------------------------------------------- |
| project `name: ""`          | runs as `#t`                                    |
| task key `""`               | runs as `p#` (selected by `--task-pattern '*'`) |
| project name containing NUL | loads; the spawn fails with `nul byte found`    |
| task name containing NUL    | runs, label `p#t\0u`                            |

`ProjectConfiguration.name` and task keys have no validation; only dependency
text goes through `TaskReference`. The plan's rule applies: reject them at
ingress with a diagnostic and a pre-v1 note. That is a step 2 decision, not a
re-plan, because it changes no stored format. The encoder vector `("", "#")`
stays encoder-only.

### Result and serde consumers

- Producers: the `--result` JSON writer, the MCP task tool
  (`serde_json::to_value` in `omni_mcp_core/src/server.rs`) and `JsonSchema`
  derives.
- In-repo consumers of the result JSON: `scripts/summarize-results` and
  `scripts/create-jobs`. They validate `full_task_name` and `dependencies` as
  strings and key on `task.project_name` and `task.task_name`; neither parses or
  round-trips the label, so the escaped label is compatible.
- No Rust code deserializes `TaskExecutionNode`, `TaskExecutionResult` or
  `TaskExecutionGraph`. The `omni_core` re-export and the serializable-graph
  note in `cli/omni/CHANGELOG.md` are the only compatibility surface.

## Boundary check against the plan's re-planning triggers

No trigger fired:

- No supported consumer round-trips a legacy label into execution.
- Reproducing the baseline needed no persistent, schema or transport change. The
  v1 leaf swaps one 32-byte leaf in the same Merkle recipe, and a test-only
  recipe reproduces the base digest exactly.
- Equivalent-input parity cannot be tested before the cutover; the pinned v1
  recipe digest is the target for step 2's parity rows.

## Findings for step 2

1. Same-project cached-log crossover (`hybrid.rs:1211`) is a live base defect
   independent of name collisions.
2. `hybrid.rs:2476` swaps project and task for meta; the plan already schedules
   the fix and a meta-templated cache path fixture.
3. `omni_cli_core/src/commands/cache.rs:591` truncates a task name containing `#`.
4. Remote opt-out sets are label-keyed (`cache_manager.rs:135,274,507`); a
   collision can send an opted-out task to the remote today.
5. Empty and NUL names are reachable (above).
6. `--result` digests are the base64 of the same 32-byte digest, so the change
   is visible to any consumer that pins hashes.
