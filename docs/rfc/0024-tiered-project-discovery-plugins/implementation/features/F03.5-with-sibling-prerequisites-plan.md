# F03.5: Prerequisites of `with` siblings

**Status:** merged ([#178](https://github.com/omni-oss/omni/pull/178)); the
batch-order follow-up is [#182](https://github.com/omni-oss/omni/pull/182). The
fix is one commit that reverts cleanly; the proof tests and the caller tests
are green. The decisions below were settled by the maintainer.
**Base:** `0805cf52` (reproduced unchanged on the pre-alias base `c7aa81fc`).
**Kind:** Medium bug fix.
**Risk:** High: it changes which tasks run and what a batch contains in the
task graph (`docs/guidelines` risk overrides). It does not touch cache keys,
storage or invalidation code.

## Assessment

- **Defect.** `get_batched_execution_selection_impl`
  (`crates/omni_core/src/task_execution_graph.rs`) computes `reachable`, the
  actual roots plus everything they depend on, and only then seeds the
  `with` (sibling) components from it. A sibling pulled in at that point is
  scheduled, but its own dependencies were never walked. The condensation then
  skips every dependency edge whose endpoint is not scheduled
  (`let Some(&dep_cid) = component_of.get(&dep) else { continue }`), so the
  sibling runs without its prerequisites. It affects canonical siblings, siblings in
  other projects, siblings named through an alias and siblings named through
  `^upstream`: they are all ordinary `Sibling` edges by then.
- **Reproduced** with a binary built from the base (`app#t` has
  `with: [tool#build-native]`, `tool#build-native` depends on `tool#setup`,
  `app` depends on `tool`):

    ```text
    $ omni run t -p app --no-cache -d
    Executing task 'tool#build-native' ...
    Executing task 'app#t' ...
    Total 2, Succeeded 2          # tool#setup is never planned
    $ omni run t -p app --no-cache --result res.json   # same two tasks;
                                    # tool#build-native lists dependencies ["tool#setup"]
    ```

    Note that `-d` is `--dry-run`; `--ignore-dependencies` is `-i`.

- **Unknowns.** None blocking. The cycle behavior for newly scheduled
  prerequisites and the within-batch ordering are decisions, listed below.
- **Effort and ownership:** one slice in one function plus its tests; one
  owner. Independent review required (High).

## Change

Replace Steps 3 and 4 by one fixed-point expansion. The other steps keep their
meaning.

| Set                           | Meaning                                                                                                        | Changed?                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `direct`                      | tasks the user's filter matched; returned to callers for reporting and `hash`                                  | no                                                            |
| `possible_roots`              | `direct`, plus (with `--with-dependents`) dependents admitted by the dependents filter                         | no                                                            |
| `actual_roots`                | possible roots that are not a dependency of another possible root                                              | no                                                            |
| `scheduled` (was `reachable`) | the closure of `actual_roots` under **dependency edges (to dependencies) and sibling edges (both directions)** | now includes pulled-in siblings and everything they depend on |

Algorithm: a worklist seeded with `actual_roots`. Pop a node; if unseen, mark
it scheduled, push its dependencies (incoming `Dependency` edges) and its
siblings (`Sibling` edges, either direction). Dependents (outgoing edges) are
never followed here: with `--with-dependents` they were already chosen in step
1.5 by the dependents filter, so a pulled-in sibling's own dependents are not
scheduled. Each node is marked once and each edge is looked at at most twice, so
it is linear in nodes plus edges, the same order as the two walks it replaces.

Then, unchanged: components are the sibling-connected components of `scheduled`
(seeds in sorted `NodeIndex` order), the condensation links
`comp(dependency) -> comp(dependent)`, levels are longest path by Kahn's
algorithm, so siblings stay co-scheduled and every dependency is strictly
earlier than its dependents. The `else { continue }` on a missing component
becomes unreachable for scheduled nodes (every dependency of a scheduled node is
scheduled); replace it with `let Some(&dep_cid) = component_of.get(&dep) else {
debug_assert!(false, "dependency of a scheduled task must be scheduled"); continue; }`.
Debug and test builds then fail loudly if a future edit reintroduces the silent
skip, and release builds keep today's behavior (skip the edge) rather than
panicking in a user's run.

Decisions this note settles (confirmed, see [below](#decisions-settled-by-the-maintainer)):

1. **User filters do not exclude required prerequisites.** `-p app`, a task
   name, `--dir`, `--meta` and `--scm-affected` select roots only. A sibling
   is already pulled in regardless of them; its prerequisites are as required
   as the dependencies of a selected task, which also ignore the filters. The
   dependents filter likewise only limits `--with-dependents` discovery.
2. **Persistent tasks.** The existing guard stays as is: a persistent task can
   not be depended upon (rejected when the graph is built). A persistent
   sibling may be pulled in with its own prerequisites; they land in earlier
   batches, and the persistent component keeps the existing rule (last batch,
   unless a scheduled dependent needs it earlier). Prerequisites can never be
   persistent, so the final-batch rule never applies to them.
3. **Cycles that were silently ignored now error.** Two shapes: a prerequisite
   chain of a pulled-in task that reaches a task whose sibling depends back on
   the chain (`t ~ b`, `b <- p`, `p ~ q`, `q <- b`), and a prerequisite that
   depends on a task co-scheduled with its own dependent (`t ~ b`, `b <- p`,
   `p <- t`). Both previously planned without `p` (and `q`). They now fail with
   the existing `task.sibling_cycle` diagnostic. The offender list is every
   component the Kahn pass could not finish (`task_execution_graph.rs:1047-1056`),
   so it also names every component it could not finish, which includes tasks
   that share a component with a task on the cycle or sit downstream of it (in
   the `p ~ q` case `t` is reported because it shares a component with `b`). The hint therefore says
   "tasks involved in or blocked by the cycle", and that the chain may run
   through a prerequisite of a `with` task.
4. **Determinism.** Seeds are sorted, so components and levels do not depend
   on hash iteration. The order _inside_ a batch comes from `HashMap`
   iteration today and no test pins it. Sorting within batches is **not** part
   of this fix. If dry-run output order must be stable, that is a recorded
   follow-up change.
5. **`--ignore-dependencies`.** Verified today: the path
   (`get_execution_plan_ignored_dependencies`) filters nodes into one batch and
   never uses the graph, so neither siblings nor prerequisites are added. It
   stays as is; the e2e proof pins it (`t` runs alone).

## Cache, hashing and callers

- **Task digests do not change.** A task's dependency digests come from
  `node.dependencies()` (graph edges) looked up in the results of tasks that
  ran (`DefaultTaskContextProvider`, `get_dependency_hashes`), so `build-native`
  already declares `setup` in its key recipe. What changes is which tasks run.
  The only entries that change are those of a pulled-in sibling in the buggy
  scenario: its digest was computed without `setup`'s hash (the dependency was
  not in the results), and now includes it. That entry was keyed on an
  incomplete input set, so the old entry becoming a miss is a correction, not
  a regression. Plans that already contained the prerequisite are unaffected.
- **Callers of the planner** (all reach `get_batched_execution_selection`
  through `get_execution_selection` / `get_execution_plan`):
    - `omni_task_executor/executor.rs` (`run`, `exec`): more tasks may run.
      `run` also calls `plan_contradictions` (`executor.rs:119-146`): a
      pulled-in sibling with explicit `cache.enabled: true` whose
      previously-skipped prerequisite has explicit `cache.enabled: false` is
      now a hard `executor.cache_contradiction` error. An implicitly uncached
      prerequisite demotes the sibling to `CacheStatus::Demoted`
      (`batch_executor.rs:670-702`, `derive_status` at `:699`).
    - `omni_task_executor/cache_inspection.rs` (`inspect_cache_eligibility`):
      the inspected set includes the prerequisites, matching what a run would
      do: same demotion (`:113`) and same contradictions (`:143-171`).
    - `omni_task_executor/batch_executor.rs` `skipped_output_dependencies`
      (`:493-511`, `:805-838`): a pulled-in sibling that opts out of remote
      caching today raises the `RemoteOptOutSkippedDependencies` notice naming
      its own skipped prerequisite. That notice is caused by this bug; the
      prerequisite is in the plan after the fix, so it goes quiet. Cover with a
      test in slice 2.
    - `omni_task_executor/cache_manager.rs` `local_only_closure` (`:315-348`):
      improves automatically. It only follows dependencies that are in the
      plan, so local-only opt-outs now propagate to a pulled-in sibling's
      prerequisites.
    - `omni_cache/cache/impls/hybrid.rs`, stale prune (`observe_prune_workspace`,
      `ignore_deps = false`): the plan is walked batch by batch to compute live
      digests, then every task is observed with `hashes.get(..)` (`:451-452`).
      **Before the fix**, when `tool#setup` is omitted, its digest is `None`, so
      `PruneInventory::observe(.., None)` marks it indeterminate
      (`prune_inventory.rs:33-35`) and `is_stale()` is false
      (`prune_inventory.rs:52-54`). `build-native` has no status for
      `tool#setup` (`statuses.get_ref` is `None` -> `DependencyOutcome::Unreusable`,
      `hybrid.rs:403-412`), is skipped from the infos and is also observed as
      `None`. Neither task can be classified stale, so none of their entries is
      ever pruned. **After the fix** both get real live digests: their current
      entries are protected as live, and old entries (including pre-fix
      incomplete-key entries of `build-native`) become prunable as stale. The
      transition is indeterminate -> determinate. Cover with a test in slice 2.
    - `omni_cache/cache/impls/hybrid.rs`, `plan_task_set` (`--dir`/`--meta`
      filters): uses `ignore_deps = true`, which never expands; unaffected.
    - `omni_context/project_hasher.rs` (`hash`): the plan grows; the digest of a
      given task is unchanged. `get_batched_execution_selection` still returns
      the same `direct` set, because `ProjectHasher` folds only direct tasks; a
      test pins its exact content.
    - `omni_execution_plan/traits.rs` and `omni_task_executor/execution_plan_provider.rs`:
      wrappers only. Benches `plan_building` and `cache_lookup` call it too.

## User-visible behavior and release note

More tasks run: the prerequisites of `with` tasks, which previously were
silently skipped. Newly surfaced errors and effects for configurations that only
worked because those prerequisites were skipped:

- `task.sibling_cycle`, when a prerequisite depends back on a task that runs
  together with it.
- `executor.cache_contradiction`, a hard error from `omni run`: a pulled-in sibling with
  explicit `cache.enabled: true` whose prerequisite has explicit
  `cache.enabled: false`.
- Cache demotion: an implicitly uncached prerequisite demotes the sibling to
  `Demoted` (shown by `omni cache eligibility` and in run results).
- The `RemoteOptOutSkippedDependencies` notice for a `with` task that opts out of
  remote caching no longer appears, because the prerequisite now runs.

> **Fix:** tasks named in `with` now run their own `dependencies` first, even
> when a project, task or other filter does not select them. Previously the
> prerequisites of a `with` task could be skipped, so the task could run
> without them. Because those prerequisites now run, they can surface errors
> that were hidden: a prerequisite that depends back on a task that runs together
> with it fails with `task.sibling_cycle` (the error lists tasks involved in or
> blocked by the cycle), and an explicitly cached `with` task whose prerequisite
> is explicitly uncached fails with `executor.cache_contradiction`. An implicitly uncached
> prerequisite makes the `with` task uncached. Pre-v1, these are hard errors
> rather than warnings.

## Rollback and undo

Revert the fix commit as a unit. No stored data, cache layout or key recipe
changes, so an older binary reads everything. After a revert, configurations
that used `with` prerequisites go back to running without them. Staged exposure
or a feature flag is omitted on purpose: this is a deterministic pre-v1 planner
bug fix with a clean single-commit revert and no stored-data change.

## Compatibility

Configuration syntax and the plan and report wire formats are unchanged. Plans
contain more tasks in the buggy cases and a later first batch, and a small set
of configurations moves from "ran without prerequisites" to a
`task.sibling_cycle` or `executor.cache_contradiction` error, or to a demoted cache
status (see the release note).

## Decisions settled by the maintainer

Both independent plan reviews and the maintainer's go-ahead agree.

1. **Decided:** required prerequisites run even when the user's filters (`-p`,
   task, `--dir`, `--meta`, `--scm-affected`) exclude them.
2. **Decided:** keep the `SiblingDependencyCycle` variant, with the hint widened
   to "tasks involved in or blocked by the cycle".
3. **Decided:** a hard error pre-v1 is acceptable for newly surfaced
   configurations, documented in the release note together with
   `task.sibling_cycle` and `executor.cache_contradiction`; no warning-only release.
4. **Decided:** sorting within batches is not part of this fix. It is a
   separate change; if dry-run output order must be stable, it is a recorded
   follow-up.
5. **Decided:** `--with-dependents` matching dependents by task name only is a
   separate change. Done: see
   [F03.6](F03.6-with-dependents-plan.md) ([#180](https://github.com/omni-oss/omni/pull/180),
   [#184](https://github.com/omni-oss/omni/pull/184)).
6. **Decided:** cache eligibility and the stale inventory include the
   prerequisites, to match a run.

## Follow-up: sort tasks within a batch

Decision 4 deferred this. `get_batched_execution_selection_impl` now sorts each
batch by `(project, task)` identity (the order `direct` already uses) after the
levels are computed. Batch membership, levels and sibling co-scheduling are
unchanged. Before, the order inside a batch came from `HashMap` iteration and
differed between builds of the same graph.

- **Proof.** `batch_order_within_a_batch_is_deterministic` builds the same graph
  26 times (3 projects, 12 independent tasks in the first batch, so 12!
  orderings; each build has fresh random hasher keys) and asserts the same
  batches in the same order, sorted. It fails on the base: a build differed from
  the first. Chance that 25 unsorted builds all agree is about 1e-200, so it is
  not a flaky proof.
- **Consumers.** None depends on the order within a batch: the executor runs a
  batch concurrently, the project hasher sorts its digests and reads dependency
  digests from earlier batches, and the cache and inspection walks only collect
  sets. The visible effect is stable ordering of dry-run output, progress and
  logs. Not fixed here: the pipeline's results are a `TaskMap` (hash maps), so
  `into_values()` order was still unstable; that is fixed separately by
  sorting the returned list by `(project, task)`
  ([#183](https://github.com/omni-oss/omni/pull/183)).
- **Benchmark** (release, `plan_building`, 8 interleaved runs, median / min):
  layered 2.638 / 2.620 ms base, 2.705 / 2.678 after; chain 2.132 / 2.115 and
  2.163 / 2.145; fan-out 2.163 / 2.130 and 2.203 / 2.184. About 1.5-2.5%
  slower, the cost of the string comparisons. Allocations are identical (18,916
  / 17,385 / 16,951 and the same bytes). A first version that sorted cloned
  nodes with the stable sort added about 100 KB of bytes; sorting the indices
  with `sort_unstable_by` before cloning removes that (identities are unique).
