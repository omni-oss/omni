# F06.1: Effective execution field audit

**Reader:** contributors implementing F06.2 (semantic projection/encoding) and F06.3
(collector plumbing and parity). This inventory identifies what must remain covered
by the combined execution key, not an implemented digest API.

**Status:** docs-only prerequisite; Medium risk. No cache-key, storage, remote-format,
or execution changes are authorized by this slice.

**Baseline:** `490e133e3684b14af919a01bd668728b29181253` (`git rev-parse HEAD`).
The symbols below were inspected in the shared checkout at that baseline; use symbol
names, not assumed line numbers, when applying the follow-up changes.

**Contract:** [F06](F06-effective-semantic-digest.md) and
[RFC §8.3](../../008.02-execution-cache-semantic-identity.md#83-fine-grained-execution-cache-integration)
are authoritative for the intended behavior. “Include” below is a future obligation;
“covered” describes only the current contribution and its limits.

## Boundaries and source inventory

Paths in this inventory are repository-relative.

### Composed configuration

`LoadedLayer::finalize_composed`, `FinalizedProject::{config, task_cache}` in
`crates/omni_configurations/src/layer.rs`; `resolve_task_layer_extensions` in
`crates/omni_configurations/src/task_extension.rs`.
Task extensions and project cache inheritance precede defaults. Project cache
alone is not the effective per-task cache.

### Task lowering

`TaskConfiguration::{into_long_form, get_task}`, `TaskConfigurationLongForm::into_task`
in `crates/omni_configurations/src/task_configuration.rs`.
Short form adds an upstream self-dependency. Project only the lowered effective
task, not authored spelling or masked ancestors.

### Extracted side data

`ProjectDataExtractor::extract_all`, `config_file_inputs`, `ProjectDataExtractions`
in `crates/omni_context/src/project_data_extractor.rs`.
Cache, args, task env, merged project/task metadata, output-log policy and redaction
leave lowering through separate maps. Auditing `omni_core::Task` alone loses semantics.

### Executable graph

`Task`, `Project` in `crates/omni_core/src/core_types.rs`; `TaskExecutionGraph`,
`TaskExecutionNode` in `crates/omni_core/src/task_execution_graph.rs`.
Nodes hold command/retry command, names, directory, resolved execution dependencies,
enabled expression, interactive/persistent flags and retry configuration.
`with` lowers to task siblings, not execution dependencies.

### Runtime context

`DefaultTaskContextProvider::get_task_context`, `create_template_context` in
`crates/omni_task_context/src/default_provider.rs`; `TaskContext` in
`crates/omni_task_context/src/task_context.rs`.
Runtime template context has platform, env, metadata and merged args.
Dependency result hashes come from the hash provider, not configuration alone.

### Cache transport

`CacheInfo` in `crates/omni_task_context/src/cache_info.rs`;
`TaskExecutionInfoExt::execution_info` in `crates/omni_cache/src/exts.rs`;
`TaskExecutionInfo`, `NewCacheInfo` in `crates/omni_cache/src/cache/types.rs`.
No effective-semantic contribution exists in these types today.
`execution_info` requires cache info but does not itself enforce enablement.

### Final collection

`ProjectTaskInfo`, `HashInput`, `Collector::{collect, get_digest}`,
`command_hash_input` in `crates/omni_collector/src/collector.rs`.
This is the current combined key boundary. Collection flags control work,
not semantic identity.

The desired definition contribution is per finalized task. Resolved dependency
identity and invocation context must be added at the boundary where they are
available. “Compute once” must not mean computing before these values exist, or
pretending a configuration-only hash covers changing runtime resolution.

## What the current collector actually covers

`Collector::get_digest` inserts these contributions into the project file hash tree:

- Collected input file paths/content through `RealDirHasher::hash_tree`. Input
  include/exclude rules select files in `Collector::collect`; their raw definitions
  are not independently hashed.
- Dependency digests sorted before insertion. This does not encode raw edge
  declarations, nor make an all-zero uncached result a valid freshness proof.
- Selected environment values: sorted `input_env_keys`, with missing keys mapped to
  `""`, encoded as newline-joined `key=value`. This block is skipped when the entire
  `env_vars` map is empty. It is not a hash of the whole process environment.
- Configured `args`, iterated from `Map`, using newline-joined debug-formatted JSON
  values. This is not the merged invocation argument map.
- Sorted output include patterns and sorted output excludes, the latter prefixed
  with `exclude:`. These are artifact-selection definitions, not output contents.
- Raw main/retry command configuration through `command_hash_input` and
  `CommandConfig::canonical`, plus `project_name#task_name`.

`CommandConfig::canonical` already tags `Operands` values as literal, expression,
or interpolated, including the interpolated literal bindings. `command_hash_input`
also labels operand commands separately from other commands. Shell and legacy
argv use their raw string/JSON encodings under the same command label; equal raw
canonical text is not proof of equal interpretation across those variants.
Empty canonical commands contribute nothing. Preserve these existing inputs;
F06.2 needs an explicitly typed projection rather than relying on accidental
properties of the old textual encodings.

`config_file_inputs` seeds the project's file and transitive extension files when
`cache.key.defaults` is true. This can cause broader invalidation than the new
per-task contribution. It does not prove completeness for inference or runtime
context, and F06 does not remove that existing behavior.

## Effective field classification

Legend:

- **Include:** required in the future effective semantic projection or a proven
  equivalent runtime contribution; currently missing or only partly covered.
- **Covered:** retain ordinary hashing; duplicate definition coverage is permitted
  where needed for a stable conservative projection.
- **Exclude:** not an independent command-semantic contribution. Explicit file
  inputs may still hash the containing configuration.

This inventory covers every field of `TaskConfigurationLongForm`, `TaskEnvConfiguration`,
`CacheInfo`, and the additional lowered project/node fields consumed by execution.

### Commands and arguments

- **`exec`, `retry_exec`: Covered definition / Include interpretation and runtime.**
  Raw commands reach the collector; execution uses `resolve_task_command` in
  `crates/omni_task_executor/src/batch_executor.rs`. Encode presence, command
  variant, ordered operands, every operand mode, expression text and literal
  bindings. Also cover resolution context; raw expression text alone is insufficient.
- **`args`, `CacheInfo::args`: Covered configured values / Include effective runtime
  values.** `create_template_context` overlays `get_task_override_args`;
  `execution_info` still sends `ci.args`. Use canonical typed values/maps for
  effective definitions; merged invocation overrides need runtime coverage.
  Defaults masked by an invocation override are not the executed value.
- **Task/project/workspace `env.vars`: Include effective definitions; partially
  Covered runtime.** Extractor retains task overrides separately;
  `LoadedContext::get_task_env_vars` expands and overlays them. Only selected key
  values reach ordinary env hashing. Cover consumed effective settings, including
  inherited changes and expansion semantics. Preserve declared runtime env inputs;
  decide conservative context coverage as below.

### Execution policy and graph

- **`enabled` / authored `if`: Include.** Lowering defaults to boolean true;
  `evaluate_bool_expr` evaluates booleans or Tera expressions against the runtime
  context before replay acceptance. Not currently in `HashInput`. Include
  boolean/expression mode and definition; cover execution-affecting context/result.
  Do not confuse task enablement with cache enablement.
- **`interactive`: Include conservatively.** Defaults false; `run_process` uses it
  for stdin handling and interactive streams. Not proven presentation-only: it
  changes process I/O. User input itself is not made repeatable by hashing this flag.
- **`persistent`: Include conservatively; eligibility separately enforced.**
  Defaults false; affects stdin and cache eligibility. Keep effective execution
  flag distinct from derived eligibility/provenance. A digest does not authorize
  caching a persistent task.
- **`retry`: Include conservatively.** `BatchExecutor::resolve_retry` overlays
  run-level settings, then `RetryConfiguration::into_policy` resolves defaults.
  Cover effective `max_retries`, `strategy`, `base`, `max_delay`, `jitter`, `step`,
  `factor` from `crates/omni_retry_config/src/retry_configuration.rs`. Delays/jitter
  are execution policy, not measured timings; do not drop them without proof.
  Invocation retry overrides need an explicit owner.
- **Task/project/resolved-node `dependencies`: Covered result digests / Include
  resolved edge semantics.** Graph resolves own/explicit/upstream references;
  collector hashes dependency results only. Use effective resolved dependencies
  rather than wholesale project configuration or inheritance text. Preserve
  result digests and aggregate forwarding. Do not admit zero sentinels from
  uncached work; eligibility propagation is a separate prerequisite.
- **`with` / lowered `Task::siblings`: Include conservatively as co-scheduling
  semantics.** It changes graph scheduling but is not a dependency-result edge.
  Record effective resolved co-scheduling relationships; do not hash sibling
  command bodies or fabricate execution dependencies. Narrowing this field away
  requires evidence/tests.

### Structure and presentation

- **Task/project `base`, `extends`: Exclude structural/provenance form.** They
  govern template removal, composition and inheritance before extraction. Include
  the effective results they cause, not ancestry, source order or overridden
  values. Removed templates have no executable-task contribution.
- **Task/project `description`: Exclude.** Lowered task description is not used by
  the inspected execution/template-context path. Keep presentation-only edits out
  of the added digest.
- **Task/project `meta`: Include conservatively, not display-only.** Extractor
  merges project metadata with task metadata; `create_template_context` exposes
  it as `meta`. Include effective merged metadata until safe expression dependency
  narrowing is demonstrated. A metadata edit used by a command/condition/path
  must invalidate even with identical raw command text.
- **`output_logs`: Exclude presentation policy.** Extractor resolves project/task
  policy; `resolve_output_logs` determines live/cached log display. Do not hash
  display mode, prefixes or redacted display commands as command semantics.
- **`redact`: Exclude.** Extracted `RedactPolicy` is explicitly display-only;
  resolution for execution precedes display sanitization. Never substitute
  redacted argv/context for real semantic inputs. Do not persist raw secret
  values in audit/debug output.

### Cache eligibility, inputs and artifacts

- **`cache.enabled`, `CacheInfo::cache_enabled`: Exclude from semantic digest;
  eligibility control.** `is_cache_eligible` in `cache_manager.rs` gates
  reads/writes, and `execute_batch_inner` rechecks replay. Apply finalized
  enablement before lookup/replay/persistence. Exclude deciding tier/source and
  derived demotion/status metadata too; identical eligible semantics must not
  differ merely by provenance.
- **`cache.key.defaults`, `CacheInfo::key_defaults`: Include effective input
  policy, not a semantic-digest switch.** Extractor uses it solely to add or omit
  default config-file inputs. Collector receives no defaults flag. Semantic
  identity must be mandatory when false, for authored and inferred tasks. Project
  effective input definitions; do not encode omitted/default spelling as a
  separate provenance distinction when semantics are equal.
- **`cache.key.files`, `CacheInfo::key_input_files` include/exclude: Covered
  selected files / Include selection semantics conservatively.** Collector
  applies include/exclude rules; two different rules may currently enumerate
  identical files. Cover effective normalized definitions, rooted-path identity
  and relevant runtime expansion. Preserve file content hashing; a definition
  digest cannot replace it.
- **`cache.key.env`, `CacheInfo::key_env_keys`: Covered selected values / Include
  selection semantics.** Collector hashes selected values with the
  empty-map/missing-value limitations above. Cover effective key selection,
  preserve runtime values, and decide missing versus empty semantics explicitly.
  Do not treat all env consumers as covered merely because some keys are declared.
- **`cache.output.files`, `CacheInfo::cache_output_files` include/exclude: Covered
  artifact-selection definitions.** Collector hashes output globs even when it
  is not enumerating output files. Retain both sides and root/mode/context
  semantics. These govern artifact preservation/replay, not the command's generated
  bytes; never hash mutable output contents as an accidental replacement for
  input semantics.
- **`cache.output.logs`, `CacheInfo::cache_logs`: Exclude from command semantics;
  artifact-policy decision open.** `record_logs` controls capture and
  `NewCacheInfo::logs` transports captured bytes. No collector log-policy field
  exists. F06.2 must explicitly decide whether changed capture policy needs a
  versioned artifact-policy contribution or an enforced replay sufficiency rule.
  Do not equate this with display-only `output_logs`, or claim that excluding it
  guarantees log availability.

### Project identity and observations

- **`Project::{name, dir}`, node names/full name/directory: Covered names /
  Include consumed location context conservatively.** Collector hashes full name;
  directory anchors hashing and process cwd but is not directly inserted as a
  string. Cover consumed path/context semantics without blindly hashing absolute
  machine paths. `TaskChildProcess::new` in
  `crates/omni_process/src/task_child_process.rs` uses project directory as cwd.
  Relocation invariance needs proof when expressions consume paths.
- **Project `file`, config extension closure: Covered when default file inputs
  enabled; Exclude independent provenance identity.** File location seeds ordinary
  inputs. Do not turn virtual project ids into file inputs. Keep declared
  config-file hashing; include resulting effective task settings rather than
  entire plugin output.
- **Other tasks, plugin artifact/options/observed discovery inputs: Exclude
  independent execution identity.** They belong to discovery
  invalidation/composition. Only their effective contribution to this task
  participates. Sibling-only changes or plugin updates yielding identical
  effective semantics must leave the added fingerprint unchanged.
- **`NewCacheInfo` duration, exit code, tries, captured logs; timestamps, notices,
  diagnostics, eligibility explanations: Exclude results/observation/provenance.**
  Result data is persisted separately, not fed into `get_digest`. Retry policy is
  included above; measured attempts/duration are not. Keep cache layout, remote
  destination/credentials, pruning sizes and last-use timestamps out of task
  semantic identity.

## Definition versus runtime context

The future combined key must cover the consumers below. This does **not** propose
hashing all ambient state into the finalized definition contribution.

### Command resolution

`resolve_command`, `resolve_command_with`, `resolve_operand` in
`crates/omni_command_config/src/resolve.rs` resolve Shell with Tera, then env
expansion, then shlex split. Legacy argv uses per-element Tera/env expansion without
splitting. Literal operands bypass both. Interpolated operands bind opaque
placeholders and substitute literal values after expansion.

Preserve interpretation and single-pass literal substitution. Cover resolved
execution contribution or sufficient real context for both main and retry
commands; display rendering is not evidence of equivalence.

### Template context and platform

`create_template_context` supplies `env`, merged `meta`, and configured args
overlaid with invocation args; `STANDARD` supplies `platform`. Only configured
args and selected env keys reach the collector today. Conservatively include
effective metadata and platform context; runtime merged args and consumed env
must have an explicit hashing owner. No static dependency-analysis proof exists
here for narrowing arbitrary Tera expressions.

`Platform::infer`, `STANDARD` in `crates/omni_tera/src/context.rs` expose
`platform.host`, `.os`, `.arch`, `.vendor`, `.binary_format`, not independently
hashed. Platform-dependent expression changes must not hit a key based on
identical raw text. Include or prove equivalent coverage; do not invent a
`platform.env` Tera field.

### Environment preparation

`ProjectDataExtractor::{get_ws_vars_vars, extract_all}` generates env values:
`WORKSPACE_DIR`, `OMNI_VERSION`, `PROJECT_NAME`, `PROJECT_DIR`, `PLATFORM_HOST`,
`PLATFORM_OS`, `PLATFORM_ARCH`, `PLATFORM_ENV`, `PLATFORM_VENDOR`,
`PLATFORM_BINARY_FORMAT`, plus workspace/project vars. These can reach expressions
and child processes. Full-name hashing covers names only indirectly, not all
generated values. Path/version/platform changes require a deliberate
projection/runtime policy.

`EnvLoader::get` in `crates/omni_context/src/env_loader.rs` and
`LoadedContext::get_task_env_vars` in `crates/omni_context/src/loaded_context.rs`
combine optional inherited environment, env files, workspace/project/task
expansion, including `CommandExpansionConfig::new_enabled` command substitution.
A fixed setting can produce changing values. Keep ordinary env/file inputs.
Resolve ownership of expansion outputs/consumed env; raw settings and env-file
names alone do not prove runtime equivalence. External command effects/tool
binaries remain declared-input/cacheability concerns.

### Executor-only resolution

`expand_templates`, `expand_omni_path` in `batch_executor.rs` Tera-expand
input/output includes and excludes with the task context, preserving `OmniPath`
root. Cover definitions and effective selected rules consistently in hashing and
maintenance. No equivalent expansion was found in direct project-hasher or hybrid
stale collection paths.

`evaluate_bool_expr`, `resolve_retry`, `run_process` in `batch_executor.rs` consume
runtime condition, invocation retry override, interactive stdin, and actual
process argv/env/cwd. Shared resolution must preserve current behavior and errors;
classify invocation overrides explicitly rather than silently adding them to a
once-per-definition digest.

### Nondeterminism and ambient process state

`one_off` in `crates/omni_tera/src/lib.rs` uses the full preset from `register_all`
in `crates/omni_tera/src/preset.rs`, which registers `now`, `get_random`, and
`shuffle`. Even a complete static context can yield nondeterministic output.
This is an open cacheability/resolution decision: context hashing alone is
insufficient. Do not claim this audit makes time/random expressions or side
effects safe to reuse.

Normal child creation in `crates/omni_process/src/child.rs` uses
`tokio::process::Command` with `.envs(env)` without `env_clear` in the inspected
normal branch. The provided task env map is not demonstrated to be the complete
child environment. Untracked ambient process reads remain a limitation; changing
process inheritance is outside F06.1.

Any safe narrowing must account for indirect indexing, conditionals and runtime
functions, not just literal occurrences of `{{ meta.x }}`. Conservative inclusion
may over-invalidate; silently treating unproven context as presentation-only risks
wrong hits. F06.2/F06.3 must distinguish completeness of expression resolution from
the ordinary contract that tasks declare filesystem/environment/tool inputs.

## Constructor and cache-maintenance inventory

All production `ProjectTaskInfo` struct literals found by repository-wide Rust
search are listed here, including the synthetic workspace path. None currently
carries the named semantic contribution.

### Extraction and execution transport

- `crates/omni_context/src/project_data_extractor.rs`:
  **`ProjectDataExtractor::extract_all`** is the sole production `CacheInfo`
  literal found. It reads `FinalizedProject::task_cache`, normalizes input/output
  globs, and supplies configured args, enablement, defaults, env keys and log
  capture. F06.3 must establish finalized definition projection here or at an
  explicitly documented later shared boundary. Retain enough data for
  post-resolution runtime contribution; no plugin-supplied signature is authoritative.
- `crates/omni_task_context/src/default_provider.rs`:
  **`DefaultTaskContextProvider::get_task_context`** borrows `CacheInfo` and builds
  template context/dependency hashes. **`TaskExecutionInfoExt::execution_info`**
  in `crates/omni_cache/src/exts.rs` constructs `TaskExecutionInfo`, omitting runtime
  template context/merged overrides. F06.3 must transport the mandatory contribution
  without using cache eligibility to erase information needed by
  hashing/maintenance. Own or delegate effective runtime resolution explicitly.
- `crates/omni_task_executor/src/cache_manager.rs`:
  **`CacheManager::{get_cached_results, cache_results}`** converts eligible task
  contexts to execution info for lookup; normal write wraps it in `NewCacheInfo`
  and calls `cache_many`. Use the same semantic inputs for lookup and persistence.
  Preserve eligibility checks and the replay recheck in
  `BatchExecutor::execute_batch_inner`.
- In the same file, **`CacheManager::cache_results` dry-run branch** constructs
  `ProjectTaskInfo` directly from execution info, then calls `Collector::new` with
  `CollectConfig { digests: true, .. }`. Copy the contribution identically;
  dry-run display/redaction must not become key input. Compare against a real run
  on unchanged input state.

### Hashing without execution

- `crates/omni_context/src/project_hasher.rs`: **`ProjectHasher::hash`** constructs
  local `ProjectTaskInfoTmp` and direct `ProjectTaskInfo` from plan batches,
  `get_cache_info`, `get_task_env_vars`, configured args and prior dependency
  digests. It calls collector with input collection/digests enabled. Plumb
  definition and runtime contribution through both temporary/final structures.
  Reconcile args and path-template resolution with executor; do not merely add a
  field and assert parity.
- `crates/omni_context/src/workspace_hasher.rs`: **`WorkspaceHasher::hash`**
  constructs a local temporary structure and direct `ProjectTaskInfo` per project
  named `temp`, commands absent, union of input includes only; empty excludes,
  outputs, env, dependencies and args. Explicit design decision required: this is
  not per-task collection today. Define deterministic aggregation of actual task
  contributions or a documented equivalent; do not give the synthetic task an
  empty digest slot and claim workspace coverage.

### Hybrid store and maintenance

These symbols are in `crates/omni_cache/src/cache/impls/hybrid.rs`:

- **`HybridTaskExecutionCacheStore::collect`** constructs `ProjectTaskInfo`
  directly from `TaskExecutionInfo`, then calls `Collector::new`/`collect`.
  It is shared by local/remote task lookup and persistence. Copy mandatory
  contribution for all callers, including `get_many` (`cache_output_dirs: true`
  implies digest) and `cache_many` (digests, inputs, outputs and cache dirs).
  No storage/remote schema change is required by the RFC.
- **`HybridTaskExecutionCacheStore::prune_caches`**, for `stale_only`, builds a
  current execution plan and `DefaultTaskContextProvider` with `HashProvider` per
  batch, calls `execution_info`, then shared `collect`, and accumulates fresh
  hashes. Recompute the same finalized/runtime identity and dependency digests as
  executor. Address missing executor path expansion here; current cache entries
  cannot supply current definition semantics.
- **`HybridTaskExecutionCacheStore::{get_stats, plan_task_set}`** reads persisted
  entries for stats, optionally filtering with a current plan. It does not
  recompute current semantic digests. Non-stale prune may plan for filters without
  collecting digests. Test report/filter behavior and stale pruning together,
  but do not describe stats as an independent fresh-key constructor.

### Collector and fixture constructors

`crates/omni_collector/src/collector.rs`: **`Collector::{collect, get_digest}`**
copies `ProjectTaskInfo` into internal holders and constructs `HashInput` for
digests/cache-output dirs. The named, versioned contribution must reach the final
hasher independently of default-file-input selection and collection flags.

Test constructors also need migration: `Project::info` and collector fixtures in
`crates/omni_collector/src/collector.rs`, `info` in
`crates/omni_task_executor/src/cache_manager.rs` (`CacheInfo`), and
`task_from_static` in `crates/omni_cache/src/cache/impls/hybrid.rs`
(`TaskExecutionInfo::new`, with `task_with_mut`/`task` helpers). Update derived `new`
call sites when type signatures change; fixtures must not make the contribution
optional for production. Re-run repository-wide constructor searches in F06.3.

## Follow-up owners and required evidence

### F06.2: Projection, encoding and unresolved policy

F06.2 owns the typed semantic projection and versioned canonical encoding contract:
fixed field order, explicit presence/type/length framing, canonical maps, preserved
order-sensitive lists, omni's content hasher, golden vectors and benchmarking of
the actual path. An illustrative slot name is `effective-task-config/v1`, not an
implemented symbol. Do not use standard-library `Hash`, an intermediate arbitrary
JSON serialization contract, a synthetic file, or the full project/plugin payload.

Before claiming completeness, F06.2 must resolve or explicitly carry forward:

1. Definition versus invocation contribution boundary: merged args, retry overrides,
   environment/platform/path expression context, and whether a shared resolved
   command contribution is needed. Rendering nondeterministic expressions twice
   is not a correctness strategy.
2. Conservative rules for metadata/env/context narrowing and absolute-path
   relocation. Existing hybrid test
   `test_moving_project_folder_should_not_invalidate_cache` documents an important
   baseline, not proof that path-consuming expressions are location-independent.
3. Artifact preservation policy: output selection is already key material;
   log capture needs an explicit sufficiency/invalidation decision separate from
   command semantics and log display.
4. Normalized resolved dependencies/co-scheduling representation, and where graph
   resolution becomes available relative to “once per finalized task.”

Required unit/golden tests: equal effective defaults and explicit values; map-order
invariance; ordered operands/list changes; presence/type/boundary collision cases;
Shell/Argv/Operands distinctions; literal versus expression with identical text;
interpolated binding values and single-pass substitution; main/retry command
changes; every included flag/retry field; rooted include/exclude differences;
metadata used in expressions; inherited changes versus masked overrides;
presentation/provenance-only edits; unrelated sibling task changes; identical
effective output after plugin changes. These are requirements, not tests added here.

### F06.3: Transport and behavioral parity

F06.3 owns all constructor/transport paths above and the explicit workspace-hasher
aggregation and shared runtime/path-resolution decisions. Required integration
fixtures must demonstrate:

- Definition changes miss with `cache.key.defaults: false`, for explicit and
  inferred effective tasks; no constructor can omit the contribution.
- Same finalized task and invocation produce matching collector identity through
  real executor lookup/write, dry-run, project hash, chosen workspace aggregation,
  hybrid lookup, and stale-prune fresh-key recomputation.
- Fixed expressions with changed consumed metadata, env, platform or invocation
  args invalidate; literal operands do not accidentally expand. Exercise
  templated input/output includes **and excludes**, not just commands.
- Output-selection changes invalidate preservation identity; log-capture tests
  enforce the F06.2 policy without making log display/redaction key material.
- Old entries become stale after a semantic change; unchanged entries remain
  fresh; stats/filter/prune observations agree. Local and remote lookup share
  identity without changing their stored formats.
- Disabled/persistent tasks cannot replay or persist, while eligible unrelated
  tasks still hit. Coordinate uncached-dependency demotion/zero-sentinel exclusion
  with its owning RFC slice; a digest contribution is not that fix.

`cache_many` recollects ordinary inputs after execution. Mutating tasks can
therefore be addressed by post-state. Parity fixtures need controlled unchanged
inputs, plus explicit mutating/idempotence cases before making reuse-safety claims.
F06 does not authorize a pre-execution snapshot redesign or certify side effects,
interactive input, ambient environment, time/random expressions or external tools
as cacheable. Those remain explicit limits/open decisions.
