# F08.4: Atomic references and lockfile publication

For source-manager contributors. Implements the single-file publication contract
approved in [F08.1](F08.1-lease-gc-reference-protocol.md).

## Assessment and plan

- **Kind / risk:** Medium / High (persistent data and cross-process concurrency).
- **Extent:** `omni_utils` publication helper, `omni_lockfile` saves and
  `omni_remote_source` reference updates. No persisted format changes.
  MCP generator/tool bounds explicitly include the new filesystem operations;
  the API and CLI are checked downstream.
- **Unknowns:** injected filesystem failure behavior, Windows replacement rename,
  and cancellation while blocking filesystem work is running.
- **Undo:** revert the code; existing file formats remain readable. Failed
  publication leaves the old file; crashed staging files are inert.
- **People / execution:** solo implementation of the approved design, independent
  PR review before merge. Three steps: test atomic publication, implement locked
  complete/additive updates and saves, then test failure and concurrent callers.
- **Checks:** crate tests, scoped clippy/format, real-filesystem process tests and
  failure-injecting filesystem adapters. Check downstream remote-source callers.
- **Next / escalation:** start with publication. Reassess if filesystem abstractions
  require a new platform layer or a format migration.

## Decisions

- D4: per-file publication, not cross-file transactions. Contributor staging and
  sequencing remain F08.5.
- D6: corrupt/unreadable reference sets are errors for both update modes. No
  implicit repair option in this slice.
- Keep `record_refs` as a documented compatibility wrapper; deprecation annotation
  waits until F08.5 migrates callers, so existing warning-denying checks still pass.
- Use exclusive-create same-directory staging, flush and sync before rename.
  Temporary names never end in `.json`. Publication is atomic visibility on
  filesystems with replacement-rename semantics, not a power-loss durability
  promise (the parent directory is not synced).
- Carry the workspace lock into the blocking publisher so cancellation cannot
  release it while an old snapshot is still being published.
- Pin persistence/reconciliation also require memory cleanup after commit. Their
  publication tail is an owned task holding the workspace guard through both
  disk save and manager-state cleanup, so cancelling the waiter skips neither.

## Acceptance

Complete updates replace, including with empty sets; additive updates union and
new pins win collisions. Concurrent merges lose no entries. Invalid IDs and pins,
corrupt sets and I/O failures leave existing data unchanged. Failed staging or
rename cleans up the staging file; reconciliation ignores crashed leftovers.
Lockfile saves publish the same sorted serialization through the same helper.

## Compatibility and limits

- Existing complete `record_refs` callers remain source-compatible. The wrapper
  now rejects invalid IDs, unsafe pins and corrupt/unreadable existing sets.
- `Lockfile::save` now requires `LockfileSaveSys` (cloneable filesystem with
  synchronous open, rename and remove operations). Read-only loading still
  requires only `LockfileSys`. Existing concrete real/memory filesystem adapters
  supply these operations.
- Production pin persistence/reconciliation own the workspace guard in a task
  spanning publication, saved-change cleanup and (for reconciliation) memory
  pruning. `save_locked` remains available for a lower-level save that only needs
  to carry the guard through publication. Legacy `RemoteSourceManager::lock` delegates to
  `persist_pins` rather than bypassing locking and changed-pin merging.
- Cancellation before handing off to an owned publisher leaves the old file.
  Once handed off it may commit the complete file after the caller is gone, but
  keeps the lock until finished. Pin operations also finish memory cleanup before
  releasing that lock; a retained manager cannot reuse a removed pin or replay
  the cancelled operation's saved changes. Publication failure leaves memory
  unchanged and is logged even when its waiter was cancelled.
  Ordinary write/sync/rename failures return errors.
  Cleanup failure is reported and may leave an inert `.tmp` file.
- Cooperative OS locks and atomic replacement rename are required. Older omni
  writers still use the old unlocked/direct-write protocol; stop them before
  relying on these guarantees. No disk-format migration prevents mixed writers.
