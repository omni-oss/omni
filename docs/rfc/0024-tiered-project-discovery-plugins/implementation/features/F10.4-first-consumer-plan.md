## Goal and done

For a **confined** script (`enable_experimental.capabilities` on, so `EffectivePolicy::enforce`) and with the new opt-in on, the two read routes read a workspace file through one `InputView::read`: authorization by the existing policy (via an adapter), containment checked at open time (Linux `openat2`, Windows handle walk), limits enforced before allocation. Done means the tests below pass on Linux, Windows and macOS (macOS asserts `Unsupported`), the release note ships, and everything else behaves exactly as before.

Out of scope: `exists`, `list`, `stat`, `is-*`, writes, `revalidate`, evidence use, symlink following (D2: configurable, rejected by default, reject-only in the first release), any change to cache keys, walking, or the three capability crates.

## Decisions (confirmed by the maintainer at build approval)

1. **Seam.** A new crate `omni_contained_read` (leaf: `omni_input_view`, `omni_containment_configurations`, `omni_capability_sys` for the `CapabilityAuthorizer` trait, `omni_capabilities` for `Request`, `omni_path_utils`, `omni_utils`, `omni_diagnostic`, `system_traits`, `tokio`, `async-trait`, `tracing`). It holds the adapter `CapabilityInputAuthorizer` (maps `CapabilityAuthorizer` to `InputAuthorizer`; builds the request from `root.join(workspace_path)`; maps `Decision::Deny` to the view-local `DenyReason`; never an implicit allow) and `ContainedReader<S>` implementing only `BaseFsReadAsync`. A new crate keeps the High-risk crates unedited; the dependency edge is one-way. Sharing the policy: `CapabilityAuthorizer` is infallible and `EvaluatingAuthorizer` is not `Clone`, and `PolicyEnforcingSys` consumes its authorizer without a getter, so the runners build the authorizer once, wrap it in `Arc`, and pass a `SharedAuthorizer<A>(Arc<A>)` newtype (defined in `omni_contained_read`, implements `CapabilityAuthorizer` by delegation) to both `PolicyEnforcingSys` and the adapter. The adapter's `AuthError` is raised only when the request cannot be built (the root-joined path is not representable); it does not claim to detect evaluation failure, which the infallible trait cannot report.

   **Composition with `TransactionSys` (generators).** `script_runner.rs` wraps `TransactionSys<S>` (overlay of uncommitted writes, deletions and dry-run state, `transaction_sys.rs:351-377`) in `PolicyEnforcingSys`. A contained read must not bypass that. `ContainedReader` is generic over a small seam trait `ReadThrough` with two methods: `resolve(path) -> io::Result<PathBuf>` (fallible: the sys's own current-directory resolution; generator: `TransactionSys::resolve`, tool: `EnvCurrentDirAsync` of the sys) and `read_through(path, real)` (the overlay mutex is held across the `spawn_blocking` contained read, as it is across the wrapped-sys read today, so timeouts and cancellation happen inside that lock) where `real` is the contained disk read. The generator implements it with a new `TransactionSys::read_with(path, real)` that serves an overlay hit, returns `NotFound` for a shadowed deletion, and only on a miss calls `real` and mirrors the bytes into the overlay exactly as today; `base_fs_read_async` is rewritten to call `read_with` with the wrapped-sys read, so existing behavior is identical. `ContainedReader` calls the adapter's `authorize` on the root-joined, cleaned path **before** `read_through` (so before the overlay is consulted), exactly the order `PolicyEnforcingSys` gives today; `InputView::read` authorizes again on a miss, an accepted double evaluation. A denied path with an overlay entry returns `PermissionDenied` (test 2). The tool runner has no overlay and uses the plain implementation.
2. **Routing (fail closed; a script cannot pick its way out).** `ContainedReader::base_fs_read_async(path)` classifies every path before any read, in this order:
   1. **Relative path:** resolved by the seam's `resolve` (the sys's own cwd, the one `set-current-dir` changes and that `InMemoryCwdSystem` and `TransactionSys::resolve` use today), then classified as absolute. A path the seam cannot resolve (cwd lookup fails; `TransactionSys::resolve` is infallible today and would return a still-relative path, so the new seam method checks that case) is `InvalidInput`, and `ContainedReader` fails closed with `InvalidInput` if the resolved path is not absolute, before `WorkspacePath::from_os_path` (which would otherwise read a relative path as workspace-relative). A test changes the directory and proves the same file is read as today.
   2. **Not UTF-8:** `InvalidInput`, nothing read (it cannot be a `WorkspacePath`; a small behavior change for opted-in runs, in the release note).
   3. **Lexical normalization:** `..` and `.` are removed with `omni_utils::path::clean` (which also normalizes Windows `\\?\` verbatim prefixes; raw `path_clean` would leave `..` after a verbatim prefix; never filesystem resolution). A cleaned path that is under the canonical workspace root (`WorkspacePath::from_os_path`, which accepts `\\?\` and drive spellings on Windows) is read through a **fresh `InputView` per call** on `spawn_blocking` with a `Cancellation` tied to the request. Only the cleaned, root-relative name reaches the view, so it cannot escape; `a/../b` where `a` is a symlink is judged by its cleaned name, never by what the OS would resolve.
   4. **Only `WorkspacePathError::OutsideRoot` may be delegated** to the existing `PolicyEnforcingSys` (remote-source store, granted extra dirs, any path wholly outside the workspace). Every other classification error (`DotDotSegment` cannot occur after cleaning, `NotUtf8`, empty, invalid) fails closed with `InvalidInput` or `PermissionDenied`; there is no "otherwise delegate".
   5. **Aliases of the workspace are not an outside path.** A delegated path is first resolved with the broker's `resolve_real_path` rules (canonicalize, deepest existing ancestor, the `has_root` precondition). That function is private to `omni_capability_sys`, so a copy lives in `omni_contained_read`, pinned to the broker's behavior by a parity test over the same fixtures; its output is passed through `omni_utils::path::clean` before the inside-root test, because a dangling link target such as `../ws/x` is otherwise left uncleaned and would classify as outside; if the resolved target is **inside the canonical workspace root** (for example `/alias-of-ws/x` through a symlinked parent, or a link outside pointing in), the read is refused with `PermissionDenied` ("use the workspace path") and never delegated. This alias check is a **best-effort, racy** pre-check, as today's broker is; the guarantee is therefore stated narrowly: *a read of a name inside the workspace that is served from disk is contained; a read served from the generator transaction overlay returns the transaction's own state, which write routes (append, copy, rename) fill through the broker, so contents copied from a symlinked source are not re-checked by the view (contained write-side routes are a later plan, named in the release note); a read that reaches the workspace through an outside alias is refused when the alias is visible at check time, and otherwise is still subject to the broker's documented residual race and the OS sandbox floor*. The plan does not claim more.

   `Missing` becomes `io::ErrorKind::NotFound`, as today. If `Root::Workspace` is absent from the policy roots, every read fails closed (tested).
3. **Per-call view, not per-run.** Runners are pooled across invocations, so one long-lived view would exhaust `max_total_bytes` and `max_operations` and keep evidence forever. A view per read gives each read the file, path and depth limits; evidence and `revalidate` are **not used** by this consumer and stay for the discovery/plugin consumers. Root-handle cost per read is one directory open (the F10.2b benchmark: about +6 us per file over plain reads).
4. **Opt-in.** New experimental key `contained_reads` in `omni_experimental_features` (`ExperimentalFeatures::contained_reads()`), **default off**. It only has an effect when capabilities enforcement is on; if it is set without enforcement, the run continues unchanged and a notice `capabilities.contained_reads_ignored` (prefix `capabilities`, owned by `bridge_rpc_runner`; `input_view` belongs to `omni_input_view` and would conflict in `omni_codes::validate`) says it was ignored (new, registered in `bridge_rpc_runner/src/notices.rs` and `omni_codes`, emitted at the same point and with the same cadence as `CapabilitiesIgnored`, i.e. once per run invocation, before the pool lookup, not per read or per process spawn). Caveat in the release note: the bare form `enable_experimental: true` enables every experimental feature, including this one; use the map form to exclude it. Why opt-in: macOS and Linux without `openat2` are `Unsupported` (D5, no fallback), so on-by-default would turn every confined read on those hosts into an error. On an unsupported host, enabling it makes every in-workspace read fail with `input_view.containment_unsupported` and its hint, and nothing is read.
5. **User-configurable limits within host bounds** (the #169 requirement). Workspace config only (a project, generator or pack cannot raise them; plugins cannot):

   ```yaml
   containment:
     limits:
       fs:
         read:
           max_file_bytes: 4194304   # any InputLimits field; absent means the default
   ```

   The key is `containment.limits.fs.read` (maintainer choice, nested): `containment` is the home for how the host bounds access, `limits` for its budgets, and `fs.read` mirrors the capability domain `fs.read` as two nested keys, so no key contains a dot (a dotted key would be ambiguous in the dotted config paths used by diagnostics and provenance). `capabilities` stays where it is; moving it under `containment` is a separate later plan. The name does not mention the mechanism (`input_view`), and a later `fs.write` or another domain sits beside `fs.read`.

   Every `InputLimits` field is accepted, as optional integers. The types, the ceiling constants, the defaults and the validation live in a new **config-only crate `omni_containment_configurations`** (higher level than `omni_input_view`: serde and schemars (behind optional features, as `omni_experimental_features` does), no OS code, no dependency on `omni_input_view`, `omni_capability_*` or `omni_configurations`; it defines `FsReadLimits` and `ContainedReads { limits: FsReadLimits }`). `omni_configurations` embeds its `ContainmentConfiguration` in `WorkspaceConfiguration`; **Dependency edges, stated exactly:** `bridge_rpc_runner` depends on `omni_containment_configurations` only, because `EffectivePolicy` (defined in `capability_plan.rs`) carries the config-side `ContainedReads`, so `bridge_rpc_runner` gains neither `omni_input_view` nor `omni_configurations`; `omni_generator` and `omni_tool`, which build the readers at their registration sites (`script_runner.rs:287`, `bridge_runner.rs:279`), depend on `omni_contained_read` (and `omni_containment_configurations`); `omni_contained_read` depends on `omni_input_view` and `omni_capability_sys`, so `omni_generator` and `omni_tool` take on OS-level code through it, in the same class as the `omni_capability_sys`/`omni_capability_enforcement` edges they already have; `omni_api` reaches the config types through a re-export from `omni_configurations`, so it gains no new edge. No cycle: none of those crates depend on `bridge_rpc_runner`, `omni_generator` or `omni_tool`. Validation runs during deserialization of `WorkspaceConfiguration::load` (which runs serde only) through a raw struct with `#[serde(try_from)]`, which also carries the cross-field rule (`max_file_bytes` ≤ effective `max_total_bytes`); the schema is generated from the raw struct (`#[schemars(with = "Raw")]`), and a snapshot test over `schemars::schema_for!(WorkspaceConfiguration)` (the raw struct's fields carry `#[schemars(range(min = 1, max = <ceiling>))]` so the schema holds the per-field bound) (the existing pattern in `workspace_configuration.rs`; there is no checked-in schema file) asserts that the schema and the deserializer agree on per-field shape, bounds and unknown keys; the cross-field rule (`max_file_bytes` ≤ effective `max_total_bytes`) cannot be expressed in the schema and is covered by deserializer tests only, documented as a known difference. The conversion into `omni_input_view::InputLimits` lives in `omni_contained_read`. A value of `0`, above the host ceiling, or a `max_file_bytes` above the effective `max_total_bytes` is a **configuration error** at load (not silently clamped), with a diagnostic naming the key and the bound. Ceilings (host-owned constants in `omni_containment_configurations`): `max_path_bytes` 4096 and `max_path_depth` 64 (lower only), `max_file_bytes` 64 MiB, `max_total_bytes` 256 MiB, `max_tracked_inputs` 32768, `max_dir_entries` 100000, `max_total_dir_entries` 500000, `max_dir_scan_entries` 1000000, `max_operations` 100000, `max_reported_changes` 1000, `max_observations_per_path` 64. Defaults are unchanged (the F10 table). Honest note for the docs: with a per-call view the path, depth, `max_file_bytes` and `max_total_bytes` (both bound a single read, so raise both) shape this consumer's behavior; the others are accepted, validated and carried so later consumers need no new key.
6. **Errors to the script (plugin-facing disclosure).** `InputError` becomes `io::Error` with a kind (`PermissionDenied` for denial, containment, name and policy errors; `InvalidInput` for limits and path shape; `NotFound` for `Missing`; `Unsupported` for `ContainmentUnsupported`; `Io` keeps its kind) and a message `"<code>: <message>"` using the existing diagnostic code and the **workspace-relative** path the script supplied. No absolute host path, no host-only detail beyond what the script already knows. Exhaustive map, pinned by test 5: `Denied`, `PolicyUnavailable`, `Symlink`, `EscapesRoot`, `MountCrossing`, `ReparsePoint`, `UnsupportedName`, `CaseMismatch`, `NotRegular`, map to `PermissionDenied`; `NotDirectory`, `InvalidPath`, `TooLarge`, `Budget` and `SymlinkPolicyUnsupported` to `InvalidInput`; `ContainmentUnsupported` to `Unsupported`; `Io` keeps its kind; `Cancelled` (no diagnostic code, `#[diagnostic(skip)]`) to `Interrupted` with the text `input_view: read cancelled`. `WorkspacePathError::OutsideRoot` embeds the absolute root and is **never** formatted into a script-facing message; routing handles it before any `InvalidPath` is built. Host side: the full diagnostic is logged with `tracing` at `warn`. No host notice is raised because the host does not continue past a failed read; the script decides (the #179 notice obligation applies to a host that skips an input, which this consumer does not).
7. **Symlinks.** `SymlinkPolicy::Reject` only. In an enforced, opted-in run, reading through a workspace symlink (pnpm `node_modules` links, a symlinked file) is an error today-allowed-becomes-rejected; this is the main behavior change and is why it is opt-in.
8. **No fallback anywhere.** No `canonicalize` path on error, no retry on the old broker for in-root reads, on any OS.

## Behavior changes (for opted-in, confined scripts reading inside the workspace)

| Before | After |
| --- | --- |
| Symlinks in the path followed if the real path is allowed | Rejected: `input_view.symlink` (Windows: any reparse point, `input_view.reparse_point`) |
| Check then open (residual swap race) | Authorize lexically, then one contained open; for a name inside the workspace a swap cannot reach outside the root. Outside aliases of the workspace are refused when visible (best effort, see decision 2.5) |
| Non-UTF-8 path | `InvalidInput` |
| `a/../b` with `a` a symlink read `target(a)/../b` | Cleaned lexically: reads `ws/b` (safe, but a different file) |
| Generator overlay (written, copied, deleted earlier in the run) | Unchanged: overlay state is served; bytes copied from a symlinked source by a write route are not re-checked on read |
| Any size, read whole file | `max_file_bytes` (8 MiB default) enforced before allocation: `input_view.too_large`; budgets per call |
| `a:b`, `con`, `x.` readable on Linux | `input_view.unsupported_name` on every OS |
| FIFO, device read (could block) | `input_view.not_regular` |
| macOS, Linux without `openat2`, aarch64 `cross` container | `input_view.containment_unsupported`, nothing read |
| Windows case-insensitive spelling | exact spelling or `input_view.case_mismatch` |

Unchanged: outside-workspace reads, all other routes, runs without the key, runs without capabilities enforcement, cache keys, `omni cache` output, config schema for existing keys.

Verified by the audit command in `docs/patterns/cache-keys.md` over the commits of this PR: the PR must touch none of the listed paths. A guard test is not needed because the PR's changed-file list is the evidence; the PR description states it.

## Failing-first tests

Written first, red against the unwired code, then made green. All Windows-portable (tempfile, `std::path`, no hard-coded separators); symlink and junction cases use `omni_test_capabilities` with the repo's `OMNI_TEST_REQUIRE_CAPABILITIES` contract; Linux-only containment cases gate on `openat2` with the named skip used by the view tests (aarch64 `cross` asserts `Unsupported`).

## Implementation record

Built as planned, with these recorded differences (found while building, none changes a decision):

- **Bounds are checked after the parse, at the context load, not during deserialization.** The configuration loader (`omni_file_data_serde`) deliberately reports only the format, key path and position of a parse failure, because a parser message can quote the file. A `try_from` error would therefore show `containment.limits.fs.read` and nothing about which limit or ceiling. The types now reject unknown keys at parse time (structural), and `FsReadLimitsConfiguration::resolve` checks `0`, the ceiling and `max_file_bytes <= max_total_bytes`. The context load runs it and raises `workspace.invalid_containment` (new code, in `omni_context`) naming the key and the bound; `WorkspaceConfiguration::contained_reads` runs it again for a configuration built in code. The schema still carries the `1..=ceiling` range per field.
- **`ContainedReads` is `Copy` and travels by value** (`Option<ContainedReads>`), including in the `Copy` `HandlerContext`, so no borrow was needed.
- **Seam:** `ReadThrough::resolve` is fallible and `TransactionSys` gains `resolve_checked` and `read_resolved` (`base_fs_read_async` now calls `read_resolved`, behavior unchanged). `omni_contained_read` implements `ReadThrough` for nothing itself; `omni_generator` implements it for `TransactionSys`, and `omni_tool` uses `PlainReadThrough`.
- **Dependencies:** `bridge_rpc_runner` depends on `omni_containment_configurations` only; `omni_generator` and `omni_tool` depend on `omni_contained_read`.
- **Verified here:** unit and integration tests for the new crates, the `TransactionSys` composition (write-then-read, delete-then-read, dry-run state, overlay miss, denied path with an overlay entry, relative path), the bridge router, the experimental key, the workspace config and its schema, the diagnostics and code registry, the fingerprint, and a real CLI end-to-end suite (`tests/omni-tests/src/generator-contained-reads.e2e.spec.ts`, 7 tests, run with `bun` as the JS runtime on x86_64 Linux). Windows and macOS behavior and the aarch64 `cross` lane are proven only by the native CI jobs.
- **Found in code review and fixed:** (1) an outside path is delegated to the broker in its cleaned form (the form that was judged), not as the script spelled it, so `outside/link/../x` cannot be resolved differently by the broker; the alias check probes both the cleaned and the original spelling. (2) The alias check refuses unless the resolved path is provably `OutsideRoot` (an inside path that is not a valid workspace path, such as a name with a backslash, is refused, not delegated). (3) The seam is keyed by the path it resolved (the form its own writes use, so the generator overlay cannot miss on Windows verbatim or drive-case spellings); the view cleans that path itself. (4) A `NotFound` from the seam (including a buffered deletion) is a plain `NotFound` without the absolute host path. The race between the alias check and the broker read is accepted and documented (best effort; the broker still checks the real path against the policy).
- **Not done, by design:** `exists`, `list`, `stat`, writes, revalidation, evidence, symlink following, contained write-side routes (bytes copied from a symlinked source stay unchecked on read from the overlay).
