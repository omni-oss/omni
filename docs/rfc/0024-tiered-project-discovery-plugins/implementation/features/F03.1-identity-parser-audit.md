# F03.1: task identity and reference-path audit

For the implementers of F03.2, F03.3 and F04. This inventory is grounded in
`490e133e3684b14af919a01bd668728b29181253` (after PR #101). It records current
behavior and required changes, not implemented scoped-reference support.

The contracts remain [F03](F03-scoped-task-references.md),
[§7.2](../../007.01-layer-order-and-merge-semantics.md#task-dependency-references-and-explicit-project-syntax),
[§7.4](../../007.03-task-scoping-aliases-and-selectors.md#qualified-reference-syntax-and-escaping)
and [§17.10](../../017.00-review-findings-and-prerequisites.md#1710-canonical-task-identity-versus-invocation-identity).
Those sections, not this inventory, own the grammar and binding policy.

## Findings that determine the implementation order

- `TaskDependencyConfiguration` accepts strings only. Its unanchored regex can
  accept a prefix/substring of malformed input; neither it nor its `Display`
  implementation handles reference escapes or activation/local-name components.
- R06 separated exact names from patterns internally, but exact names are still
  compared to a node's task-name string. CLI positional arguments and MCP `tasks`
  still enter the pattern path. R06 did not complete F04.
- Scoped identity cannot be implemented by escaping just the dependency parser.
  Task declarations, extension lookup, executable graph keys, extracted context,
  result/dependency lookup and cache adapters all carry task identity.
- `TaskLayer::Alias` exists for programmatic composition tests; its `alias` key
  is not deserializable. Aliases are neither resolved nor indexed for selection.
- Runtime override arguments are **one flat map for the call**, not a per-task
  map: `ContextWrapper::get_task_override_args` ignores its project/task
  parameters. Keep that behavior; there is no existing multi-binding machinery
  to extend by introducing a new invocation key.

### Parser and schema acceptance handoff (F03.2)

Implement one escape-aware full-input parser and canonical formatter, followed by
surface-specific kind validation. Do not distribute ad hoc `split('#')` or `::`
logic across CLI, configuration and graph consumers.

Required cases from the existing RFC:

- `lint:fix` remains an ordinary name; `native::build` is scoped reference
  syntax, while `native\:\:build` refers to an unqualified literal name.
- `app#native::check\#fast` separates raw project, activation and local task;
  escaped hashes/backslashes/carets survive one decode and round trip.
- Distinguish raw `build::debug`, raw `build\:\:debug`, and raw `build#debug`.
  An object `{project: common, task: 'native::build'}` never reparses `task`
  as a scoped shorthand. Adding `plugin: native` explicitly supplies scope.
- Reject unsupported escapes, dangling backslashes, empty required components,
  extra unescaped separators, unknown/duplicate object fields and mixed
  `project`/`project_root` selectors. Share component validation across objects
  and shorthand, but do not apply shorthand unescaping to object components.
- Declaration keys/`extends`/aliases are same-project identities; exact
  selectors may additionally name a project but cannot be upstream/root
  references. Dependency/`with` references support upstream lookup.
- `project_root` remains typed host/plugin intermediate data using
  `omni_path_utils::ProjectRootId`, not a new handwritten selector. Do not
  expand the handwritten schema just because an internal enum has this variant.
- Dictionary operator framing is independent of name escaping: retain explicit
  additive envelopes for operator-named tasks such as `merge` and `replace`.

Legacy unescaped `::` **declaration keys** need the RFC's activation-aware
migration policy, not a blanket reinterpretation in the lexical parser. Known
configured activations, disabled activations with missing bindings, unresolved
activation IDs, and unknown/removed activations have different outcomes/notices.
The current tree has no activation registry, so record that integration gate
rather than silently activating a new declaration meaning in F03.2.

## Lowering and validation handoff (F03.3)

Observed pipeline:

1. `ProjectConfigLoader::load_project_configs` loads layers, builds the explicit
   file extension graph, composes and calls `LoadedLayer::finalize_composed`.
2. `finalize_composed` resolves task-layer extensions and effective cache
   settings, then finalizes `ProjectConfiguration`.
3. `ProjectDataExtractor::extract_all` creates core tasks; the config dependency
   conversion is currently an infallible `From` into `omni_core::TaskDependency`.
4. `ExtractedDataValidator` checks duplicate project names and missing **own**
   task dependencies/siblings. Graph construction resolves explicit-project and
   upstream edges later.

F03.3 must retain root references and binding/provenance until the surviving
project catalog and task set are available, after composition/inheritance but
before conversion to executable references and final target validation. A
root-based reference must not use the current infallible conversion to guess a
project name. Resolve roots to final runnable project names; keep `dir` real.
Name collisions, removed/non-runnable targets and retained malformed inputs
must fail at their appropriate boundaries.

`add_upstream` in `task_execution_graph.rs` currently recurses through upstream
projects without the named task to find available ancestors. Preserve that
traversal policy while resolving the requested alias separately in each
candidate project; a missing name contributes no edge, while an existing
invalid alias is an error. Apply the same handling to sibling (`with`) edges.

Required integration fixtures: renamed target project preserves root reference;
removed direct target fails; a well-formed reference removed by a later
collection replacement does not fail target existence; malformed/escaping
roots fail at the input boundary even if later replaced; explicit cross-project
objects and equivalent shorthand agree for both dependencies and `with`.

## Rollout and remaining gates

- F03.2 owns parser/type/schema conformance and boundary fixtures. Choose the
  shared low-level type owner before adding dependencies: `omni_configurations`
  already depends on `omni_core` and `omni_types`, while neither depends on
  configurations. Do not introduce a reverse edge or duplicate parsers.
- F03.3 owns composed-catalog root lowering, canonical graph/context wiring and
  final reference validation. It cannot complete root support by adding a
  deserializable enum variant alone.
- F04 owns public exact/pattern CLI/MCP migration, alias-aware selection,
  request-level missing-exact diagnostics, and user migration docs. Its task
  dependency on F03.2 is a minimum, not proof that alias/binding integration is
  already complete.
- Plugin-origin binding, configured-activation migration notices and automatic
  aliases remain gated on the relevant plugin/configuration work. Keep this
  distinction visible in follow-up PR scope and status.
- Preserve R06's explicit all-task requests: hybrid cache planning and
  `ProjectHasher::hash` already use `Call::all_tasks` or `Call::pattern_tasks`,
  not literal `"*"` exact selectors. Bench/test callers also use intentional
  patterns. Do not undo this migration.

This audit changes no parser, public schema, executable identity or cache key.
Undo is removal/revision of the audit. Future code slices require their own
scoped tests and High-risk review.
