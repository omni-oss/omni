# F10 implementation plan: captured input view

**Status:** approved. F10.2a is implemented and its native CI passed on Linux, Windows and macOS (see [F10.2a implementation record](#f102a-implementation-record)); F10.2b is implemented (see [F10.2b implementation record](#f102b-implementation-record)); F10.2c is implemented (see [F10.2c implementation record](#f102c-implementation-record)); F10.3 is implemented (see [F10.3 implementation record](#f103-implementation-record)). All maintainer decisions, including the decision 1 amendment, are recorded below (see [Confirmed maintainer decisions](#confirmed-maintainer-decisions)); no maintainer confirmation is pending. Items the plan author could not verify are F10.2a verification items, not open questions. **Size:** Large (two slices after the F10.1 design). **Risk:** High. The view is a new containment boundary beside the capabilities crates ([AGENTS.md](../../../../../AGENTS.md) risk overrides).
**Design:** [F10.1](F10.1-captured-input-view-design.md) (API, evidence, authorization order, limits, errors). This plan does not repeat it; it fixes the build order, the code seams and the decisions the design left open. Facts below were read in the code at `origin/main` (`e1cdb515`).

## Scope and finish line

Slices F10.2 (tracked contained `read`/`exists`/`list` with limits) and F10.3 (revalidation, reject-on-change). Done when the [F10 acceptance list](F10-captured-input-view.md#acceptance) passes on Linux and Windows and macOS is a tested `Unsupported`. macOS stays `Unsupported` until native macOS CI proves beneath-root containment (decision 5).

Recorded maintainer decisions (see [README](../README.md#decisions-for-finishing-the-standalone-features)), encoded here:

- **D2:** symlinks are configurable and **rejected by default**. The first release is reject-only; the follow mode exists only as a typed option and is not implemented (see F10.2c).
- **D5:** **macOS returns `Containment::Unsupported`** until a verified beneath-root open exists. No best-effort walk on macOS.
- **D9:** **reject** Windows alternate data streams and reserved device names.
- **D6:** `ENOTDIR` on a parent counts as `Missing`. **D8:** a case-spelling mismatch is rejected by the view (exact behavior in [D8 behavior](#d8-case-spelling-behavior), confirmed). **D3:** an atomic replace with identical bytes is not a change.

Maintainer decisions on this plan (previously open questions):

1. **Build on `cap-std`** (not raw `libc`; see the amendment for the Linux `rustix` and Windows `windows-sys` parts), gated on the F10.2a proof fixture. **Amended by the maintainer:** Linux uses a direct `rustix::fs::openat2` and `cap-std` stays for Windows only; see [Decision 1 amendment](#decision-1-amendment). The source evidence shows the fixture cannot pass on Linux with `cap-std` by design.
2. **Symlink follow (F10.2c) is not in the first release.** Ship reject-only with the follow mode kept as a typed option for later. Windows junctions are never followed.
3. **The D9 name check lives only inside the view**, not in `WorkspacePath::parse`.
4. **Digest:** a local digest trait implemented with `blake3`. Do not reuse `omni_hasher::Hasher` (avoids `system_traits` and async dependencies).
5. **CI:** native macOS and Windows test runs are required before the view claims beneath-root containment on those OSes. Until then macOS stays `Unsupported` (D5). The F10.2a proof fixture running on the native CI jobs is what verifies it.
6. **Linux without `openat2` (or equivalent):** always `Containment::Unsupported`. No best-effort containment.

Out of scope: plugin permission schema and hook host services, the restart loop, a transactional snapshot, any change to the task hasher or its index, and edits to `omni_capabilities`, `omni_capability_sys`, `omni_capability_enforcement`, `dir_walker`, `omni_ignore_*` and `omni_glob*`. No discovery consumer is wired here; discovery adopts the view in its own plan (F10 is "usable by", not "used by").

## Slices

Each slice leaves a working system, adds a crate nothing depends on yet, and is reviewed separately. Risk is per slice, set below. F10.2a, F10.2b and F10.3 are High (they hold the containment primitive, the name validator, authorization and the change decision; [AGENTS.md](../../../../../AGENTS.md) security-boundary override): second reviewer, platform CI results attached, and no edit to a capabilities crate in the same PR. F10.2c is Medium only because no follow logic ships; it still gets the same CI evidence.

### F10.2a: crate skeleton, containment primitive and proof fixture

**Risk:** High. It contains the beneath-root primitive, the D9 name validator and the proof fixture, which together are the security boundary. Landed first, with no API on top, so the dangerous part is reviewable alone.

- New leaf crate `crates/omni_input_view` (workspace `crates/*` glob already includes it; add the `[workspace.dependencies]` entries). Dependencies: `omni_path_utils`, `blake3`, `thiserror`, plus the per-OS primitive below: `rustix` (Linux; check whether it is already in `Cargo.lock` as a transitive dependency and add a direct workspace entry, `cap-std` brings `rustix` transitively but the view must name the version it uses), `cap-std` and `windows-sys` (both `cfg(windows)` only; `windows-sys` at `0.61`, the version the workspace crates `omni_capability_enforcement` and `omni_setup` already declare and the one `cap-primitives 4.0.3` resolves in `Cargo.lock` as `0.61.2`; features `Win32_Foundation` and `Win32_Storage_FileSystem`, which cover `GetFinalPathNameByHandleW`, `FILE_SHARE_*`, `FILE_FLAG_*` and `FILE_ATTRIBUTE_REPARSE_POINT`). `cap-fs-ext` is not needed on Windows. Not `omni_capabilities` (see [DenyReason](#denyreason-placement)). No `system_traits`, plugin, runtime, Wasm or discovery crate.
- Types from F10.1 with no behavior: `InputLimits`, `InputError`, `ContainmentViolation`, `BudgetKind`, `Observation`, `Evidence`, `Cancellation`, `InputAuthorizer`, `DenyReason` (view-local). No `ContainmentMode`: there is only one mode (decision 6).
- **Primitives (see the amendment below):**
    - **Linux:** direct `rustix::fs::openat2` relative to the held root `OwnedFd`, with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` (plus `RESOLVE_NO_XDEV` to stop mount crossings), opening with `O_RDONLY | O_CLOEXEC | O_NONBLOCK | O_NOCTTY` (plus `O_DIRECTORY` for `list`). **No fallback.** `ENOSYS` or `EPERM` (seccomp) returns `ContainmentViolation::Unsupported` and reads nothing; `EAGAIN` is retried a small bounded number of times, then returns `InputError::Io { kind: WouldBlock }` (retryable, not a containment claim). `ELOOP` maps to `Symlink`. `EXDEV` (a mount crossing inside the root, from `RESOLVE_NO_XDEV`) maps to its own `ContainmentViolation::MountCrossing`, distinct from `EscapesRoot` (a lexical or `RESOLVE_BENEATH` escape); F10.1 lists it. The kernel enforces the boundary for the whole lookup, including a concurrent rename of an intermediate directory.
    - **Windows:** a component walk the view owns, built only from public APIs. For each component: `cap_std::fs::Dir::open_with(component, &opts)` where `opts` is a `cap_std::fs::OpenOptions` extended with `cap_std::fs::OpenOptionsExt::{share_mode, custom_flags}` (`FILE_SHARE_READ | FILE_SHARE_WRITE`, **no** `FILE_SHARE_DELETE`; `FILE_FLAG_OPEN_REPARSE_POINT`, plus `FILE_FLAG_BACKUP_SEMANTICS` on directories **and on final-component opens**; see the rules below). The handle is wrapped with `Dir::from_std_file` and retained as the base for the next component, so every ancestor handle stays held for the whole walk. After each open the view reads `FILE_ATTRIBUTE_REPARSE_POINT` from the handle's metadata (`cap_std::fs::MetadataExt::file_attributes`, or the std `File`'s metadata; not `std::os::windows::fs::MetadataExt` on cap's `Metadata`, which does not implement it) and rejects any reparse point (symlink, junction, mount point), then checks the final handle with `GetFinalPathNameByHandleW` against the root's final path. **Not** `cap-fs-ext` `DirExt::open_dir_nofollow`: it takes no `OpenOptions` (so no share mode) and only refuses symlinks, not junctions. The Win32 pieces (`GetFinalPathNameByHandleW`, the `FILE_*` constants) come from `windows-sys` because `cap-std`/`cap-fs-ext` do not expose them (`cap-primitives` `windows/fs/mod.rs` `file_path` is `pub(crate)` and the constants are not re-exported).
        - **Why the view owns the walk (verified in `cap-primitives 4.0.3`):** a single `open_at` is handle-relative (`CreateFileAtW` with the start handle, `windows/fs/open_unchecked.rs`). `manually::open` does open intermediate directories with `dir_options()` (`windows/fs/dir_utils.rs:62-72`: `share_mode(READ | WRITE)`, no `FILE_SHARE_DELETE`; used at `fs/manually/open.rs:222`); the `READ | WRITE | DELETE` default in `windows/fs/open_options_ext.rs:31` applies only to file `OpenOptions`, so share mode is not the reason. The reason is that `manually::open` follows in-root symlinks and junctions, drops its ancestor handles as it goes, and offers no `GetFinalPathNameByHandleW` check; the view must reject **all** in-root reparse points, retain every ancestor handle and run the final-path check itself. The view still sets the share mode explicitly on its own opens. That held handles block an ancestor rename is **unverified** until the Windows gate passes.
        - **`FILE_FLAG_OPEN_REPARSE_POINT` is what makes the walk safe (verified in `cap-primitives 4.0.3`).** With it in `custom_flags`, cap's own nofollow enforcement is off (`windows/fs/open_unchecked.rs:162-163`: `enforce_nofollow` requires the flag to be absent), so the open returns the reparse point itself instead of `manually::open` following it (`fs/manually/open.rs:268-280,376-382`). Without it, a final-component symlink can be followed. The gate must include a test that omits the flag (or otherwise lets a final-component symlink be followed) and **must fail**, proving the flag is load-bearing.
        - **Exactly one normal path component per `open_with`.** Passing more makes cap's `manually::open` walk the rest itself and drop those intermediate handles, which breaks "retain every ancestor handle". The view validates each component as a single normal name first.
        - **Final-component classification:** also pass `FILE_FLAG_BACKUP_SEMANTICS` on final-component opens (compare `windows/fs/stat_unchecked.rs:29`), so a final junction or directory symlink opens as a reparse point and is classified `Containment::Symlink`/`ReparsePoint` rather than `Io(PermissionDenied)`.
        - **`windows-sys` declaration:** the workspace root `Cargo.toml` has no `windows-sys` entry; existing crates (`omni_capability_enforcement`, `omni_setup`) declare `windows-sys = { version = "0.61", features = [...] }` directly under a `cfg(windows)` target table. `omni_input_view` does the same (features `Win32_Foundation`, `Win32_Storage_FileSystem`), rather than adding a workspace entry.
        - **Reserved names:** cap already returns `NotFound` for reserved device names, but D9 rejects them before any open, so tests assert the D9 error (`NameUnsupported`) and its order, never `Missing`/`NotFound`.
        - **Unsafe boundary:** the only `unsafe` is the one `GetFinalPathNameByHandleW` call (raw handle from `AsRawHandle`, UTF-16 buffer, size-query then fill, retry on a too-small buffer). It lives in one private function in a `windows` module behind a safe signature `fn final_path(&File) -> io::Result<PathBuf>`, with `// SAFETY:` notes, no handle escaping, and `#![deny(unsafe_code)]` everywhere else in the crate (`allow` on that module only). It is tested on the Windows CI job: normal path, long path (over `MAX_PATH`), a `\\?\` prefix on the root, and a handle whose directory was renamed (not expected to succeed; see the gate).
    - **macOS and other OSes:** `ContainmentViolation::Unsupported` without any filesystem walk (D5).
- **Proof fixture (the thin slice):** one function opening a file beneath the root via `WorkspacePath` segments with the primitive above, returning `ContainmentViolation::Symlink` on any symlink component.
- Name validation for D9 (inside the view only, decision 3). Rule per OS: see [D9 portability](#d9-portability). Table-driven unit tests run on all OSes (pure function); real-file behavior runs on Windows.

**Gate (all must pass on native CI; a missing capability fails on CI, it does not skip):**

- Symlink-swap loop: a thread swaps a component between a directory and a symlink to an outside file while the reader loops; no outside bytes in 10,000 iterations on each supported OS. The statistical loop is not the proof: it sits next to **deterministic variants** with an injected hook between the component resolutions (the Windows walk) or between the check and the open, which must reject every ordering.
- Linux move-out-and-back parent-rename race: a thread renames an intermediate directory out of the root and back during the open; no outside bytes ever (deterministic variant included).
- Linux without `openat2`: an injected `ENOSYS` and an injected `EPERM` (test seam in front of the syscall, plus one run under a real seccomp filter where CI allows it) return `Unsupported` and read nothing; the fallback path does not exist to be taken.
- Windows: a rename of a held ancestor directory fails (held-handle rename rejection) and the move-out-and-back sequence cannot be executed; if the rename succeeds, Windows becomes `Unsupported` (re-planning trigger).
- macOS returns `Unsupported` without reading (D5).
- **Test skip contract:** follow the repo's `OMNI_TEST_REQUIRE_CAPABILITIES` contract (`run-omni-jobs.yaml`, "Capabilities this lane must prove": `symlink,hardlink,git[,reflink]` required on every lane). Symlink tests on Windows **fail on CI** if the privilege is missing and may skip only locally, with a named skip. Windows junction tests (`mklink /J`, which needs no privilege) **never skip**.

**CI requirement:** `crates/omni_input_view/project.omni.yaml` must extend `rust-lib` **and** `rust-multiplatform` (the latter defines the per-target `test:*` tasks, including `x86_64-apple-darwin`, `aarch64-apple-darwin` and the Windows targets; `omni_task_executor` extends only `rust-lib`, so its tests do not run per-target). Verified runner facts: `omni/presets/rust-multiplatform.omni.yaml:318-332` maps `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` to `ubuntu-latest`, both Apple targets to `macos-latest` and `x86_64-pc-windows-msvc` to `windows-2022` (`aarch64-pc-windows-msvc` is commented out); `run-omni-jobs.yaml:181-185` and `:248` set `OMNI_TEST_REQUIRE_CAPABILITIES` per target. Extending both presets therefore reaches all three OSes; the PR states which jobs are new or reused. Until the native jobs pass, that OS stays `Unsupported`.
**aarch64 Linux lane:** it runs under `cross` in a container (`run-omni-jobs.yaml:186-187`) that may block `openat2` with `EPERM`. That lane must only assert the `Unsupported` mapping (and that nothing is read) if `openat2` is blocked there, and its tests must not claim containment; full containment proof (swap loop, rename race) is required on x86_64 Linux.
**Rollback:** delete the crate; nothing depends on it.

### F10.2b: tracked `read` / `exists` / `list` with limits

**Risk:** High (containment, authorization). Implements [F10.1 design](F10.1-captured-input-view-design.md#design-proposed): authorize first, then open beneath the root, `fstat` regular-file check with non-blocking open, limits checked before allocation, per-entry `list` authorization with the separate raw-scan counter, evidence kept per observation with conflict marking, cancellation recording nothing.

Interfaces and data shapes are those in F10.1 (`InputView::{open, read, exists, list, evidence}`; `Read`, `Exists`, `Listing`, `Observation`, `PathEvidence`, `InputError`). Decisions fixed here:

- `InputView::open(root: &Path, options: InputViewOptions)` takes an absolute workspace root plus an options struct (`InputViewOptions { authorizer: Arc<dyn InputAuthorizer>, limits: InputLimits, symlinks: SymlinkPolicy }`, the one shape used in F10.1 as well) and holds one root directory handle (`OwnedFd` on Linux, a directory handle on Windows). No API returns a handle or absolute path.
- Authorization uses the lexical path (root path joined with the validated suffix) because symlinks are rejected in the default mode.
- Default `InputLimits` values are the recorded maintainer decision below (accepted for now, adjustable later); the checks do not depend on the values. Limits are host-owned: plugins cannot raise them.
- `ENOENT` and `ENOTDIR` are `Missing`; `EACCES`, symlink, non-regular and other errors are `InputError` (D6, confirmed). Case-spelling: see [D8 behavior](#d8-case-spelling-behavior).

**Gate:** the F10.1 F10.2 test list, plus the benchmark on a 1,000-file tree in `crates/omni_bench` against plain reads. Authority tests: the view refuses everything the authorizer denies (denied path, denied `list` child, unevaluable policy), everything containment rejects even when allowed, and everything over the limits, so effective authority is `authorizer ∩ containment ∩ limits`. Running the unchanged `omni_capabilities` and `omni_capability_sys` suites proves only that those crates were not edited, not that the view grants nothing.
**Rollback:** revert the slice; the crate has no consumers.

### F10.2c: symlink policy, reject-only (D2)

**Risk:** Medium, **only** because no follow logic ships and the default behavior is unchanged from F10.2b; if any follow code is added, it becomes High. Adds `SymlinkPolicy::{Reject (default), FollowInRoot { max_hops }}` as a field of `InputViewOptions` (one placement; not on `InputLimits`, which are numeric budgets). Following is not in the first release (decision 2).

- `Reject` is the default and the only implemented mode. Selecting `FollowInRoot` returns `InputError::SymlinkPolicyUnsupported` (a distinct variant, not `ContainmentViolation::Unsupported`, which means the platform cannot contain) and follows nothing; no resolver, hop counter or re-authorization of resolved paths is written.
- Windows junctions and mount points are rejected and are never followed, in any mode.
- **Deferred:** the follow implementation. A later plan must resolve each link itself, cap hops, re-authorize every resolved `WorkspacePath`, reject targets that leave the root (absolute, `..` chains), never `canonicalize` then open, and record the requested path as evidence so a retargeted link is `Modified`. `cache_restore.rs` `Workspace::relative_target`/`resolve_link` are ideas only (trusted restore, not untrusted reads).

**Gate:** reject-matrix (absolute target, `..` target, loop, dangling, retarget mid-read, Windows junction) on Linux and Windows all return containment errors; selecting the follow option returns the typed error and reads nothing.
**Rollback:** remove the option; default behavior is already `Reject`.

### F10.3: revalidation and reject-on-change

**Risk:** High (decides whether stale input is accepted). Revalidation uses the same primitives as F10.2b. `InputView::revalidate`, `Revalidation`, `Change`, `ChangeKind` per F10.1. Always re-read and re-digest tracked files; `FileIdentity` is advisory only and never skips the digest. Denial, containment or I/O failure during revalidation is an error, not a `Change`. Output truncates at `max_reported_changes`. Default consumer policy "reject on any `Changed`" is a helper, with no retry loop.

**Gate:** same-size same-mtime edit (`set_modified` restore), `Created` after `Missing`, `Deleted`, `KindChanged`, `MembershipChanged`, atomic replace with identical bytes is `Unchanged` (D3), case-spelling revalidation per [D8 behavior](#d8-case-spelling-behavior), repeatability, cancellation leaves state untouched. Acceptance repeats the honest guarantee: changes are detected only up to the last re-observation of each path; an edit after that is not detected, and the tests do not assert otherwise ([§17.2](../../017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs)).
**Rollback:** revert the slice; F10.2 evidence remains usable without revalidation.

### F10.2a implementation record

Crate `crates/omni_input_view` (extends `rust-lib` and `rust-multiplatform`; the real CI planner schedules its `test` on all five targets, the same set as `omni_setup`: `x86_64` and `aarch64` Linux on `ubuntu-latest`, both Apple targets on `macos-latest`, `x86_64-pc-windows-msvc` on `windows-2022`). Implemented as planned, with these recorded details:

- **Linux** is one `rustix::fs::openat2` with `BENEATH | NO_SYMLINKS | NO_MAGICLINKS | NO_XDEV` and no fallback. `rustix` is a direct workspace dependency (`1.1.5`, features `std`, `fs`; the same copy already in `Cargo.lock`). `EAGAIN` and `EINTR` are retried four times, then `Io { WouldBlock }`.
- **`EXDEV` finding:** the kernel also returns `EXDEV` when it detects a `RESOLVE_BENEATH` escape during a concurrent rename of a directory on the path (seen in the move-out-and-back race). `EXDEV` therefore maps to `MountCrossing` for both causes. Both are refusals, so the boundary is unaffected; only the diagnostic cannot tell them apart. `EscapesRoot` is produced by the Windows final-path check. This refines the plan's "`EXDEV` is a mount crossing, distinct from `EscapesRoot`".
- **Windows** follows the plan (one-component walk, retained handles, `FILE_FLAG_OPEN_REPARSE_POINT`, `FILE_FLAG_BACKUP_SEMANTICS`, the one `unsafe` `GetFinalPathNameByHandleW` call in `windows/sys.rs`). Any reparse point is `ContainmentViolation::ReparsePoint` (the std handle metadata does not separate symlink from junction tags), so Windows never reports `Symlink`. Reparse placeholders (cloud files, dedup) are rejected too. The share-mode and held-handle claims are verified only by the Windows CI job.
- **Other OSes (macOS included)** return `Unsupported` from `ContainedRoot::open` before touching the filesystem.
- **D9** rejects `:`, trailing dot or space and reserved names `CON PRN AUX NUL COM0-9 LPT0-9` (also with an extension or trailing spaces, and `COM`/`LPT` with `¹ ² ³`, `CONIN$`, `CONOUT$`) on every OS, checked before any open.
- **Tests:** Linux has deterministic hook variants (directory and final file swapped for a symlink, intermediate directory moved out and left, moved out and back), 10,000-read statistical loops (symlink swap and move-out-and-back, each with at least 100 swaps), injected `ENOSYS`/`EPERM` (asserting one syscall and nothing else), a real seccomp filter run in a child process, and a flag-assertion test. On a sandbox that blocks `openat2` (the aarch64 `cross` lane), the containment tests skip with a named `SKIPPED[capability=openat2 ...]` and the injected tests still run; on x86_64 a block fails the test. Windows tests cover the held-handle rename rejection (ancestors, final file and root), junctions (never skipped), symlinks (gated by `OMNI_TEST_REQUIRE_CAPABILITIES`), real alternate streams, deterministic swap hooks and a test that omits `FILE_FLAG_OPEN_REPARSE_POINT`.
- **What guards which flag:** `NO_SYMLINKS` is guarded by behavior tests; `BENEATH`, `NO_XDEV` and `NO_MAGICLINKS` are guarded only by the flag-equality test (the ancestor race additionally asserts that the kernel's `EXDEV` escape check fired). The Linux move-out-and-back hook runs before the syscall, so it cannot cover a rename during the lookup; the statistical loop does. A real `NO_XDEV` mount test needs a mount namespace and is left to a later slice.
- **Review fixes:** the D9 order is tested through a shared `open_beneath_with` seam (the OS open is never called for a rejected name); `COM0`/`LPT0` are reserved too; the Windows root open reports `NotADirectory` for a non-directory root and `is_under` is strict and fail-closed; the omit-flag test uses a final-component symlink (cap-std follows it without the flag).

### F10.2b implementation record

`InputView::{open, read, exists, list, evidence}` with `InputViewOptions { authorizer, limits }` (the symlink field arrives in F10.2c). Order per call: charge `max_operations`, cancellation, path length and depth, the D9 name check, the authorizer, then the open. Decisions made while building it (recorded here, not asked):

- **`exists` records `Observation::Present(EntryKind)`** instead of a content `File` or `Dir` observation, so probing existence never reads or lists. `Present(k)` is compatible with a `File` or `Dir` of the same kind (no conflict); any other difference, including `Missing`, marks the path conflicting. F10.3 re-probes `Present` by kind only.
- **`list` returns `List::{Found(Listing), Missing}`** (like `Read`), because a missing directory is a tracked result (D6). Listing a file is `InputError::NotDirectory(kind)`; reading a directory is `NotRegular(Dir)`.
- **Probe first (Linux):** the kind is learned with an `O_PATH` open (no read, no device or FIFO side effect), and only a regular file or directory is then opened for reading. This closes the review nit about opening device nodes. Windows opens once and reuses the handle.
- **Repeated reads** return the first captured bytes without touching the file; `exists` and `list` re-observe every time.
- **Name rules in `list`:** an entry is authorized first, so a denied entry is omitted whatever its name. An allowed entry whose name the D9 rule rejects, and any entry whose name cannot be a workspace path at all (not UTF-8, a backslash, a drive prefix such as `c:x`), fails the whole `list` with `NameUnsupported` (design: rejected when listed, never skipped). The unrepresentable-name case cannot be authorized, so it can fail a list even if the policy would have denied it: a small existence disclosure of the same class as the `DirScan` exception, documented here. Strict on Linux, where `a:b` is a legal file name.
- **Raw-scan counter:** denied children count only toward `max_dir_scan_entries`; the visible budgets count authorized entries only.
- **Budgets charge on attempt and are never refunded.** `max_total_bytes` is charged from `fstat` before allocating and again for growth beyond it; a file that grows during the read is caught by the `limit + 1` cap (`TooLarge`).
- **D8 on Windows** is checked from the final path of the opened handle: the on-disk names must equal the requested names byte for byte, otherwise `CaseMismatch` (nothing recorded). No directory listing is needed, and it also rejects 8.3 aliases. Linux and macOS do not check it: Linux names are case-sensitive here (a case-insensitive Linux mount is not handled) and macOS is `Unsupported`.
- Windows listing uses cap-std `Dir::entries` on a handle that is already contained and held without `FILE_SHARE_DELETE`.

**First native Windows run (PR #176, head `edb62b18`):** 58 of 59 tests passed on `windows-2022`, including the held-handle rename rejection, the root probe (`exists(".")`, `list(".")`, `read(".")`), both reject matrices and the other Windows containment tests. The one failure was the F10.2a flag-omission test: its expectation (the followed link reads the target's bytes) predates the F10.2b final-path check, which now refuses the followed handle (`a/b/file` instead of the requested `a/b/link_file`) as a spelling mismatch. That is a second layer behind `FILE_FLAG_OPEN_REPARSE_POINT`, and the test now asserts the new result plus the absence of `ReparsePoint`. No containment claim changed.

**aarch64 Linux `cross` lane (verification item resolved, PR #176 head `f71f3e5f`):** the container blocks `openat2`: every real access returned `Containment(Unsupported)`, which is the planned mapping, so Linux aarch64 under `cross` is `Unsupported` in CI and only x86_64 Linux proves Linux containment. The F10.2a tests already skipped there with the named `openat2` gate, but the F10.2b to F10.3 view tests did not, so that lane failed 47 tests. They now probe first: where `openat2` is blocked they assert `Unsupported` (and that nothing was read or recorded) and skip the rest with the named gate; on x86_64 Linux a block fails the test. `OMNI_INPUT_VIEW_ALLOW_NO_OPENAT2=1` lifts that failure locally, which is how the skip path was verified here by running the test binaries under a seccomp filter that blocks `openat2`.

### F10.2c implementation record

`SymlinkPolicy::{Reject (default), FollowInRoot { max_hops }}` is a field of `InputViewOptions`. Only `Reject` exists: `InputView::open` with `FollowInRoot` returns `InputError::SymlinkPolicyUnsupported` before the root is touched, so nothing is opened, authorized, read or followed, and no resolver, hop counter or re-authorization of resolved paths was written. Windows junctions and mount points are rejected in every mode (`ReparsePoint`). Risk stays Medium: no follow code ships and the default behavior is the F10.2b behavior.

- **Reject matrix (view level):** Linux covers an absolute target, a `..` target, a loop, a dangling link, an in-root absolute and relative link, an intermediate directory link, a retargeted link (always `Symlink`, never bytes; the same name as a real file reads normally) and a listed symlink (reported as `Symlink`, listing it is a containment error). Windows covers junctions (never skipped, including a retargeted junction) and symlink shapes (absolute, `..\`, dangling, loop, directory link; gated on `OMNI_TEST_REQUIRE_CAPABILITIES`, so they fail on CI when the privilege is missing).
- **Cancellation after admission:** evidence and cached results are published only for a call that is not cancelled, checked under the state lock (review feedback on #176); tests cancel from the read hook and from an authorizer.

### F10.3 implementation record

`InputView::revalidate(&Cancellation) -> Result<Revalidation, InputError>` with `Revalidation::{Unchanged, Changed { changes, remainder }}`, `Change { path, kind }`, `ChangeKind::{Modified, Created, Deleted, KindChanged, MembershipChanged}` and the default policy helper `Revalidation::reject_on_change() -> Result<(), InputsChanged>` (no retry loop). Decisions made while building it:

- **Baseline per path:** the strongest observation (content, then kind, then absence). `Missing` baseline: any existing kind now is `Created`. `Present(kind)`: gone is `Deleted`, another kind `KindChanged`, content ignored. `File`: the bytes are re-read and re-digested (identity and mtime are never used); gone is `Deleted`, no longer a regular file `KindChanged`, different bytes or length `Modified`. `Dir`: re-listed with the same authorization filter; gone `Deleted`, not a directory `KindChanged`, different membership digest `MembershipChanged`.
- **Conflicting evidence is a change by itself**, without re-reading: the first disagreeing pair gives the kind (`Missing` then present is `Created`, present then `Missing` is `Deleted`, kinds differ `KindChanged`, two files `Modified`, two directories `MembershipChanged`).
- **D3:** an atomic replace with identical bytes is `Unchanged`. **D6:** an `ENOTDIR` parent is `Missing`, so a tracked file below a directory that became a file is `Deleted`. **D8:** a case-only rename is `CaseMismatch` on a fresh access and is reported as `Deleted` here (the exact spelling is gone); a name tracked as absent that now exists with another spelling is `Created`; any other error stays an error.
- **Errors, not changes:** denial, policy failure, containment violation (a file replaced by a symlink), I/O failure, a limit hit (a file that grew past `max_file_bytes`) and cancellation fail the whole pass.
- **Own budgets:** each pass gets fresh operation, byte and directory-entry counters (the limits are the same), so a pass over everything that was tracked is not starved by the reads that tracked it. The live counters are untouched.
- **Read-only and repeatable:** evidence and captured bytes are never modified; a denied entry appearing or disappearing is invisible, as for `list`.
- **Output:** changes are in path order, truncated to `max_reported_changes`; `remainder` counts the rest (the pass still observes every path).
- **Honest guarantee (RFC 0024 section 17.2):** changes are detected only up to the last re-observation of each path; an edit after that, or during the pass itself, is not detected, and no test asserts otherwise.

The refactor that made this possible split `read`, `exists` and `list` into capture steps (`capture_kind`, `capture_file`, `capture_dir`) shared with the pass; the live behavior and tests are unchanged.

### Diagnostics and maintainer decisions after merge

Recorded after #174 and #176 merged (maintainer answers):

- **aarch64 Linux under `cross` is accepted as `Unsupported` in CI,** with this note: the container blocks `openat2`, so only x86_64 Linux proves Linux containment in CI. Real aarch64 kernels support `openat2`, so users there are not affected, but nothing tests it. The consumer's release notes carry it as a documented limit ("Linux containment is CI-tested on x86_64 only").
- **Windows case semantics (D8):** NTFS is case-insensitive but case-preserving, so an OS-level read of `Readme.md` finds `README.MD`. The view never case-folds, so on a case mismatch it refuses (`CaseMismatch`) instead of pretending the exact name exists or is absent. Revalidation follows from that: a tracked name whose exact spelling is gone is `Deleted`; a name tracked as absent that now exists under another spelling is `Created`, because the OS would now find a file where the pass saw none. `Created` is therefore the correct semantics, not just the fail-safe choice. No code change.
- **Failures must say why (diagnostics, not silence).** `InputError` derives `omni_diagnostic::Diagnostic` under the new prefix `input_view` (registered in the diagnostic prefix table): every failure has a stable code and a hint, and carries the workspace-relative path it is about. Changes this made: the containment variants (`Symlink`, `ReparsePoint`, `EscapesRoot`, `MountCrossing`) carry the path and `ContainmentUnsupported` has its own code and hint (Linux 5.6+, not blocked, or Windows; macOS unsupported); D9 is now `UnsupportedName { path, problem }` with a `NameProblem` (stream, reserved device name, trailing dot or space, not representable) instead of `ContainmentViolation::NameUnsupported`; `NotRegular`, `NotDirectory` and `TooLarge` carry the path. A directory that fails `list` because of an unsupported entry name now names that entry (for example `docs/a:b`) and the reason. `InputError::containment()` still maps back to the primitive's `ContainmentViolation`. `Cancelled` stays a plain error.
- **Notices:** the view raises none. A consumer that chooses to continue after a failed read (for example a plugin run that skips an input) should emit a notice carrying the diagnostic, so the user sees which input was skipped and why. That belongs to the consumer's plan.
- **Plugin-facing disclosure:** the paths in these messages are host-side information. A plugin-facing adapter decides what to pass on (the earlier rule that `Io` carries only the normalized path still holds).

## Decision 1 amendment

The maintainer chose "build on `cap-std`, gated on the proof fixture". Reading `cap-primitives 4.0.3` shows the fixture cannot pass on Linux by design:

- `rustix/linux/fs/open_impl.rs` calls `openat2` with `ResolveFlags::BENEATH | ResolveFlags::NO_MAGICLINKS` only. It does **not** pass `NO_SYMLINKS`, so in-root intermediate symlinks are followed. The view must reject them (decision 2, F10.1 symlink rule).
- On `ENOSYS`, on `EPERM` (seccomp) and after four `EAGAIN` retries, `open_impl` silently falls back to `manually::open`, a userspace component walk. There is no API to detect or forbid that fallback, so decision 6 ("no best-effort containment") cannot be enforced through `cap-std`.
- The per-component alternative (`open_dir_nofollow` in a loop) reintroduces the move-out-and-back rename race (F10.1, Linux section).

**Amendment:** Linux uses `rustix::fs::openat2` directly with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` and no fallback. `cap-std` is kept only where its semantics are proven: on Windows, as the handle-relative `Dir::open_with` (`CreateFileAtW` with the `start` handle, verified in `windows/fs/open_unchecked.rs`), with the view doing its own one-component-at-a-time walk, because `cap-std`'s own Windows `open` is `manually::open` (follows in-root symlinks and junctions and does not retain ancestor handles); `windows-sys` supplies `GetFinalPathNameByHandleW` and the Win32 constants (see the Windows primitive in F10.2a). Whether held handles block renames is proven only by the F10.2a Windows gate. Cost: a security-review-heavy Linux path owned by this crate (rustix's `openat2` is a safe API), `rustix` as a direct dependency, and one contained `unsafe` FFI call on Windows.

**Confirmed by the maintainer:** this amendment is a recorded decision (including `RESOLVE_NO_XDEV` and no fallback).

## D8 case-spelling behavior

Confirmed design (maintainer decision): the view never reports a spelling mismatch as a `Change`.

- **Initial access (F10.2b):** on a case-insensitive filesystem (Windows, default macOS) the view compares the requested segment to the on-disk name byte for byte, taken from the parent directory listing. A mismatch returns `InputError::CaseMismatch { path: WorkspacePath }` (a new variant, fatal). It records no evidence and is never `Missing`.
- **Revalidation (F10.3):** every tracked path was accepted with an exact spelling, so a later mismatch means the entry was renamed (case-only) on disk. Revalidation reports it as `ChangeKind::Deleted` for the old spelling (the exact name no longer exists), not a new kind, so `ChangeKind` stays `Modified | Created | Deleted | KindChanged | MembershipChanged`. If the re-observation returns `CaseMismatch` the pass maps it to `Change { kind: Deleted }`; any other error stays an error.
- This replaces the earlier wording "a case-spelling mismatch counts as a change". Confirmed by the maintainer.

## D9 portability

Decision: reject `:` in any segment and reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM0-9`, `LPT0-9`, with or without an extension, any case) plus trailing dot or space on **all** OSes inside the view, so a discovery run does not accept on Linux a path that fails on Windows. The cost is rejecting legal Linux names (`a:b`, `con`). The alternative (OS-specific rules: Windows only) lets discovery results diverge by OS. Table-driven tests run on all OSes. **Confirmed by the maintainer:** the all-OS rule applies.
