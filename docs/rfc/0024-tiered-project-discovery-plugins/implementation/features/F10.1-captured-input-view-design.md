# F10.1: Captured input view design

**Type:** design doc (slice 1 of [F10](F10-captured-input-view.md)) · **Risk:** Medium for this doc; the implementation slices are High (see the [plan](F10-implementation-plan.md); capabilities and security-boundary rule in [AGENTS.md](../../../../../AGENTS.md)) · **Status:** design; fully implemented in crate `omni_input_view` (F10.2a [#174](https://github.com/omni-oss/omni/pull/174); F10.2b, F10.2c and F10.3 [#176](https://github.com/omni-oss/omni/pull/176)); nothing consumes it yet. ## Problem

Frozen claims do not freeze the filesystem ([§17.2](../../017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs)). Code that reads several files can see different versions of one file, miss a file created mid-pass, or trust a cache record whose input changed. Reads today check the path and then open it separately, so a component swapped for a symlink between the two steps can escape the check. The task hasher's size/mtime shortcut cannot prove that content is unchanged.

The goal is one command-local service that (a) enforces containment at open time, (b) hashes the bytes it actually returned, (c) records positive and negative observations and directory membership, and (d) revalidates the set at the end and reports detected change. It is not a transactional snapshot: an edit after revalidation is not detected ([§17.2](../../017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs)).

- Plugin permission profile schema, hook host services, `ReadObservation` wire shapes ([§12.4](../../012.00-rust-trait-sketches.md#124-host-services-plugin-side-view)). A later adapter maps the core types to those.

## Design (proposed)

### Crate placement and dependency direction

New leaf crate `omni_input_view`. It must not depend on any plugin, runtime, Wasm, hook, or discovery crate. Dependencies:

- `omni_path_utils` for `WorkspacePath`.
- No `omni_hasher`: a two-method digest trait local to the crate, implemented with `blake3` (decision 4; D4 resolved), avoiding `system_traits` and async dependencies.
- A small authorization trait defined in the new crate (`InputAuthorizer`). The consumer (not `omni_capability_sys` or `omni_capabilities`) provides the adapter from `CapabilityAuthorizer`/`omni_capabilities::evaluate`. This keeps the core free of `system_traits` and lets the policy crates stay unchanged. The crate does not depend on `omni_capabilities`: it defines its own `DenyReason` (see Error taxonomy).
- OS access behind `cfg`, not through `system_traits` (a path-based trait cannot express `openat` and relative handles): direct `rustix::fs::openat2` on Linux, and `cap-std` handle-relative opens plus a small `windows-sys` call for `GetFinalPathNameByHandleW` and the Win32 constants on Windows (decision 1 as amended in the plan). The original raw-`libc` sketch is superseded; `windows-sys` is used only for what `cap-std` does not expose.

Direction: `plugin host / discovery / cache validation` → `omni_input_view` → `omni_path_utils`. Nothing under `omni_capabilities` depends on the view.

### API shape

```rust
pub struct InputView { /* root handle, authorizer, limits, symlink policy, evidence, budgets */ }

impl InputView {
    pub fn open(root: &Path, options: InputViewOptions) -> Result<Self, InputError>;
    pub fn read(&self, path: &WorkspacePath, cx: &Cancellation) -> Result<Read, InputError>;
    pub fn exists(&self, path: &WorkspacePath, cx: &Cancellation) -> Result<Exists, InputError>;
    pub fn list(&self, dir: &WorkspacePath, cx: &Cancellation) -> Result<Listing, InputError>;
    pub fn evidence(&self) -> Evidence;                   // sorted by WorkspacePath
    pub fn revalidate(&self, cx: &Cancellation) -> Result<Revalidation, InputError>;
}

pub enum Read { Found(Arc<[u8]>), Missing }            // Missing is tracked, not an error
pub enum Exists { File, Dir, Missing }                  // other kinds are NotRegular errors
pub struct Listing { entries: Vec<(String, EntryKind)> } // sorted by name, single level

pub struct InputViewOptions {
    pub authorizer: Arc<dyn InputAuthorizer>,
    pub limits: InputLimits,
    pub symlinks: SymlinkPolicy,
}

pub trait InputAuthorizer: Send + Sync {
    // Err means the policy could not be evaluated (fatal; see rule 5 of Authorization order).
    fn authorize_read(&self, path: &WorkspacePath) -> Result<AuthDecision, AuthError>;
}
pub enum AuthDecision { Allow, Deny(DenyReason) }
pub enum SymlinkPolicy { Reject /* default */, FollowInRoot { max_hops: u8 } /* not implemented in v1 */ }
```

Rules:

- Inputs are validated `WorkspacePath` values. `InputPath` (`@project/...`) resolution and per-root scope checks are the caller's job ([`InputPath` definition](../../006.04-hook-and-claim-schemas.md#path-normalization)); the view sees only a concrete workspace identity and the authorizer decides.
- The view never returns a raw handle, an absolute path, or a canonical path.
- Within one view, repeated `read` of the same path returns the first captured bytes (shared read view). A later divergence is a revalidation finding, not a silent second version.
- `list` is one directory level. Recursive traversal is the caller's loop (each level counts against the budgets), so depth and entry limits are enforced by the view rather than by a walker.
- Evidence is recorded only after the operation completes, so a cancelled or failed call records nothing. Budget counters are charged for the attempt regardless ([§8.1](../../008.00-performance-and-shared-safeguards.md#81-shared-safeguards) "account for all attempted reads").

### Evidence format

Evidence is keyed and ordered by `WorkspacePath` (`BTreeMap`) so it is deterministic and byte-comparable. Each path holds **every distinct observation made in the pass**, not just the latest: an `exists` that saw `Missing` and a later `read` that saw `File` are both kept. Two observations of the same path that disagree (`Missing` then `File`, `File` then different bytes, `File` then `Dir`) mark the entry `Conflict`, so `revalidate` returns `Changed` for it (`Created` or `Modified`) without depending on a later re-read to notice. Replacing an earlier observation with a later one is never allowed, because it would hide a change that happened during the pass.

```rust
pub enum Observation {
    File { len: u64, digest: Digest, id: Option<FileIdentity> },
    Missing,
    Dir  { entry_count: u32, membership_digest: Digest, id: Option<FileIdentity> },
}
pub struct PathEvidence { observations: Vec<Observation>, conflict: bool } // bounded per path
pub struct FileIdentity { /* dev+ino, size, mtime_ns, ctime_ns where the OS gives them */ }
```

The per-path observation list is bounded (`max_observations_per_path`, default 16, a recorded maintainer decision in the plan; counted in `max_operations`); repeated identical observations collapse to one. Exceeding it is `Budget(Observations)`.

`digest` is over the exact returned bytes. `membership_digest` is over the sorted `(name, kind)` pairs, using names as the filesystem reported them (no case folding). `FileIdentity` is advisory, see below. The persisted inference-cache form is out of scope here; this type is in-memory command state.

### Containment and symlink rules

Authorization and open happen on the same object, not on a re-resolved path.

- **Root:** `open` canonicalizes the workspace root once and holds a directory handle. All access is relative to that handle, never by joining a string and calling `open`.
- **Linux:** a direct `rustix::fs::openat2` relative to the root fd with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`. `cap-std 4.0.3` is **not** used here: it passes `BENEATH | NO_MAGICLINKS` but not `NO_SYMLINKS`, and silently falls back to a userspace walk on `ENOSYS`, `EPERM` and repeated `EAGAIN` (`cap-primitives` `rustix/linux/fs/open_impl.rs`) with no way to detect or forbid it. The kernel enforces the boundary for the whole lookup, including against a concurrent rename of an intermediate directory, so this is the only path that is race-safe by construction. This is the plan's **decision 1 amendment**, a recorded maintainer decision (it also passes `RESOLVE_NO_XDEV`).
- **Linux without `openat2` (decision 6): no fallback.** A component walk cannot be made race-safe against something that can rename directories during the walk: an opened directory can be moved outside the root, a child opened through it, and the directory moved back, after which every identity and location check passes although the child was opened outside the root. So there is no fallback walker and no best-effort mode. `ENOSYS` or `EPERM` (seccomp) from `openat2` returns `Containment::Unsupported` (fatal) and reads nothing; a bounded number of `EAGAIN` retries then `Io { kind: WouldBlock }`. Kernels older than Linux 5.6 are therefore unsupported.
- **macOS (D5):** `Containment::Unsupported` without any filesystem walk, until a verified kernel-enforced beneath-root open exists and native macOS CI proves it. No best-effort `O_NOFOLLOW` component walk.
- **Windows:** component walk opening each component relative to the held parent handle with `cap_std::fs::Dir::open_with` and `OpenOptionsExt::{share_mode, custom_flags}` (`FILE_FLAG_OPEN_REPARSE_POINT`; explicit `share_mode(READ | WRITE)`, no `FILE_SHARE_DELETE`), wrapping each handle with `Dir::from_std_file` and retaining all ancestors. Any reparse point (`FILE_ATTRIBUTE_REPARSE_POINT`: symlink, junction, mount point) is rejected. `FILE_FLAG_OPEN_REPARSE_POINT` is what makes this safe (it disables cap's own nofollow enforcement, so the reparse point is returned, not followed); each `open_with` gets exactly one normal component; final-component opens also set `FILE_FLAG_BACKUP_SEMANTICS` so a junction or directory symlink is a containment error, not `PermissionDenied`; attributes come from `cap_std::fs::MetadataExt`; reserved names are rejected by D9 before any open. The gate includes a test omitting the flag that must fail. See the plan's F10.2a for the verified sources and the `windows-sys` declaration. Not `cap-fs-ext` `open_dir_nofollow` (no `OpenOptions`, symlink-only check) and not `cap-std`'s `Dir::open`, which delegates to `manually::open`: that follows in-root symlinks and junctions and drops ancestor handles (it does open intermediate directories without `FILE_SHARE_DELETE` via `dir_options()`, `windows/fs/dir_utils.rs:62-72`, so share mode is not the reason to own the walk). Holding each directory handle **without** `FILE_SHARE_DELETE` is the proposed rename boundary and is unverified until the held-handle rename test passes. `cache_restore.rs` follows junctions and so is not precedent for junction rejection. After open, verify the final path of the handle (`GetFinalPathNameByHandleW`, via `windows-sys` in one contained `unsafe` function; `cap-primitives` keeps its own `file_path` `pub(crate)`) is still under the root handle's final path. The plan specifies the dependency and the unsafe boundary.
- **Symlinks (default):** any symlink or reparse-point component is `Containment::Symlink`, a fatal error, never `Missing`. A dangling symlink is also rejected. Following in-root symlinks is deferred (D2, decision 2). `SymlinkPolicy::FollowInRoot` exists as a typed option and returns `InputError::SymlinkPolicyUnsupported` (distinct from `Containment::Unsupported`, which means the platform cannot contain); if later implemented it must be done by this walker with a hop limit and a re-authorization of each resolved `WorkspacePath`, never by `canonicalize` followed by open. On Linux that needs a new primitive, since `RESOLVE_NO_SYMLINKS` forbids following.
- **Name rules:** the walker reads names from the directory handle. A name that cannot become a `WorkspacePath` (backslash, non-UTF-8), or that the D9 rule rejects, is rejected when selected or listed ([path normalization](../../006.04-hook-and-claim-schemas.md#path-normalization)), not silently skipped or rewritten. An unrelated unlisted file with such a name does not matter.
- **File kind:** after open, `fstat` the handle. Only regular files are read. FIFOs and devices are rejected `NotRegular` without a blocking read; the open uses non-blocking flags so open itself cannot hang.

### Authorization order, and no new authority

The view adds checks; it never grants.

1. Validate the `WorkspacePath` (no filesystem access).
2. Ask the authorizer for `fs.read` on the concrete path (`Request::Fs { write: false, .. }` with the absolute path built from the root handle's path and the normalized suffix). On `Err` (policy cannot be evaluated) return a fatal `PolicyUnavailable` error and treat the path as denied for disclosure purposes (never allow, never `Missing`). On `Deny`, return `Denied` before any open, stat, or existence disclosure. A denied path is never reported as `Missing` ([§6.4](../../006.04-hook-and-claim-schemas.md#tracked-reads-and-expected-absence)).
3. Open under the containment rule above. Containment failure is its own error, even for an allowed path.
4. Authorization uses the lexical, symlink-free path. Because symlinks are rejected, lexical and real paths coincide, so the view does not need `resolve_real_path`, and it removes the window that function's docs admit.
5. **`list` authorizes every entry, not only the directory.** Allowing a directory does not allow its children. After the directory is authorized and opened, each child name is authorized as `fs.read` on `dir/child` before it can appear in a `Listing` or in `membership_digest`. A denied child is **omitted**, not reported as denied and not counted, so a successful listing never discloses the existence, name, kind or count of a denied entry. **One bounded exception:** the raw-scan cap (`max_dir_scan_entries`) counts denied entries, so at that exact threshold one more denied child can turn a successful `list` into `Budget(DirScan)`, and a caller who already knows every other entry can infer that a denied child exists. This is an accepted, documented residual, not a hidden channel: it reveals only "the raw directory exceeds the cap", never a name, kind or exact count, and it is why the cap is set far above the visible limits (D7) and the error carries no counts. The `Dir` evidence and `membership_digest` are computed over the authorized view only, and revalidation re-lists with the same filter, so a denied entry appearing or disappearing is invisible to a successful listing and is not a `MembershipChanged` (the raw-scan exception above is the only way it can surface). The directory itself being denied is `Denied` as for any path. Authorizing a child is charged to a separate raw-scan counter (`max_dir_scan_entries`, below), **not** to `max_dir_entries`, `max_total_dir_entries` or `max_operations`, so the visible-entry budgets and their errors depend only on authorized entries and a denied child can never cause or move a visible-budget error. A policy that cannot be evaluated for an entry fails the `list` (fatal), never falls back to including it.

Consequences:

- Effective authority is `authorizer ∩ containment ∩ limits`. The view cannot read anything the policy denies. On platforms where containment is supported (Linux `openat2`, Windows with the verified held-handle boundary) it also cannot read outside the workspace root even if a policy pattern would allow it. Elsewhere the view returns `Unsupported` and reads nothing; there is no weaker mode.
- No evidence value, `FileIdentity`, or `Evidence` object is a capability. Holding evidence for a path does not permit a later read.
- The view has no write method and does not touch `fs.write`, `net`, `env`, or `process`.
- `omni_capabilities` is unchanged. Policy semantics (deny-dominance, fail-closed, rooted pattern resolution) are reused through the adapter. A policy pattern that cannot be resolved because a root is unregistered continues to match nothing, as `rule_matches` does today.
- The OS sandbox remains the floor for untrusted runtimes. This view is host-side; it does not replace `omni_capability_enforcement` and is not relied on to confine a guest's own syscalls.

### Negative (missing) reads

`Missing` means the authorized path does not exist at that moment: `ENOENT` on the final or an intermediate component, or `ENOTDIR` on an intermediate component (D6). It is recorded as `Observation::Missing` for the requested normalized path without pretending anything was canonicalized. It is a successful result.

Not `Missing`: permission denial, `EACCES`, `ELOOP`/symlink, non-regular file, over-budget, any other I/O error. Those are errors.

Revalidation of a `Missing` entry re-probes the same path; if it now exists as any kind, that is `Created`.

### Content and identity capture versus size/mtime

Observed: the hasher index treats equal `(mtime-in-ms, size)` as equal content. That is unsafe as evidence because mtime can be coarse (some filesystems store seconds), can be set explicitly, and a same-size edit within one tick is invisible.

Proposed rule: **the content digest is the evidence; identity and stamps are hints only.**

- Revalidation re-reads and re-digests every tracked file. A matching `FileIdentity` never lets revalidation skip the digest. This costs at most one extra read of bytes already budgeted, and is what catches a same-size, same-mtime edit.
- `FileIdentity` (inode, mtime, ctime) is recorded for diagnostics and to order checks cheaply. An identity change with an equal digest (atomic replace with identical content) is not reported as a change (D3 confirms).
- A fast path that skips rehashing based on stamps (git's "racy clean" rule: trust a stamp only if the mtime is older than the capture time by more than the filesystem granularity) is explicitly deferred and must be justified by a benchmark before adoption, and must default off.
- The view does not read or write the task hasher's index and does not change it. The two systems stay separate; the task hasher's behavior is unchanged by this work.

Directory evidence is the sorted `(name, kind)` digest over the **authorized** entries only (see the per-entry rule above). Revalidation re-lists with the same filter and compares. Creation, deletion, rename, or kind change of an authorized entry changes the digest.

### Final-pass revalidation

`revalidate` takes a bounded pass over all evidence and returns:

```rust
pub enum Revalidation { Unchanged, Changed { changes: Vec<Change>, remainder: u64 } } // changes bounded; remainder = omitted count
pub struct Change { path: WorkspacePath, kind: ChangeKind } // Modified|Created|Deleted|KindChanged|MembershipChanged
```

Semantics:

- Each entry is re-observed through the same containment and authorization path as the original, in `WorkspacePath` order, without adding new evidence.
- A policy denial, containment violation, I/O error, or budget exhaustion during revalidation is an error (fatal), not a `Change`. The pass fails either way, but a diagnostic can tell "input moved" from "access broke".
- The `Changed` list is truncated to `max_reported_changes` with a `remainder` count, so a mass change cannot allocate unboundedly. Evidence order makes it deterministic.
- The caller's default policy rejects the pass on any `Changed` (F10 slice 4). The view reports; the caller decides. No retry or restart lives in this crate.
- Honest guarantee: detects changes that happened before the last re-observation of each path. It cannot detect an edit after that, and acceptance tests repeat this wording. Document the same wording as [§17.2](../../017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs).
- Revalidation is read-only and leaves evidence untouched, so it is safe to cancel or run twice.

### Limits and budgets

Limits are an `InputLimits` struct supplied by the host. Every limit is checked **before** the allocation or work it bounds. Defaults are set by decision D7 (see the F10 plan); the checks do not depend on them. Limits are host-owned and must become user-configurable within host-owned bounds once the first consumer lands (config key and lower-only rule are decided in that consumer's plan; F10 adds no config surface).

| Limit                       | Checked                                                                                                                            | Failure                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `max_path_bytes`            | at `WorkspacePath` parse (existing `DEFAULT_MAX_WORKSPACE_PATH_LEN`)                                                               | `InvalidPath`             |
| `max_path_depth` (segments) | before opening                                                                                                                     | `Budget(PathDepth)`       |
| `max_file_bytes`            | from `fstat` length before allocating; the read is also capped at `limit + 1` bytes so a file that grows during the read is caught | `TooLarge`                |
| `max_total_bytes`           | charged before allocation, across reads and revalidation separately                                                                | `Budget(TotalBytes)`      |
| `max_tracked_inputs`        | before recording an observation                                                                                                    | `Budget(Inputs)`          |
| `max_dir_entries`           | while iterating, stop at limit + 1                                                                                                 | `Budget(DirEntries)`      |
| `max_total_dir_entries`     | across all `list` calls, authorized entries only                                                                                   | `Budget(TotalDirEntries)` |
| `max_dir_scan_entries`      | raw directory entries read per `list`, including ones the policy denies; checked while iterating, stop at limit + 1                | `Budget(DirScan)`         |
| `max_reported_changes`      | revalidation output                                                                                                                | truncates, never errors   |
| `max_observations_per_path` | before recording an observation for a path                                                                                         | `Budget(Observations)`    |
| `max_operations`            | every attempt, including misses and failed attempts                                                                                | `Budget(Operations)`      |

Failed and `Missing` attempts count toward `max_operations` so repeated probing cannot hide work. Budgets are per view; a host-wide budget layer sits above this and may share one view across consumers.

### Error taxonomy

**As built:** the shapes below were refined so every failure carries its path and a diagnostic code: containment failures are separate variants with the path, D9 is `UnsupportedName { path, problem }`, and `NotRegular`, `NotDirectory` and `TooLarge` carry the path. See the plan's [Diagnostics and maintainer decisions after merge](F10-implementation-plan.md#diagnostics-and-maintainer-decisions-after-merge).

```rust
pub enum InputError {
    InvalidPath(WorkspacePathError),
    Denied(DenyReason),                  // policy; never downgraded to Missing; view-local type
    PolicyUnavailable,                   // authorizer returned Err; fatal
    Containment(ContainmentViolation),   // Symlink | EscapesRoot | MountCrossing | ReparsePoint | NameUnsupported | Unsupported
    CaseMismatch { path: WorkspacePath }, // D8
    SymlinkPolicyUnsupported,            // FollowInRoot selected; not implemented
    NotRegular(EntryKind),
    TooLarge { len: u64, limit: u64 },
    Budget(BudgetKind),
    Io { path: WorkspacePath, kind: io::ErrorKind },
    Cancelled,
}
```

- **Tracked, successful:** `Read::Missing`, `Exists::Missing`, and a recorded `Observation::Missing`.
- **Fatal for the operation (and, by caller default, the pass):** everything in `InputError`. A caller that swallows one and treats it as empty is a bug; the types make `Missing` the only absence result.
- `Io` carries the normalized `WorkspacePath` and the error kind, not an absolute path or OS message, so a plugin-facing adapter cannot leak host layout. Host diagnostics may attach more locally.
- `Denied` carries a view-local `DenyReason { path: WorkspacePath, cause: NoMatch | ExplicitDeny | Other }`; the consumer's adapter maps `omni_capabilities::DenyReason` into it (the crate does not depend on `omni_capabilities`, whose dependencies are heavy). A recorded maintainer decision in the plan.

### Cancellation

A cooperative `Cancellation` is checked before open and between read chunks. On cancel, `Cancelled` is returned, no partial bytes are exposed, and no evidence is recorded for that call. Already completed evidence remains valid. Budget charges for the interrupted attempt are not refunded.

### Cross-platform notes

- **Case-insensitive filesystems (Windows, default macOS):** names come from directory listings; the view never case-folds. Opening a path whose spelling differs from the stored name succeeds at the OS but yields an unverified spelling. The view confirms that the on-disk name equals the requested segment; otherwise initial access returns `InputError::CaseMismatch` and records nothing, and revalidation reports the tracked path as `Deleted` (exact spelling gone). See the plan's [D8 behavior](F10-implementation-plan.md#d8-case-spelling-behavior), a recorded maintainer decision. Two entries differing only by case in one listing are reported, not merged, as [§6.4](../../006.04-hook-and-claim-schemas.md#path-normalization) requires.
- **Unicode normalization (macOS):** names are compared byte-for-byte; a filesystem that normalizes will present one form, and the view takes that form.
- **Windows names:** backslash cannot occur in a Windows name, but trailing dots/spaces, reserved device names (`CON`, `NUL`), and alternate data streams (`name:stream`) can. Per the plan's recorded maintainer decision, `:` and reserved names are rejected on all OSes inside the view so discovery does not diverge by OS (D9).
- **Timestamps:** resolution ranges from nanoseconds to 2 seconds (FAT). This is the reason content, not stamps, is the evidence.
- **Windows reparse points:** junctions and mount points are rejected like symlinks by default.
- **Kernel support:** `openat2` needs Linux 5.6. Older kernels, and sandboxes that block `openat2` with `ENOSYS`/`EPERM`, get `Unsupported`; there is no fallback walk.
- **No `system_traits` use in the core:** an in-memory fake for tests is a separate `InputFs` seam inside the crate, with the real implementation using handle-relative calls. Tests that need real symlinks run against a temp dir.

## Worked example

A discovery pass reads `packages/web/pnpm-lock.yaml`, probes `packages/web/yarn.lock`, and lists `packages/web`.

1. `read(pnpm-lock.yaml)` → authorized, opened beneath the root, `fstat` regular and under `max_file_bytes`, bytes captured with digest `D1`. Recorded `File{len, D1}`.
2. `read(yarn.lock)` → authorized, `ENOENT`. Recorded `Missing`. Returned `Read::Missing`.
3. `list(packages/web)` → recorded `Dir{membership_digest: M1}`.
4. Meanwhile another process rewrites the lockfile to different bytes of the same length and resets its mtime, and creates `yarn.lock`.
5. `revalidate` re-reads the lockfile: digest `D2 ≠ D1`, so `Modified`. Re-probes `yarn.lock`: exists, so `Created`. Re-lists: `M2 ≠ M1`, so `MembershipChanged`. The result is `Changed` with three entries and the caller rejects the pass.
6. If instead `packages/web` were swapped for a symlink to `/etc` before step 1, step 1 returns `Containment(Symlink)`, not bytes, not `Missing`.

## Alternatives rejected

- **Canonicalize, authorize, then open (current `PolicyEnforcingSys::guard`).** Leaves the swap window the code itself documents. Kept for existing generator paths, not for this view.
- **Rely on the OS sandbox alone.** Not available for host-side reads and does not provide tracking or revalidation.
- **Trust size+mtime for revalidation.** Fails the same-size same-stamp requirement.
- **Extend `omni_capabilities` with limits and tracking.** Breaks its "pure policy, no I/O" contract and widens a High-risk crate.
- **Put the view in `omni_capability_sys`.** That crate is a `system_traits` decorator; path-based traits cannot express handle-relative opens.
- **Tie it to plugin host services now.** Violates the F10 note; the core stays generic and the plugin adapter comes later.

## Test plan mapped to slices

F10 slice 2 → **F10.2** (read, exists, list, limits, tracking). F10 slices 3 and 4 → **F10.3** (revalidation and reject-on-change outcome, no retry).

**F10.2**

- Path validity: non-normalized, backslash, over-length, over-depth rejected without I/O.
- Containment: symlink final component, symlink intermediate component, dangling symlink, `..` smuggled via symlink target all fail as `Containment`. Platform tests (Linux, macOS, Windows reparse points) gated by `cfg`.
- Swap race: a thread repeatedly swaps a directory component between a real directory and a symlink to an outside file while the reader loops; no outside bytes are ever returned. Deterministic variants use an injected hook between the check and the open (Windows walk) and an injected syscall seam (Linux), next to the statistical loop.
- Authorization: denied path returns `Denied` and never `Missing`; denied path does not disclose existence; allow-but-outside-root fails containment; explicit deny beats allow.
- List authorization: a directory allowed with one denied child returns the listing without that child (name, kind and count never disclosed); the omitted child does not change `membership_digest`; a policy-evaluation failure for an entry fails the `list`.
- Raw-scan threshold: a directory with exactly `max_dir_scan_entries` raw entries lists successfully; adding one denied child makes the same `list` fail with `Budget(DirScan)`. The test asserts this exact documented behavior, that the error carries no counts or names, and that no visible-budget error appears at any point.
- Budget side channel: the same directory listed with and without N denied children (N varied) yields identical visible-budget outcomes (`DirEntries`, `TotalDirEntries`, `Operations`); only the separate `DirScan` cap can fail, with an error that carries no entry counts and names no entry. The documented residual is that `DirScan` reveals the raw directory is larger than the cap, so it is set well above the visible limits.
- Conflicting observations: `exists` returns `Missing`, the file is then created, `read` returns `File`; both observations are kept, the entry is marked conflicting, and `revalidate` returns `Changed` (`Created`) even though the final state is stable. Same for `File` then different bytes.
- Linux rename race and no fallback: a concurrent thread that renames an already opened intermediate directory out of the root, then **back**, while `openat2` runs must never cause bytes from outside the root to be returned. An injected `ENOSYS` and an injected `EPERM` return `Unsupported` and never read. Windows: the same move-out-and-back sequence against a held directory handle must fail to rename, validating the no-`FILE_SHARE_DELETE` boundary, or Windows stays unsupported. macOS returns `Unsupported` with no walk.
- Case spelling (D8): on a case-insensitive filesystem a wrong-case request returns `CaseMismatch` and records nothing.
- Platform skip rule: symlink tests on Windows follow `OMNI_TEST_REQUIRE_CAPABILITIES` (fail on CI when the privilege is missing, skip only locally); junction tests never skip.
- Missing: `ENOENT` and `ENOTDIR` become tracked `Missing`; `EACCES`, non-regular, symlink do not.
- Limits before allocation: a file reported larger than `max_file_bytes` fails without allocating its size (assert via an allocation-counting reader); growth during read caught by the cap; directory with `limit+1` entries stops; `max_operations` counts misses.
- Non-regular: FIFO and device return `NotRegular` without blocking.
- Cancellation: cancel mid-read leaves no evidence and no exposed bytes.
- Repeated read returns the first captured bytes.
- Benchmark: overhead on a 1,000-file tree versus plain reads.

**F10.3**

- Same-size, same-mtime edit (mtime restored with `set_modified`): `Modified`.
- Created file after a `Missing` read: `Created`. Deleted file: `Deleted`. File replaced by directory: `KindChanged`.
- Directory add, remove, rename: `MembershipChanged`.
- Case-only rename of a tracked path: `Deleted` (D8).
- Truncation: more changes than `max_reported_changes` returns the bounded list plus `remainder`.
- Honest guarantee: an edit after the last re-observation is not asserted as detected.
- Atomic replace with identical content: `Unchanged`.
- Denial, containment violation or I/O error during revalidation is an error, not `Changed`.
- `Changed` output is bounded and deterministic.
- Revalidation is read-only and repeatable; cancel leaves state untouched.
- Default policy outcome: any `Changed` produces the reject outcome; no retry is attempted.
- Mutation during revalidation itself is the documented residual and is not asserted as detected.

Authority is tested on the view itself: it refuses what the authorizer denies, what containment rejects even when allowed, and what exceeds limits (`authorizer ∩ containment ∩ limits`), and an unevaluable policy fails closed. The unchanged `omni_capability_sys` and `omni_capabilities` suites only show those crates were not edited.

## Risks

- **Security:** a bug here weakens containment for every consumer. Treat F10.2a, F10.2b and F10.3 as High-risk review (capabilities rule in [AGENTS.md](../../../../../AGENTS.md)): second reviewer, platform tests required, and no change to `omni_capabilities` in the same PR.
- **Portability:** the Windows strategy is an unverified design and macOS is `Unsupported`; the Linux `openat2` path is the best understood. Do not claim cross-platform containment until each platform's tests pass.
- **Residual race:** an edit after the last re-observation is undetected, by design.
