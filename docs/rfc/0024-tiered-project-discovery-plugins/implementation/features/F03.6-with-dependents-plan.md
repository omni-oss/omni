# F03.6: `--with-dependents` matching

**Status:** gap 1 decided (maintainer approved the direction); Phase 1 proof
tests are written and fail on the base. The same-name rule is intended and is
documented (help text, API doc comment, guide). Gap 2 (aliases) is decided: keep per-project alias matching; nothing to
build.
**Base:** `98949020` (`origin/main`); the investigation was on `dd2ebb95`.
**Kind:** Medium (one function, but a visible behavior change).
**Risk:** High: gap 1 changes which tasks run (`docs/guidelines` risk
overrides). It does not touch cache keys, storage or invalidation code. Needs a
plan (this note), proof tests first and independent review.

## Assessment

- **Question.** Is "`--with-dependents` adds only dependents with the same task
  name" a bug, a limitation or the design?
- **Answer: the design.** Evidence:
    - The introducing commit `f0421a4d` ("feat: implement --with-dependents")
      builds a second `DefaultTaskFilter` from the requested task names only
      (`tf_dependents`) and passes it to
      `get_batched_execution_plan_with_dependents`.
    - `tests/omni-tests/src/run.e2e.spec.ts` pins it twice: `-w` with `-p`
      runs `app#build` for `lib#build`; and "`-w` + `-m` filters roots by meta,
      then pulls dependents in by task name", whose comment says `-w` "pulls in
      every dependent sharing the queried task name regardless of its own meta".
    - `with_dependents_keeps_the_qualifier_on_the_seed_only`
      (`execution_plan_provider.rs`) pins that a `project#task` qualifier scopes
      the seed only.
    - F03.5 decision 5 calls "matching by task name only" a separate issue, not
      a defect of that fix.
    - The CLI help ("Run the task along with its dependents. Useful for
      combining with filters") was the only user-facing text, and it did not say
      any of this. The `omni_api` comment ("tasks that depend on the matching
      tasks") implied all tasks.
- **Upstream convention.** All three selectors work on packages, not tasks:
  turbo `--filter=...pkg` and pnpm `--filter ...pkg` select `pkg` and its
  dependent packages (transitively), and the requested task runs in those that
  have it. nx `affected` / `run-many -t build` do the same over the project
  graph. None of them runs other tasks of the dependents, so "same task name"
  matches them. They differ in one way: the dependents are found on the package
  graph, so a package that lacks the task does not interrupt the search. Omni
  searches the task graph and stops at a non-matching task (gap 1).
- **Unknowns.** How common gap 1 and gap 2 are in real workspaces; none was
  measured. Both need a task graph where a differently named task sits between
  two same-name tasks, or an alias used with `-w`.
- **Undo.** Docs: revert. Any semantic change: revert the one graph or provider
  commit; no data or cache format changes.

was regenerated with `omni declspec dump` and `bun run gen:refdocs`):

- `-w` help in `crates/omni_cli_core/src/commands/run.rs` and its reference page.
- The doc comment of `TaskRunRequest::with_dependents` (`omni_api`).
- New guide `apps/site/content/docs/guides/with-dependents.mdx`.

No release note: behavior is unchanged.

## Gap 1: the search stops at a differently named task (decided: fix)

`end#build` depends on `mid#test`, which depends on `core#build`. It is a
transitive dependent of `core#build`, and `pnpm --filter ...core build` would
run it, but `omni run build -p core -w` does not. Step 1.5 only pushes a
dependent onto the stack when the name filter accepts it, so one filter decides
both "include" and "keep walking".

### Decision

Separate the two questions. Walk every dependent along `Dependency` edges and
add only the ones whose name passes the dependents filter. The seed keeps
today's behavior. The change only adds tasks; it never removes one.

### Exact semantics

In `get_batched_execution_selection_impl` (`crates/omni_core/src/task_execution_graph.rs`),
step 1.5:

1. `visited`: a set of nodes already walked. `dependents`: the nodes to add.
2. Start the stack with the seed nodes (step 1 matches). Seeds are in
   `possible_roots` already and are not filtered again.
3. Pop `i`. If `visited.insert(i)` is false, continue. For each outgoing
   `Dependency` neighbor `n` (a task that depends on `i`): push `n`
   unconditionally; if `with_dependents_filter(n)` is true, insert `n` into
   `dependents`.
4. `possible_roots.extend(dependents)`. Steps 2 and 3 are unchanged: roots that
   are dependencies of other roots drop out of `actual_roots`, and step 3
   schedules the closure of the actual roots over `Dependency` and `Sibling`
   edges.

Consequences:

| Question                                                  | Answer                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Is a non-matching task between two matches added?         | No. It is walked through but not a root. It runs only if an added task needs it (step 3), and then with its dependencies and siblings.                                                                                                                                                           |
| Is a task that depends only on a non-matching task added? | No (`other#lint` stays out), unless its name was requested.                                                                                                                                                                                                                                      |
| Several requested names                                   | The filter accepts any requested name (and `--task-pattern` globs). A name outside the set is walked through. Today a requested name carries the search on and an unrequested one stops it; after, nothing stops it, and the set only decides what is added.                                     |
| Persistent tasks                                          | A persistent task cannot be depended on (`task.persistent_dependency`), so it has no outgoing `Dependency` edges and is never walked through. A same-name persistent dependent is added, including one reached through other tasks.                                                              |
| `Sibling` edges                                           | Not followed in step 1.5 (F03.5). A walked-through task that no added task needs is not scheduled, and neither are its `with` siblings. Once an added dependent needs it, it runs as a dependency, and step 3 also schedules its dependencies and its `with` siblings (and their prerequisites). |
| Cycles                                                    | The task graph rejects dependency cycles when it is built, so the walk is over a DAG. `visited` still bounds the walk to one visit per node (a diamond or a long ladder is not walked once per path), so the cost stays O(V+E).                                                                  |
| Filters                                                   | Unchanged: `-p`, `--dir`, `-m`, `--scm-affected` scope the seed only. `project#task` scopes the seed project only.                                                                                                                                                                               |
| Aliases                                                   | Unchanged (gap 2): the dependents filter still matches the requested name per project.                                                                                                                                                                                                           |
| `with_dependents == false`, MCP                           | Unchanged.                                                                                                                                                                                                                                                                                       |
| `direct` (hash input)                                     | Unchanged: it is the step 1 match, taken before step 1.5.                                                                                                                                                                                                                                        |

Not changed: gap 2, MCP (`with_dependents` stays `false`), following `with`
siblings.

### Compatibility and release note

This changes what runs: workspaces that chain through a differently named task
between two same-name tasks run more tasks, and CI times grow with them. A
failing added task now fails a run that used to pass. Pre-v1, so no flag or
deprecation period. A release note is needed (it changes what runs), in the
style of `apps/site/content/docs/guides/with-sibling-prerequisites.mdx`: a guide
page "Dependents through other tasks", description starting "Release note
(pre-v1):", with a short example (`end#build` -> `mid#test` -> `core#build`),
the one-line rule "walked through, added only if the name matches", the
statement that other-name tasks are still not added (use `build test`), and how
to see it (`omni run build -p core -w -d`). It must also say that a `-w` run
can now execute intermediate tasks, their dependencies and their `with`
siblings, and may surface `executor.cache_contradiction`, `task.sibling_cycle`,
`CacheDependencyDemoted` or newly scheduled persistent tasks. It ends with a
short Rollback section (upgrade is a revert of the graph commit; no data
change). The existing `with-dependents.mdx`
changes in the same commit: remove the bullet "Not added: dependents reached
through another task" and add the new rule under "What is added".

User-facing text that changes with the fix (build phase, same change as the
behavior), because today's wording says "same task name" and "not added:
reached through another task":

- `crates/omni_cli_core/src/commands/run.rs` (~47): the `-w` help.
- `crates/omni_api/src/operations/task.rs` (~81): the doc comment of

### Performance

One pass over the same graph, still O(V+E) because of `visited`. Non-matching
nodes are now also visited, which only costs the walk, and only when `-w` is on.
Check with `omni_bench` (`crates/omni_bench/src/harness.rs` passes
`.with_dependents(false)`): add one `true` variant on the large fixture and
compare before and after; expect no measurable change. Step 2 root pruning is quadratic in the number
of roots, and the fix can add many roots, so the `with_dependents(true)` bench
variant must watch it.

### Fan-out evidence

Before and after the fix, diff `omni run build -p <leaf> -w -d` (a leaf
project of this repo's own workspace) and one aggregate-task case on the same
workspace. Record how many tasks are added; this measures the real growth in
what runs.

### Rollback

One revertable commit in `omni_core` (plus the docs commit). No format, cache or
storage change, and selection does not feed the cache key: `direct` is taken
before step 1.5 (pinned by `with_dependents_walk_does_not_change_the_direct_set`).
Reverting restores the smaller plan.

## Gap 2: aliases are matched per project (DECIDED: keep, option A)

`compile -p core -w` seeds `core#build` through the alias, but dependents are
matched with the same selector, so a dependent without a `compile` alias is
skipped even though its `build` is the same task name. This is consistent with
how selectors work for any project (F03.4) but surprising with `-w`.

### Options

- **A. Keep, documented** (done in the guide). Cheapest, no behavior change.
- **B. Match dependents by the canonical name of the seeds.** `compile -p core
  -w` adds `build` in the dependents. Needs the seed's canonical task names from
  the alias index, and a decision for patterns and for aliases that retarget
  differently per project. It can remove matches as well as add them:
  if `compile` resolves to `build` in the seed project but to a dependent
  project's `test` task, today's per-project alias matching selects that `test`
  task and canonical-only matching would not. To avoid removals, match a
  dependent by the canonical names of the seeds or by the existing per-project
  alias match (union). Alias is new (#175), so few users are affected.

## Rejected: all dependent tasks regardless of name

Adding every transitive dependent task would turn `-w` into "run everything
downstream" (including `test`, `deploy`, persistent-adjacent tasks), is
unlike turbo, pnpm and nx, and contradicts the pinned e2e tests. A user who
wants that can name the tasks (`omni run build test -p lib -w`).
