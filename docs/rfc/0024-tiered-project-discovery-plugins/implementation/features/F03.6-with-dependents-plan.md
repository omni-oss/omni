# F03.6: `--with-dependents` matching

**Status:** investigated, no production change. The same-name rule is intended
and is now documented (help text, API doc comment, new guide). Two narrow gaps
are recorded below for a maintainer decision; nothing here is approved to build.
**Base:** `dd2ebb95`.
**Kind:** Small (docs, done) and Medium if either gap is changed.
**Risk:** docs: Low. Changing the gaps: High, because it changes which tasks run
(`docs/guidelines` risk overrides). It does not touch cache keys, storage or
invalidation code.

## Assessment

- **Question.** Is "`--with-dependents` adds only dependents with the same task
  name" a bug, a limitation or the design?
- **Answer: the design.** Evidence:
    - The introducing commit `f0421a4d` ("feat: implement --with-dependents")
      builds a second `DefaultTaskFilter` from the requested task names only
      (`tf_dependents`) and passes it to
      `get_batched_execution_plan_with_dependents`.
    - `tests/omni-tests/src/run.e2e.spec.ts` pins it twice: `-w` with `-p`
      runs `app#build` for `lib#build`; and "`-w` + `-m` filters roots by meta,
      then pulls dependents in by task name", whose comment says `-w` "pulls in
      every dependent sharing the queried task name regardless of its own meta".
    - `with_dependents_keeps_the_qualifier_on_the_seed_only`
      (`execution_plan_provider.rs`) pins that a `project#task` qualifier scopes
      the seed only.
    - F03.5 decision 5 calls "matching by task name only" a separate issue, not
      a defect of that fix.
    - The CLI help ("Run the task along with its dependents. Useful for
      combining with filters") was the only user-facing text, and it did not say
      any of this. The `omni_api` comment ("tasks that depend on the matching
      tasks") implied all tasks.
- **Upstream convention.** All three selectors work on packages, not tasks:
  turbo `--filter=...pkg` and pnpm `--filter ...pkg` select `pkg` and its
  dependent packages (transitively), and the requested task runs in those that
  have it. nx `affected` / `run-many -t build` do the same over the project
  graph. None of them runs other tasks of the dependents, so "same task name"
  matches them. They differ in one way: the dependents are found on the package
  graph, so a package that lacks the task does not interrupt the search. Omni
  searches the task graph and stops at a non-matching task (gap 1).
- **Unknowns.** How common gap 1 and gap 2 are in real workspaces; none was
  measured. Both need a task graph where a differently named task sits between
  two same-name tasks, or an alias used with `-w`.
- **Undo.** Docs: revert. Any semantic change: revert the one graph or provider
  commit; no data or cache format changes.

## Observed behavior (base binary, `-d`, fixture described below)

Fixture (projects of one workspace): `core` (`build`, `gen`); `lib` and `ali` and `top` and `app` depend

`lib#docs`, `lib#test` depend on `lib#build`; `app#verify` depends on
`^test`; `differ#pack` depends on `core#build`; `mid#test` depends on
`^build`; `end#build` depends on `mid#test`; `client#serve` depends on
`^serve`; `server#serve` has `with: [core#build]`.

| `build -p core -w` vs `end#build`               | not added: it depends on `core#build` only through `mid#test`      |

| `build -w -m 'tier == "fast"'`                  | seed is `core#build`; `slow` dependents are added                  |
| `build -b HEAD~1 -t HEAD -w` (core changed)     | all of `lib` `app` `ali` `top` `build`, though unchanged           |
| same, then `-p app`                             | error `executor.nothing_to_execute` (the seed has to match both)   |
| `serve -p server -w`                            | `client#serve` added                                               |

`--ignore-deps` with `-w` is rejected by the CLI. The MCP tool always sends
`with_dependents: false`.

## Outcome

**B, plus two optional gaps.** The semantics are intended and matched by the
upstream tools, but they were undocumented and the help text and API comment
were misleading. Done in this change (docs and strings only; the reference page
was regenerated with `omni declspec dump` and `bun run gen:refdocs`):

- `-w` help in `crates/omni_cli_core/src/commands/run.rs` and its reference page.
- The doc comment of `TaskRunRequest::with_dependents` (`omni_api`).
- New guide `apps/site/content/docs/guides/with-dependents.mdx`.

No release note: behavior is unchanged.

## Gap 1: the search stops at a differently named task

`end#build` depends on `mid#test`, which depends on `core#build`. It is a
transitive dependent of `core#build`, and `pnpm --filter ...core build` would
run it, but `omni run build -p core -w` does not. Step 1.5 only pushes a
dependent onto the stack when the name filter accepts it.

### Proposed change

Walk outgoing `Dependency` edges through every node and add to the roots only
the nodes the name filter accepts. In
`crates/omni_core/src/task_execution_graph.rs`, step 1.5: keep a `visited`
set separate from `dependents`; always push; call `with_dependents_filter` only
to decide membership. `mid#test` is not added, and runs only if `end#build`
needs it, because step 3 schedules dependencies.

- Included: same-name tasks reachable over `Dependency` edges, through any
  task. Not included: other names, as today.
- `Sibling` edges: still not followed (F03.5, unchanged). Persistent tasks: a
  persistent task cannot be depended on, so it is never walked through; a
  same-name persistent dependent is added as it is today.
- Filters: still scope the seed only.

### Behavior change and release note

Gap 1 only adds to today's plan: workspaces that chain through a different
task name between two same-name tasks run more tasks. Release note (pre-v1):
"`--with-dependents` now also finds same-name dependents that depend on the
selected task only through tasks with another name. It runs more tasks in
workspaces that have such chains."

### Tests, proof first

1. Graph-level, `omni_core`: the `mid#test`/`end#build` chain fails today and
   passes after; a chain with no intermediate and a diamond are unchanged; a
   cycle through a non-matching node terminates (the `visited` set); `Sibling`
   and persistent cases are unchanged.
2. Provider-level: `-w` with `--task-pattern` and an alias selector keeps the
   filter semantics.
3. E2E in `run.e2e.spec.ts`: node marker commands and the chain above. Dependency
   scheduling also runs `mid#test` because `end#build` needs it, so a marker
   test cannot expect both `end#build` and no `mid#test` marker. Distinguish
   "added as a root" from "run as a dependency": assert on the dry-run root
   listing (`end#build` is a root, `mid#test` is not), or expect the `mid#test`
   marker as a dependency of `end#build`. A run without `-w` is unchanged. No shell
   syntax and no pinned path separators, so it runs on Windows.

### Performance

One pass over the same graph, so still O(V+E). The traversal now also visits
non-matching nodes, which only matters for the plan size. Check with the
existing `omni_bench` harness (it already passes `with_dependents(false)`; add
one `true` variant) on the large fixture; expect no measurable change.

## Gap 2: aliases are matched per project

`compile -p core -w` seeds `core#build` through the alias, but dependents are
matched with the same selector, so a dependent without a `compile` alias is
skipped even though its `build` is the same task name. This is consistent with
how selectors work for any project (F03.4) but surprising with `-w`.

### Options

- **A. Keep, documented** (done in the guide). Cheapest, no behavior change.
- **B. Match dependents by the canonical name of the seeds.** `compile -p core
  -w` adds `build` in the dependents. Needs the seed's canonical task names from
  the alias index, and a decision for patterns and for aliases that retarget
  differently per project. It can remove matches as well as add them:
  if `compile` resolves to `build` in the seed project but to a dependent
  project's `test` task, today's per-project alias matching selects that `test`
  task and canonical-only matching would not. To avoid removals, match a
  dependent by the canonical names of the seeds or by the existing per-project
  alias match (union). Alias is new (#175), so few users are affected.

## Rejected: all dependent tasks regardless of name

Adding every transitive dependent task would turn `-w` into "run everything
downstream" (including `test`, `deploy`, persistent-adjacent tasks), is
unlike turbo, pnpm and nx, and contradicts the pinned e2e tests. A user who
wants that can name the tasks (`omni run build test -p lib -w`).

## Rollback and compatibility

Each slice is one revertable commit with no format, cache or storage change.
Gap 1 only grows the plan, so rolling it back restores the smaller plan. Gap 2

tasks again. Cache keys are
unchanged; selection does not feed the key (not re-verified here, check in slice 1).

## Decisions needed from the maintainer

0. With several requested names, `-w` matches any requested name at every step
   (`omni run build test -p core -w` reaches `end#build` through `mid#test`),
   while a single name stops at the first mismatch. Keep this per-name traversal
   or change it? Documented as is in this PR; no behavior change here.

1. Is gap 1 (pass through differently named tasks) wanted, or is the current
   stop-at-mismatch rule to be documented as final? Recommendation: fix it; it
   is a small superset change with a clear upstream precedent. It is not urgent.
2. Gap 2: keep per-project alias matching (option A, recommendation) or match by
   canonical name (option B)?
3. Should the MCP `task_run` tool and the `omni_api` request expose
   `with_dependents` to agents? Today the tool hard-codes `false`; out of scope
   here.
4. Should `with` siblings be followed when searching for dependents? Today
   they are not (F03.5). Recommendation: no.
