# F04.2: exact task filters for `hash` and `cache` plan

**Status:** implemented in this batch (pending review). Hard break, no deprecation period.
**Kind / risk:** Medium / **High**. `cache prune` deletes data and `omni_cache` is a repository High-risk area. No cache key, storage format or invalidation rule changes.

## Goal

Make `-t/--task` on `omni hash project`, `omni cache stats` and `omni cache prune` exact names, and add a repeatable `--task-pattern <glob>` to each, matching `omni run` ([F04](F04-exact-selectors-and-task-patterns.md)). Same for the MCP `hash_project`, `cache_stats` and `cache_prune` parameters. Breaking, as agreed.

## What exists

- Three places match task names by glob: the cache entry scan in `hybrid.rs` (`include_set`, which defaults to `*`), the planner calls in `plan_task_set` and the prune plan (`Call::pattern_tasks`), and `ProjectHasher` (`Call::pattern_tasks` plus a second `include_set` over digests).
- `CacheStatsArgs` and `PruneCacheArgs` carry `task_name_globs: &[&str]`; `ProjectHasher::hash` takes `task_names: &[&str]`.

## Approach

1. **Args.** Replace `task_name_globs` with a small `TaskNameFilter { exact, patterns }` (both empty means every task). A cache entry matches when its task name equals an exact name or matches a pattern. Used for the entry scan and for building `Call::Tasks` selectors for the plan.
2. **Planner strictness.** `run` and `hash` should fail on an exact name that matches no task (the F04 check). `cache stats/prune` must not: cache entries outlive tasks, so `cache prune -t removed-task` has to keep working. Add `DefaultExecutionPlanProvider::allow_missing_exact(true)` (default off) and use it only from the cache store.
3. **Hash.** `ProjectHasher` takes selectors; both the plan and the digest filter use them. The hash value for the same selected tasks must not change.
4. **Surfaces.** CLI `-t/--task` exact plus `--task-pattern`; MCP `tasks`/`task` exact plus `task_patterns`; update the reference docs by regenerating only the three touched pages; migration note in a `feat!` commit.

## Verification (High risk)

- Prune is the guarded failure: tests that an exact name removes only that task's entries, never a glob-like neighbour; a literal `*` task is distinct from the pattern `*`; exact plus pattern union; no filter still means everything; dry-run reports without deleting; `--stale-only`, `--dir` and `--meta` with exact names still work, including a removed task.
- Stats: same selection matrix. Hash: same hash for the same selected tasks before and after; a golden value for a fixed fixture; an unknown exact name errors.
- Existing glob-based tests are moved to `--task-pattern` / `patterns`, not loosened. E2E specs updated.
- Mutation checks on the exact-vs-pattern matching and on `allow_missing_exact`.

## Undo

Revert; no stored data changes. Residual risk: scripts that pass globs to `cache prune -t` or `hash -t` will now match nothing (prune) or fail (hash). Prune then deletes nothing rather than too much, which is the safe direction.

## Implementation record

- `omni_cache`: a `NameMatcher` (exact set plus globs, neither means all) replaces the glob-only task match in stats and prune. `CacheStatsArgs` and `PruneCacheArgs` gain `task_names` (exact) beside `task_name_globs`, so existing glob-based callers and tests are unchanged. The plan calls build `Call::Tasks` selectors and use `DefaultExecutionPlanProvider::with_allow_missing_exact(true)`.
- `omni_execution_plan`: `with_allow_missing_exact` (default off) skips the exact-task existence check; `run` and `hash` keep it.
- `omni_context`/`omni_api`: `ProjectHasher`, `LoadedContext::get_project_hash(_string)` take `TaskSelector`s; `hash_project(name, tasks, task_patterns)`.
- CLI: `-t/--task` exact plus `--task-pattern` on `hash project`, `cache stats`, `cache prune`. MCP: `hash_project` (`tasks`, `task_patterns`), `cache_stats` and `cache_prune` (`task`, `task_pattern`).
- Tests: `NameMatcher` unit tests; store tests for stats and prune (exact never matches a glob-like neighbour, a literal `*`, union, dry-run, an unknown exact name deletes nothing); planner test for `allow_missing_exact`; MCP parameter tests; the e2e spec covers hash and cache end to end, including `--dir` with a removed task.
- Mutation checks: treating exact names as globs in `NameMatcher` fails four tests. Making the plan call treat exact names as patterns is not caught: the entry scan already filters by `NameMatcher` first, so that is an equivalent mutant (defense in depth), not a gap.
- The hash value for the same selected tasks is unchanged: `-t build` and `--task-pattern build` hash alike, and `--task-pattern '*'` equals no selector.

## Review follow-ups

An independent review (Claude Opus 5.5) found no path that deletes more than the user selected and confirmed `allow_missing_exact` cannot reach `run`, `exec` or `hash`. Its findings were fixed: every project glob must match on its own (an exact name beside it no longer hides a typo), the exact-task existence check is one scope filter plus map lookups instead of rebuilding a filter per name, the "nothing to execute" message prints project selectors with `Display`, and a prune test asserts which entries were pruned. Documented, not changed: with `--dir`, `--meta` or `--stale-only`, entries of removed tasks or projects cannot be matched (they are not in the plan), so pruning them needs the plain exact name; issue #136 tracks `--orphan`. Known and pre-existing: the plan's `project#task` key is ambiguous for a project named `a#b`; a tuple key would remove it.

## Decisions

- Hard break, no deprecation period.
- Cache stats/prune accept an exact name that matches nothing without erroring (entries outlive tasks), through `allow_missing_exact`; they do nothing for it. `hash` errors on an unknown exact name, like `run`.
- A cache-entry "orphan" mode is out of scope; tracked in issue #136.
- Independent review is required before merge, per the High-risk bar.
