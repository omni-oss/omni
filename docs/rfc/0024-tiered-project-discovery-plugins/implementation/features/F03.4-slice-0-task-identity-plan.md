# F03.4 slice 0: Structured task identity and cache-key cutover

**Status:** proposed; no implementation started. Two independent High-risk
reviews of revision `2fadb9f5` (Claude Opus 5.5 and Gemini 4 Neon) returned
BLOCKED. This revision folds in their findings and the earlier GPT-6.2-sol
review, and records two maintainer decisions: the graph/report compatibility
boundary and the inventory `--dir`/`--meta` rule (the latter is decision D2 in
the [alias plan](F03.4-authored-alias-plan.md#build-gate)). It needs a fresh
independent review before any build.
**Base:** `27203b50` (`main` after F05.2 and F09 landed; the first review used `e1f502e4`). **Reader:** the
implementer and reviewer of [F03.4's identity prerequisite](F03.4-authored-alias-plan.md#0-remove-joined-name-identity-from-internal-lookups).
The maintainer approved the direction, not a waiver of this plan's build gate.

## Goal, scope, and assessment

A canonical task is identified by its raw `(project, task)` pair. Before this
slice, two distinct pairs could render the same unescaped `project#task` label
and be confused; the escaped label below renders them distinctly, and no two
pairs share graph edges, configuration, results, output, or cache observations. All current consumers of
the task digest switch to one versioned identity contribution. Land and be able
to revert this prerequisite without authored aliases, new exact-selector
semantics, declaration-key decoding, inventory hints, F06.3's semantic digest,
or plugin scopes. Those changes remain in their owning slices. In particular,
stats and prune match stored canonical names, not live aliases; nothing in this
slice expands an exact miss or changes how a confirmation authorizes paths.

**Kind: Large. Risk: High.** The change crosses graph, execution, display and
cache boundaries. The largest unknown is whether all consumers can switch in
one release without changing persisted entries or losing structured data at a
serialization boundary. Resolve that first with a small end-to-end fixture. The
binary is reversible before aliases ship, but the cutover deliberately starts
cold; old entries survive unless normal retention/pruning removes them. Budget
one integration owner for the proof, cutover and combined checks, plus a fresh
read-only reviewer at each High-risk gate. The approval to plan does not
authorize delegation or a branch update. Persistent format, transport, or
broader hashing changes require a new plan.

## Identity and boundaries

**Structured identity everywhere internally; labels only at boundaries.** Every
internal decision (graph edges, context lookups, results, statuses, cache
observations, digest maps, output routing, contradiction detection) uses the
`(project, task)` pair. A `project#task` label is produced only when data
leaves the system (CLI text, JSON, MCP, notices, logs) and parsed only where
text enters (exact selectors, deserialized reports), converting to a pair at
once. No internal API takes a label as an identity, and a label is never a map
key.

**The label is escaped and round-trippable.** Render it with the shared
reference grammar (`omni_types::TaskReference`, project and task only): `\#`,
`\\` and the grammar's other escapes apply, so distinct pairs render distinct
labels and `parse(format(pair)) == pair`.

```text
("a#b", "c")  -> a\#b#c
("a", "b#c")  -> a#b\#c
```

- Names without reserved characters render exactly as today. Only names that
  contain `\`, `#`, or adjacent colons, or a project name that begins with `^`,
  change their label. State exactly this as a pre-v1 note.
- The round-trip guarantee holds for names the grammar accepts (non-empty, no
  NUL). During the proof, audit whether empty or NUL project or task names are
  reachable from configuration or discovery. If they are, reject them at
  ingress with a diagnostic and a pre-v1 note; if not, assert the invariant in
  `TaskKey` construction. The formatter is infallible for valid keys.
- Diagnostics use the same formatter: graph cycle and persistent-task errors,
  the extracted-data validator, meta-filter errors and project-config error
  locations all currently join labels by hand.
- A single shared formatter and a display-only label type (no conversion into a
  map key) produce every label. A hand-built `format!("{}#{}")` task label is a
  review/lint finding, since it would disagree for reserved characters.
- Stored canonical names and the cache digest recipe are unchanged by this
  decision; the label is not persisted identity.
- Exact-selector parsing is deferred (see scope), so a displayed label is not
  yet an accepted selector. Once alias slice 3 activates shared-grammar selector
  parsing, a displayed label becomes a valid exact selector.
- Labels written by earlier versions remain ambiguous for colliding names;
  parse only at ingress, never to recover identity inside the executor.

- Put an owned `TaskKey` and a borrowed `TaskKeyRef<'a>` in `omni_types` (re-export
  the graph-facing name from `omni_core`). Compare and hash both components by
  contents; pointer identity, a digest, and a rendered label are never equality.
  Use shared immutable component storage (e.g. `Arc<str>`) for node-owned keys
  and ordered edge lists so a plan/node clone does not copy strings per edge.
  Project-scoped storage and name-based lookups use nested project/task maps
  with borrowed `&str` lookups. Use borrowed pairs in bounded scratch maps and
  visited sets, and own keys only where they outlive their source. Do not build
  a fresh owned key to probe a map. No process-global interner or graph-local
  node index crossing the graph boundary as a task identity.
- Populate the structured dependency list at `add_edge_by_names` from the
  resolved endpoint. Keep declaration order and explicit duplicate dependency
  occurrences, sibling edges separate, and the existing cycle/scheduling
  behavior. Forwarding deduplicates by structured pair within one walk, not
  across callers' explicit dependency slots. Neither parse legacy labels nor
  change the grammar or what counts as a root.
- `full_task_name`, rendered `dependencies`, event `task_id`, skip dependency,
  cache demotion causes and notice fields remain presentation data, rendered
  with the escaped label above. Keep existing result JSON/schema field names,
  string/array types and redaction; only the label's value changes, and only
  for names with reserved characters. Populate legacy node projection fields directly from runtime
  components and ordered edge keys; never reconstruct a runnable node's edges
  from that projection. A deserialized result is a report, not an execution
  plan. Snapshot node/results including completed, errored, skipped and
  cache status; test that the formerly colliding pairs yield separate items with distinct
  escaped labels, and that canonical `project_name` and `task_name` identify them.
- **Graph and report compatibility (maintainer decision: preserve the wire
  formats, add a typed execution boundary).** Keep the documented serialized
  `TaskExecutionNode`, result and report formats: field names, types and the
  rendered `dependencies` strings. `omni_core` re-exports the graph type
  publicly and `cli/omni/CHANGELOG.md` announced serializable graphs, so do not
  remove its serde. Executable nodes are built only by the graph builder with
  typed `TaskKey` edges. A deserialized node or result is a **report**, never an
  executable node; distinguish them by type, not by an empty edge list, since a
  runtime task with zero dependencies is valid. Replace the string-edge
  `TaskExecutionNode::new`/`deconstruct` surface with a typed constructor
  (a pre-v1 Rust API change; note it). On deserializing a full graph, rebuild
  the typed index from each node's own project and task fields and the edge
  table, and ignore the serialized hashed `node_map`. During the proof,
  enumerate every executable ingress (plan building, `ExecutionPipeline::new`)
  and show that a report is rejected there. Test ordinary, skipped and errored
  results round-tripping as reports, a genuine runtime node with zero edges as
  executable, and a report with legacy ambiguous labels being rejected at
  executable ingress rather than guessed.
- Stored canonical components are unchanged UTF-8 names; there is no escape
  processing in storage. `CachedTaskExecution`, `CachedTaskExecutionHash`,
  last-used DB, project directory encoding, digest address encoding, archive,
  schema/path versions, partitions, signatures and origin markers stay as they
  are. `DefaultHash` remains the digest type, not an identity for an in-memory
  task. Content-address lookups still validate project, task and digest before
  reuse or publication. Cache output directories use base58 project and digest
  encodings, which share the case-insensitive-filesystem caveat of capture
  files below; this slice does not change them (existing behavior, and address
  validation prevents wrong hits).

Alternatives rejected: using the escaped joined string as an _equality key_
would couple internal equality to one presentation grammar (the escaped label
is adopted only as the boundary spelling); hashing two components into a `u64`
leaves digest equality masquerading as name equality; introducing a separate
storage namespace or dual-read would add rollout complexity or admit old
ambiguous hits. The existing maps and cache address formats suffice.

## Identity leaf v1

Replace **one** leaf in `Collector::get_digest`, at the same insertion point
(after command/retry contributions, before commit). Feed `BLAKE3` the
concatenation of these exact bytes:

```
b"omni.task-id\0" || 0x01 ||
u64_le(project UTF-8 byte count) || project UTF-8 bytes ||
u64_le(task UTF-8 byte count)    || task UTF-8 bytes
```

There is no UTF-8 normalization, trimming, escaping, NUL terminator on either
name, or native endian/word size. `||` denotes byte concatenation, not Rust's
boolean operator. Count with a checked `usize` → `u64` conversion, and stream
the slices through a small BLAKE3 helper in `omni_hasher` that yields exactly
`DefaultHasher::hash` over the whole preimage: plain, unkeyed BLAKE3, so the
vectors pin the full leaf (no heap allocation for framing). The collector owns the domain/version and field order; the leaf is
still a single 32-byte hash. No additional leaves, seed change, ordering or
dedup of input files, env, args, commands, dependency digests or output globs.
Do not use the encoded bytes or their hash as runtime task equality. The
domain and framing version the input recipe, not the persisted metadata.

Vectors (hex, spaces only for readability):

| Pair                                           | Complete v1 preimage                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| Shared prefix of every vector                  | `6f 6d 6e 69 2e 74 61 73 6b 2d 69 64 00 01`                                  |
| `("a#b", "c")`                                 | prefix + `03 00 00 00 00 00 00 00 61 23 62 01 00 00 00 00 00 00 00 63`       |
| `("a", "b#c")`                                 | prefix + `01 00 00 00 00 00 00 00 61 03 00 00 00 00 00 00 00 62 23 63`       |
| `("é", "🧪")`                                  | prefix + `02 00 00 00 00 00 00 00 c3 a9 04 00 00 00 00 00 00 00 f0 9f a7 aa` |
| Encoder-only empty component check `("", "#")` | prefix + `00 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00 23`                |

The first two pairs had the same legacy preimage (`61 23 62 23 63`). V1
cannot confuse the split because each length locates the next component
uniquely, even when names contain delimiters. This proves distinct preimages,
not mathematical collision freedom of BLAKE3. Pin the actual old leaf and
legacy full digest from the base, and the v1 leaves/full digests from the same
input fixtures. Compare against a test-only legacy recipe with just the
identity leaf swapped; no legacy reader, fallback or promotion in production.

## First proof and landing order

1. **Prove the boundary first, after review.** Capture a baseline on the base
   binary with a deliberately ordinary undecorated task (controlled input
   files, env, default args, and cache paths); keep the old digest, metadata
   bytes or decoded field snapshot, paths and response schema for tests.
   Add a fixture with projects `a#b` and `a`, including tasks `c` and `b#c`
   respectively, and an `app` with independent consumers of the two tasks.
   Define distinct commands, output/log markers, env, meta, default args and
   cache settings; disable default config-file hashing in this fixture when
   isolating identical collector inputs. Use raw task declarations as accepted
   today; address dependencies with the existing escaped project/task
   references `'a\#b#c'` and `'a#b\#c'` (or raw structured graph fixtures for
   independent graph tests). Select the `app` consumers or select all; don't
   rely on unshipped exact-selector parsing. Expect two pair-distinct nodes in
   the same plan, correct targets, both results/logs, matching cache read/write
   for each, and distinct downstream dependency inputs. Also test equal
   non-identity collector inputs to isolate the identity leaf. Show a test
   failing on the base (context or results), not just a new encoder unit test.
   Keep this proof/test-only legacy comparison out of production until the
   coherent cutover; discard or revise the prototype if boundaries fail.
2. **Land one coherent runtime cutover.** Integrate structured ownership from
   graph through result/report, cache and inventory, and switch the one leaf.
   The smallest independently landable production change is this atomic
   prerequisite, with no alias, selector or schema activation. A key-only
   change leaves in-memory overwrites; an isolated graph conversion leaves
   downstream merges; separate digest switches create false misses or stale
   candidates. The proof may be built beside the old path under tests but do
   not ship a fallback or mixed-recipe binary. Complete the matrix below and
   have the integrated implementation independently reviewed. Add a release
   note in non-generated site content with the cutover (cold task caches and
   changed hash outputs; no manual data conversion; avoid stale pruning during
   a mixed fleet, with an example command; and labels containing reserved
   characters now render escaped in CLI, JSON and MCP output, with examples). Revert as a unit before going on to the authored feature.
3. **Hand off activation, not part of slice 0.** If F06.3 happens to ship in
   the same release, let release owners coordinate the cutover without
   importing F06.3 code here. Once this prerequisite passes, use the parent
   plan for escaped authored names, alias graph and live run/hash selection
   in the same activation, and canonical-only inventory (optional exact-miss
   hint separately). Undo later activation with its consumers before reverting
   slice 0.

## Mandatory parity matrix

inputs. Compare leaf/task digest before aggregation as well as public hash
output where applicable. On this base `hash project` hashes raw cache patterns,
has no invocation args and supplies direct predecessor digests; live and stale
paths expand cache templates and have their own skip/forwarding and eligibility
rules. Workspace hashing is an input union, not execution. The cutover must
give full parity on equivalent inputs, not silently make those different
contracts equivalent. Test and record existing differences separately; if
parity requires unifying task-input policies, re-plan rather than quietly
changing those policies.

## Mixed versions, rollback and re-planning triggers

V0 and v1 share the same paths/metadata _format_, not digest addresses. An old
client reads/writes v0; a new client reads/writes v1; neither may use the other's
entries as hits. A v1 run against v0-only local and remote stores misses, fills
v1, then hits v1; rerunning the old binary still hits v0 if retained and misses
if only v1 is present. Rehearse both directions against the same disposable
store and remote fake; no migration, rewrite, special GC, or old-probe request.
Raw name inventory can list both versions. Stale classification compares the
observing binary's digests, **not** the tool versions running in other worktrees:
v1 may classify v0 entries stale and vice versa when observations are decisive.
Mixed-version builds can coexist; defer stale pruning until the fleet is aligned
if retaining the other version's warm cache matters. Roll back the binary and
do not remove v1 entries as part of rollback; their existence does not grant
reuse. Rollback cannot recover entries already pruned. Project and workspace
hash string consumers should expect a new value at upgrade and the old recipe
on revert.
