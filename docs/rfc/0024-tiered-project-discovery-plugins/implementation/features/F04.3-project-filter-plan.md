# F04.3: exact project filters and `--project-pattern` plan

**Status:** proposed; awaiting approval before implementation.
**Kind / risk:** Medium / **High**, because it reaches `cache prune` and `omni_cache` the same way [F04.2](F04.2-hash-cache-selectors-plan.md) does. No cache key, storage format or invalidation rule changes.

## Goal

Make the project filter match the task filter ([F04](F04-exact-selectors-and-task-patterns.md)): `-p/--project` becomes an **exact** project name, and a repeatable `--project-pattern <glob>` selects by glob. Exact and pattern selectors union. Breaking, in the same batch as F04 and F04.2.

## Surfaces

Only real filters change:

- `omni run` and `omni exec` (`-p/--project`, in the shared run arguments).
- `omni cache stats` and `omni cache prune` (`--project`).
- The MCP counterparts: `task_run` and `exec_command` (`project`), `cache_stats` and `cache_prune` (`project`), and `hash_project`'s project name is already a single exact name.

Not changed: `generator run --project` and `tool run -p`, which take one project name already; `hash project <name>`, a single name; `--dir`, which stays a glob over paths (assumed; see questions).

## What exists

`DefaultProjectFilter::new(&[&str])` and the planner's `project_filters: &[&str]` build one glob set. The same strings flow through `get_execution_plan`, `DefaultTaskFilter`, the cache stats/prune args (`project_name_globs`), the task-executor config, and the API requests. A project filter that matches nothing is already an error (`plan.no_project_found_for_filter`).

## Approach

1. Add a `ProjectSelector { exact, patterns }` (empty means every project) beside `TaskSelector`, and use it in `DefaultProjectFilter`, `DefaultTaskFilter` and the planner entry points. A signature change, so every caller moves together (CLI, API, task executor, cache, benches).
2. Exact names that match no project fail with `plan.no_project_found_for_filter`, with a hint to use `--project-pattern` when the name looks like a glob, as the task side does.
3. Cache stats/prune use the selector for the entry scan and plan, and tolerate an exact name with no current project (entries outlive projects), through the same `allow_missing_exact`-style option as the task side.
4. CLI `--project-pattern`, MCP `project_patterns`; regenerate only the touched reference pages; migration note in a `feat!` commit: `omni run -p 'app-*'` becomes `omni run --project-pattern 'app-*'`.

## Verification (High risk)

Same matrix as F04.2 for projects: exact never matches a glob-like neighbour, a project literally named like a glob is distinct from the pattern, exact plus pattern union, no filter still means every project, dry-run deletes nothing, `--dir`/`--meta`/`--stale-only` still work. Existing glob tests move to the pattern path rather than being loosened. This repository's own CI uses exact `-p` names only (checked), so it keeps working. Mutation checks on the matching.

## Undo and risk

Revert; no stored data changes. A script using `-p 'glob*'` now errors (run, exec) or matches nothing (cache prune), the safe direction.

## Open questions (assumptions)

- `--dir` stays a glob. Is `--dir-pattern` wanted too?
- Cache stats/prune with an unknown exact project: tolerate silently (assumed), same as for tasks.
- Short flags: `-p` stays on `--project` (now exact); `--project-pattern` and `--task-pattern` get no short flag.
