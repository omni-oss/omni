# F06.3 follow-up: deliver workspace `env.vars` to every project (plan)

Status: PLAN, awaiting build approval. Risk: **High** (changes the environment tasks receive,
a cache-key input). Origin: "Known pre-existing runtime quirk" in
`F06.3-plumbing-plan.md` (branch `feat/rfc0024-f06-3-digest-in-key`, PR #190).

## Bug

`crates/omni_context/src/project_data_extractor.rs` (~line 242) expands the workspace
`env.vars` and merges them into `project_extras` only inside
`if !overrides.as_map().is_empty()`, where `overrides` is the project's own `env.vars`. A
project with no `env.vars` never receives workspace variables. Repro: workspace
`env.vars {X: w}`, project without `env`, a task printing `process.env.X` prints `undefined`;
adding any unrelated project `env.vars` entry makes it print `w`.

## Intended behavior (existing precedence kept)

1. Workspace vars reach every runnable project, with or without project `env.vars`.
2. Project variables still expand against the workspace's (the `command_config` and
   `expand_into_with_command_config` step stays as is).
3. A workspace value wins over a project value for a colliding key (`extend(ws_vars)` after).
4. The task layer is applied last (unchanged; it lives in `task_env_var_overrides`).
5. Unchanged: `definitions_only` and an empty workspace `env.vars` still yield nothing extra.

## Change

Keep the existing guarded block exactly as is (project vars, expansion against the
workspace vars, then `extend(ws_vars)`), and add an `else` branch for a project with no
`env.vars`:

```rust
if !overrides.as_map().is_empty() {
    /* unchanged */
} else if !ws_vars.is_empty() {
    project_extras.extend(ws_vars.clone());
}
```

Rationale (Gemini review): with no project vars there is nothing to expand against the
workspace, so skip building `command_config` and expanding the built-in keys
(`PROJECT_DIR` etc.); projects with `env.vars` behave byte for byte as today. `ws_vars` is
empty when there are no workspace vars or `definitions_only`, so those cases are unchanged.
Only the project-has-no-env case changes. Nothing else is touched.

Side effects of the same change, stated so they are not a surprise:

- `EnvLoader::get` layers the overrides over `.env` files, so for these projects workspace
  `env.vars` now win over the project's `.env` values (as for projects that already have
  `env.vars`). Both go in the release note.
- Values pass through expansion twice (`get_ws_vars_vars`, then the loader). Existing
  behavior that now reaches more projects.
- Tasks that do not list `X` in `cache.key.env` get an unchanged key (stale-hit hazard);
  tasks that do list it get a new key. The conclusion (not cache-neutral) stands.
- Anyone who ran a locally built #190 binary holds version 1 entries that this fix would
  replay as stale; acceptable for unreleased builds, said in the docs note.

## Tests (failing first; Windows-portable, no `node`, no shell commands)

In `project_data_extractor.rs` tests, using the `extracted_inputs` style (tempdir, `RealSys`,
`EnvLoader`, `inherit_env_vars` false, `definitions_only` false), a helper that returns the
vars the loader resolves for the project (`env_loader.get` with the same args, or the
extractor output that feeds it). Cases:

1. Workspace `{X: w}`, project with no env: project env has `X=w`. **Fails today.**
2. Workspace `{X: w}`, project `{Y: p}`: both present (regression guard, passes today).
3. Collision: workspace `{K: w}`, project `{K: p}`: `K=w` for a project with and without
   other vars (workspace wins; unchanged).
4. Expansion: project `{Y: "${X}-p"}` with workspace `{X: w}` gives `Y=w-p`; and workspace
   `{X: w}`, project `{X: p, Y: "${X}"}` gives `X=w, Y=p` (unchanged).
5. Task overrides are recorded unchanged in `task_env_var_overrides` (the task-last merge
   lives in `loaded_context.rs:248-264`; add a case there if a harness exists, else rely on
   the existing tests).
6. No workspace vars: nothing extra added; `definitions_only` adds nothing.
7. A project at the workspace root (`start_dir` equals the root) gets the workspace vars.
8. Workspace var beats the same key in the project's `.env` file for a project with no
   `env.vars` (pins the side effect above).

Test helper: assert on what `extract_all` leaves in the loader cache
(`env_loader.get_cached(project_dir)`, as `loaded_context.rs:248` does): `Some(vars)`
normally, `None` under `definitions_only`, where `get` would instead load from disk. A fresh `get`
with hand-built args would bypass the bug and not fail first. Keep `inherit_env_vars`
false so CI host variables do not leak, and keep temp paths free of `$` assumptions.

Paths use `tempfile` and `Path` joins only; no `/` literals compared, no shell. Confirm test
1 fails on the unfixed code before applying the fix, and record that.

## Cache interaction and base branch (revised: base on `origin/main`, independent of #190)

The code fix does not depend on #190. Verified on `origin/main`:
`omni_collector/src/collector.rs` has no `CACHE_KEY_VERSION`, and the key hashes only the
env vars a task lists in `cache.key.env` (lines ~250-272). The workspace layer is not
recorded there. Consequences on `main`:

- A task that lists `X` in `cache.key.env` now sees `X=w` instead of nothing, so its key
  changes correctly (cold start for that task only, no stale hit).
- A task that does not list `X` keeps its key and now receives `X`. That is `main`'s
  existing policy (unlisted env is not a key input), not a new hazard, so **no version
  bump and no cache-key docs change are needed on `main`**.

Interaction with #190 (a PR open on the same files' neighbors, not the same lines): #190
records the whole workspace layer in the key, which makes the fix non-cache-neutral there
(a fixed binary would hit entries recorded while `X` was unset). Handling, on #190's side:

- If this lands on `main` first, #190 rebases over it, keeps `CACHE_KEY_VERSION = 1`
  (never shipped), and updates its "Known pre-existing runtime quirk" section to say fixed,
  noting the env a task receives now includes workspace vars for projects without
  `env.vars`. Because #190's version-1 epoch has not shipped, no extra cold start.
- If #190 ships in a release before this fix, the fix then needs a `CACHE_KEY_VERSION`
  bump to 2 with the release note and `cache-keys.md` updates (second cold start). Say so
  in this PR's description and tell the #190 owner either way.

Never force-push #190's branch; this change does not touch it. Own branch
`fix/workspace-env-vars` off `origin/main`.
