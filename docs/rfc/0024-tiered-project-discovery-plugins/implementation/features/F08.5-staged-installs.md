# F08.5: Staged installs and caller migration

For source-manager contributors. Implements the install sequencing approved in
[F08.1](F08.1-lease-gc-reference-protocol.md).

## Assessment and scope

- **Kind / risk:** full F08.5 is Large / High (multi-crate lifetimes, persistence
  and concurrency). This first independently reviewable batch is the reference
  publication part: Medium / High across utils, source manager and API/CLI callers.
- **Unknowns:** stage/rename failures and cancellation. Fault-injected tests must
  show that no rename starts before every selected set is staged.
- **Undo:** revert; no file format changes. Before commit, failure leaves all
  selected sets unchanged. After commit starts, each file is old-complete or
  new-complete and re-running install converges; no cross-file rollback.
- **Execution:** solo implementation, independent PR review before merge.
- **Steps:** add batch publication with staging cleanup; collect every
  contributor before updating refs; migrate existing complete-set writers to
  explicit modes; verify manager and API failure paths.
- **Checks:** scoped tests/lint/format plus downstream API, CLI and MCP checks.
- **Escalation:** a format migration or a new lease-lifetime contract goes in the
  follow-up batch, not this reference-publication change.

## Boundaries

The first batch alone does not claim leased runtime protection. Runtime readers
were migrated in batch 2; install readers are covered in batch 3 below.
D1 (store version compatibility) remains a release-owner decision; no store
version bump is made here.

Complete generator/tool lists and projection full-sync use `ReplaceComplete`.
Targeted projection still writes no refs. The old `record_refs` wrapper remains
source-compatible for external/test callers. No genuine partial production caller
is introduced merely to exercise `MergeAdditive`.

## Behavior and verification

- `update_ref_sets` validates unique safe IDs and existing sets under one
  workspace lock. Every set is serialized before filesystem staging begins.
  The owned blocking publisher stages all files, then renames them in input order.
  Cancellation cannot release its lock halfway through publication.
- `run_contributors` collects every result before calling the batch API, then
  reconciles pins only after successful publication. A cancelled install may
  commit refs without reaching reconciliation, just as a crash could; retry
  converges. The existing per-file failure contract is not strengthened into
  a cross-file transaction.
- Generator/tool API and generator CLI writers now explicitly use
  `ReplaceComplete`; projection does so only on full sync, as before.
- Manager tests inject second-file open/write and second-rename failures, check
  cleanup, complete-file partial commit and convergence; cover duplicate IDs,
  corrupt later sets, cancellation and failed reconciliation after publication.
- API tests cover a later contributor failing without changing refs/lockfile,
  empty selected sets releasing refs, unselected sets unchanged, and existing
  shared-source counting.
- Library and atomic-reference-test clippy pass. API/CLI/MCP test targets compile.
  Platform filesystem behavior beyond Linux remains for CI.
- Verification: 136 tests pass across `omni_utils`, `omni_lockfile`,
  `omni_remote_source` and `omni_remote_source_contributors`, plus seven API
  remote-source tests. Rust/docs formatting and the task-graph check pass.

## Layout marker race (found by CI)

A macOS CI run of `gc_leases` failed with "unrecognized store layout marker": a
lock-free reader (`store_entries`) read `store/VERSION` while another manager's
first-use initialization was writing it directly (truncate, then write). The marker
is now created under a short store-initialization lock (`.layout.lock`, never held
while taking a remote lock), rechecked after acquiring it so a late initializer
cannot overwrite a peer's marker (including a newer layout), and published through
the staged atomic writer. Two tests in `atomic_refs.rs` pin both properties; each
fails without its fix. This bug predates F08.5 and was exposed by the lease race test.

## Batch 2: leases for runtime readers

**Status:** merged (#113). Batch 3 (install contributors) is below and also merged (#131).

Who holds a lease, and for how long, depends on how long the caller reads the
checkout.

| Caller                                                        | Reads the checkout                                | Lease lifetime                                            |
| ------------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| Generator and tool run, list, inspect, validate (API and CLI) | Templates and tool files, after discovery returns | The whole operation                                       |
| Projection sync                                               | Source files copied or linked after expansion     | The whole sync                                            |
| Pack expansion                                                | Manifests, then node roots read by the caller     | The `ExpandedPacks` value, or whatever absorbs its leases |
| Install contributors                                          | Manifests only, during the install pass           | Manifest expansion (batch 3)                              |

Decisions:

- A `LeaseSet` collects the leases one operation holds; clones share the set, so the
  parallel retrieval tasks can add to it, and the last handle dropping releases
  everything. `RemoteSourceManager::materialize_into(source, &leases)` materializes
  and records the lease in one step.
- `get_generators` and `get_tools` return `(items, LeaseSet)`. Callers bind the set
  to a named variable (`_leases`, never `_`), which keeps it alive to the end of the
  operation. This is a convention: nothing stops `let (g, _) = ...`, so the guard
  test below exists.
- `ExpandedPacks` carries a `leases` field instead of `expand_packs` gaining a
  parameter, so its roughly fifteen callers are unchanged and a pack's leases live
  as long as the roots they protect. A caller whose own scope is longer absorbs them
  (`LeaseSet::absorb`).
- No plain `materialize` remains in a runtime path. A source-scanning test in
  `omni_api` fails if one returns or if a path stops leasing.

Not in batch 2: install contributors (batch 3), a store `VERSION` bump (D1, release
owner), reference-driven retention (D3).

Verification: a lease set protects every source until its last handle drops, including
across `absorb`, against a prune with real git checkouts; `expand_packs` leases a git
pack root and the lease survives moving to another set; the guard test. The pack and
guard tests each fail when the lease wiring is removed.

Limits: leases bind cooperating omni processes on filesystems with working locks. A
generator or tool run that starts a long-lived process outliving the operation is
not covered. Nothing here tests a prune racing a real generator run end to end; the
protection is established at the manager and pack level plus the structural guard.

## Batch 3: leases for install manifest readers

**Status:** merged ([#131](https://github.com/omni-oss/omni/pull/131)) under the
[approved plan](F08.5-install-contributor-plan.md). Medium / High: the scope is small, but prune
concurrency makes it High risk.

`ProjectionRemoteContributor` now uses `materialize_into` and owns a `LeaseSet`
throughout expansion. A local child inside a git checkout can be read after its
parent's classification returns, so releasing a lease at the end of `classify`
would be too early. Completion, expansion errors and cancellation release the set.

The contributor audit found no additional checkout readers to migrate:

- Pack expansion already leases every remote manifest root; `PackRemoteContributor`
  keeps its `ExpandedPacks` alive while collecting child refs.
- Flat generator/tool contribution (including a pack's flat child-source lists)
  materializes a source and copies its pin; it does not read checkout files. It
  deliberately retains plain `materialize`.

No trait signature, reference publication, cache key, storage format or retention
rule changes. Leases protect reads, not refs awaiting publication. Revert the
projection wiring to undo this batch; no data migration is needed.

Verification:

- Three real-git regressions pause a nested local projection manifest read while
  a separate manager prunes. The reader's checkout is skipped and an unrelated
  checkout is reclaimed. After success, an injected read error, or cancellation,
  the reader's checkout is reclaimable too. Waits are bounded; no timing sleeps.
- All three fail on the old unleased implementation, then pass with the fix.
- Remote-source and contributor suites pass (117 tests), including existing pack
  lease tests. Library clippy passes. Integration-target clippy remains blocked
  by the existing `eprintln!` skip notices in `tests/contributors.rs`; this change
  adds none.
- API/CLI/MCP test targets compile. Filesystem locking on non-Linux platforms is
  left to CI. Independent review is required before merge.

Store `VERSION` compatibility (D1), reference-driven retention (D3), and pending
cleanup (D7) are still separate decisions, not completed by this batch.
