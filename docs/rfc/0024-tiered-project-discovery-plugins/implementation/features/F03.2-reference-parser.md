# F03.2: Escape-aware task reference parser (part 1)

**Reader:** contributors wiring task references into configuration (the rest of F03.2),
root lowering (F03.3) and the CLI/MCP selectors (F04). **Status:** merged: part 1 (the parser,
[#116](https://github.com/omni-oss/omni/pull/116)) and part 2 (`dependencies`/`with`, [#117](https://github.com/omni-oss/omni/pull/117)). **Risk:** Medium: a new self-contained module that nothing calls yet, so
no behavior, schema or cache key changes. The grammar is the contract, so it is tested
exhaustively. Slice 2 of [F03](F03-scoped-task-references.md), against the inventory in
[F03.1](F03.1-identity-parser-audit.md) and RFC [§7.4](../../007.03-task-scoping-aliases-and-selectors.md#qualified-reference-syntax-and-escaping).

## What this part is

`omni_types::TaskReference`: one full-input, escape-aware parser (`parse`, `FromStr`) and one
canonical formatter (`format`, `Display`), plus per-surface kind validation. It lives in
`omni_types` because that is the lowest crate every consumer already depends on, so no
reverse dependency edge is introduced (the F03.1 audit's constraint).

Grammar: `["^"] [project "#"] [plugin "::"] task`. Only unescaped `#`, `::` and a leading
`^` are syntax; a single `:` is ordinary (`lint:fix`). `\\`, `\#`, `\:` and `\^` are the only
escapes. Any other escape, a dangling backslash, an empty component, a NUL, an extra
separator, or a `::` before the `#` (which would scope the project) is an error with a
byte position. Nothing is matched as a substring or silently truncated, which the old
unanchored regex could do.

`native::build` is plugin `native`, task `build`; `native\:\:build` is the unscoped task
literally named `native::build`; `build::debug`, `build\:\:debug` and `build#debug` are three
distinct identities, as the RFC requires.

`from_raw_components` builds a reference from structured data (a handwritten object or plugin
output) without unescaping or reparsing it, so `{ project: common, task: "native::build" }` is
the literal local name and never becomes plugin `native`.

`validate_for(surface)` applies the RFC's surface table after parsing: declaration keys and
`extends`/alias targets are same-project only (no `project#`, no `^`); dependencies and `with`
accept own, upstream and explicit-project; exact selectors reject `^` but keep `\^name` for a
task literally named `^name`. Errors name the surface and the reason.

## The injectivity decision

The RFC requires that escaping be injective. The formatter escapes `\` and `#` everywhere,
every colon that touches another colon, a plugin's **trailing** colon, and a `^` that starts
the output. The trailing-colon rule is the non-obvious one: plugin `p:` with task `x` would
otherwise format as `p:::x`, which parses as plugin `p`, task `:x`. A task that _starts_ with a
colon after `::` needs no escape, because the parser takes the first two colons as the
separator; `a:::b` parses as plugin `a`, task `:b`, and that is documented behavior. Only a
`^` that begins the whole output is escaped, since that is the only place it is syntax.

## Verification

- 29 tests in `omni_types`, 19 of them new. Beyond the RFC's worked examples, error cases and
  surface restrictions, the injectivity claim is checked exhaustively, not by example:
  every project, plugin and task of up to two characters over `a : # \ ^` in every
  combination of presence and `^` (29,760 references) round-trips; longer components
  (up to four characters) round-trip next to each other across the `::` separator; every
  parseable string up to six characters over the same alphabet reformats to a canonical
  form that parses back to the same reference and is a fixed point; and no two distinct
  references share text.
- Each escaping rule is load-bearing: removing the plugin trailing-colon rule, the
  touching-colon rule, the leading-caret rule or `#` escaping each fails several tests, most
  of them the exhaustive ones.
- An unreachable error variant I had written (a `#` after the plugin) was removed because
  the scoped-project check always fires first.
- Library and test-target clippy and formatting pass.

## Part 2: wiring into `dependencies` and `with`

`TaskDependencyConfiguration` (the type behind task `dependencies` and `with`) now parses
strings with `TaskReference::parse` plus `validate_for(DependencyOrWith)`, and formats with
`TaskReference::format`, so serialization round-trips. The enum variants are unchanged
(`Own`, `ExplicitProject`, `Upstream`), so `omni_core::TaskDependency` and the graph are
untouched. The regex and its `omni_configurations` copy are removed.

It also accepts a strict object `{ project?, task }`. Values are literal: `task:
"native::build"` is the local name, never plugin `native`. Unknown and duplicate fields, a
missing `task`, and empty or NUL values are errors. The JSON schema is now `anyOf` string or
that object.

Behavior changes (pre-v1 corrections, call these out in release notes):

- The old unanchored regex matched a substring, so `"a b"` silently became `a`. Strings are
  now parsed whole: `a b` is the task `a b`, and input with extra separators (`a#b#c`),
  an empty string, a bad escape or `^project#task` is an error.
- A backslash is now an escape (`\\`, `\#`, `\:`, `\^`). A task name that contained a literal
  backslash must write `\\`.
- A `::` now means a plugin scope. No plugin variant exists yet, so a plugin-scoped
  dependency is rejected with a message that points at the escape (`native\:\:build`) for a
  literal task name. A task literally named with `::` previously parsed; it needs the
  escape or the object form.
- A hand-built invalid variant (empty task) cannot be formatted: `Display` prints a
  placeholder and `Serialize` errors instead of panicking.

Checked: the repository's own workspace still loads and runs under the new parser;
`omni_configurations`, core, context, task-context, CLI, execution-plan, task-executor, MCP
and API suites pass.

## Not done in F03.2 (part 3 and after)

- **Plugin and `project_root` components** on the dependency type (`{ plugin? }`, mixed
  `project`/`project_root` rejection). Adding variants ripples into `omni_core::TaskDependency`
  and the graph, which is F03.3's territory.
- The unused `omni_cli_core` copy of `TASK_DEPENDENCY_REGEX` is left; it has no consumer.
- Other string surfaces that still use their own parsing (declaration keys, `extends`).
- The cache CLI's `split('#')` grouping (F03.1) and the exact-selector CLI/MCP plumbing (F04).
- `project_root` (a typed `ProjectRootId`, lowered after composition) and the legacy
  unescaped-`::` declaration-key migration. Both need things that do not exist yet (the
  composed project catalog and an activation registry), so the parser deliberately does not
  guess.
- Dictionary-operator framing for tasks literally named `merge`/`replace`, which the RFC
  separates from name escaping.
