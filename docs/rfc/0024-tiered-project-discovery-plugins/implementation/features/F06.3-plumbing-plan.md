## Assessment

**Kind: Large. Risk: High** (`AGENTS.md`: cache keys are always High).

- Every task key changes once (a wrong key is a wrong hit or a silent miss), and five
  independent constructors must produce the same value for the same task.
- The largest unknown is whether one builder can feed all of them from the data each
  site already has (finalized node, `CacheInfo`, meta). Section
  [Building the config](#what-each-site-gets-and-where-the-config-is-built) resolves it on
  paper; the first implementation slice proves it with the failing tests listed below.
- Undo: revert the cutover as one commit and ship the previous binary. See
  [Rollback](#mixed-versions-and-rollback).
- Out of scope: any storage, remote, metadata or path-layout change; platform, loaded
  env values and `.env` file contents, and nondeterministic expressions (see decisions);
  `omni_migration` (RFC 0032). No automatic migration, legacy promotion, dual read or
  old-key probe. (Invocation `--arg` overrides are now **in** scope: decision Q1.)

## Maintainer decisions (approved 2026-11-27)

1. **No key auto-migration, no legacy promotion.** A key-affecting change bumps the key
   cache key version and is a cold start. Old entries become unreachable, old and new
   binaries coexist, rollback is by binary, stale pruning cleans old entries. No
   rewrite, no special GC, no old-key probe, no dual read. A fallback read is safe only
   for a pure re-encoding of identical inputs, never for F06.3: the digest is a new
   input that old entries never recorded, so promoting an old entry could return a wrong
   hit. RFC 0032 says the same ([F06.3 legacy promotion](../../../0032-pre-v1-migration-infrastructure.md)),
   and **F06.3 does not depend on `omni_migration`** (it is unwired; the key construction is
   not a store format).
2. **F06.3 is the single bundled key-affecting change of this release epoch.** See
   [The epoch audit](#the-epoch-audit-and-what-the-second-cold-start-is).
3. **Platform stays out of the key** (users can configure it explicitly through `env` or
   `meta`). The workspace and project hashes include the real digest (decision D2). The
   release note ships with the cold start. The merged invocation `--arg` overrides are
   **not** platform or display data: they are key inputs (decision Q1).
4. **Key-change policy**, in [`docs/patterns/cache-keys.md`](../../../../patterns/cache-keys.md)
   (indexed from `docs/patterns/README.md`), written in this phase because it applies
   to the identity leaf already.

5. **D1 DECIDED (2026-11-27): a `CACHE_KEY_VERSION` leaf covering the whole key, in addition to
   the effective leaf's own `0x01`.** Reason: the key has no cache key version
   today, so a future change to any input (not only the effective task) would have no
   single tag to bump. The cold start is already happening, so adding the leaf now is
   free; it is what makes the policy's rule 1 enforceable.
6. **D2 DECIDED: the workspace hash folds each project's real task digests** (sorted,
   domain-separated; 0-task projects handled). The constant-digest alternative is
   **removed** because it violates approved decision 3 (workspace and project hashes
   include the digest) and RFC 0032:31 (a hash that claims coverage it does not have).
   The task-graph cost in `hash workspace` is measured in the benchmark gate.
7. **Q1 DECIDED: the merged `--arg` invocation overrides enter the key now**, through
   `TaskExecutionInfo.args` (not `EffectiveTaskConfig.args`, which stays "configured
   args" as F06.2 defines it). Reason: it fixes an existing wrong hit (see Q1 below)
   and the cold start is free. With no `--arg` the key does not change because of this
   part, and `hash project` parity holds.
8. **Q2 DECIDED: carry `with` siblings** on `TaskExecutionNode` (`siblings:
   Vec<TaskKey>`, no serde attribute: the node serializes through
   `#[serde(into = "TaskExecutionNodeReport")]`, and `From<TaskExecutionNode> for
   TaskExecutionNodeReport` ignores `siblings`, which is what keeps report formats
   unchanged), and fill
   `EffectiveTaskConfig.siblings`.
9. **Q3 DECIDED: key the configured `env.vars` definitions** of workspace, project and
   task as **three unmerged layers** (raw and pre-expansion; fix round 4: a merge loses
   a project value that expansion can still read, see the Build result) in
   `EffectiveTaskConfig.env_workspace`, `env_project` and `env_task`. `.env` file contents and the process environment are
   **not** keyed; users opt in through `cache.key.env` / `cache.key.files`. A known
   limit, written in the release note.
10. **Q4 DECIDED: `enabled` is keyed by its definition text** (Bool vs Expression), not
    by what an expression renders to.

## Exact semantics

### What the digest covers

`EffectiveTaskConfig::digest()` (F06.2, `effective-task-config/v1`) over the finalized
task: command and retry command (with interpretation mode), `enabled` (boolean or
expression), `interactive`, `persistent`, the resolved retry policy, configured `args`,
the configured `env.vars` definitions as three unmerged layers (workspace, project,
task; raw, pre-expansion; Q3), merged project and task `meta`,
resolved dependencies and siblings (Q2: `TaskExecutionNode.siblings` is populated where
`EdgeType::Sibling` edges are added in `omni_core` `task_execution_graph.rs`), input rules (`key_defaults`, includes, excludes, env keys), output rules and
`capture_logs`. `args` is the **configured** set (`CacheInfo.args`, F06.2); the merged invocation
overrides reach the key through `TaskExecutionInfo.args` instead (Q1), so the effective
digest, and `hash project`, do not move with `--arg`. Presentation (description, provenance, notices, redaction, display
policy, `cache_enabled_source`) and `cache.enabled` have no field and cannot reach it.

**Mandatory in every key**, including `cache.key.defaults: false`: the contribution is
not a file input and is not gated by `key_defaults`, the collection flags or the input
walk. Tests: `defaults_off_still_invalidates_on_a_definition_change` (omni_context) and
the e2e spec, both of which turn defaults off.

### Placement: its own versioned leaf, not a collector domain version

Decision: **a new named, versioned leaf, inserted last, after the identity leaf, before
`tree.commit()`**.

```
leaf = BLAKE3( b"omni.effective-task\0" || 0x01 || effective_digest[32 bytes] )
```

Why a leaf and not a collector domain version:

- The collector has no cache key version today. The only versioned input is the
  identity leaf (`omni.task-id\0\x01`). F06.3 adds a cache key version leaf (D1, below) and
  the effective leaf keeps its own `0x01`: two tags, two owners.
- Appending after the identity leaf leaves every earlier leaf in its tree position; the
  proof tests build the expected key from the existing test-only oracle plus this one
  leaf, so a mistake in position is caught.
- The `effective-task-config/v1` tag already sits inside the 32 bytes. The leaf's `0x01`
  versions the framing (domain, position, width). Two tags, two owners: an encoding
  change bumps `effective_task::VERSION`; a framing or placement change bumps the leaf
  byte. Either one is a cold start and follows the policy.
- It is a single 32-byte leaf like the identity leaf, so tree size grows by one leaf.

A task with no execution info (no `CacheInfo`, for example a commandless aggregate or
an `omni exec` node) never reaches the collector, so no digest is needed for it.

**Cache key version leaf (D1).** Inserted after the identity leaf, before the effective leaf:

```
leaf = BLAKE3( b"omni.cache-key\0" || u32_le(CACHE_KEY_VERSION) )   // CACHE_KEY_VERSION = 1
```

`CACHE_KEY_VERSION` is one constant in `omni_collector`. Any change to **any** key input
or to the key construction (a leaf, an order, a collection rule, the contribution of
`TaskExecutionInfo`) bumps it, in addition to the leaf you touch; that is the enforceable
form of policy rule 1 ([cache-keys.md](../../../../patterns/cache-keys.md)). The final
order is: tree of input files, dependency digests, env, args, output globs, command,
identity leaf, **cache key version leaf, effective leaf**.

### Field order inside the digest

Unchanged from F06.2 (the contract, with golden vectors): version, then fields
1 to 13 in the order of `EffectiveTaskConfig::encode`. F06.3 adds no field. Adding or
changing one needs a new `VERSION` and is a key change under the policy.

### Final key oracle (test oracle, until the code exists)

`collector.rs::tests::reference_digest` (test-only copy of `get_digest`) takes the trailing
leaves, and the oracles `cache_key_version_leaf_v1` and `effective_leaf_v1` build them. The
proof test `the_final_key_carries_the_effective_task_leaf` builds the expected key from
both, and `the_final_key_golden_vector_for_the_ordinary_task` pins the result for the
ordinary fixture with a default config:
`e5e46763eebbd009eba7d973a96e6f3296a6b52bfad1e45f83f88ceef27168cd` (current key:
`baccd2c4...e174`). D1 recomputed it by changing only the oracle (the earlier
effective-leaf-only value was `af976dd4...e1d1`).

## What each site gets, and where the config is built

All sites must read one value computed by one builder. Design:

- `omni_task_context::effective_task::build(node, cache_info, meta) -> EffectiveTaskConfig`
  (new, pure; `omni_task_context` gains an `omni_collector` dependency, which has no
  cycle: the collector depends on neither). It reads only the finalized
  `TaskExecutionNode` (command, retry command, enabled, interactive, persistent, retry,
  dependencies, siblings), the **unexpanded** `CacheInfo`, and the task meta with the
  project meta fallback the provider already applies. It formats dependencies and
  siblings with the injective `TaskKey::label()` ([task-identity.md](../../../../patterns/task-identity.md)),
  **never** a raw `format!("{project}#{task}")`, so `a#b`/`c` and `a`/`b#c` stay apart.
- `CacheInfo` gains the configured env definitions as `EnvLayers` (raw, pre-expansion,
  unmerged: workspace, project and task `env.vars`; the runtime order is project, then
  workspace over it, then task over both (`project_extras`,
  `project_data_extractor.rs` ~241-264 and `loaded_context.rs` ~244-269; see the
  precedence table below), filled by
  `ProjectDataExtractor::extract_all`, so the
  `omni_task_context::Context` trait and its three implementations
  (`LoadedContext` wrapper, `hybrid.rs` `ContextWrapper`, test contexts) do not change.
  `#[serde(default)]` keeps older serialized `CacheInfo` readable.
- `DefaultTaskContextProvider::get_task_context` builds the config once per task and
  stores `effective_digest` on `TaskContext`. `expand_cache_paths` clones the context
  and keeps the field: the digest is of the **unexpanded** rules. Equal digests do
  **not** mean equal expansions: the template context also holds the loaded env values
  (`.env` files, process env) and the `--arg` overrides, which are not in the digest.
  That is harmless only because the collector hashes the **expanded** input file set
  (the file contents it walks) and the **expanded** output globs
  (`collector.rs` ~290-324), so a different expansion shows up as a different key; and
  the merged args are now a key input themselves (Q1, below). Platform stays excluded
  (decision 3).
- Q1: `TaskContext` gains the merged args (configured overlaid with the invocation
  overrides, computed once in `get_task_context` with the same merge
  `create_template_context` uses, `default_provider.rs` ~104-114, so the template and
  the key cannot diverge); `execution_info` sets `TaskExecutionInfo.args` from it.
  `ProjectHasher::hash` passes `CacheInfo.args` (no invocation), so with no `--arg` all
  sites agree.
- `TaskExecutionNode` gets `siblings: Vec<TaskKey>` (Q2), filled from the **configured** `task.siblings` where `EdgeType::Sibling` edges are
  added (`task_execution_graph.rs` ~384) and in the `--ignore-dependencies` node builder
  (`execution_plan_provider.rs` ~240). The report wire format stays unchanged because
  `From<TaskExecutionNode> for TaskExecutionNodeReport` ignores `siblings`; a serde
  attribute on the field would do nothing (`#[serde(into = ...)]`). The derived
  `PartialEq`/`Eq`/`PartialOrd`/`Ord` on the node now include `siblings`. Checked by grep:
  no hash or ordered set/map keys nodes; plans are sorted by `key` (`task_execution_graph.rs`
  ~1127) and compared as strings; the only consumer is the `omni_core` test
  `test_batched_execution_plan_must_not_include_persistent_tasks_if_not_matching_filter`
  (~1704), which sorts and compares expected nodes with derived `Ord`/`Eq`, so its
  expected nodes with siblings (`sibling-1`) must carry them too (keys are unique, so
  the order is unchanged). Nothing else depends on node equality.
- **Selection independence (decided).** `siblings` holds the configured siblings even
  when a sibling is filtered out of the selected graph, so the key does not depend on
  which tasks were selected (parity with `ProjectHasher::hash`, dry run, stale prune).
  Verified: `from_project_graph` first adds every node of every project, then every
  `Dependency` and `Sibling` edge from config (~340-390); no filter runs while building.
  Filters (`get_batched_execution_plan_impl`) only choose roots on that complete graph
  and clone nodes from it, so the sibling set is always the configured one. Two
  places build nodes outside the graph and must fill the same set: the
  `--ignore-dependencies` path (`execution_plan_provider.rs` ~240, projects filtered by
  `-p`, dependencies and siblings passed as `vec![]` today) and the synthetic `exec`
  nodes (no configured siblings: empty is correct). Test expectation: for a task whose
  sibling is excluded by `-p`/task filters or `--ignore-dependencies`, the key equals
  the key of the full run and of `hash project`.
- `TaskExecutionInfo` gets a non-optional `effective_digest: DefaultHash`;
  `ProjectTaskInfo` gets the same. Non-optional means a new constructor cannot omit it:
  the compiler enforces the inventory below.

## Cache semantics, remote and CI

- **Local:** every key changes once. First run misses and fills; the second hits. Old
  entries are unreachable (never matched), not converted. `omni cache prune --stale`
  removes them (the observing binary computes new keys, so old entries are stale).
- **Remote:** a remote cache uses the same digest as its address (`get_many` and
  `cache_many` GET and PUT it; the server stores under the scoped artifact key and never
  recomputes it). So the cold start is also remote. Expected CI behavior at upgrade: the
  first CI run on a new binary misses everything and repopulates; later runs hit. No
  server, client, signature, partition or archive change; old artifacts stay on the
  server until its own retention removes them. Old and new runners can share one server
  without poisoning each other because their digests differ.
- **Not changed:** `cache.meta.bin` and every metadata or layout format (the digest is not
  persisted), output directories (they derive from the digest), the last-used db, stats.
- **Stale prune and `--arg` (Q1 consequence).** Prune builds its fresh keys from contexts
  that return no override args (`omni_api/src/operations/cache.rs` ~535,
  `get_task_override_args` returns `None`), so it computes the key of a run **without**
  `--arg`. An entry written by `omni run t --arg k=v` has a different key, so
  `cache prune --stale` judges it stale and may remove it, though a rerun with the same
  `--arg` would still hit it. What prune should do: nothing special. Removing an entry
  only loses a future hit and never causes a wrong one, and telling the entries apart
  would need the invocation recorded in the entry metadata, which is out of scope (no
  metadata change). So: say it in the release note, recommend `--dry-run` first, and
  keep the contexts as they are. If it proves painful, a follow-up can record an
  "invocation args used" marker in the entry (its own key change, so its own epoch).
- **Hash APIs:** `omni hash project` and `omni hash workspace` change value once, and
  now move with an effective-only change. Anything pinning them updates.

## Mixed versions and rollback

- Three cache key versions may coexist: `v0.21.0` (legacy leaf), `main` between #171 and F06.3
  (identity v1), and F06.3. None reads another's entries; each fills its own. A new
  binary against an old-only local or remote store misses, fills, then hits. The old
  binary against a store written by the new one misses unless it has its own entries.
- Stale classification compares the **observing binary's** digests, not the tool
  versions in other worktrees: a new binary classifies old entries stale and an old
  binary classifies new entries stale. Defer `omni cache prune --stale` until the fleet
  (worktrees, CI) is aligned if the other version's warm cache matters.
- **Rollback:** install the previous binary (revert the cutover as one unit). Its own
  entries hit again unless pruned; the new entries are left in place and are not
  reused. Do not remove them as part of the rollback. Entries already pruned cannot be
  recovered. Project and workspace hashes return to the old values. **Caveat:** the
  previous binary does not see effective-only edits (inherited settings, retry,
  `enabled`, env definitions, siblings, `--arg`), so after a rollback its entries hit
  again with the **stale-hit** behavior this change fixes. Rolling back restores the
  bug along with the cache.
- **Rehearsal** (also in the policy doc): build the previous binary from the base SHA in
  a temporary worktree, set `OMNI_TEST_BASELINE_BIN`, and run
  `tests/omni-tests/src/cache-cross-version.e2e.spec.ts`. That spec currently asserts
  that the two binaries share entries; **it will fail by design after the cutover**.
  An unconditional inversion would be permanent and would break the next compatible
  release, so **phase 2 parameterizes it**: `OMNI_TEST_EXPECT_COLD_START=1` (set for
  cold-start epochs, i.e. when the baseline predates the last key change) asserts each
  side misses the other's entry and neither promotes (and no old-key request on a fake
  remote); the default asserts sharing. In both modes **each side also asserts it hits
  its OWN entry**. The spec's comment still says "the pre-R08 build"; phase 2 rewrites
  it to name the base and the mode. This is plan/phase 2 text only: the spec is **not
  changed in phase 1** (it is skipped without `OMNI_TEST_BASELINE_BIN`, and flipping it
  now would make it fail against the current binary). Rehearse both directions against
  one disposable store.

## Compatibility and release note

A new page, `apps/site/content/docs/guides/effective-task-cache-keys.mdx`, in the style

- **Lead with the breaking cold-start summary**, in the style of
  `task-identity-and-cache-keys.mdx`: every task misses once, local and remote, then
  hits again.
- **What changes:** the key follows the effective task: an inherited setting that changed,
  command context a command consumes, retry, `enabled`, dependencies, siblings,
  `env.vars` definitions (workspace, project, task, each keyed separately) and output rules now invalidate;
  **the `--arg` values of the run are part of the key** (a different `--arg` is a miss;
  this fixes a stale replay); presentation does not. This holds with
  `cache.key.defaults: false`.
- **Second cold start, for people on `main`:** if you ran a build of `main` between
  #171 (identity leaf, 2026-11-25) and this change, you get a second cold start, and your
  identity-only entries are now stale; `omni cache prune --stale` clears them. People
  upgrading from `v0.21.0` see only one.
- **Stale prune and `--arg`:** `cache prune --stale` computes keys without `--arg`, so it
  may remove entries written by runs that used `--arg`; that costs a hit, never a wrong
  one. Use `--dry-run` first.
- **Cold start:** every task misses once, local and remote; CI repopulates on the first
  run. Old entries are not matched or converted; `omni cache prune --stale` removes them
  once every checkout and CI job runs the new version.
- **What does not change:** storage, remote formats and server; platform is not in the
  key (set it explicitly through `env`/`meta` if a task depends on it).
- **How to see it:** run twice (miss, hit), edit an inherited setting (miss);
  `omni hash project` shows a new value; `omni cache prune --stale --dry-run` lists the
  old entries.
- **Hashes change once:** `hash project`, `hash workspace`, `--result` `hash`.
- **Mixed versions and rollback:** as above, linking the identity note, **plus the
  rollback caveat**: rolling back restores the stale hits on effective-only edits (the
  previous binary does not see them), so roll back only for a real defect.
- **Rust API changes (pre-v1)**, for crates that embed these types:
  `TaskExecutionInfo::new` gains a positional parameter (and the merged args and the
  digest are required); `effective_digest` is non-optional on `ProjectTaskInfo`,
  `TaskExecutionInfo` and `TaskContext`; `CacheInfo` has a new `env` field
  (`EnvLayers`, `serde(default)`); `TaskExecutionNode` has a new `siblings` field (derived equality and
  ordering include it; report formats unchanged because the report conversion ignores it); `omni_task_context` gains the `omni_collector` dependency.
- **Known limits:** the **loaded** environment (`.env` file contents and the process
  environment) is not in the key: the **definitions** of `env.vars` are, but a task that
  reads a value from a `.env` file or the process must list it under `cache.key.env`
  or `cache.key.files` to opt in. `enabled` expressions are keyed by their text, not by
  what they render to (Q4). Nondeterministic expressions (`now`, `get_random`) are not
  in the key.

## Decisions and former open questions (all DECIDED 2026-11-27)

- **D1 DECIDED: cache key version.** A `CACHE_KEY_VERSION` leaf covering the whole key
  (`BLAKE3(b"omni.cache-key\0" || u32_le(version))`) **in addition to** the effective
  leaf's own `0x01`. Reason: it makes future whole-key bumps possible with one named
  constant, and is what lets the policy say "any change to any key input or the key construction bumps
  `CACHE_KEY_VERSION`" enforceably. It costs nothing now because the cold start is
  already happening. Golden vectors were recomputed by changing only the oracle.
- **D2 DECIDED: workspace hash.** Fold each project's real task digests (sorted by task
  name, each as a domain-separated leaf `omni.workspace-task\0 || project || task ||
  digest`, so a rename or reorder is not confused with a change). A project with no tasks
  folds an empty set under its own domain tag, so it is not skipped. A task graph that
  cannot be built (cycle, invalid) fails `hash workspace` with the graph error rather than
  hashing a partial set. The constant-digest alternative is **removed**: it breaks
  approved decision 3 and RFC 0032:31 (a hash that claims coverage it does not have).
  The cost is a task graph build; it is measured in the benchmark gate (hash workspace,
  120 projects).
- **Q1 DECIDED: invocation arguments are keyed now.** Today `omni run t --arg k=v`
  merges the override into the template context (`batch_executor.rs` ~714-717,
  `default_provider.rs` ~104-114) while the key sees only the configured
  `CacheInfo.args` (`omni_cache` `exts.rs:27`, `cache_manager.rs:210`), so `--arg k=v1`
  then `--arg k=v2` replays the `v1` result: an **existing wrong-hit bug**, not caused
  by this plan. The merged set goes in `TaskExecutionInfo.args` and **not** in
  `EffectiveTaskConfig.args`, which stays "configured args" (F06.2) so the digest and
  `hash project` are invocation-free. With no `--arg` the key is unchanged by this part
  and `hash project` parity holds. Consequence for stale prune: see the cache semantics
  section (entries from `--arg` runs are judged stale by prune; accepted, documented).
- **Q2 DECIDED: carry `with` siblings** on `TaskExecutionNode` (see above).
- **Q3 DECIDED: key the configured `env.vars`** of workspace, project and task;
  not `.env` contents or the process environment (opt in via `cache.key.env` and
  `cache.key.files`); documented as a known limit. **Fix round 4:** the three layers are
  recorded unmerged (round 3's "runtime winner" merge dropped a shadowed project value
  that expansion reads); see the Build result.
- **Q4 DECIDED: `enabled` is keyed by its definition text** (Bool vs Expression).

### Env precedence and the unmerged record (fix rounds 3 and 4)

The task environment is built by `project_data_extractor.rs` (`project_extras`, about
lines 241-255; expansion in `crates/env/src/expand/mod.rs` about 522-535) and read through
`LoadedContext::get_task_env_vars`, the one source for the executor, dry run, `hash
project` and the cache paths. The order is: the project's raw definitions are expanded
**in order, starting from the workspace's raw definitions**, each project key is added as
it is expanded, and only afterwards do the expanded workspace values overwrite the
colliding keys; the task's `env.vars` apply last.

| Case (key `X` unless noted)                              | Task sees     | Winner                          |
| -------------------------------------------------------- | ------------- | ------------------------------- |
| workspace `W`, project `P` (project has overrides)       | `W`           | workspace                       |
| workspace `W`, project defines only `Y`                  | `W`           | workspace                       |
| project `P` only                                         | `P`           | project                         |
| workspace `W` only, project has **no** `env.vars`        | unset         | none                            |
| workspace `W`, project `P`, task `T`                     | `T`           | task                            |
| workspace `X: w`, project `X: p1`, `Y: ${X}` (expansion) | `X=w`, `Y=p1` | `Y` reads the **project's** `X` |

Round 3 recorded one merged map (project, workspace over it, task over both). That map
drops the shadowed project value, but `Y: ${X}` reads it: changing `p1` to `p2`
changed the task's `Y` and left the key unchanged (a stale hit; reproduced on a built
binary with `printenv X Y`: the `p1` run executed, the `p2` run was a cache hit, `-f`
showed `w p2`). It was keyed correctly before round 3, so round 3 regressed it.

**Decision (round 4): record the layers separately.** The effective digest carries the
workspace, project (composed through `extends`) and task `env.vars` as three canonical
(key-sorted) maps with fixed field ids (`ENV_WORKSPACE` 8, `ENV_PROJECT` 14, `ENV_TASK`
15; the stream order is 8, 14, 15 in the old env position). `CacheInfo.env` is an
`EnvLayers { workspace, project, task }`. Any definition the task can observe through
expansion changes the key. This over-invalidates when only a shadowed project value
the task does not read changes (the e2e test `re-runs a task when a shadowed project
value changed even if the task does not read it` pins this); that is the safe direction
and avoids a second cold start if the record is ever refined. Runtime behavior is
unchanged. The earlier tests that asserted a shadowed project value keeps the key
(`a_shadowed_project_value_change_keeps_the_final_key` and the e2e guard) were flipped.

**Version byte:** `effective-task-config/v1` is unchanged. `git tag --contains` the
commit that added `crates/omni_collector/src/effective_task.rs` lists no release tag
(the newest tags, `v0.22.0` and `omni-v0.21.0`, are the same commit `6eac1c99` and predate it; the F06.2 encoding has never shipped), so the F06.2 golden
vectors were re-pinned under the same version instead of bumping it.

### Known pre-existing runtime quirk (follow-up issue candidate, not fixed here)

When a project defines no `env.vars`, the workspace `env.vars` are not delivered to its
tasks at all. The guard is `if !overrides.as_map().is_empty()` in
`crates/omni_context/src/project_data_extractor.rs:242`: the workspace expansion and
`project_extras.extend(ws_vars)` live inside that block. Reproduction idea: workspace
`env.vars: {X: w}`, a project with no `env` and a task `node -e "console.log(process.env.X)"`:
it prints `undefined`; adding any unrelated `env.vars` entry to the project makes it print
`w`. The key records the workspace layer regardless, so today this only over-invalidates.

**Fixing the quirk is NOT cache-neutral.** The key already contains the workspace layer,
so a binary that delivers `X=w` to such a project's tasks computes the same key as a binary
that does not. After the fix it would hit entries recorded while `X` was unset, and those
hold outputs from runs without `X`: a replay of stale output. The environment a task
receives is a key input, so by the cache-key policy the fix must bump `CACHE_KEY_VERSION`
(one more cold start) and carry a release note. Two ways to handle it, to be chosen by the
maintainer: (1) fix the quirk in the same release epoch, before F06.3 ships, so there is no
extra cold start (the version stays at 1 and nothing stale exists yet); or (2) fix it later
with a `CACHE_KEY_VERSION` bump. It is not fixed in this change.

### Stage-1 decisions recorded

- (a) **Absolute unrooted default config-file rules are left out of the digest.** The
  builder drops an absolute unrooted rule (the config-file ids that
  `cache.key.defaults` adds), since keeping it would tie the digest to the checkout
  location, and treats a relative unrooted rule as project-rooted. The collector still
  hashes those files' contents under their workspace-relative names. **Status:
  confirmed by independent review pending.** Specific check item for the reviewer: that
  a change to a default config file still invalidates (through the collector's file
  hashing) and that two checkouts at different paths share one digest.
- (b) **Graph-built nodes had `task_retry_exec = None`: fixed on `origin/main` by #189
  (`756fb291`, B05), and this branch is rebased onto it.** The node now takes
  `task.1.retry_exec.clone()`. The rebase had no textual conflict: #189 edits the
  `retry_exec` argument of the `TaskExecutionNode::new` call and this branch adds
  `with_siblings` after it. After the rebase the effective-task digest, the executor key,
  the dry-run key, `ProjectHasher::hash` (so `hash project`) and the workspace hasher
  all see the same retry command; `key_parity.rs`
  (`a_task_with_retry_exec_has_the_same_key_everywhere`) proves it for a real run, a dry
  run and `get_project_hash`, and that `retry_exec` changes the key. #189 on its own
  changes the executor key of tasks with `retry_exec` (see the epoch audit), so it is one
  more key change in the same release epoch as F06.3, not an extra cold start.
- (c) **`--retry` overrides are not in the key** (matches the plan), and an invalid retry
  policy digests as the default policy, because the run fails first.
