# F08.1: Lease, GC and reference protocol

**Type:** design doc (slice 1 of [F08](F08-source-acquisition-leases.md)) · **Risk:** Medium ·
**Status:** proposal; nothing here is implemented · **Baseline:** `de561116b2a04589d2179a087b9e4d2616c07b33`

This document fixes the protocol that slices F08.2-F08.5 implement. Statements marked
**Observed** describe the code at the baseline. Statements marked **Proposed** are design,
not behavior. Where the RFC and the code disagree, the code is the baseline and the
difference is listed in [Drift from the RFC](#drift-from-the-rfc).

Sources: [§15.2](../../015.00-remote-source-integration.md#152-contributor-install-selection-and-references),
[§17.6](../../017.00-review-findings-and-prerequisites.md#176-artifact-digests-versus-mutable-artifact-loading),
[§18.3 source manager row](../../018.00-readiness-and-open-decisions.md#183-implementation-gates-grounded-in-current-code).

## Scope

In: retention of checkouts in the shared store, and the atomicity of per-subsystem
reference sets. Out: verified module ownership and byte capture
([§17.6](../../017.00-review-findings-and-prerequisites.md#176-artifact-digests-versus-mutable-artifact-loading),
F10), the plugin contributor, and any change to what is hashed or executed. A lease is a
retention mechanism only; it is never activation or permission.

## Current behavior (observed)

Symbols are in [`manager/default_impl.rs`](../../../../../crates/omni_remote_source/src/manager/default_impl.rs)
unless noted.

The store root is not under the workspace; the lockfile and `refs/` are. So a lock inside
the store coordinates **all workspaces**, while a lock beside `lock.json` coordinates one.

### Lock primitive

`omni_utils::lock::LockGuard` ([`lock.rs`](../../../../../crates/omni_utils/src/lock.rs)) opens
(creating) a file and calls `File::lock` / `File::lock_shared` on a blocking thread. Drop
unlocks. It has no non-blocking variant. Its doc states the OS releases the lock on
process exit (`flock` on Unix, `LockFileEx` on Windows).

manager owns all file I/O ([`contributor.rs`](../../../../../crates/omni_remote_source/src/contributor.rs)).

### Gaps this design closes

1. No active-use protection: `prune_store` can delete a tree a process is reading.
2. The publish → use window is unprotected, and the fast path takes no lock at all.
3. `record_refs` is replace-only and lock-free. Today's callers write complete sets (projection
   guards targeted runs with `full_sync`), but a future partial caller, such as lazy plugin
   loading, would drop other references, so the API must make the intent explicit.
4. `run_contributors` can leave a mix of replaced and old sets after a failure.

### Drift from the RFC

[§15.2](../../015.00-remote-source-integration.md#152-contributor-install-selection-and-references)
and the F08 text say "union-reference GC" and that `retain` locks only reconciliation. At
the baseline there is no `retain` symbol (the symbol is `reconcile_pins`), and no
reference-driven store GC exists: references only decide which **lockfile pins** survive.
Store deletion is the explicit `prune_store`. This design therefore treats **`prune_store`
as the GC** that must honor leases, and does not introduce reference-driven deletion
(see D3). The RFC wording should be corrected when F08.3 lands; this task does not edit it.

## Lock hierarchy and ordering (proposed)

Acquire in this order and never in reverse. Release in any order.

| Level | Lock                                                    | Scope               | Mode                                                        |
| ----- | ------------------------------------------------------- | ------------------- | ----------------------------------------------------------- |
| 1     | Remote lock `locks/<kind>/<slug>.lock` (observed)       | Store, per remote   | Exclusive. Serializes resolve/publish/delete of one remote. |
| 2     | Lease lock `leases/<kind>/<slug>/<pin>.lease` (**new**) | Store, per checkout | Shared by readers; GC takes exclusive, **non-blocking**.    |
| 3     | Advisory lock `lock.json.lock` (observed)               | Workspace           | Exclusive. Now also guards `refs/` read-modify-write.       |

Rules:

- Levels 1 and 2 are per-store and cross-workspace; level 3 is per-workspace and must
  never be held while waiting on level 1 or 2. Reference and pin updates take only
  level 3.
- Lease acquisition by a reader blocks (shared); GC never blocks on a lease. A blocked GC
  would be a stall bounded by the lifetime of a session.
- Reusing the advisory lock for `refs/` adds no new lock and no new level. It already
  covers the reconcile read of `refs/`, so reads and writes of `refs/` become mutually
  exclusive.
- A process holding a lease must not take the remote lock for the same remote while a GC
  waits on it in a way that blocks the lease holder; this cannot deadlock because GC only
  `try`-locks leases while holding the remote lock.

## Lease primitive

### Options

| Option                                                | Crash-safe | No stale marker retains content               | Cross-workspace | Verdict                                                                                              |
| ----------------------------------------------------- | ---------- | --------------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------- |
| **A. Per-checkout shared OS lock held by the reader** | Yes        | Yes (file is empty; only lock state protects) | Yes (in store)  | **Recommended.**                                                                                     |
| B. One store-wide shared lock per session             | Yes        | Yes                                           | Yes             | Rejected: blocks all GC for the life of any session, contradicting §15.2 ("not a store-wide lock").  |
| C. PID/heartbeat marker files                         | No         | No                                            | Yes             | Rejected: needs liveness checks; PID reuse; stale files retain content, forbidden by §15.2.          |
| D. Refcount file or directory of hard links           | No         | No                                            | Yes             | Rejected: a crash leaves counts or links that retain content.                                        |
| E. Reuse the remote lock (shared for readers)         | Yes        | Yes                                           | Yes             | Rejected: the remote lock covers every pin of a remote and is taken exclusively for network resolve. |

### Recommended: A (process-held OS lock)

- A **lease** is a shared lock on a per-checkout lease file, held through an owned guard
  (`SourceLease`) for as long as descriptor/module loading or a live runtime may read the
  tree. Dropping the guard, or process exit by any means including `kill -9`, releases it.
  This is the property `LockGuard` already documents.
- The file is empty and carries no state. An orphaned file retains nothing: protection
  exists only while a process holds the lock. This satisfies "stale marker files alone
  must not retain artifacts".
- Scope is the immutable checkout `(kind, slug, pin)`, the same identity as `tree_dir`.
  It is independent of lockfile pins and refs, so advancing a mutable ref or dropping a
  reference does not affect an older reader's lease.
- Child processes: `std` opens with close-on-exec on Unix, so a spawned child does not
  inherit and silently extend a lease. A runtime that outlives the parent must acquire its
  own lease.
- Multiple leases on one checkout in one process (separate opens) are independent;
  `flock` and `LockFileEx` both conflict across separate handles in one process, so a
  same-process GC sees an own-process lease as held. This is wanted.

### Format and location

- Path: `<store_root>/leases/<kind>/<slug>/<pin>.lease`. `LEASES_SEGMENT = "leases"` is
  defined next to `LOCKS_SEGMENT` in the manager (store-local; the constant in
  `omni_constants` of the same name `locks` is the unrelated `.omni/locks`).
  `kind`, `slug` and `pin` are already restricted to safe path segments
  (`is_safe_segment`, `safe_slug`), so no new path validation is introduced.
- Content: zero bytes. No version field, no PID, no timestamps. Nothing reads the content,
  so no format needs migration and nothing can go stale.
- It lives in the store, not the workspace, so it is not committed and needs no ignore
  entry.
- New non-blocking operations are needed on `LockGuard`: `try_acquire_exclusive` returning
  "would block" distinct from I/O errors (uses `File::try_lock`, stable at the repo's
  `rust-version`). `acquire_shared` already exists.

## Acquisition protocol (proposed)

New API, additive: `materialize_leased(source) -> LeasedSource { source: MaterializedSource, lease: SourceLease }`.
`materialize` keeps its signature and meaning (no lease) so existing callers and tests
are unchanged until migrated.

```
materialize_leased(kind, spec):
  fast path (locked pin, no remote lock):
    L = shared-lock lease(kind, slug, pin)             # blocks only while a GC holds it
    if lease file is not the file at its path: drop L, retry        # see "Lease file removal"
    if tree_is_complete(tree): mark_used; return (tree, pin, L)
    drop L                                              # tree gone/incomplete: slow path

  slow path:
    R = exclusive remote lock                           # observed
    resolve pin; export + publish if incomplete          # observed, under R
    L = shared-lock lease(kind, slug, pin)              # still holding R, BEFORE returning
    verify tree_is_complete; mark_used
    release R; return (tree, pin, L)
```

Why there is no gap:

- **Publish → lease.** In the slow path the lease is taken while the remote lock is still
  held. `prune_store` must hold that same remote lock to delete this remote's trees, so it
  cannot run between publish and lease.
- **Fast path → lease.** The fast path holds no remote lock, so it takes the lease **first**
  and only then checks completeness. A GC that selected the entry earlier either (a) won
  the exclusive try-lock and deleted the tree, in which case the reader sees an incomplete
  tree after its shared lock is granted and falls to the slow path, which re-publishes
  under the remote lock; or (b) lost the try-lock and skips the entry.
- **Pin update / ref advance.** The lease names the pin directory, not the ref, so a
  mutable ref moving elsewhere cannot unprotect it.

### Lease file removal

Removing a lease file while a reader opens it can leave the reader holding a lock on an
unlinked inode while a second opener locks a new file at the same path. Two safe options:

1. **Never unlink lease files in GC.** Zero-byte files accumulate, bounded by pins ever
   used. Simplest, no race.
2. **Unlink only under the exclusive lease lock and have every acquirer verify, after
   locking, that its handle is still the file at the path** (Unix: device+inode compare;
   Windows: file identity, or fall back to option 1). Retry on mismatch.

Recommendation: ship option 1 in F08.2/F08.3, and add option 2 only if litter proves a
problem (D2). Either way the file never retains content.

## GC interaction (proposed)

Applies to `prune_store`, the only deleter.

```
for entry in selected:                       # filter semantics unchanged
  R = exclusive remote lock(kind, remote)     # observed
  X = try exclusive lease lock(kind, remote, pin)
  if would-block:  skip entry, report as "in use"; continue
  match remove_tree_checked(entry):            # fallible, manifest first; see below
    Ok  -> removed.push(entry)
    Err -> failed.push((entry, err))           # recorded, run continues
  release X
  (remote now empty -> existing cleanup of trees/ parent and raw/ dir, observed)
```

- **Fallible removal, manifest first.** The current `remove_tree` (private, returns `()`)
  swallows every error, so a partial failure is indistinguishable from success. F08.3 adds a
  checked removal that returns the error. A recursive directory removal is **not atomic** and
  can fail after deleting some files, so the order matters: the `.manifest` is the
  completeness marker, and a half-deleted tree that still has its manifest would read as
  complete. Therefore delete the `.manifest` **first** (the tree now reads incomplete and
  can never be reused), then remove the directory, then the `.used` marker. If the
  directory removal fails, the entry goes to `PruneReport.failed` (not `removed`, and not
  an early `?` return that would abort the rest of the run), `.used` is left, and what
  remains is an inert incomplete tree that the next publish or prune clears. Publishing keeps
  using the existing best-effort `remove_tree` for incomplete trees.
- Leased checkouts are skipped; unleased, unrelated checkouts are reclaimed in the same
  run, including under `all`.
- A skipped entry is reported, not an error. `StorePruneFilter::only` keeps its
  "confirmed list" meaning; a leased entry in `only` is skipped, not deleted.
- **Result type (compatibility).** `prune_store` returns `Result<Vec<StoreEntry>, Error>`
  today and keeps that signature and meaning (the entries actually removed). F08.3 adds a
  new `prune_store_report` that returns a `PruneReport { removed, skipped_in_use, failed }`;
  `prune_store` calls it and returns only `removed`. Callers that need the skipped list
  migrate to the report; no existing caller breaks.
  **The one production caller** is `omni_api::operations::remote_source`
  (`handle_remote_sources_prune`, the CLI and MCP prune command). It migrates to
  `prune_store_report` in F08.3 so failures cannot be lost: `RemoteSourcesPruneResponse`
  gains additive `skipped_in_use` and `failed` lists next to `checkouts` (the removed
  entries); skipped-in-use entries are reported as a notice, not an error; a non-empty
  `failed` list makes the command fail (non-zero exit) **after** reporting what was
  removed, with each failed checkout and its cause in the diagnostic. Dry runs report
  would-remove and would-skip only. The generated MCP/JSON schema and command reference
  are regenerated, not hand-edited. The test-only callers of `prune_store` in
  `omni_remote_source/tests` keep compiling and asserting `removed`.
- The remote-empty cleanup must not delete `trees/<kind>/<slug>` or `raw/` while any lease
  is held for that remote. Because the cleanup only runs when the parent directory is
  empty, a leased tree (which still exists) already prevents it.
- `store_entries` / dry run stays lock-free and may over-report; the real prune re-checks.
- References are **not** consulted by `prune_store` today and this design does not add
  that (D3). References and leases are independent retention inputs: a checkout is safe if
  it is leased now. Persistent protection of installed-but-idle sources is a reference
  concern deferred to D3.

## Atomic reference API (proposed)

Replaces `record_refs`; keep `record_refs` as a deprecated wrapper for
`replace_complete` until F08.5 removes its callers.

```rust
enum RefUpdate { ReplaceComplete, MergeAdditive }
async fn update_refs(&self, id: &str, mode: RefUpdate, refs: &[RemoteSourceRef]) -> Result<(), Error>
```

(Names `replace_complete` and `merge_additive` are the contract; Rust spelling is for
F08.4 to settle.)

| Semantics               | `replace_complete`                                                                                 | `merge_additive`                                                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Meaning                 | `refs` **is** the subsystem's full resolved set. May be empty, which releases every old reference. | `refs` are newly materialized. The result is existing ∪ `refs`. Never removes a key.                                                  |
| Caller                  | Only after the subsystem fully and successfully resolved (install, projection full sync).          | Genuinely partial runs: lazy plugin load (no code yet) and any future single-source caller. Targeted projection writes nothing today. |
| Key collision           | n/a                                                                                                | Same `kind/locator/selector` with a different pin: the new pin wins (it was just resolved). Different keys coexist.                   |
| Missing file            | Creates it.                                                                                        | Treated as empty.                                                                                                                     |
| Unreadable/invalid file | Overwrites only if the caller explicitly opted in; default is an error.                            | **Error, no write.** Never silently reset an unreadable set to the additive subset.                                                   |

Common guarantees:

- **Exclusive lock.** Read-modify-write runs under the advisory lock, so `reconcile_pins`
  (which reads all of `refs/`) and concurrent merges are mutually exclusive. Two
  concurrent merges union; neither is lost.
- **Atomic publish.** Serialize to a temp file in `refs/` (a name without the `.json`
  suffix, which `reconcile_pins` already skips), flush, then rename onto `refs/<id>.json`.
  The current writer, `omni_file_data_serde::write_async`, picks the format from the path
  extension and errors on an extensionless name, so F08.4 must serialize explicitly (or use
  `write_with_format_async` with the JSON format) for the temp file. This is not a drop-in
  change to `record_refs`.
  A reader (reconcile, a concurrent process) sees the old or new complete file, never a
  partial one. Stale temp files are inert: they retain nothing, and are not `*.json`.
- **Failed install never partial.** An update either commits one whole file or leaves the
  previous one byte-for-byte. A failed write removes its temp file and returns an error;
  the old set remains. Callers must not call `replace_complete` with the result of a
  failed or partially-successful resolution.
- **Subsystem isolation.** An update touches exactly `refs/<id>.json`. `id` must be a safe
  path segment (validated; today it is formatted into a path unchecked). No update reads
  or writes another subsystem's file, so an unselected subsystem's roots are never
  discarded.
- **Install sequencing** (`run_contributors`, F08.5): run every selected contributor
  first, collecting refs. A contributor failure (before any write) leaves every set and
  the lockfile exactly as they were, which is stricter than today, where contributors are
  committed one at a time. Serialize and stage every new set to its temp file before the
  first rename, so a serialization or write failure is also caught before any set changes.
  The commit phase then renames each staged file and runs `reconcile_pins`.
  **Guarantee, stated precisely:** all-or-nothing across sets holds for failures up to and
  including staging. It does **not** hold if a rename or `reconcile_pins` fails part-way:
  earlier sets stay replaced. That state is valid (each set is a complete, parseable set),
  install reports the failure, and a re-run is idempotent and converges (D4). A cross-file
  rollback or journal is rejected as not worth its complexity; a crash has the same
  outcome. **Lockfile (observed gap):** `omni_lockfile::Lockfile::save` currently writes
  `lock.json` directly through `write_async`, with no staged rename, so a failed or
  interrupted write can leave a partial lockfile. "The lockfile is unchanged by a failed
  reconcile" is therefore **only true once the lockfile is published atomically**. F08.4
  includes that change in `Lockfile::save` (serialize explicitly to a same-directory temp
  file, flush, rename onto `lock.json`; the temp name needs an explicit format because the
  writer infers it from the extension). Until then the guarantee is narrowed to the refs
  sets, and a partial lockfile is recoverable only from version control, since it is
  committed.
- Zero enabled sources still runs the contributor and calls `replace_complete` with an
  empty set ([§15.2](../../015.00-remote-source-integration.md#152-contributor-install-selection-and-references)).

## Platform notes

| Topic                     | Unix (`flock`)                                                                | Windows (`LockFileEx`)                                                                                                                                                                                                                                                                   |
| ------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Release on crash          | OS closes the descriptor; lock released.                                      | OS closes the handle; lock released.                                                                                                                                                                                                                                                     |
| Advisory vs mandatory     | Advisory: only cooperating omni processes honor it. `rm -rf` ignores a lease. | Byte-range locks are mandatory for reads/writes of the locked range, but the lease file is never read, so effect is the same. Other tools can still delete the tree.                                                                                                                     |
| Delete while held         | Unlinking a locked file succeeds, leaving a held lock on an orphan inode.     | `std` opens with delete sharing, so deletion may succeed into delete-pending; new opens can then fail. Verify in F08.2.                                                                                                                                                                  |
| Locking the lease file    | `flock` on the open file description; shared by `dup`/`fork`.                 | Per handle.                                                                                                                                                                                                                                                                              |
| Network/odd filesystems   | `flock` may be unreliable on NFS or some FUSE mounts.                         | Network shares may not honor locks.                                                                                                                                                                                                                                                      |
| Read-only tree vs removal | Directories stay writable by design (`tree::seal`), so `remove_tree` works.   | Read-only file attributes can make `remove_dir_all` fail; this exists today for `prune_store`, and a failure must be reported (`PruneReport.failed`). Removal is not atomic: it may leave a partial tree, which is safe because the manifest is deleted first so it reads as incomplete. |

Because the lock is advisory, a lease protects against omni GC only. This matches the
goal: "retention mechanism, not activation or permission".

## Failure and crash cases

| Case                                                | Expected outcome                                                                                                                                                                                                                                                                                                                              |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reader killed (`kill -9`) holding a lease           | OS releases lock; next prune may reclaim the tree. Empty lease file left, retains nothing.                                                                                                                                                                                                                                                    |
| Reader holds lease; prune runs                      | Entry skipped and reported; unrelated entries reclaimed.                                                                                                                                                                                                                                                                                      |
| Reader holds lease; pin advances or ref dropped     | Old tree unaffected; reconcile only edits `lock.json`.                                                                                                                                                                                                                                                                                        |
| Prune wins try-lock before a fast-path reader locks | Reader's shared lock waits, then sees incomplete tree, re-publishes under remote lock.                                                                                                                                                                                                                                                        |
| Crash between `rename` of tree and manifest write   | Tree reads incomplete (observed); next acquire re-exports. Lease unaffected.                                                                                                                                                                                                                                                                  |
| Crash after publish, before lease                   | Not possible in slow path: lease taken under the remote lock before it is released.                                                                                                                                                                                                                                                           |
| Crash mid ref write                                 | Only a temp file is partial; `refs/<id>.json` is the old complete file.                                                                                                                                                                                                                                                                       |
| Ref write/rename fails                              | Temp removed, error returned, previous set intact.                                                                                                                                                                                                                                                                                            |
| Concurrent `merge_additive` from two processes      | Serialized by the advisory lock; union of both.                                                                                                                                                                                                                                                                                               |
| `merge_additive` on corrupt existing set            | Error; nothing written; reconcile also errors on the unreadable file (observed `read_async`).                                                                                                                                                                                                                                                 |
| One contributor fails mid-install                   | No set replaced, `reconcile_pins` not run, lockfile unchanged.                                                                                                                                                                                                                                                                                |
| Crash or failure during the commit phase            | Staged files are inert. Renames already done stay: each set is old-complete or new-complete, never partial; the lockfile is unchanged by a failed reconcile only after F08.4 makes `Lockfile::save` atomic (today a failed write can leave it partial); re-running install converges. Cross-set all-or-nothing is not promised after staging. |
| Prune on a layout newer than this omni              | Refuse (observed `check_layout_readonly`).                                                                                                                                                                                                                                                                                                    |
| Older omni prunes while a newer omni holds a lease  | Unprotected unless the layout version gates it (D1).                                                                                                                                                                                                                                                                                          |
| Store on a filesystem without working locks         | Leases degrade to no protection; document as unsupported, same as the existing remote lock.                                                                                                                                                                                                                                                   |

## Compatibility

- **`lock.json`:** unchanged. Pin semantics, `changed` merging, and `persist_pins` stay.
- **`refs/<id>.json`:** unchanged (`RefSetData::V1_0_0`, `deny_unknown_fields`, sorted).
  No schema or version change; the new API only changes how it is written.
- **Store trees, manifests, `.used`, `.pending`, `locks/`:** unchanged.
- **New:** `<store_root>/leases/` (empty lock files), additive. An older omni ignores it,
  which is the one real compatibility hazard: it can still `prune_store` a leased tree. A
  layout bump `VERSION` 1 → 2 makes an older omni refuse prune (it already does so for
  newer layouts), but also stops it using the shared per-user store at all. This is the
  only change that could justify a format change, and it is left open (D1) rather than
  assumed.
- **API:** `materialize`, `record_refs`, `persist_pins`, `reconcile_pins`, `prune_store`
  keep their signatures; additions are `materialize_leased`, `update_refs`, and
  `prune_store_report` (returning removed, skipped-in-use and failed entries; `prune_store`
  delegates and still returns only the removed entries). Existing remote-source, pack, generator and projection tests
  must pass unchanged ([F08](F08-source-acquisition-leases.md#acceptance)).

## F08.6 pending cleanup

Decision D7: `.pending` leftovers are reclaimed. Implemented in `omni_remote_source`
(`manager/pending.rs`).

- Every pending path (export directory or manifest staging file) is owned by a
  `PendingPath` guard. It holds an exclusive OS lock on a unique sibling file
  `<name>.lock` and removes the path and the lock file on drop, so errors,
  cancelled futures and panics leave nothing behind.
- After a kill (SIGKILL, power loss) the kernel releases the lock. A cleaner
  deletes a pending path only after taking its lock exclusively without waiting:
  success means the owner is gone, failure means it is live. The pid in the name
  is never trusted (pid reuse).
- The publisher locks the file before creating the path and checks the file still
  exists once locked, retrying otherwise. The cleaner also skips entries younger
  than 60 seconds (by lock file mtime).
- Unlike lease files, these lock files are unique and single-use, so the cleaner
  deletes the lock file together with the path while holding the lock. The lease
  "never unlink" rule does not apply to them.
- Cleanup runs at the start of each publish and in `prune_store`/`prune_store_report`.
  `PruneReport::reclaimed_pending` lists the paths removed, or for a dry run those that
  would be.
- Entries with no lock file (left by older omni versions) are not touched. No store
  `VERSION` bump (D1 stays open); D3 stays out of scope.
