## 5. Activation, identity and delivery

Proposed `workspace.omni.yaml`:

```yaml
projects:
  include: ["crates/**", "packages/**"]
  exclude: ["**/fixtures/**"]

plugins:
  - source: builtin # enabled defaults to true for listed entries
    name: "@omni/javascript" # effective id defaults to this full name
    options: {}

  - source: builtin
    name: "@omni/rust"
    options: {}

  - source: local
    path: ./omni/plugins/company # id inferred from manifest name

  - id: frontend # optional consumer alias overrides the inferred id
    enabled: false
    source: git
    uri: https://github.com/example/omni-frontend.git
    rev: <immutable-commit>
    subdir: plugins/frontend # optional literal directory; default is repo root
```

- `plugins` defaults to `[]`, enabling nothing. Each explicitly listed entry's
  optional `enabled` defaults to `true`; listing an entry is the explicit opt-in.
  Disabled entries are not fetched, loaded or executed. Structural declaration
  errors are still reported without reading their source.
- `id` is optional. The effective consumer handle is an explicit `id`, otherwise
  the full canonical plugin `name`: builtin locator name or external manifest
  name, such as `@omni/javascript`. Do not strip the scope, infer from a repo
  basename or append numeric suffixes. External manifests retain their author
  `name` and metadata `version` independently of consumer aliases.
- `builtin` resolves a compiled registry entry. External `local`/`git` entries
  resolve one `plugin.omni.*` manifest at the selected artifact directory using
  existing source materialization and immutable lock identity (RFC 0013), not
  a separate downloader. Local `path` is one literal directory; Git `subdir`
  defaults to the checkout root. Neither accepts discovery globs.
- Loading an enabled plugin with no mutually supported protocol version or an
  unsupported runtime is an error. There is no silent fallback to another tier.
- A built-in's implementation identity includes the omni build. An external
  plugin's identity includes the verified artifact and bundled module digests;
  a version string alone is never a cache or trust identity.

Effective ids must be unique across enabled activations, including explicit vs
inferred collisions. Resolve all enabled descriptors and validate that uniqueness
before invoking any hooks. Multiple activations of the same canonical plugin
(different versions, subdirectories or options) need distinct explicit aliases
where their inferred names would collide. Report both declaration locations and
suggest `id`; list order never chooses a winner.

Project `inference.plugins` allowlists, provenance, state partitions and cache
keys use the effective id. For example, an unaliased Rust builtin is selected
with `plugins: ["@omni/rust"]`; an explicitly aliased plugin uses its alias.
Source fetch/pin/GC identity remains independent of the effective id.

Validate explicit id syntax for all entries and explicit-id collisions among
enabled entries from workspace declarations without source access. Disabled ids
do not reserve handles. Resolve omitted external ids only for enabled entries; disabled
entries remain unresolved and never require fetching a manifest merely to learn
a name. Cross-source inferred-id collisions and allowlist resolution are checked
against enabled descriptors. Before an id is known, identify errors by source
locator and declaration location, not an invented placeholder plugin id.

Canonical plugin names retain the shared `@scope/name` convention used by pack
and projection manifests. Reserve `::` for system-composed parent/child
hierarchies; it is not an alternate publisher-scope separator. Effective plugin
ids are logical references, not filesystem paths.

Unlike recursive pack/projection traversal, plugin source materialization does
not require an id for pre-fetch subtree selection or composed child ids. This
proposal therefore permits omitted ids for local/git plugin entries without
changing other subsystems' required-id rules. A plugin author renaming its
canonical name changes an unaliased effective id; stale allowlist references
must fail clearly. Explicit aliases stabilize references across such updates;
renames never silently transfer old session state to a different identity.

### 5.1 Declared inference dependencies and consumer bindings

A plugin may declare named inference-dependency slots in its static manifest;
omni binds those slots to enabled effective activation ids. Workspace id passing
is optional and needed only to select a producer given an explicit activation id.
The author declares the required producer's canonical plugin identity, not a
consumer alias. Illustrative manifest syntax:

```yaml
inference_dependencies:
  javascript:
    plugin: "@omni/javascript"
```

Without an explicit producer id, resolve the slot by its declared canonical plugin
name, which is also the producer's default effective activation id. For example,
an enabled unaliased `@omni/javascript` satisfies the slot above with no
`inference_bindings` entry. Do not require users to repeat the canonical name in
workspace bindings. If the producer has an explicit id such as `frontend`, the
consuming activation supplies that id independently of its own id:

```yaml
plugins:
  - id: frontend
    enabled: true
    source: builtin
    name: "@omni/javascript"
  - id: company
    enabled: true
    source: local
    path: ./plugins/company
    inference_bindings:
      javascript: frontend
```

The plugin receives a dependency handle associated with its author-defined slot,
not a requirement to discover or embed consumer activation ids. Bindings select
the producer activation and therefore its configured artifact/version/options;
validate the selected producer against the slot's declared identity. Multiple
activations of one artifact remain distinct. A dependency declaration never
implicitly enables, fetches or installs another plugin. Resolve and validate the
enabled activation dependency graph before hooks; missing required dependencies,
invalid bindings and cycles fail actionably rather than relying on list order.

An omitted binding selects the enabled producer under its canonical default id,
not an arbitrary activation with matching artifact identity. Do not
guess an explicitly aliased producer even if it is the only matching artifact.
If no default producer exists, report the missing dependency and request the
explicit id binding. If default and explicitly aliased activations coexist, the
default remains selected unless the consumer explicitly binds the slot elsewhere.
An explicit id whose text equals the canonical default name needs no redundant
binding: id passing is needed when selecting a different effective id. The plugin's
author-defined slot remains stable; callers need not pass ids into plugin-private
options or hard-code workspace aliases in the artifact.

Inference follows this graph within the existing inference phase ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)), not new
fixed stages for every plugin integration. Workspace declaration order schedules
otherwise-ready activations; native registration order is not a dependency or a
semantic precedence rule. Ordered contribution composition retains stable
effective-id order and explicit conflict handling ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)), not execution-order wins.

Dependency handles initially expose only deliberately published typed claims, such
as ecosystem package identity, workspace membership and dependency metadata.
They do not expose private state, raw manifests, inferred project/task fragments
or final effective configuration. If a consumer needs information already derived
by a producer, define a published claim rather than granting arbitrary access to
the producer's configuration. Claims have a versioned producer/consumer contract
and remain subject to host-controlled query authorization, scopes and budgets.
Reading a claim grants no filesystem authority or cross-plugin task-reference
authority. Execution order grants no override precedence; composition still uses
[§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)'s conflict rules beneath explicit configuration.

A required inference dependency guarantees an available compatible bound producer
whose scheduled inference finishes successfully, not the presence of particular
claims or ecosystem packages. A producer with no eligible roots or no matching
published claims may complete successfully and expose an empty claim view/query
result. The consumer interprets that successful absence under its documented
adapter rules: it may decline a root, continue without that information or fail
if the information is necessary for correctness. The host does not invent a
missing-producer error merely because no claims matched.

Keep successful empty results distinct from missing/disabled producers, incompatible
contracts, denied queries, exhausted resources and producer execution failures.
Never convert those failures to empty output or run a dependent consumer against
partial/stale claims. Negative queries participate in snapshot/cache validation:
newly published matching claims must invalidate reuse of a previously empty result.

A binding is also the claim-access grant. Manifests declare the omni-defined claim
types a plugin publishes and consumes (illustratively
`claims: {publishes: [...], consumes: [...]}` under its `project_discovery`
capability); a consumer sees only the intersection with its bound producer's
published types, in every stage that queries claims. Undeclared or unbound access is
an error, not an empty result. See
[§6.1](006.01-claims-and-queries.md#claim-visibility-and-grants).

These remain the same required inference-dependency slots even when the consumer
uses their claims only during resolution. Their producer-order/cycle validation
does not disappear after the inference phase: mutual bindings are rejected even
if a resulting project graph could be acyclic. This is the initial acyclic slot
contract, not an implicit second graph of unordered resolution grants. Supporting
that different model later would require an explicit versioned change.

**Remaining specification:** define the concrete claim schemas, version negotiation
and bounded query/access contract for this claims-only surface ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)). Canonical-
name default binding and explicit-id passing follow the agreed rules above.
Dependencies are required initially; optional dependencies are deferred rather
than silently treating a missing required producer as empty output.

An external manifest might be:

```yaml
name: "@example/company"
version: 0.1.0
protocol: ">=0.1.0, <0.2.0"
runtime: wasm # JavaScript runtime support is deferred
entry: ./dist/plugin.wasm
capabilities:
  - name: project_discovery
    api: ">=0.1.0, <0.2.0"
    required: true
    requires_features: []
    hooks: [on_workspace, filter_candidates, infer_roots, resolve_dependencies]
    claims:
      publishes: [package_identity]
      consumes: []
discovery:
  markers: [company.project.json]
  inputs:
    include: ["@project/company.project.json", "@workspace/company.workspace.json"]
```

Marker and input declarations are static data readable without starting the
runtime. JavaScript entries are self-contained bundles (or an explicitly listed,
hashed local module graph); no npm resolution, network imports, install scripts
or ambient Node installation. Source and entry paths cannot escape the
selected artifact directory, not merely the surrounding repository. Git source
availability, lazy materialization, pinning and offline behavior follow [§15](015.00-remote-source-integration.md#15-remote-source-integration)'s
shared-source integration. No registry is required for v1.

Capability names are canonical protocol identifiers; `project_discovery` is the
initial namespace. Each capability has an API requirement independent of the
plugin envelope's protocol requirement. Both use explicit semver ranges;
experimental examples deliberately constrain the minor version. `required`
defaults to `true`. An unknown/incompatible required capability or missing
required feature fails activation; an explicitly optional capability can instead
be skipped with a notice and inspection entry. Unknown hooks within a negotiated
capability version are errors, not silently ignored. Hook declarations are
validated against the handler's supported-hook set before scheduling. See [§14](014.00-versioning-compatibility-and-migrations.md#14-versioning-compatibility-and-migrations)
for negotiation, stabilization and migration guarantees.
