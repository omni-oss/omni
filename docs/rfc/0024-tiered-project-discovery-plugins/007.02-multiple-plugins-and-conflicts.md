### 7.3 Multiple plugins and conflicts

_The title keeps the old name for link stability; plugins are composed by ordered precedence, not conflict detection._

Plugins are opt-in ([§5](005.00-activation-identity-and-delivery.md#5-activation-identity-and-delivery)):
`plugins` defaults to `[]` and enables nothing, and listing an entry, built-in or
external, is the explicit opt-in. The activation list is therefore explicit user
configuration, and its order is an intentional choice. **The order of the
activation list decides precedence between plugins: when several plugins set
different values for the same shared project field (within one tier for
`cache.enabled`), the activation listed later wins.** Plugin-inferred tasks stay
activation-scoped, so two plugins never share a task key. Scheduling order, hook completion order, runtime tier, native registration
order and the order application files finish loading never decide winners. Explicit
layers still override every plugin contribution ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
Fields with a tiered fallback, such as `cache.enabled`
([§7.1](007.00-project-modes-and-apply.md#71-project-modes)), resolve their
tiers first: list order decides only within a tier, and between plugins at the
same tier. An earlier plugin's task-level `enabled` therefore beats a later
plugin's project-level `enabled`
([C01](007.04-composition-golden-fixtures.md#c01--cache-enablement-tier-matrix)).

Compose the activations at one root in activation-list order, earlier first:

- Disjoint fields compose; semantically equal values coalesce and keep their
  contributors.
- A scalar field set to different values takes the later activation's value,
  including when equal text differs only in interpretation mode. This covers the
  shared project-level fields (`description`, `env.vars`, `meta`, `cache.enabled`
  and so on).
- Dictionary fields compare at the key or nested-field boundary, not as whole
  dictionaries.
- Plugin-inferred tasks stay activation-scoped (`frontend::build`,
  `native::build`, [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)):
  two activations emitting a local `build` produce two distinct tasks and never
  merge, and a plugin cannot emit aliases or modify another activation's tasks.
  Property-by-property task merge and whole replacement on a declaration-kind
  change, as in
  [C10](007.04-composition-golden-fixtures.md#c10--declaration-kind-changes-replace-atomically),
  apply only when ordered layers share one task key: explicit and applied layers,
  and the synthetic same-key contributors that the F07.3 tests use. An unqualified
  local name that two activations both infer remains an ambiguous automatic alias
  and an error ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases),
  [C20](007.04-composition-golden-fixtures.md#c20--alias-and-inheritance-failures-validate-surviving-graphs)),
  unchanged by list order.
- Additive lists concatenate in activation-list order, preserving each
  contribution's internal order and repetitions.

Contributions here include their activation-local application under
[§7.1](007.00-project-modes-and-apply.md#71-project-modes); one activation's
applied replacement or subtraction never edits another activation's contribution.
The activation's position in the list is the position of its fully applied
contribution. Direct plugin-emitted collections use only the additive forms allowed
by their collection validator; destructive replacement and positional merge
operations are rejected at the output boundary. Explicit layers retain their full
existing collection operators. Plain contribution values are not instructions to
replace another plugin's collection; composition remains field-specific.

No stable effective-id order is used in composition. Effective ids are unique
across enabled activations ([§5](005.00-activation-identity-and-delivery.md#5-activation-identity-and-delivery)),
so the activation list totally orders them (the same activation cannot be enabled
twice: listing a plugin again needs a distinct `id`, so every position is one
activation); built-in and external plugins sort only
by their position in the list, not by source kind. A built-in is a plugin listed
by its locator name, such as `@omni/javascript`, with no implicit precedence over
or beneath a user-listed plugin: it wins or loses by list position alone. The
host fallback for cache enablement and other tier defaults
([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics),
[C01](007.04-composition-golden-fixtures.md#c01--cache-enablement-tier-matrix)) is
a separate mechanism, not a plugin contribution, and takes no part in this
ordering. Within one activation, inferred
fragments precede its applied layers in declared application order
([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
Precedence across declaration layers is less specific first, more specific
later, so the more specific layer wins: plugin activation contributions, then the
explicit project's base layers in extension order, then the concrete explicit
project ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
Precedence between plugins always follows the workspace `plugins` list order
([§5](005.00-activation-identity-and-delivery.md#5-activation-identity-and-delivery)).
A project `inference.plugins` allowlist
([§7.1](007.00-project-modes-and-apply.md#71-project-modes)) only narrows which
activations contribute at that root; it does not reorder them or add a second
list. Should a further declaration level ever carry plugin lists, the same
direction would apply (less specific composed first, more specific after); this
is a principle for layers that already exist (`extends` and project layers,
[§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)),
not a new configuration surface.

Effective ids still name contributors in diagnostics and provenance and take part
in the inference-cache key ([§8.1](008.00-performance-and-shared-safeguards.md#81-shared-safeguards)).

Reordering the activation list changes which value wins and the order of additive
lists, so it changes the composed project the same way changing an id can. Per-
activation hook records ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)) are keyed by the activation, not its position, and stay
valid. Anything that stores composed output must key on the ordered effective-id
list ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)),
so a reorder never reuses a result composed under the old order. The per-task
effective-field digest that task-cache keys use
([§8.3](008.02-execution-cache-semantic-identity.md#83-fine-grained-execution-cache-integration))
hashes the resulting effective values only, without plugin order or provenance, so
a reorder that leaves a task's values unchanged keeps its cache hits.

For plugin-contributed list fields, initially accept only the explicit `append`
envelope, which means additive contribution, not replacement. Reject a plain list,
`prepend`, `replace` and positional `merge` at the plugin output boundary, even if a later
explicit layer would discard their effects. This restriction is kept
conservatively, and may be relaxed once plugins exist: one plugin must not
discard or reorder another plugin's entries, and destructive operators are not
needed for inference. Activation order does not grant that power, so plugins cannot
request placement ahead of another contributor. Apply the field-specific
normalization below, not blanket list deduplication; “identical values coalesce”
is not permission to erase meaningful repeated list entries.

Preserve original entries and ordered operations through project-layer replay,
task inheritance and project-to-task settings composition. Normalize only after
all applicable composition finishes, so deduplication cannot change what a later
positional operation addresses. Use these effective-field rules regardless of
whether entries came from inference or explicit configuration:

| Field kind                                            | Effective duplicate handling                                                                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Project dependencies and task `dependencies` / `with` | Deduplicate equivalent edges after target resolution and task alias canonicalization, retaining the distinction between dependency and `with` relationships                    |
| `cache.key.env`                                       | Treat repeated environment-variable names as one effective input, comparing literal names without case folding                                                                 |
| File-pattern include/exclude lists                    | Preserve composed pattern entries; matching one file through several patterns does not make it several file inputs/outputs. Preserve the shared include/exclude matching rules |
| Order-sensitive lists                                 | Preserve order and meaningful repetitions; no generic uniqueness pass                                                                                                          |
| Command argv                                          | Preserve argument order and every occurrence; argv is not a plugin list-collection operator surface                                                                            |

Do not fold case, rewrite paths or infer equality between different patterns to
deduplicate configuration entries. Retain raw-layer operations for replay and
inspection rather than replacing them with normalized effective lists. Cache
consumers and semantic-digest projection must use the effective field rules;
repeated `cache.key.env` names must not be hashed as multiple inputs. This is a
documented pre-v1 normalization correction, not a change to existing task-cache
storage formats or remote transport.

This restriction applies to plugin list collections, not dictionary `merge`
envelopes or command argv values. Explicit configuration retains its existing
plain-list semantics (a plain list replaces, as `ListConfig` handles a value like
`replace`) and all supported operators, including `prepend`. Keep
`ListConfig<T>` unchanged; enforce the plugin profile through its enclosing
field validator/schema and equivalent checks for directly constructed native
output. SDK and inference-cache serializers must emit the `append` envelope for
plugin lists and never a bare list, which would read as replacement in explicit
configuration, and must preserve it on round trips.

Keep `ListConfig<T>` and `DictConfig<T>` unchanged. Reuse configuration field
definitions through a defaulted `V: CollectionConfigValidator` parameter on
enclosing layer types, illustratively
`ProjectLayer<V = StandardCollectionConfigValidator>`. Propagate `V` through
nested task/cache/environment layers. Field-level `deserialize_with` validator
drivers preserve/check envelope shape before the existing decoder can discard
information, then invoke `V` on the decoded collection before returning success.
`StandardCollectionConfigValidator` retains ordinary operation semantics;
`AdditiveCollectionConfigValidator` enforces the initial plugin profile:
only the `append` envelope for lists (a plain list is rejected), and the allowed
additive dictionary forms.
The generated schema must reflect the same restrictions; Serde field attributes
alone do not provide that. This selects validation policy, not a different merge
algorithm, and requires neither duplicated project/task definitions nor
compile-time removal of collection enum variants.

`CollectionConfigValidator` is specifically a **deserialization-boundary
mechanism**, not a general mutation guard or a replacement for composition/output
validation. Its contract is to constrain accepted serialized collection forms.
It does not prevent Rust code from constructing or modifying collection values,
and does not require changing ordinary collection constructors or merge methods.

For serialized plugin output and restored inference-cache payloads, enforce the
restriction inside deserialization, not a separate later validation pass. A
forbidden decoded operator produces a Serde error; envelope and decoding budgets
still apply. Public constructors or enum variants
are not a security boundary. Direct typed native output does not pass through
Serde: its output boundary must separately enforce the same additive contribution
contract, without attributing that enforcement to `deserialize_with`. Native
calls need not serialize merely to use this deserialization-boundary mechanism.
Reject forbidden operations before
composition, even when an explicit layer would later remove their effects, with
plugin/root/field diagnostics. Define additive list behavior per field, preserving
order-sensitive duplicates where meaningful; do not substitute the existing
plain-list replacement behavior (a plain list from a plugin is rejected, not
reinterpreted) or introduce blanket deduplication.

The existing `DictConfig::deserialize` recognizes an object-valued `merge` or
`replace` key and decodes only that key's value, silently ignoring sibling keys.
A post-decode `V` check cannot recover those siblings or validate malformed task
declarations hidden there. The enclosing field driver must therefore reject a
mixed operator envelope before delegating: an operator envelope contains exactly
its operator key; literal operator-named entries use the unambiguous outer envelope
in [§7.4](007.03-task-scoping-aliases-and-selectors.md#collection-operator-names-are-not-task-name-escapes).
The same pre-decode rule applies to `ListConfig` operator objects: its decoder
also selects a recognized array-valued operator and can discard siblings. An
`append` envelope cannot hide a second forbidden/malformed operator or extra
field. Keep plain lists and raw command argv distinct from operator objects.
Apply this shape check to plugin/cache and authored application/explicit layers,
without changing `DictConfig<T>` itself. Document rejection of formerly ignored
siblings as a pre-v1 input-validation correction, with diagnostics telling authors
to move every entry inside the intended envelope. Test malformed hidden siblings,
both operator keys, envelope round trips and directly constructed native output;
later replacement cannot excuse invalid original declarations.

When a later plugin overrides a different value set by an earlier plugin, the
result is not an error; it is recorded so the override is not silent:

- Provenance names the winning tier and file as before and also lists the
  overridden contributors: their effective plugin ids and activation declaration
  locations, per root and structured field path. It lists them whenever provenance
  is shown, including when an explicit layer replaces the field.
- An info-level notice (code illustratively `composition.plugin_override`) reports
  that some number of fields in some number of projects were overridden by a later
  plugin, with the details in inspection output. It is raised only when a plugin wins
  over a different plugin value and no explicit layer replaces the field;
  coalesced identical values, additive lists and fields an explicit layer
  replaces raise nothing. No message, notice or inspection field contains raw
  values.

Users can change the result by reordering the activation list, narrowing
contributors with a project `inference.plugins` allowlist, replacing the field in
the explicit file, or choosing `replace`. Duplicate final project names across
distinct roots remain errors; never silently choose a project. Malformed output
is an error, not something an unrelated explicit field or a later plugin can mask.

**Host-owned fields and trust.** Plugin output cannot set `cache.remote`, `redact`,
capability grants, ignore rules or other host/security policy
([§6.4](006.04-hook-and-claim-schemas.md#64-hook-claim-and-query-schemas-project_discovery-v0),
[§9](009.00-failures-security-and-observability.md#9-failures-security-and-observability));
only explicit configuration can, including workspace-selected `apply` files, which
the user authors and the plugin never ships
([§7.1](007.00-project-modes-and-apply.md#standard-host-managed-apply)). A later
plugin therefore cannot silently flip the remote-cache opt-out of a release, deploy
or signing task. The project-level fields that order can still override
(`env.vars`, `cache.enabled`, `cache.key.defaults`) rest on the trust assumption
that the user explicitly opted in to every listed plugin; provenance names the
overridden contributors and the aggregated notice reports the override.

**Decided by the maintainer (2026-11-26).**

1. Ambiguous automatic alias is the one place where list order does not decide a
   winner: two activations inferring the same local task name stay an error
   ([C20](007.04-composition-golden-fixtures.md#c20--alias-and-inheritance-failures-validate-surviving-graphs)).
   Decided: keep the error; list order does not resolve it. C20 is unchanged.
2. `cache.remote` is excluded from plugin output. Decided: only explicit
   configuration sets it; provenance and the notice are not a substitute for the
   exclusion.
3. Plugin output may not use a plain list for list fields. Decided: plugin-contributed
   lists must use the explicit `append` envelope, and a plain list from a plugin is
   rejected at the output boundary like `prepend`, `replace` and positional `merge`.
   This supersedes the earlier rule that accepted plain lists as additive. Reason:
   the same text `[x]` meant replace in explicit configuration and append in plugin
   output, which is surprising and a round-trip hazard for SDK and inference-cache
   serializers; requiring `append` makes the additive intent explicit and keeps one
   meaning for a plain list everywhere. Plain lists in explicit configuration are
   unchanged (replace), `ListConfig` and every merge semantic are unchanged, and
   the dictionary rules are unchanged by this decision.
