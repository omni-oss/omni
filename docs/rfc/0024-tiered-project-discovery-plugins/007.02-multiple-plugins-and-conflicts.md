### 7.3 Multiple plugins and conflicts

Do not let scheduling, runtime tier or activation-list order decide winners.
Disjoint contributions compose; identical values coalesce. Different values
for the same scalar or task field are a conflict unless a higher explicit layer
replaces that field/subtree. Contributions here include their activation-local
application under [§7.1](007.00-project-modes-and-apply.md#71-project-modes); do not replay one activation's applied replacement against
another's contribution. Direct plugin-emitted collections use only the additive forms
allowed by their collection validator; destructive replacement and positional
merge operations are rejected at the output boundary. Explicit layers retain
their full existing collection operators. Order-sensitive additive contributions
use a documented stable plugin-id order, with dependencies normalized to unique
resolved edges. Plain contribution values are not instructions to replace another
plugin's collection; composition remains field-specific. Changing ids can therefore change ordered-list output
and invalidates the inference cache.

For plugin-contributed list fields, initially accept only plain lists and explicit
`append`; both mean additive contribution, not replacement. Reject `prepend`,
`replace` and positional `merge` at the plugin output boundary, even if a later
explicit layer would discard their effects. Plugins cannot request placement
ahead of another contributor. Combine contributions in stable effective plugin-id
order, preserving each contribution's internal order and repetitions wherever
meaningful. Apply the field-specific normalization below, not blanket list
deduplication; “identical values coalesce” is not permission to erase meaningful
repeated list entries.

Preserve original entries and ordered operations through project-layer replay,
task inheritance and project-to-task settings composition. Normalize only after
all applicable composition finishes, so deduplication cannot change what a later
positional operation addresses. Use these effective-field rules regardless of
whether entries came from inference or explicit configuration:

| Field kind                                            | Effective duplicate handling                                                                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Project dependencies and task `dependencies` / `with` | Deduplicate equivalent edges after target resolution and task alias canonicalization, retaining the distinction between dependency and `with` relationships                    |
| `cache.key.env`                                       | Treat repeated environment-variable names as one effective input, comparing literal names without case folding                                                                 |
| File-pattern include/exclude lists                    | Preserve composed pattern entries; matching one file through several patterns does not make it several file inputs/outputs. Preserve the shared include/exclude matching rules |
| Order-sensitive lists                                 | Preserve order and meaningful repetitions; no generic uniqueness pass                                                                                                          |
| Command argv                                          | Preserve argument order and every occurrence; argv is not a plugin list-collection operator surface                                                                            |

Do not fold case, rewrite paths or infer equality between different patterns to
deduplicate configuration entries. Retain raw-layer operations for replay and
inspection rather than replacing them with normalized effective lists. Cache
consumers and semantic-digest projection must use the effective field rules;
repeated `cache.key.env` names must not be hashed as multiple inputs. This is a
documented pre-v1 normalization correction, not a change to existing task-cache
storage formats or remote transport.

This restriction applies to plugin list collections, not dictionary `merge`
envelopes or command argv values. Explicit configuration retains its existing
plain-list semantics and all supported operators, including `prepend`. Keep
`ListConfig<T>` unchanged; enforce the plugin profile through its enclosing
field validator/schema and equivalent checks for directly constructed native
output. SDK and inference-cache serializers must preserve the accepted additive
meaning on round trips.

Keep `ListConfig<T>` and `DictConfig<T>` unchanged. Reuse configuration field
definitions through a defaulted `V: CollectionConfigValidator` parameter on
enclosing layer types, illustratively
`ProjectLayer<V = StandardCollectionConfigValidator>`. Propagate `V` through
nested task/cache/environment layers. Field-level `deserialize_with` validator
drivers preserve/check envelope shape before the existing decoder can discard
information, then invoke `V` on the decoded collection before returning success.
`StandardCollectionConfigValidator` retains ordinary operation semantics;
`AdditiveCollectionConfigValidator` enforces the initial plugin profile:
plain lists and `append` only for lists, and the allowed additive dictionary forms.
The generated schema must reflect the same restrictions; Serde field attributes
alone do not provide that. This selects validation policy, not a different merge
algorithm, and requires neither duplicated project/task definitions nor
compile-time removal of collection enum variants.

`CollectionConfigValidator` is specifically a **deserialization-boundary
mechanism**, not a general mutation guard or a replacement for composition/output
validation. Its contract is to constrain accepted serialized collection forms.
It does not prevent Rust code from constructing or modifying collection values,
and does not require changing ordinary collection constructors or merge methods.

For serialized plugin output and restored inference-cache payloads, enforce the
restriction inside deserialization, not a separate later validation pass. A
forbidden decoded operator produces a Serde error; envelope and decoding budgets
still apply. Public constructors or enum variants
are not a security boundary. Direct typed native output does not pass through
Serde: its output boundary must separately enforce the same additive contribution
contract, without attributing that enforcement to `deserialize_with`. Native
calls need not serialize merely to use this deserialization-boundary mechanism.
Reject forbidden operations before
composition, even when an explicit layer would later remove their effects, with
plugin/root/field diagnostics. Define additive list behavior per field, preserving
order-sensitive duplicates where meaningful; do not substitute the existing
plain-list replacement behavior or introduce blanket deduplication.

The existing `DictConfig::deserialize` recognizes an object-valued `merge` or
`replace` key and decodes only that key's value, silently ignoring sibling keys.
A post-decode `V` check cannot recover those siblings or validate malformed task
declarations hidden there. The enclosing field driver must therefore reject a
mixed operator envelope before delegating: an operator envelope contains exactly
its operator key; literal operator-named entries use the unambiguous outer envelope
in [§7.4](007.03-task-scoping-aliases-and-selectors.md#collection-operator-names-are-not-task-name-escapes).
The same pre-decode rule applies to `ListConfig` operator objects: its decoder
also selects a recognized array-valued operator and can discard siblings. An
`append` envelope cannot hide a second forbidden/malformed operator or extra
field. Keep plain lists and raw command argv distinct from operator objects.
Apply this shape check to plugin/cache and authored application/explicit layers,
without changing `DictConfig<T>` itself. Document rejection of formerly ignored
siblings as a pre-v1 input-validation correction, with diagnostics telling authors
to move every entry inside the intended envelope. Test malformed hidden siblings,
both operator keys, envelope round trips and directly constructed native output;
later replacement cannot excuse invalid original declarations.

Report unresolved conflicts with both plugin ids, root and field path. Users
can resolve them in the explicit file, select contributors with its allowlist,
or choose replacement. Duplicate final project names across distinct roots
remain errors; never silently choose a project. Malformed output is an error,
not a merge conflict that an unrelated explicit field can mask.
