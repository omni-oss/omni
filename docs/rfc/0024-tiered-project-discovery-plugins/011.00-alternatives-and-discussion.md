## 11. Alternatives and discussion points

- **Call everything extensions:** broader branding, but less precise and
  confusable with existing inheritance. Recommend plugins.
- **Discovery only returns roots:** smaller API, but still requires every user
  to write project tasks and dependencies. Recommend bounded project inference.
- **Plugins register tools/generators too:** convenient single-author story,
  but duplicates packs and couples cheap discovery to global registry mutation.
  Recommend colocated plugin + pack now; revisit a separate capability only
  with concrete cases static packs cannot express.
- **Explicit files replace inference by default:** strongest isolation from
  inference changes. Extend is chosen for gradual adoption,
  with an obvious complete-replacement switch and field-level inspection.
- **Activation-list order decides precedence (chosen):** the later listed plugin
  wins a shared project field (within one tier for `cache.enabled`); plugin-inferred
  tasks stay activation-scoped; explicit layers still override every plugin
  ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)). Plugins are opt-in
  ([§5](005.00-activation-identity-and-delivery.md#5-activation-identity-and-delivery)),
  so the list is explicit user configuration and its order is an intentional
  choice. Overrides are made visible through provenance and an info notice rather
  than silent. Built-ins get no special ordering.
- **Conflicts are errors, no order decides winners (superseded 2026-11-26):** the
  earlier rule rejected list order because reordering unrelated entries could
  change results and treated different values as an error until an explicit layer
  resolved them. Superseded because the list is always present and user-authored,
  so a hard error forces users to restate in the explicit file what the list
  already expresses.
- **Hybrid, error by default and order resolves (rejected):** collapses into the
  chosen rule. The list is always present, so the unordered case where the error
  would apply never exists.

**Decision (2026-11-26, maintainer approved).** Activation-list order decides
precedence between plugins, later wins. Reasons: opt-in activation makes the list
explicit user configuration; Nx applies the same rule (plugins process in `plugins`
array order and the one listed last takes precedence); the hybrid collapses into
it. Built-in plugins sort by list position like any other. Declaration layers go
less specific first, more specific later. The §7.3 plugin-list restrictions stay
for now and are revisited once plugins exist.

**Threat review.** Order-wins lets a later plugin override an earlier one, so
host-owned fields are not plugin-settable: `cache.remote` (the opt-out for
release, deploy and signing output), `redact`, capabilities and ignore rules are
excluded from plugin output. The project-level fields order can still override
(`env.vars`, `cache.enabled`, `cache.key.defaults`) rest on explicit user opt-in
to each plugin, with overridden contributors in provenance and an aggregated
notice. Confirmed by the maintainer on 2026-11-26: (1) the `cache.remote` exclusion
stands; (2) the ambiguous automatic alias error (the one place list order does not
decide a winner) stays an error and is not resolved by list order.

**Decision (2026-11-26, maintainer approved): plugin lists require `append`.**
The earlier rule accepted a plain list from a plugin as additive. Superseded: a
plain list from a plugin is rejected at the output boundary, like `prepend`,
`replace` and positional `merge`. Reason: the same text `[x]` meant replace in
explicit configuration and append in plugin output, which is surprising and a
round-trip hazard for SDK and inference-cache serializers. Requiring `append`
makes the additive intent explicit and keeps one meaning for a plain list
everywhere. Explicit-configuration plain lists still replace; dictionaries and
`ListConfig` are unchanged. The rule covers activation `defaults` as well as
plugin output because they share one additive profile, and a bare `key.files`
pattern is rejected too (maintainer confirmation, 2026-11-27).

- **Only native or only Wasm:** native alone blocks user-authored adapters;
  Wasm alone imposes authoring/startup costs on built-ins. One contract and
  staged runtime adapters retain both advantages. JavaScript is an ergonomic
  option, not a requirement to embed Node.
- **Hard native deadlines:** require process isolation, with IPC/startup cost.
  Recommend reviewed cooperative native code initially; revisit worker-process
  isolation if benchmarks or the trust model require a hard resource boundary.
- **One-shot fragment return instead of hooks:** simpler API, but forces every
  plugin to do all work in one call and prevents the host from batching,
  deferring cross-root resolution, or reusing partial state. Recommend the
  hook model with omni-owned session state.

Before acceptance, complete the remaining specification prerequisites in [§17](017.00-review-findings-and-prerequisites.md#17-resolved-review-findings-and-remaining-specification-prerequisites),
including shared claim/query schemas and hook payloads, and settle benchmark-
calibrated limits and enforcement requirements. Wasmtime is the selected Wasm engine;
the Component Model ABI was selected from prototype evidence ([§10](010.00-implementation-and-rollout.md#10-implementation-and-rollout)),
not a blocker for runtime-neutral/native foundations. The original review's
architectural policy choices are resolved; these specifications implement them.
JavaScript engine selection is deferred. The initial builtin set is JavaScript
and Rust ([§4.3](004.01-native-ecosystem-adapters.md#43-initial-native-ecosystem-plugins)). Extend remains the chosen default, with explicit full replacement.
None of those specifications should weaken activation, explicit authority,
deterministic output or the ban on unbounded external execution.

The current assessment in [§18](018.00-readiness-and-open-decisions.md#18-code-grounded-readiness-and-open-decisions)
distinguishes completed policy from actual implementation readiness and tracks
new code-grounded decisions in one checklist. Those entries supersede any blanket
claim that there are no remaining policy choices; they do not reopen historical
options above. Measurement gates apply before releasing their affected runtime,
not as a reason to block independent runtime-neutral specification work.
