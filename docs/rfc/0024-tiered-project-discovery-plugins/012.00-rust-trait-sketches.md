## 12. Rust trait sketches (proposal)

These are illustrative, not final APIs. Native plugins implement capability
traits; external runtimes adapt the same logical calls over the wire. Hooks are
namespaced by capability, so capability traits are separate and independently
versioned. Plugins are observationally stateless; authoritative progress lives in
host-owned workspace/root state partitions. Supporting request/result types are abbreviated
below; these sketches describe ownership and dispatch, not a complete SDK.

### 12.1 Identity and capability registration

`omni_plugin_configurations` owns manifest/configuration types. A capability
declaration contains its canonical name, API version range, required/optional
flag, required features and supported hooks. The manifest also declares its
supported protocol range. These are data, not executable handlers.

The resolved effective activation id belongs to the host binding, not the author handler:
the same artifact may be enabled with different ids/options. Native plugins
register typed handlers using a host registry:

```rust
pub trait Plugin: Send + Sync {
    fn manifest(&self) -> &PluginManifest;
    fn register(&self, registry: &mut CapabilityRegistry)
        -> Result<(), PluginError>;
}

impl CapabilityRegistry {
    pub fn project_discovery(
        &mut self,
        hooks: ProjectDiscoveryHooks,
        handler: Arc<dyn ProjectDiscoveryCapability>,
    ) -> Result<(), PluginError>;
}
```

The registration method fixes namespace `project_discovery` and declares handler
versions/features; it cannot register a discovery handler under an unrelated name. Future
capabilities add typed registration entries. Duplicate registrations, unknown
hooks, manifest/handler disagreement and hook implementation mismatches fail
validation. SDK registration helpers/derive generate the supported-hook set from
explicitly annotated implementations; do not attempt runtime reflection over
Rust trait overrides. External modules provide the equivalent validated export
table. One plugin can register several independent capability handlers.

### 12.2 Capability traits (plugin side)

Each capability is its own trait. Adding a capability means adding a trait and a
namespace; existing capabilities are untouched.

```rust
pub trait ProjectDiscoveryCapability: Send + Sync {
    fn on_workspace(
        &self,
        ctx: &WorkspaceContext<'_>,
        req: OnWorkspaceRequest,
    ) -> Result<WorkspaceOutput, ProjectDiscoveryCapabilityError> {
        Ok(WorkspaceOutput::unchanged())
    }

    fn filter_candidates(
        &self,
        ctx: &CandidateContext<'_>,
        req: FilterCandidatesRequest,
    ) -> Result<FilterCandidatesResponse, ProjectDiscoveryCapabilityError> {
        Ok(FilterCandidatesResponse::keep_all(req))
    }

    fn infer_roots(
        &self,
        ctx: &InferenceContext<'_>,
        req: InferRootsRequest,
    ) -> Result<InferRootsResponse, ProjectDiscoveryCapabilityError> {
        Ok(InferRootsResponse::decline_all(req))
    }

    fn resolve_dependencies(
        &self,
        ctx: &ResolutionContext<'_>,
        req: ResolveDependenciesRequest,
    ) -> Result<ResolveDependenciesResponse, ProjectDiscoveryCapabilityError> {
        Ok(ResolveDependenciesResponse::unchanged())
    }

    fn observe(
        &self,
        ctx: &ObservationContext<'_>,
        req: ObserveRequest,
    ) -> Result<ObserveResponse, ProjectDiscoveryCapabilityError> {
        Ok(ObserveResponse::empty())
    }
}
```

Contexts contain read-only state views. Requests/results are distinct types per
stage: inference may return project fragments, resolution may return root edges,
and observation may return notices/inspection metadata only. Inference responses
also carry explicit per-root acceptance/decline dispositions ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)); generic state
or an empty fragment is not a substitute. Defaults preserve incoming state and
produce no contributions; filtering's default keeps all candidates. The
`unchanged()` sketches do not imply inference acceptance or resolution eligibility.
Inference's illustrative `decline_all(req)` default emits one explicit declined
result per assigned root without project/edge contributions or state changes;
registered inference implementations report their actual accepted/declined
results using the tagged alternatives in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle).
Registered hooks are the only methods omni schedules; omitted inference is never
implicitly invoked through its trait default.

Use `ProjectDiscoveryCapabilityError` for discovery hook failures rather than
adding every discovery-specific variant to a generic `PluginError`. Capability
contracts own their error taxonomy and versioned error representation. Generic
registration/activation/runtime-transport failures may retain shared error types;
the host maps capability failures into the common diagnostic envelope with
activation/capability/hook/root provenance instead of flattening all capability
variants into one ever-growing enum. External adapters preserve the same typed
failure distinction over the wire. Keep large payloads indirect where needed
and validate concrete error layouts during implementation: a more specific name
alone does not guarantee a smaller Rust error value. Reuse host errors without
duplicating their full payloads into every capability variant.

### 12.3 Host-owned state

```rust
pub struct StateValue {
    pub version: u32,
    pub bytes: Vec<u8>, // bounded serialized form
}

pub struct StateSnapshot {
    pub workspace: Option<StateValue>,
    pub roots: BTreeMap<ProjectRootId, StateValue>, // assigned-root view only
}

pub struct RootOutput<T> {
    pub root: ProjectRootId,
    pub contribution: T,
    pub state: StateUpdate, // Keep | Replace(StateValue) | Clear
    pub notices: Vec<PluginNotice>,
}

pub enum InferenceOutcome<T> {
    Accepted { contribution: T },
    Declined,
}

// infer_roots uses RootOutput<InferenceOutcome<...>>; only Accepted carries
// project/edge contributions. Separately typed supporting facts may accompany
// either outcome under §6.1; publishing facts never implies acceptance.
```

Snapshots are immutable invocation inputs. The host checks root ownership,
budgets and stage-allowed writes, then commits the entire validated stage
transaction. Workspace output can update workspace state only during
`on_workspace`. There is no plugin-visible `StateStore` or mutable shared
handle. Serialized state is an interchange/cache format, not a requirement to
encode/decode native state on every invocation.
`RootOutput<T>` is an ownership sketch, not permission to use arbitrary `T` in
every stage. Inference uses the tagged accepted/declined alternatives above;
the wire form carries an explicit outcome tag. Per-root state/notices and any
separately permitted supporting facts cannot substitute for that outcome or grant
project/edge payloads to `Declined`. The response validator also checks exactly
one result per assigned root; the enum alone cannot establish batch coverage.
The complete inference response includes a separately typed supporting-fact
channel associated with its assigned-root result. Accepted and declined outcomes
may publish permitted facts under [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle); do not place all facts inside the
accepted-only contribution payload or expose opaque private state as facts.

### 12.4 Host services (plugin side view)

```rust
pub trait TrackedInputs: Send + Sync {
    fn read(&self, path: &WorkspaceInputPath) -> Result<InputBytes, HostError>;
}

pub struct InferenceContext<'a> {
    pub inputs: &'a dyn TrackedInputs,
    pub state: &'a StateSnapshot,
    pub options: &'a PluginOptions,
    pub limits: &'a PluginLimits,
    pub cancellation: &'a Cancellation,
}
```

Only inference contexts expose file-content reads. Other contexts expose the
appropriate bounded file index, immutable assigned-root state or query service
over the authorized frozen facts/project snapshot ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)). Complete host snapshot
ownership does not imply copying it into each external request.
The input service owns containment, declared-scope checks, negative-read
tracking and allocation budgets. It never returns a raw filesystem handle or
absolute canonical paths. No context exposes immediate user-facing publication;
notices are transactional output values.

#### Reuse the capability policy core; enforce at the Wasm boundary

Security permission rules are distinct from protocol capability namespaces such
as `project_discovery`. Reuse `omni_capabilities` for permission policy, not as
an enforcement mechanism. It is runtime-neutral and has no engine dependency.
Define a discovery permission profile in `omni_plugin_configurations` with
`CapabilityProfile::SUPPORTED = &[CapabilityDomain::FsRead]`. Its selector and
evaluation context may scope rules to activations/stages; the host supplies that
context, never guest code. `PathRoots` already supports project/workspace roots,
and profile-aware schemas filter the domain enum. Validate every policy at load:
`SUPPORTED` restricts schema/validation, not the set of runtime operations a
caller can construct. Independently reject forbidden operations at the host ABI.

Use the existing shrink-only `evaluate_layered` engine for applicable host,
workspace and declared-input ceilings. Preserve policy levels rather than
concatenating their allow rules into one grant set. Include a nonempty host
read ceiling derived from approved scopes: empty levels are pass-through in
this evaluator, not deny-all boundaries. With no authorized inputs, expose no
read authority. Plugin declarations cannot widen host policy. Compile/cache
authorization for immutable invocation contexts where safe; avoid rebuilding
all rules for each byte/read or making batch size determine permissions.

Implement Wasm enforcement in `omni_plugin_runtime_wasm`: a validated import
allowlist, stage-specific host bindings, guest-memory checks and engine resource
limits. No ambient WASI, raw filesystem handles, environment, clocks, randomness,
network or process imports are linked. Unsupported imports fail loading, and
initialization/start functions run under the same budgets and stage restrictions
as hooks. Native handlers use the same logical input service without wire
marshalling, but remain trusted in-process code rather than sandboxed Wasm.

Expose a narrow system interface: tracked bounded file reads during inference,
plus authorized metadata/index views where stages permit them. Directory/index
queries must filter entries to authorized scopes, bound returned membership and
track it for invalidation; they are not raw filesystem traversal APIs. Artifact
module loading is a separate loader permission, not workspace-read authority
exposed to the guest. Do not register the generator's full bridge services.

The Wasm boundary authorizes host reads using the shared policy engine, then
performs containment-safe bounded I/O and records successful/missing inputs.
Reusing `CapabilityAuthorizer` or pieces of `omni_capability_sys` is appropriate,
but its broad `PolicyEnforcingSys` decorator is not the guest interface. It does
not provide discovery tracking or pre-allocation byte budgets, and its real-path
check documents a check/open symlink race. The discovery reader must enforce
containment at access time, not assume Wasm isolation protects unsafe host calls.

Do not inherit `CapabilityFloors` generator defaults (workspace read/write),
the experimental unconfined fallback, direct untracked read grants or permissive
`on_unenforceable` handling. Discovery's permission configuration must reject
unsupported fields/relaxations or constrain them to fail-closed values. A profile
currently filters domains, not every shared rule field, so add discovery-specific
validation/schema restrictions rather than assuming the profile alone suffices.

The current `omni_capability_enforcement` backend model returns process-oriented
`SpawnPolicy`/shim plans and classifies floors as runtime launch flags or OS
sandboxes. Do not disguise an embedded Wasm import boundary as a spawn backend
or claim the existing bridge descriptor installs it. Initially keep actual
Wasm enforcement with its runtime adapter and reuse policy/diagnostic concepts;
if a shared enforcement planner is needed, extend its mechanism model explicitly
to represent embedded-runtime/import confinement and its verified coverage.

File decoding/deserialization helpers are candidates, not required host imports.
Prefer SDK-side parsing of tracked bytes initially. Any future host JSON/TOML/YAML
helper must use the same authorized tracked read path, bound parser work/depth,
allocation and output, forbid external includes/entity resolution or executable
extensions, and version its observable parsing semantics. Host parser CPU and
allocations are outside Wasm fuel/linear memory and need separate budgets; add
such helpers only when benchmarks justify their host ABI and maintenance cost.

### 12.5 Runtime adapters

External runtimes implement the same logical capability calls through the selected
interchange/binding mechanism and enforce budgets. The adapter owns module/instance
handles. Keep reusable Wasm engine mechanics below discovery-specific capability
adapters; a future generator/tool adapter may reuse that foundation without
depending on project discovery or receiving its state/services. Plugin-private
memory may be reused under [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)'s observational contract, but is never the
authority for session progress or a prerequisite for restoring cached results.

The byte-oriented interface below is illustrative, not a decision against the
Component Model ([§10](010.00-implementation-and-rollout.md#10-implementation-and-rollout)). Generated typed component bindings may implement the same
logical boundary if prototype evidence favors them. Preserve the shared logical
data contract without requiring a redundant encoded-byte round trip solely to
match this sketch.

```rust
pub trait RuntimeAdapter: Send + Sync {
    fn kind(&self) -> RuntimeKind;
    fn invoke_hook(
        &self,
        module: &ModuleHandle,
        hook: &HookId, // validated namespace + stage + capability version
        request_bytes: &[u8],
        state_bytes: &[u8], // bounded workspace seed + assigned-root state view
        services: &InvocationServices<'_>, // stage-scoped, tracked host imports
        limits: &PluginLimits,
    ) -> Result<Vec<u8>, PluginError>; // encoded stage-specific output,
                                      // including allowed state updates/notices
}
```

### 12.6 Hook dispatch (host side)

The host keeps heterogeneous registered handlers as typed trait objects, not a
generic `dispatch<C>` trait. The scheduler matches the registered capability and
stage to its typed request, calls the corresponding method, validates the
stage-specific output and commits a stage transaction. Request/stage mismatches
must not be representable in the typed native call path. External adapters
validate the same pair at the wire boundary.

Adding a capability adds its own trait, registration entry, stage types and
namespace. Existing capability traits and hook names do not change.
