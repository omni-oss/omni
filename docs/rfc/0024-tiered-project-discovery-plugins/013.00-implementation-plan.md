## 13. Implementation plan

### 13.1 New crates

| Crate | Purpose |
| --- | --- |
| `omni_source_configurations` | Shared generic source/profile definitions extracted from `omni_configurations`, with compatibility re-exports there |
| `omni_plugin_configurations` | Activation/source declarations, manifests, capability/version/hook declarations, options and limit configuration; data only |
| `omni_plugin` | Runtime-neutral contract: typed handlers/registration, requests/results, state views/updates, host-service interfaces and errors |
| `omni_plugin_host` | Scheduling, batching, negotiated capabilities, transactional state/notices, budgets, cancellation and inference-cache orchestration |
| `omni_plugin_builtins` | Initial native JavaScript and Rust handlers, compiled into omni |
| `omni_plugin_runtime_wasm` | Later: discovery/plugin adapter over reusable Wasm engine mechanics, with fuel/epoch/memory limits; preserve potential generator/tool reuse without sharing authority ([§10](010.00-implementation-and-rollout.md#10-implementation-and-rollout)) |
| `omni_plugin_runtime_js` | Later: JavaScript adapter with interrupt/heap limits |

Extract shared source types, scaffold the configuration/contract/host foundations, then the native
pilot. Create runtime crates when implementing their adapters, not as empty
placeholders. No runtime engine dependency belongs in the contract.

The reusable Wasm foundation may begin as a clearly separated module or become a
lower-level crate when justified by implementation/prototype evidence. Do not
force generator/tool consumers to depend on discovery/configuration graphs, and
do not introduce empty future-consumer crates or integrations merely to demonstrate
reuse. Keep profile-specific host-service installation outside the engine core.

Dependency direction (`A -> B` means A depends on B):

```text
omni_source_configurations -> existing low-level config/path/URL types
omni_plugin_configurations -> omni_source_configurations
omni_plugin_configurations -> omni_capabilities (discovery permission profile)
omni_configurations -> omni_source_configurations + omni_plugin_configurations
omni_plugin -> omni_plugin_configurations + omni_configurations
omni_plugin_host -> omni_plugin + existing source/cache services
omni_plugin_builtins -> omni_plugin + ecosystem parsers
omni_plugin_runtime_{wasm,js} -> omni_plugin + respective engine
omni_context -> omni_plugin_host + omni_configurations
CLI/MCP composition roots -> context + builtins + enabled runtime adapters
```

`omni_configurations` owns recursive project/task/cache/env layer types and the
restricted plugin-contribution types that reuse them without allowing
host-managed fields or project-file `extends` paths ([§6.3](006.03-data-boundary-and-literal-values.md#63-data-boundary)). `omni_plugin` uses
those types in hook results;
`omni_configurations` never depends on `omni_plugin` or the host. Manifest and
activation types have exactly one owner: `omni_plugin_configurations`. Keep
that crate independent of the contract and project configurations, preventing a
dependency cycle. Use existing low-level types for paths/globs where needed.
Extract generic `SourceConfig`, its variants and `SourceConfigProfile` into
`omni_source_configurations` first; preserve existing import paths through
re-exports. Subsystem-specific profiles and validators stay with their owners.
Plugin configuration owns its external-source profile and builtin wrapper;
adding `builtin` for plugins does not add it to every subsystem's source enum.

The host accepts a registry supplied by the CLI/MCP composition root; it does
not import concrete builtins or engine adapters. No-plugin invocations need not
initialize them. Source contributors bridge existing local/git materialization
to descriptors; capability negotiation precedes hook scheduling.

### 13.3 Phases

   - Land `omni_plugin_configurations`, then `omni_plugin` types and typed
     capability registration, with required/optional negotiation tests.

     and execution. No manifest or dependency implicitly adds activation entries.

     pre-hook graph validation ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)). Finalize the facts-only schemas and query/
     authorization contract before fixing dependent-inference request/host-service
     types; inferred/effective configuration is not an exposed dependency surface.
   - Add `inference` controls to `ProjectConfiguration`.
   - Add standard activation-level `apply`, shared extension-closure traversal,
     tracked raw-layer replay and activation-scoped existing-task patching ([§7.1](007.00-project-modes-and-apply.md#71-project-modes)).
     Apply files within each activation in declared list/extension order, then
     combine activation contributions under the shared conflict rules. Preserve
     inferred-value trust restrictions and silent unmatched-patch inspection.
     Use standard collection validators for applied files, including replacement;
     test inferred → applied `replace` → explicit omission/append/prepend/replace,
     extension-closure replay, dictionary operations and task scoping. Direct plugin
     output remains additive-only and inherited inferred environment values stay literal.
     Test empty `apply` by default, no automatic plugin-shipped files, workspace
     declaration-relative paths, nested per-file `extends` origins and shared

     input/output settings must keep their intended roots without changing project
     directories or reading a default config as though it were a project manifest.
     Cover multiple activations' disjoint task patches, conflicting shared fields,
     activation-local subtraction preserving another contributor's dependencies,
     global replacement by later explicit layers and operation-preserving task
     inheritance. Reordered execution/loading must not select conflict winners.
     Verify applied own/upstream/cross-project unqualified references retain
     originating-activation binding through file/task inheritance and caches;
     changed public aliases cannot redirect them. Explicit qualified cross-plugin
     targets in workspace-authored files remain valid/strict, absent local-script
     rules retain their documented handling, and source patches cannot modify
     another activation's tasks or grant plugin-emitted cross-plugin authority.
   - Introduce recursive presence-aware layers, including tasks/cache/env,
     preserving omission, explicit values and existing merge operators.
   - Replace eager explicit-file deserialization with layer loading; preserve
     extension closure, per-layer path origins, aliases and existing ordering.
     Apply defaults and final validation only after all applicable project/task
     composition and inheritance, including project-to-task settings.
   - Implement conflict detection and provenance tracking.
   - Implement structured scoped task identity, one shared full-input parser/
     formatter and qualified object schemas under [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics),
     [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases) and
     [§17.8](017.00-review-findings-and-prerequisites.md#178-scoped-object-references-and-alias-aware-selectors). Preserve raw
     plugin/object components and activation-bound inferred references.
   - Implement consistent field-level normal-task composition, expanding
     shorthand without eager defaults ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)), atomic normal-task/alias transitions
     ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)), and alias-aware inheritance.
   - Define the literal command-operand contract and boundary/round-trip fixtures
     before adapter command generation. Existing argv strings still expand Tera/
     environment syntax; include expression-to-data transitions and display/hash
     paths rather than treating structured argv as sufficient by itself.
   - Validate collection-envelope shape before the shared decoders can discard
     siblings, then apply the selected field/operator validator. Test malformed
     hidden declarations and document the pre-v1 validation correction.
   - Add per-project alias indexes, exact positional selection, repeatable
     `--task-pattern` selection and per-target upstream lowering before executable
     graphs ([§17.8](017.00-review-findings-and-prerequisites.md#178-scoped-object-references-and-alias-aware-selectors)). Permit pattern-only requests and union/deduplicate mixed
     selectors; add CLI/MCP schema, escape and migration fixtures. Preserve the

     Migrate generated/internal globs too, including the cache store's all-task

### 13.4 Integration points in current plumbing

- `omni_context::ProjectDiscovery` remains the single ignore-aware walker. Add
  plugin marker names to the same walk; do not add per-plugin walkers.
- `Context::discover_project_paths` builds candidate roots and explicit files.
  Plugin scheduling happens after explicit inference controls are read.
- `Context::load_discovered_project_configs` becomes:
  1. Load explicit files and their extension closure into recursive layers,
     preserving field presence and path origins rather than applying defaults.
   2. Apply root-local replacement/base exclusions, allowlists and filter
      dispositions, then invoke registered inference hooks only for eligible
      assigned roots using frozen stage snapshots and transactional output commits.
   3. Freeze inference fragments, then invoke dependency hooks for eligible
      activation/root participants under [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle). They return root-based edges;
      no later plugin stage may edit project fields.
   4. Compose inference/application layers within each activation, combine their
      contributions beneath explicit extension/concrete layers, then resolve
      aliases before task inheritance ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)), then task extensions and
      project/task settings with presence preserved. Apply defaults, resolve
      surviving project edges and lower task references, then validate.
   5. Run optional read-only observation hooks, revalidate the pass input view,
      then publish accepted cache entries/notices and return effective projects.
      Rejected passes execute no tasks and expose no new reusable entries.
- Refactor `ProjectConfigLoader` to expose layer loading and closure/path
  resolution. Retaining its current eager `ProjectConfiguration::load` path for
   plugin-enabled composition would lose presence and reject inferred names too
   early. A no-plugin entry point finalizes the same layers with [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)'s corrected
   inheritance semantics, not a legacy eager-default compatibility mode.
- Inference-cache identity includes plugin artifact/module fingerprints,
  options and tracked dependencies ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)). Task execution identity retains its
  existing inputs plus the fine-grained effective semantic contribution ([§8.3](008.02-execution-cache-semantic-identity.md#83-fine-grained-execution-cache-integration)),
  not a blanket plugin-artifact/project fingerprint.

### 13.5 Risky changes requiring care

- Virtual project identity touches discovery classification and location-aware
  inspection boundaries, not ordinary effective-task consumers or an additional
  virtual-path task-cache input. Distinguish logical ids from optional physical
  config files;
  `dir` remains the real project root, never a synthetic directory. Never pass
  a logical config id into file-read APIs. Reuse the core graph's associated
  identity type rather than assuming the generic trait itself must change.
- Presence-aware deserialization is a schema/loader change; tests must cover
  absence vs default values.
- Plugin output must be validated before entering graph state; malformed output
  is fatal.
- Do not reuse stale inferred output after a failed or changed run.

### 13.6 Definition of done for v1

- No enabled plugins: equivalent discovery selection except the documented
  duplicate-explicit-file rejection ([§6.2](006.02-discovery-pipeline-and-lockfiles.md#62-pipeline)), plus unchanged extension ordering/path
  resolution and ignore/cache exclusions. Presence-aware explicit inheritance
  uses the documented pre-v1 correction in [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics), with migration examples and
  regression tests rather than blanket effective-configuration parity.
- JavaScript and Rust builtins discover projects without per-project omni files,
  with correct names, tasks and local dependency edges. JavaScript fixtures cover
  npm, Yarn, pnpm and Bun, including workspace and package-manager ambiguity;
   Rust fixtures cover Cargo packages/workspaces and [§4.3](004.01-native-ecosystem-adapters.md#43-initial-native-ecosystem-plugins)'s normal/build versus
   development-only project-edge policy, potential optional/target-specific normal/
   build dependencies and documented conservative graph limitations.
   Both use manifest roots
  with tracked lockfile-assisted inference, not lockfile-only project creation.
- Extend/replace and allowlists work; conflicts are deterministic.
- Wasm conformance fixtures match native output. JavaScript runtime delivery is
  deferred and is not a v1 requirement of this RFC.
- Benchmarks meet proposed budgets or revised documented budgets.
- CLI and MCP expose effective provenance and cache status.
