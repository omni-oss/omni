### 4.3 Initial native ecosystem plugins

Name builtins consistently by ecosystem, not by a mix of language and tool:

- **`@omni/javascript`** initially discovers JavaScript/TypeScript projects from
  `package.json`, inferring package names, scripts, workspace membership and
  local dependency edges. npm, Yarn, pnpm and Bun are supported package-manager
  choices within this plugin, not separate discovery plugins. Package-manager
  detection selects task commands without running installs or scripts during
  discovery. The precedence and ambiguity policies below are settled; concrete
  format/version coverage and ownership evidence belong in the adapter specification.
- **`@omni/rust`** initially discovers Cargo projects from `Cargo.toml`, including
  workspace membership and local dependency edges, and infers ordinary Cargo
  task definitions. It is not a promise to support every Rust build system or
  every Cargo feature in the first release.

For `@omni/javascript`, choose the package manager in this order:

1. An explicit package-manager option for the activation.
2. The applicable package/workspace manifest's `packageManager` declaration.
3. A uniquely identified manager from the relevant lockfiles.
4. npm when no declaration or identifying lockfile is present.

If relevant lockfiles indicate multiple managers and no stronger explicit choice
resolves the ambiguity, fail with an actionable diagnostic rather than selecting
by filename/traversal order. Unsupported selected declarations and failures to
read required inputs do not silently fall through to npm. Detection uses only
authorized tracked reads, misses and membership observations; never execute a
manager, version probe, install or script to decide. The adapter specification
must implement the workspace-context rules below and define concrete ecosystem
ownership/detection fixtures before implementation.
Precedence does not promise that all lockfile formats/versions are supported.

Determine relevant manager declarations/lockfiles from verified ecosystem-workspace
ownership, not directory ancestry alone. A standalone package uses its own
declarations and lockfiles; a member may also use those of its confirmed owning
workspace. A genuine nested ecosystem workspace forms a separate manager-selection
context rather than inheriting an outer context merely because it is nested.
An unrelated ancestor declaration/lockfile does not select the package's manager.
Ownership must be established from ecosystem declarations and authorized tracked
inputs/membership observations, not “first matching ancestor wins.” Supporting
workspace roots need not be selected runnable projects, but reads remain within
declared permissions and the omni workspace; ownership never widens project
selection or revives skipped inference.

Within one verified context, conflicting manager declarations fail actionably
unless an explicit activation option resolves the choice. Report the conflicting
locations rather than silently preferring the child or parent manifest. Use the
chosen context's relevant lockfiles only at the lockfile tier of the precedence
rule above. The adapter specification must enumerate supported ownership evidence,
nested-workspace boundaries and ambiguity handling for npm/Yarn/pnpm/Bun; these
policy rules do not assume that each manager has identical workspace semantics.

Both are opt-in native handlers using `project_discovery` and the same lifecycle
and host services as external plugins. Ecosystem names leave room for future
manifest support without renaming; they do not imply that additional formats
are supported today. Keep detailed ecosystem inference rules and fixtures with
each adapter, separate from the generic contract.

Separate JavaScript and Rust adapter specifications plus representative fixtures
are prerequisites to implementing the native pilots. Each must define dependency
kind mapping (including development/build/optional/target-specific relationships),
local versus external resolution, task naming and upstream scheduling, manager/
workspace detection precedence, and supported/unsupported feature behavior.
Do not turn every ecosystem relationship into an unconditional omni project
edge: valid Cargo development-dependency layouts can contain cycles that omni's
project graph rejects. Explicitly specify which relationships are included,
omitted with notices or require another representation; never silently drop
arbitrary edges merely to make the graph acyclic.

For the initial Cargo adapter, confirmed workspace-local normal and build
dependencies may contribute omni project edges; development-only dependencies
do not contribute automatic project edges. Retain development relationship
information inside the adapter for correct ecosystem interpretation rather than
pretending it was absent from the manifest. If a pair also has a supported normal/
build relationship, omitting its development relationship does not erase that
independently justified edge. This is a category policy applied consistently,
not opportunistic edge removal only when a cycle appears. Surviving cycles among
included relationships remain errors unless resolved through ordinary explicit
composition; never pick an arbitrary edge to discard.

Omitted development relationships must not cause missed tests: if `A` has a
development dependency on `B`, a change to `B` must still be able to select `A`'s
tests under dependent-expanding affected selection. Preserve them as bounded
`package_dependency` claims (resolution `workspace`, concrete root, no project edge)
that feed a cycle-tolerant **impact relation** used only for selection, never for
scheduling or cycle validation. Until that mechanism exists, dependent-expanding
selection falls back conservatively to including projects with any retained
workspace relationship to a changed project. Expansion is transitive: iterate
cycle-safely to a fixed point across retained relationships and project edges, so `A`
(dev-depends on `B`) is selected when `B` dev-depends on changed `C`. A notice alone is
not sufficient.
Users may also add explicit project relationships, subject to normal cycle validation.

Within the included normal/build categories, infer confirmed workspace-local
relationships regardless of optionality or target-specific conditions. Treat
them as potential project dependencies rather than predicting which feature set
or target will make them effective in a later Cargo invocation. Do not prune
them using the discovery machine's current platform, guessed task arguments or
default-feature assumptions. Development-only relationships remain omitted under
the category policy above, including optional/target-specific development cases.
Repeated relationships to the same resolved root normalize to one project edge.

This conservative graph may over-include projects in affected/dependent selection;
document that limitation rather than claiming invocation-specific precision.
Surviving conditional/optional edges obey the same target-existence and cycle
validation as other included edges, with ordinary explicit replacement available
before final validation. Discovery does not execute Cargo to determine activation.
Project edges do not manufacture task edges, and selected Cargo commands still
use Cargo's ordinary execution-time feature/target/dependency orchestration. A
future active-context graph would require a separate explicit feature/target and
invalidation design; it is not an implementation prerequisite for this RFC.

For accepted Cargo package roots, initially infer `build`, `check` and `test`
tasks using the corresponding ordinary Cargo subcommands. These are
scoped inferred tasks, with no automatic omni task dependencies and no built-in
`cache.enabled` value. Applied and explicit configuration may customize them
under the shared composition rules. Automatic `fmt` and `clippy` inference is
deferred; neither is part of the initial task set. Users may define formatting
and linting tasks in ordinary explicit project configuration. Revisit their
inference, command targeting and cache safety in a later adapter extension.

Do not probe Cargo/rustup or installed components during discovery, auto-install
rustfmt/Clippy, or vary inferred task availability based on ambient installations.
Missing tools/components for a user-authored task fail through ordinary execution;
discovery neither installs them nor changes the initial inferred set. This initial
task set also does not promise automatic `run`, `bench`, `clean` or arbitrary Cargo
alias/subcommand inference.

Target each inferred Cargo task explicitly at its accepted package, using both
the package manifest and declared Cargo package name, with the real project root
as the working directory. For example, use structured argv equivalent to
`cargo build --manifest-path Cargo.toml --package core`; apply equivalent targeting
to `check` and `test`. The Cargo name is ecosystem data, not the omni
project's final name, scoped task name or requested alias. Explicit omni renaming
must not redirect package selection. Use each supported subcommand's correct
argument/separator syntax; concrete version/argv conformance remains adapter work.

Do not broaden inferred defaults with `--workspace`, `--all`, `--all-features`,
`--all-targets` or similar selection flags. Cargo still performs its ordinary
dependency work for the selected package; explicit targeting is not a promise to
build no dependencies. Selecting several omni projects must not cause each task
to repeat an inferred workspace-wide command. Users can deliberately configure
workspace-wide variants in explicit project/task configuration.

For accepted JavaScript roots, prefer the declared `package.json` name as the
inferred omni project name. If the manifest omits a name, fall back to the
normalized workspace-relative root path, such as `packages/web`, using `.` for
the workspace root. Do not use only the directory basename or append numeric
suffixes to avoid collisions. Invalid declared names follow the adapter's normal
validation rules rather than silently triggering the missing-name fallback.
Explicit project/base/application configuration may supply a different final
omni name under the ordinary composition rules; final duplicate project names
still fail.

This fallback names an omni project only. It does not manufacture an ecosystem
package name or `package_identity` claim, nor establish local dependency identity
from a directory name. Preserve root-based references through explicit renames.
The rule does not turn a Cargo aggregate workspace manifest into a package or
bypass candidate acceptance, runnable classification or project selection.

For the initial JavaScript adapter, include confirmed workspace-local relationships
from `dependencies`, `devDependencies` and `optionalDependencies` as project edges.
Local development tooling such as compiler plugins or code generators may affect
their consumers, so do not omit a confirmed local relationship merely because it
is development-only. Optionality does not remove the potential relationship. Use
actual ecosystem resolution evidence, not name matching, to distinguish local
packages from same-named external packages. Normalize repeated resolved target
roots to one edge.

**Partial workspaces (JavaScript and Cargo).** Emit a project edge only to a root
that is a selected project in the final catalog (a selected plugin candidate or a
selected explicit-only project; final runnable-target validation still applies). When project selection excludes a
confirmed local dependency, retain the relationship as claim evidence (resolution
`workspace`, concrete root, no edge) instead of an edge that final target validation
would reject, and surface a bounded notice. Fixtures: `projects` selects
`packages/app` but excludes workspace dependency `packages/lib`, for both adapters,
yields no invalid edge, no discovery failure and the retained evidence. Evidence for an
excluded root also seeds impact: a changed path under `packages/lib` selects `app`'s
tasks under affected-with-dependents by mapping the path through the retained claim
to its dependents, without creating a `lib` project or task node. Because inference
runs only for selected candidates, an excluded root publishes no dependency claims of
its own, so evidence from selected projects alone cannot connect `app` -> excluded `lib`
-> selected `core`. When the host cannot establish that transitive evidence from
bounded authorized supporting manifest reads of the excluded root, fall back
conservatively to treating every selected project with a relationship to any excluded
root as impacted by a change under **any excluded root or any selected project**, so
`app` -> excluded `lib` -> excluded `core` still selects `app` when `core` changes. If
even this bounded fallback cannot be computed, fail dependent-expanding selection with
an actionable diagnostic rather than return an incomplete selection. Add both chains
(selected and excluded `core`), the direct case,
and an edge to a selected explicit-only project, to the fixtures.

Include peer-dependency project edges only when authorized tracked manifest/
lockfile resolution evidence establishes a concrete workspace-local supplier.
A peer declaration, matching name or merely compatible workspace package version
does not by itself prove which package supplies the peer. External peers contribute
no local project edge. Unresolved peers contribute no guessed edge; preserve their
unresolved dependency claims and expose the graph limitation through bounded
notices/inspection. Optional peers use the same evidence rule rather than being
unconditionally omitted or included. Deduplicate confirmed local peer targets with
other relationships to the same root, and validate surviving targets/cycles after
application/explicit composition as usual. No package-manager invocation is allowed
to discover the supplier during inference.

Unsupported required inputs, parse failures, denied reads and resource failures
remain errors; never disguise them as an unresolved peer or empty successful
resolution. The adapter specification must define concrete supplier evidence for
each supported manager/format. This is an evidence-based inclusion policy, not a
promise of Turborepo/Nx behavior compatibility or a name/version-only fallback.

JavaScript ecosystem dependency cycles can be valid while omni project cycles are
not. Surviving included cycles fail after ordinary composition/target validation;
users may adjust the activation's edges through workspace-selected applied files
or later explicit configuration. Do not drop arbitrary development/optional edges
to force acyclicity. Document the policy and its graph-filter implications rather
than claiming complete ecosystem compatibility. This differs deliberately from
Cargo's development-only omission; adapter policies need not map categories
identically. Project-edge inference still adds no automatic task dependencies.

Infer all valid declared `package.json.scripts` entries by default, not only a
shortlist of conventional names. Preserve each raw local script name, including
custom names such as `generate-client` or `check:translations`; omni scopes and
escapes task references without renaming the underlying script. Lifecycle-named
scripts such as `prebuild` remain selectable inferred tasks, but their presence
adds no automatic omni task dependencies and discovering them never executes
them. Workspace-selected application files customize eligible inferred tasks;
inference-specific options may narrow script selection. Invalid script declarations
receive normal adapter diagnostics rather than silently disappearing. Define
concrete selection-option schemas and script validation fixtures in the adapter
specification without changing this all-valid-scripts default.

Infer JavaScript script commands through the selected package manager's explicit
script-runner mechanism, not by copying script bodies into omni `exec`. For a
`build: "vite build"` script with pnpm selected, infer the logical command
`pnpm run build`. Preserve the manager's ordinary script environment, executable
lookup and lifecycle behavior rather than reproducing them in omni. This describes
selected task execution only; discovery never invokes the manager. Manager-driven
lifecycle scripts do not become inferred omni task dependencies.

Use structured argv and manager-specific argument/separator rules so raw script
names, including option-looking or delimiter-containing names, cannot become shell
syntax or unintended manager flags. Do not shell-concatenate ecosystem names or
reparse omni-qualified/escaped display names as script names. Concrete invocation
forms and supported manager/version behavior require adapter fixtures.
Structured argv alone is not enough: today's command resolver still expands Tera
and environment syntax in each argv element. Preserve ecosystem-derived operands
as literal command data under [§6.3](006.03-data-boundary-and-literal-values.md#literal-command-operands),
including through command validation, cache round trips and execution/display.

Contribute the executing package's `package.json` as an explicit task-cache file
input. A script-body edit changes execution even when inferred argv remains
`pnpm run build`; lifecycle/environment changes in that manifest matter too.
Observed inference reads alone are not automatic task-cache inputs ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)).
Declare this manifest input as real task-cache input configuration, not merely a
default-file input that vanishes with `cache.key.defaults: false`. Applied and
explicit configuration retain their ordinary input-list override authority; do
not invent a plugin-private execution-cache bypass. Further relevant workspace/
manager files and output policies remain the adapter's correctness responsibility.

Specify inferred task form and dependencies explicitly rather than accidentally
inheriting shorthand behavior: today's short-form task adds an implicit upstream
self-task dependency, while long-form tasks need that relationship declared.
Fixtures must verify intended scheduling and explicit overrides, not just
inferred command strings. Package-manager detection must remain read-only and
deterministic. Keep these ecosystem policy decisions outside the generic hook
contract while requiring them before adapter implementation.

Built-in plugins infer no task-to-task dependencies by default, including no
automatic upstream `build` relationship. Ecosystem project-dependency inference
is separate and does not itself schedule upstream tasks. Because the planner
traverses task edges, dependent-expanding affected selection must not rely on them:
select dependents through the project/impact relation above (project edges plus
retained dependency evidence) without adding any task ordering. Fixture: with `app`
depending on `lib` and no task edges, a change in `lib` selects `app`'s inferred
`test` under affected-with-dependents, and execution order is unchanged. Emit normal long-form
task patches without accidental shorthand upstream sugar; commands may still use
their ecosystem tool's own ordinary dependency orchestration when executed.

Plugins may infer task inputs, outputs and caching policies suited to the
workspace. Built-in adapters emit no `cache.enabled` value, so inferred tasks are
uncached by default through the host fallback `false` (see
[§7.1](007.00-project-modes-and-apply.md#standard-host-managed-defaults)), not
through a hard value on every task. That fallback is the lowest tier: workspace
`defaults`, `apply`, explicit configuration or an opinionated plugin value can
opt a task in, subject to the documented tier order. Handwritten tasks keep their
ordinary default. This does not change inference-cache enablement. Concrete
input/output inference remains an adapter correctness responsibility; do not infer
cache safety merely from task names, and do not claim discovery certifies it.
Reuse `defaults`, applied and explicit configuration for user cache choices rather
than adding a duplicate inline task-cache settings language to plugin options.

Use workspace-selected `apply` files for opt-in task wiring, not a second
`options.task_dependencies` language. For example, the activation selects
`./configs/javascript-defaults.omni.yaml` through its standard `apply` list;
that file may contain:

```yaml
tasks:
  build:
    dependencies: ["^build"]
  test:
    dependencies: [build]
```

Here an inferred `build` script may depend on upstream `build` scripts, and an
inferred `test` script may depend on its package's inferred `build` script. The
host applies the existing-task and missing-local-target rules in
[§7.1](007.00-project-modes-and-apply.md#71-project-modes); no task is manufactured
for an absent or selection-filtered script. Upstream missing tasks retain their
ordinary skip rule. Applied references bind to the originating activation unless
the workspace author deliberately qualifies a cross-plugin target.

This permissive handling occurs while evaluating applied inference-wiring rules,
not when validating ordinary explicit references or direct plugin-emitted output.
Malformed configuration and surviving cycles remain errors. A later explicit
removal does not turn an already retained direct reference into an optional one.
Cargo uses its inferred task set, not a fictional scripts map, for the same
host-managed application rules. Third-party plugins retain their documented
inference behavior; no adapter-specific task-settings language is required.

The initial plugins use **manifest-based project roots with lockfile-assisted
inference**, not lockfile-only projects. JavaScript inputs may include
`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` and legacy
`bun.lockb`; Rust inputs may include `Cargo.lock`. Declare only formats the
adapter can parse safely and document actual format/version coverage. These
examples are not a promise that every lockfile version is supported initially.
Lockfiles enrich workspace/dependency resolution but do not replace project
manifests as the source of names, scripts or task definitions.
