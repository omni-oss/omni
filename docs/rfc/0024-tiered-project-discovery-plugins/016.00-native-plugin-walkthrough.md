## 16. End-to-end native plugin walkthrough

This is a narrated simulation of the proposed design, not a description of
functionality already implemented. Assume a workspace explicitly enables
`@omni/javascript` and `@omni/rust`, omitting their consumer ids, and contains:

- `packages/web/package.json` with a build script.
- `packages/web/project.omni.yaml` extending inference and overriding only the
  qualified JavaScript build command ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).
- `crates/core/Cargo.toml` describing a Rust package.
- Relevant workspace manifests and lockfiles.

The user asks omni to run the web project's build task.

### 16.1 Bootstrap and bind handlers

Omni finds and loads `workspace.omni.yaml`, including project selection and
explicit plugin activation. The effective ids default to `@omni/javascript`
and `@omni/rust`.

Their native implementations are already compiled into omni; nothing is
downloaded. Other compiled-in plugins remain inactive. Omni looks up the two
builtin descriptors, negotiates protocol/capability versions and validates
handler registrations, supported hooks and effective-id uniqueness before any
hook runs. Each handler is bound to its activation options, budgets and host-owned
state namespace.
Any declared inference-dependency slots are bound and checked for compatibility
and cycles here as well; missing producers are not enabled or fetched implicitly.

Omni captures the pass's explicit layers, marker selection and tracked input view
under [§17.2](017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs). Stage commits below remain private to this pass until final input
revalidation succeeds; they are not yet reusable cache entries or published notices.

### 16.2 Index candidates once

The shared ignore-aware walk indexes explicit project files and the enabled
plugins' markers. It finds the JavaScript and Cargo manifests. Lockfiles are
available as declared supporting inputs or candidate triggers, not automatic
project roots. Every candidate still obeys workspace selection, exclusions and
containment rules.

### 16.3 Read explicit configuration layers

Omni loads the web file and its explicit extension closure into recursive
presence-aware layers. Web extends inference and overrides its qualified
JavaScript build command;
other omitted fields remain absent instead of becoming default values.

If web specified `inference: {mode: replace}`, omni would exclude that root
from inference. Workspace inputs shared with other inferred roots may still be
read where authorized; replacement skips contributions for a root, not all
interpretation of its surrounding ecosystem.

### 16.4 Initialize sessions

Omni creates separate workspace/root state partitions for each plugin's
discovery capability. Registered `on_workspace` hooks receive options and static
scopes, without file-content access. Omni validates and commits their workspace
state seeds. Handlers may keep transparent private caches, but authoritative
session progress remains in host-owned state and cannot require instance reuse.

### 16.5 Filter candidates

Each registered filter hook receives its relevant candidate batches and bounded
file index. The JavaScript handler retains `package.json` candidates; the Rust
handler retains `Cargo.toml` candidates. Filtering can reject roots using the
authorized index, but distinguishing aggregate-only manifests by their contents
waits for inference: filtering has no file-content service. No package manager
or Cargo command runs.

### 16.6 Infer project fragments

Omni batches `infer_roots` calls as efficiently as permitted. Bound producers
finish all their validated inference before consumers start, exposing only their
authorized frozen published-claim views; these predecessor results remain private
to the inference stage/pass. Otherwise-ready activations use workspace declaration
order, not registry order or an override-precedence rule. The JavaScript
handler reads `package.json` and relevant declared workspace/lockfile inputs
through the tracked input service. It explicitly accepts or declines each assigned
root and returns permitted names, raw local script task definitions, dependency
claims, root-state updates and notices. The Rust handler similarly reports
dispositions and contributions derived from Cargo inputs. A decline remains
binding even if another plugin or an explicit file establishes that project;
state or claims alone cannot create a project.

Both describe commands; neither executes them. Workspace state and stage-start
root state are immutable inputs. Each invocation may return writes only for its
assigned roots, independent of batch neighbors and invocation order.

### 16.7 Commit the inference stage

Omni validates root ownership, configuration fields, budgets, state updates and
notices. Parallel batches cannot overwrite one another's roots. Only after all
required invocations succeed does omni atomically commit that stage's results.
A failed/cancelled stage publishes no partial state, contributions or notices;
retrying uses the same stage-start snapshot.

### 16.8 Resolve local dependencies

Omni freezes the inference snapshot and invokes registered dependency hooks only
for eligible activation/root participants under [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle), not declined roots or
implicitly accepted omitted inference hooks.
They receive assigned-root state and query the shared frozen published claims
through bounded bulk lookups, without copying every root into each request.
They return workspace-local root references,
not guessed final names. Registry dependencies do not become omni project
edges. Resolution can target host-approved explicit-only project roots as well
as inferred roots: the read-only root catalog includes both. Supporting ecosystem
identity for a replacement root must already come from authorized tracked reads
during another root's inference, not new resolution-stage reads. Cross-plugin
project edges are supported; selecting another activation's task remains explicit
configuration's responsibility. No dependency hook may edit project fragments
after their freeze.

### 16.9 Compose effective projects

For each root, omni applies each activation's configured files to that activation's
inference, combines the contributions using conflict rules, then replays explicit
base layers and the concrete explicit file. The qualified JavaScript build command override
wins; other inferred fields
survive according to the shared merge rules. Conflicting contributions without
an explicit resolution fail deterministically.

Omni generates/resolves aliases before task inheritance ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)), then resolves
task extensions and applicable project/task settings while retaining
presence/operations, then applies defaults. It resolves root-based edges to final
project names and validates configuration and graph
invariants. Renaming web explicitly does not break root-based references to it.
Task references retain their originating activation through inheritance/lowering;
explicit replacement can discard references before target-existence validation.
For example, the unique eligible `@omni/javascript::build` receives the public
`build` alias unless an explicit declaration occupies that name. Overriding its
qualified command affects every alias; a named task using `extends` instead
creates a distinct task, not another alias.

### 16.10 Observe the frozen result

Registered observation hooks can inspect the final frozen projects/dependencies
and return notices or inspection metadata. They cannot change project fields,
edges or session state. Their outputs are validated and committed transactionally
like other stage results.

Omni then revalidates captured content, missing paths, membership and selection.
Only an accepted pass publishes new reusable inference entries and user-facing
notices. A detected change rejects the pass by default and executes no tasks;
optional bounded whole-pass restarts remain disabled unless explicitly enabled.

### 16.11 Use the normal execution pipeline

The planner receives ordinary effective projects and tasks, not separate plugin
execution paths. Omni selects web's exact `build` name through its alias index;
an explicit `--task-pattern` would instead match public canonical/alias names.
Both inputs share the existing filters and canonical deduplication, not a separate
planner. Omni computes/checks the selected task's execution-cache identity,
including the named effective semantic digest, and runs it through the existing
executor and policies.
During configuration/environment lowering, inferred environment values remain
literal under [§6.3](006.03-data-boundary-and-literal-values.md#63-data-boundary); host expansion cannot become a discovery sandbox escape.
The discovery plugin is not the task executor. Inference changes participate in
effective configuration identity so an old result cannot mask a changed task.

### 16.12 Reuse work on the next command

Omni checks tracked inputs, options, builtin/build identity, negotiated versions,
incoming state and relevant snapshots. Matching cached hook results can be
restored without invoking handlers. Input edits invalidate dependent results;
cross-root resolution also invalidates when its frozen catalog/claims change.
Long-lived MCP sessions use the same invalidation rules as CLI invocations.

In short: plugins contribute claims and configuration at defined stages; omni
owns discovery boundaries, scheduling, state, composition, caching and execution.
