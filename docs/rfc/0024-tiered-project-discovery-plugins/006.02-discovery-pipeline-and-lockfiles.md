### 6.2 Pipeline

1. Load workspace config and validate explicit activation. With no enabled
   plugins, initialize no runtime and recognize only ordinary explicit files;
   still use the shared validation and corrected layer pipeline ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
2. Resolve enabled plugin descriptors. Compile their marker/input globs with
   the shared glob model, not one glob implementation per runtime. Validate
   inference-dependency slots, activation bindings and cycles before hooks ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)).
3. Use one host-owned, ignore-aware walk to index explicit project files and
   enabled markers. Keep `projects` includes/excludes, ignore files, cache
   exclusions and symlink containment identical across tiers. No plugin may
   expand discovery outside that boundary.
4. Reject duplicate selected explicit files at each canonical root, then read
   explicit-file inference controls before scheduling plugin work. Roots
   marked `replace` need no inferred contribution. Batch remaining candidate
   roots by plugin; do not invoke an interpreter per directory.
5. Load the explicit extension closure as presence-aware layers, preserving each
   layer's path origin. Run inference hooks in declared dependency order, exposing
   validated frozen predecessor views only to bound consumers. Produce fragments;
   freeze the complete inference result
   before plugin dependency-resolution hooks query the frozen snapshot.
   Resolution hooks return root-based edges, not edits to project fields.
6. Apply each activation's configuration files to its inference, combine the
   activation contributions beneath explicit base/concrete layers ([§7](007.00-project-modes-and-apply.md#7-explicit-configuration-and-composition)),
   generate/resolve task aliases before task inheritance ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)), resolve task
   extensions while preserving presence/operations, and compose
   applicable project/task settings before applying their defaults. Resolve
   root-based edges to final effective project names, then run
   configuration/graph validation.
7. Invoke optional read-only observation hooks on the final frozen snapshot.
   Return one project model for all downstream consumers.

Use a shared per-pass captured input view and revalidate observed content,
missing paths, membership and project selection before accepting the result
([§17.2](017.00-review-findings-and-prerequisites.md#172-frozen-facts-do-not-imply-frozen-filesystem-inputs)). A detected concurrent input change rejects discovery by default with
an actionable diagnostic; do not execute tasks against the rejected graph.
Provide a bounded restart mechanism for future use, but disable automatic
restarts by default (zero retries). An explicitly enabled restart creates a new
input view and session and reruns discovery, not just the interrupted batch.

Multiple markers at one canonical root produce one grouped candidate root and
at most one effective project, not duplicate projects; participants may still
decline the candidate. Nested roots are independent if selected; detecting a
parent does not implicitly claim or suppress its children. Ecosystem workspace membership can
help interpretation but cannot bypass omni's selection boundary.

Keep current **file-based project selection**: `projects` include/exclude
patterns match each discovered file path, not its parent directory. Enabled
plugins widen the recognized marker filenames/patterns in the shared walk;
ordinary explicit project filenames remain recognized independently of plugins.
A selected marker contributes its parent directory as a candidate for the
declaring plugin. Group marker hits by canonical root while retaining which
plugins/markers matched, then schedule bounded batches under [§8](008.00-performance-and-shared-safeguards.md#8-performance-is-a-contract). A marker hit
requests evaluation, not unconditional project creation.

For example, `packages/**` selects explicit files and enabled ecosystem markers
beneath that path, whereas `**/project.omni.yaml` selects only that explicit
filename and does not implicitly select adjacent `package.json` or `Cargo.toml`.
Preserve file-specific includes/excludes and ignore behavior rather than silently
reinterpreting them as directory selectors. Supporting workspace inputs use
separate declared read scopes; authorizing an input does not select its parent
as a project. No separate inferred-project selection setting is introduced.

Require at most one selected explicit `project.omni.*` file per canonical
discovered root across all supported formats (`yml`, `yaml`, `json`, `toml`).
If discovery selects multiple explicit files at one root, fail before inference
or composition and report every conflicting path. Do not select by format
priority, merge those files or let traversal order choose inference controls.
Multiple ecosystem markers at that root remain valid and distinct from this
explicit-file ambiguity. Apply the same validation with no enabled plugins;
this is a documented pre-v1 discovery validation change, not blanket parity
with previously accepted duplicate-file layouts. Base configs reached only
through explicit `extends` are not additional discovered concrete files merely
because they reside in the same directory.

Workspace-level manifests may be declared read-only inference inputs without
making their directories projects. Return no project for aggregate-only
manifests unless the ecosystem adapter can justify a runnable root project.

#### Lockfiles as markers and inputs

The static marker/input model permits lockfiles in either role. A marker hit
requests evaluation of a candidate directory; it does **not** establish that
directory as a project. A workspace lockfile may describe many packages and
its directory may be aggregate-only. Inference may decline it or consult
associated manifests through the tracked input service.

For the initial JavaScript/Rust adapters, independently index supported project
manifests during the shared walk. Lockfile/workspace membership may help select
or interpret those candidates, but lockfile entries never directly create new
roots. All returned roots must already be host-approved manifest candidates
within `projects` includes/excludes and ignore/containment boundaries. A future
bounded candidate-proposal stage would require separate validation and protocol
design; it is not implicit permission granted by reading a lockfile.

Workspace lockfiles can be tracked read-only inputs even when their own
directories are not selected project roots, under the same workspace-input
scope rules as aggregate manifests. Changes, creation/deletion and missing
reads invalidate dependent hook results. Only validated workspace-local
relationships become omni edges; registry packages in a lockfile are not
projects. Do not infer a local edge from matching package names alone when
the manifest/lockfile resolves that dependency externally.

Parsing must stay inside the plugin's resource budget, with explicit supported
format/version handling. Never invoke npm/Yarn/pnpm/Bun/Cargo or a formatter to
decode, regenerate or normalize lockfiles during discovery. In particular,
binary formats need a bounded in-process parser or an explicit unsupported
format policy; do not fall back to running a package manager.

Initially fail actionably when a lockfile relevant to the selected manager/
workspace context cannot be read or parsed, or has an unsupported format/version.
Include the path and supported-format/version guidance where available. Do not
silently discard it, substitute stale cached facts or automatically fall back to
manifest-only inference. This includes relevant binary formats without a supported
bounded parser; discovery cannot invoke a tool to make them usable. A future
manifest-only fallback would require a deliberate adapter-specific, versioned
correctness policy, not generic parse-error recovery.

A genuinely absent lockfile is not the same as an unreadable or malformed present
file. Inference may proceed when authorized manifest evidence is sufficient,
tracking the missing-file observation so later creation invalidates reuse. Do not
weaken local/external resolution evidence or guess targets because a lock is
absent. Unrelated lockfiles outside the selected manager's verified context need
not be parsed merely because they exist. Manager-selection ambiguity still follows
[§4.3](004.01-native-ecosystem-adapters.md#43-initial-native-ecosystem-plugins); a stronger explicit choice does not make an unrelated stale lock relevant.

Validate manifest/lockfile consistency needed for the facts and project edges
actually inferred. When supported evidence contradicts itself about a relevant
dependency resolution, such as a workspace request versus a recorded external
target, fail with the dependency and conflicting file locations plus an actionable
resolution-data update hint. Do not arbitrarily prefer the manifest or lockfile,
emit stale relationships or execute an install/regeneration to repair the inputs.
Adapter specifications must define authoritative evidence and genuinely
contradictory combinations for each supported manager/format; a textual/version
difference alone is not automatically a contradiction.

This is bounded inference consistency validation, not a complete package-manager
installation or frozen-lockfile validator. Do not require unrelated resolution
data to be freshly installed or prove every external package version matches.
Narrow checks only where facts/edge correctness can be established; uncertainty
cannot justify contradictory published facts or name-only local-target guesses.
Independent static disagreement is distinct from [§17.2](017.00-review-findings-and-prerequisites.md#172-frozen-facts-do-not-imply-frozen-filesystem-inputs)'s detected concurrent
input changes and does not trigger whole-pass restart recovery.
