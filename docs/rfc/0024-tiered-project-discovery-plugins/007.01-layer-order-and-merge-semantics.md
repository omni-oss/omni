### 7.2 Layer order and merge semantics

Low to high precedence:

1. For each selected activation at this root, its inferred fragments followed by
   its applied configuration layers ([§7.1](007.00-project-modes-and-apply.md#71-project-modes)), in declared application order. Combine
   these activation contributions using [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts), not cross-activation last-writer wins.
2. Explicit project's resolved base-file layers, in existing extension order.
3. The concrete explicit project's own fields.

Project inference is applied once at the discovered root, not recursively at
every `extends` target. Resolve task extensions after project-layer composition,
as today. An extension target is not activated as a runnable inferred project
merely because another project references its file.

The project extension graph contains explicit file layers only. Resolve its
structure, cycle checks and existing traversal order before composition, but
retain the ordered raw layers and their operations rather than flattening them
into one merged explicit configuration. Inference fragments and inferred-only
logical project identities are not inserted as project-extension graph nodes.
For each discovered root, replay inference/application layers per activation,
combine their contributions, then replay explicit bases and the concrete layer
sequentially. These inputs
produce one effective project, not separate downstream project models.

Collection operations are not associative: inference `[inferred]`, an explicit
base `replace: [base]`, then a child `append: [child]` must yield `[base, child]`.
Premerging the explicit layers can retain only an `append` operation and wrongly
yield `[inferred, base, child]`. Do not regroup layers or reuse an already-merged
effective project as an explicit base. Cache raw layers/ordered traversal plans,
or cache final results keyed by the complete composition inputs; a flattened
explicit value is not a substitute for replaying its original operations.

If B extends A's explicit file, B inherits A's explicit file closure, never A's
root-specific inference, effective defaults or inference controls. A and B each
receive inference independently at their own discovered roots. Preserve existing
ordering and shared-ancestor visitation behavior for multiple bases and diamonds.
Task extension resolution remains a separate step over the composed task set;
explicit tasks can therefore extend inferred tasks that survive composition.

Normalize ordinary short-form tasks into presence-aware long-form patches before
project/task composition, not today's default-filled long-form values. Shorthand
contributes its command and existing implicit upstream self-task dependency;
other inheritable fields remain absent. Expand this sugar once for each original
declaration, preserving its declared task identity and reference-origin binding,
before replaying its ordered operations. Do not regenerate the dependency using
an alias or an inheriting task's name. Plugin-origin dependencies retain their
activation binding; handwritten dependencies retain their authored meaning.

All normal-task short/short, short/long, long/short and long/long pairs then use
the same field-level composition rules. A full-form partial override of a
shorthand task retains its command and other unspecified fields. A shorthand
command override preserves unrelated lower-layer environment/cache settings,
while still contributing its implicit upstream dependency through the ordinary
ordered dependency operations. Full-form `exec` alone does not introduce that
shorthand dependency. Structural markers retain their declaration-local rules.
No normal-task pair silently replaces the entire definition merely because its
representations differ; explicit dictionary/project replacement remains available.

This deliberately changes today's `TaskConfiguration::merge` replacement of
mixed short/long and short/short forms before v1. Publish old/new fixtures and
migration examples for callers relying on shorthand to erase lower-layer fields.
Aliases remain distinct declarations, not shorthand commands or field patches;
declaration-kind changes replace the entry atomically under [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases), rather than
merging normal-task fields into an alias or inheriting its target configuration.

Keep task field presence and ordered operations until task inheritance and
project-to-task settings composition have also completed. A task assembled from
several project layers is not yet a default-filled reusable task base. Replaying
its original operations against a task-extension base must preserve replacements
just as project-layer replay does. The implementation must define/test that
traversal without reusing a flattened task patch that loses operations. Apply
each field's defaults only after its last applicable inheritance boundary.

**Preserve field presence until composition finishes.** Do not deserialize a
partial explicit file into today's default-filled `ProjectConfiguration` and
accidentally erase inference with missing fields. Introduce a typed project
layer/patch representation recursively, including task/cache/environment layers,
compose it, then finalize applicable inheritance/settings before applying defaults
and validating the final `ProjectConfiguration`. Extend mode may omit `name` when inference
provides it; replace mode must obtain a name from explicit configuration or its
explicit bases, as normal. This is a deliberate schema/loader change.

Use these presence-aware semantics consistently for explicit-to-explicit
inheritance as well as inference composition, even when no plugins are enabled.
This is an intentional pre-v1 breaking correction, not a separate plugin-only
merge model or an opt-in configuration version. Omitted inheritable fields keep
lower-layer values; explicit values override using their field's merge rules;
defaults fill remaining omissions only after composition. Structural markers
remain exceptions: project/task `base` is declaration-local and defaults to
false for the concrete declaration, while inference controls belong only to the
concrete discovered file. Do not accidentally inherit template status or
inference controls through the new layer representation.

For example, a base's `cache.output.logs: false` now survives a child's omission
of that field; today's eager defaulting instead supplies `true` in the child.
To preserve that old effective result, explicitly set `cache.output.logs: true`
in the child. Apply the same rule to omitted task-level cache overrides so they
do not reset project-level settings. Absence must survive every inheritance
boundary until the applicable effective configuration is composed, not merely
the initial project-layer merge.

Publish release notes and migration examples for changed default-reset cases,
with regression fixtures recording old and new results. Preserve discovery
selection except for [§6.2](006.02-discovery-pipeline-and-lockfiles.md#62-pipeline)'s duplicate-explicit-file validation, along with
extension ordering/path origins, explicit collection operators and existing
null behavior except where a separately documented correction is necessary;
zero-plugin compatibility does not promise identical effective configurations
for cases affected by this presence/default correction. No-plugin loading uses
the same layer pipeline rather than retaining legacy eager-default semantics.

Reuse `config_utils` semantics for collections, including explicit `merge`,
`append`, `prepend` and `replace` where supported. For example, discard all
inferred dependencies or tasks without disabling other inference:

```yaml
dependencies:
  replace: []
tasks:
  replace:
    build:
      exec: ./build.sh
```

Explicit scalar values win; absent values inherit. Do not invent a generic
`null` deletion rule or silently change existing merge behavior. In extend
mode, overriding only a qualified inferred task's `exec` retains its other fields;
use the task dictionary's `replace` form or project replacement when that is
undesired. Fine-grained removal of a single inferred task is deferred unless
the shared config model gains that operation for all configuration sources.

#### Dependency composition before target resolution

Use one typed intermediate dependency collection: plugin contributions refer to
workspace-local roots, while explicit layers retain project-name references.
This is an internal representation, not new user-facing dependency syntax.
Edges returned by `infer_roots` and `resolve_dependencies` both belong to the
inferred dependency layer; neither may append edges after explicit composition.
Apply the ordered explicit collection operations to these references before
resolving surviving roots to final runnable project names. Then deduplicate
resolved edges and validate target existence and graph cycles.

In particular, `dependencies: {replace: []}` removes every inferred dependency
for the root. If a removed reference points to an excluded or nonexistent
project, it does not cause a final target-resolution error. A surviving reference
to such a target fails with provenance identifying the contributing plugin/file.
Explicit renaming preserves surviving root-based edges. Shape, containment,
source-root ownership and resource validation still happen at the plugin output
boundary: an escaping path or otherwise malformed output cannot be made valid
by a later replacement. A well-formed workspace-local target need not already
exist in the final runnable catalog merely to survive that structural check.
This does not authorize plugins to create undiscovered roots.

#### Task dependency references and explicit-project syntax

Extend the typed task dependency representation with
`ProjectRoot { project_root: ProjectRootId, task: String }`, alongside the existing
`Own`, `Upstream` and `ExplicitProject` variants. These variant sketches retain
today's `task: String` notation only for brevity: task identity must preserve
scope and raw local-name components through composition ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)). Apply it
consistently to task `dependencies` and `with`. Plugin contributions can identify a specific target
by stable workspace-relative root without guessing its final omni name. This
variant is initially plugin/intermediate data; it does not require exposing a
new handwritten root-reference syntax.

Allow handwritten explicit-project task references in both existing shorthand
and object form, mapping to the same `ExplicitProject` variant:

```yaml
dependencies:
  - common#build
  - { project: common, task: build }
with:
  - common#watch
  - { project: common, task: watch }
```

Each pair above demonstrates equivalent unqualified alternatives, not a
requirement to declare the relationship twice. Own-task `build` and upstream-task
`^build` retain their lookup roles under the shared escape-aware grammar.
Explicit-project objects require `project`
and `task`, with optional `plugin` for qualification; reject unknown/missing fields
and ambiguous selectors, and validate names using the same component rules as
shorthand. Update the shared task
dependency deserializer and generated schema to accept both forms; preserve
existing canonical shorthand serialization for `ExplicitProject`. Root references
use the distinct object form `{ project_root: packages/shared, task: build }` in
plugin/intermediate data. Require `project_root` and `task`, with optional `plugin`; reject
objects combining `project` and `project_root`. Never overload a project-name
string or reinterpret a `project` value as a filesystem path.

Use `plugin`, not `scope`, as the configuration field for an effective activation
id: a consumer alias such as `native`, or the full canonical name such as
`@omni/rust` when unaliased. It is not an artifact locator or an arbitrary
namespace. For example:

```yaml
dependencies:
  - common#native::build
  - { project: common, plugin: native, task: build }
```

These are equivalent alternatives. The corresponding plugin/intermediate root
reference is `{ project_root: packages/common, plugin: native, task: build }`.
Without `plugin`, a handwritten object selects an unqualified task or alias;
`{ project: common, task: 'native::build' }` instead selects the unqualified task
literally named `native::build`. Object components remain raw and never need
task-reference escaping. Preserve plugin and local-name components separately;
canonical shorthand serialization formats from structured identity rather than
concatenating or reparsing raw components. Internal architectural terminology
may still call this task scoping. Plugin-origin implicit binding remains
host-owned: a root-based task reference with raw local name `build` and no
explicit target activation binds to the originating activation's `build` at the
target root, not its public `build` alias. Plugins need not know or emit their
own effective activation id. Multiple activations of the same artifact remain
distinct, and changing public aliases cannot redirect inferred references.
A surviving direct reference to a missing task fails; never fall back to another
activation or an unqualified alias. Upstream references retain [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)'s missing-task
skip rule. Preserve this binding through inheritance and cache restoration.
Ordinary handwritten project/base references without `plugin` retain public
unqualified lookup, while handwritten `plugin` explicitly selects that activation.
Workspace-selected application files are a contextual exception: their unqualified
task references bind to the originating activation under [§7.1](007.00-project-modes-and-apply.md#71-project-modes), with deliberate
explicit cross-plugin qualification still available. Initially, deliberate
cross-plugin task wiring is available only through explicit configuration.
Plugin-emitted task references stay within their originating activation, including
own, upstream and cross-project targets; reject output attempting to select
another activation or request public-alias lookup. Raw local names containing
qualification-looking text remain literal, not an escape from that binding.
The `plugin`-bearing root object above describes host/intermediate identity, not
guest authority to choose another activation. Plugins need not emit their own id.

Cross-plugin project dependency resolution through authorized published claims
remains supported: project edges do not select another contributor's task.
Automatic cross-plugin task coordination, advertised task roles and host-bound
provider selection are deferred to a future versioned feature with a concrete
adapter use case. They are not prerequisites to the initial task contract ([§17.8](017.00-review-findings-and-prerequisites.md#178-scoped-object-references-and-alias-aware-selectors)).

Preserve typed references through explicit project/task composition and task
inheritance. Lower surviving root-plus-task references after task extensions
and final project naming, before conversion to executable task dependencies and
final target/cycle validation. Explicit collection/task replacement can discard
references before target existence checks; malformed or escaping references
still fail at the plugin output boundary. A surviving target must resolve to a
final runnable project and a surviving non-template task. Diagnostics retain
contributor provenance. Root references survive explicit project renames;
explicit name references retain their existing name-based meaning.

A direct task dependency does not automatically add a project dependency edge
or alter upstream-task semantics. The task `ProjectRoot` variant is confined to
configuration/protocol composition and lowering: resolve it to an ordinary named
task dependency before handing it to the planner/task graph. It does not trickle
into the project graph or require graph/execution consumers to understand a new
syntax. Project-level root references resolve separately through the existing
proposed root-to-final-name project-edge pipeline. Execution continues through
the normal planner.
Test both explicit-project forms in `dependencies`/`with`, schema and serde
round trips, malformed objects, root-based renames, removed/missing target tasks,
base tasks, explicit replacements, inherited references and resolved cycles.
