## 18. Code-grounded readiness and open decisions

Assessment baseline: repository revision `3ce79ad6`, with static inspection of
the current configuration, context, command, planning, cache, capability and source
code. This is a design/readiness review, not a claim that plugin functionality or
the conformance tests are implemented. The RFC remains draft.

**Assessment:** no fundamental crate-dependency or lifecycle impossibility was
found in the inspected paths. The architecture can support staged implementation,
but the external contract is not implementation-ready as a frozen SDK, and the
native pilots are not release-ready. There are substantial configuration/task
identity refactors and concrete specifications to complete, not just runtime
adapters to add. The gates below apply to their affected work, not every independent
foundation change.

### 18.1 Open decision checklist

This is the single active decision list. Historical options in §17 are resolved
rationale. Keep only genuinely open choices here; ordinary schema, algorithm and
fixture work belongs in §18.3. Resolve items one at a time when requested. After
a decision, update its normative section and required fixtures, **remove its
entire checklist entry**, and remove/update inbound references to that entry.
Do not leave completed boxes here or renumber the remaining stable decision ids.
No new choice is implied merely because an implementation detail is unspecified.

- [ ] **D1 — Fact/query visibility and the meaning of authorization.**
  The RFC separates query authority from filesystem authority but does not define
  the grant that authorizes reading another activation's published facts or the
  root/final-project catalog. A producer can read supporting workspace inputs
  unavailable to a consumer; calling those derived values “published” is not a
  complete confidentiality policy. The `FsRead` profile in `omni_capabilities`
  cannot itself authorize a fact query.
  **Decide:** does explicitly enabling/binding a producer authorize its supported
  published views by default, subject to workspace narrowing, or must workspace
  configuration separately grant fact types/producers/root scopes? Define the
  corresponding defaults for global resolution and read-only observation, not
  only declared-producer inference. Do not invent authority from catalog membership
  or silently return an empty result on denial.
  **Recommendation:** explicit typed view grants, with a concise binding-level
  grant form rather than filesystem-permission inference; any convenience default
  must be documented as an information-sharing grant. This is a policy choice,
  not a proposed final field spelling.
  **Blocks:** cross-activation query authorization/schema and its cache context.
  **Acceptance evidence:** a producer reads a restricted supporting manifest;
  allowed/denied consumers, negative queries, scoped paging, observation and cache
  hits all enforce the same chosen policy without leaking denied facts/counts.
  **Normative homes:** §§5.1, 6.1, 12.4 and 14.2.

- [ ] **D2 — Safe caching of mutating/non-replayable inferred tasks.**
  `fmt` is intentionally mutating, while built-ins currently promise to leave
  `cache.enabled` absent and ordinary finalization enables it. Current
  [`BatchExecutor::replay_cached_results`](../../../crates/omni_task_executor/src/batch_executor.rs)
  skips an output path if it already exists.
  With source files absent from the input key, a successful formatting result can
  be reused against unformatted existing source without formatting/restoring it,
  even if source is declared as output. However,
  [`cache_many`](../../../crates/omni_cache/src/cache/impls/hybrid.rs) recomputes file
  digests after execution: complete source/config inputs can instead key a
  deterministic idempotent formatter's already-formatted state, preventing a hit
  on restored unformatted content. Do not incorrectly assume current storage
  always uses the pre-execution source digest. Arbitrary JavaScript scripts can
  also have effects that neither file hashing nor file restoration represents.
  **Decide:** retain unset enablement and require a proven complete/idempotent
  post-state policy for cacheable mutators, permit a narrow safety exception
  disabling caching for known non-replayable tasks, or require explicit workspace
  cache configuration for tasks whose safe effects cannot be inferred.
  Extending ordinary cache replay to overwrite existing source is a separate,
  wider alternative requiring mutation/conflict safety design; do not silently
  introduce it through discovery. Do not change `fmt` to check-only to avoid the issue.
  **Recommendation:** retain existing defaults where adapter fixtures prove safe
  post-state reuse; permit documented per-task disablement where they cannot,
  rather than requiring a new overwrite-on-hit executor. This would narrow the
  blanket unset-enablement promise, so it needs an explicit decision. Unknown
  script effects still need an honest adapter/user policy; task names alone do
  not establish cache safety.
  **Blocks:** the adapter caching contract for mutating tasks, not discovery ABI
  or ordinary configuration composition. The prior unset default remains the
  recorded policy until this entry is resolved; do not claim it is already safe.
  **Acceptance evidence:** run formatting, restore the same unformatted content,
  then run again with the prior entry present; it must execute on a miss or safely
  reproduce formatting, never report a hit leaving that content unchanged. Verify
  that already-formatted content can be reused only under a proven safe policy.
  Also test deleted build outputs and commands with non-file side effects under
  the chosen documented policy.
  **Normative homes:** §§4.3, 8.3 and the separate adapter specifications.

- [ ] **D3 — Wasm ABI/engine, intentionally deferred to prototype evidence.**
  Compare core-Wasm SDK message bindings with the Component Model and candidate
  engines using equivalent workloads and enforcement tests. Evaluate cold/warm
  start, transfers/host calls, cancellation, memory, metering, platform/tooling
  support and reusable mechanics for future generators/tools without sharing
  authority. This is not a request for a preference before measurement.
  **Blocks:** final external bindings and runtime dependencies only; native and
  runtime-neutral contract/composition foundations proceed independently.
  **Acceptance evidence:** published measurements, containment/interruption tests
  and a documented selection under §10. JavaScript runtime work stays deferred.
  **Normative homes:** §§10, 12.5 and 13.3.

### 18.2 Reconciled findings that need no new decision

- Replaced the stale inline `options.task_dependencies` example with standard
  workspace-selected `apply` task patches. Defined the existing-task evaluation
  boundary and preservation of empty collection operations; ordinary surviving
  direct references stay strict.
- Kept literal ecosystem operands separate from executable command expressions.
  Structured argv alone does not prevent current Tera/environment expansion.
  Added the required validation/resolution/serialization/hash audit and fixtures,
  without disabling authored command expressions or changing raw script names.
- Required envelope-shape validation before list/dictionary decoding can discard
  operator siblings. Post-decode collection validation cannot validate lost data;
  the enclosing driver supplies the correction without changing the shared enum.
- Clarified raw hook-output versus applied/composed cache records and their
  different collection profiles. Applied `replace` is valid authored configuration,
  not an additive-only plugin result.
- Replaced whole inferred-configuration fingerprint wording with mandatory
  per-task effective semantic identity, and called out command-context inputs
  missing from raw-command-only hashing.
- Moved payload/query specifications and representative fixtures ahead of final
  contract types, instead of postponing them until native pilots. Preserved the
  independent Wasm prototype gate and acknowledged existing additive pin writes
  without confusing them with reference publication or leases.
- Included internal `*`/`**` pattern requests and direct project-hash/stale-cache
  collector paths in the selector and semantic-digest migration. Clarified that
  lazy runtime startup cannot silently omit registered singleton hooks, and that
  pass consistency includes the workspace configuration used during bootstrap.
- Repaired malformed split-document cross-references and an incomplete example
  version requirement. These edits do not reopen resolved architecture policies.

### 18.4 Practical implementation order and readiness exit

1. Complete the pure contracts and golden fixture inputs for each foundation;
   independent source-type extraction, presence-aware replay and identity/parser
   work can proceed without a Wasm engine. Do not freeze query authorization
   before D1 or claim complete adapter caching before D2.
2. Integrate the shared zero-plugin layer/alias/selection pipeline and semantic
   identity with migration/regression fixtures. Migrate internal pattern callers
   alongside CLI/MCP; a public flag alone leaves current cache planning broken.
3. Land captured-input services, transactional host scheduling, local cache
   primitives/records and native adapters only behind their completed contracts.
   Exercise the full pass, rejected-pass invisibility and ordinary task execution,
   not only mock capability calls.
4. Finalize acquisition/leases and prototype-backed Wasm bindings/enforcement
   before enabling external artifacts. Source installation stays separate from
   hook execution; generators/tools do not gain implementations through this work.
5. Release only after the affected gates, adapter coverage and conformance tests
   are demonstrably complete. Static review and Markdown/link checks do not
   establish runtime correctness, containment, cache safety or benchmark results.
