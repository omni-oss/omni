### 7.4 Host-owned task scoping and aliases

Omni, not plugins, scopes inferred tasks by effective activation id. A plugin
emits local task names such as `build` and knows only its own invocation context;
it does not construct `plugin-id::build`, discover its public aliases or require
knowledge of other activations. Keep activation ownership separate from local
task names internally. Omni preserves that context through composition, input
interpretation, inheritance and cache restoration, and binds plugin-origin own,
upstream and root-based cross-project references in that activation context rather
than through public unqualified aliases.
Explicitly authored references retain their written meaning. The same root may
therefore contain runnable build tasks from several plugins without their task
fields competing for one unqualified dictionary entry.

Use `::` for task qualification: `native::build`, `frontend::build` and
`app#@omni/rust::build`. Scope by the unique effective activation id, not the
canonical publisher name when an alias was supplied. Keep identity as structured
activation/local-name components, not concatenated strings used as internal keys.
Literal delimiters in components are supported through the escaping grammar below;
omni autoescapes ecosystem-derived names when generating reference strings.

Provide explicit task aliases, illustratively `build: {alias: native::build}`.
An alias is another name for a canonical runnable task, not a new task with a
dependency edge to it or a task-extension copy. It cannot also declare execution,
environment, cache, dependency or inheritance overrides. Users customize an
inferred task directly through its qualified entry; all aliases then use that
same customized task. An explicit task extending it instead creates a distinct
task definition. Plugin-scoped inferred tasks remain runnable, not implicit bases.

During ordered explicit-layer composition, normal-task/alias kind changes replace
the entire entry atomically. An explicit alias replacing a lower normal task
discards all of its command, environment, cache and dependency fields; surviving
references to that name follow the new alias. This includes a qualified inferred
entry such as `native::build` explicitly redirected to `frontend::build`. Validate
the surviving alias chain for missing/non-runnable targets and cycles as usual.
Conversely, an explicit normal task replacing a lower alias starts a distinct
normal definition at that entry, without inheriting the alias target's settings.
This does not manufacture a missing activation/contributor binding for an otherwise
invalid qualified override. Normal/normal pairs retain [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)'s field-level merge;
alias/alias pairs select the higher explicit layer's target as a whole. Plugin
contributions remain subject to [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)'s conflict/additive rules, not implicit
last-writer precedence.

Validate each declaration's shape at its input boundary. An alias cannot combine
`alias` with `exec`, `extends`, environment, cache, dependencies or other task
override fields, even if later composition would discard that declaration. A
kind transition is replacement between separately valid declarations, not a way
to repair a malformed mixed alias/task object. Preserve replacement and target
provenance for inspection and diagnostics.

Omni automatically exposes a local-name alias when exactly one eligible plugin
task contributes that name and no explicit declaration occupies it. If multiple
contributors compete for that implicit alias, unresolved ambiguity is an error:
report the qualified candidates and require an explicit alias selection rather
than selecting by plugin order or silently accepting an ambiguous alias. An
explicit alias stabilizes the user's choice when plugins are added or removed.

Alias resolution produces canonical task identities for planning, execution,
task-name expressions, working directories and cache identity; the requested
alias is presentation metadata only. Multiple aliases of the same canonical task
collapse to one executable node for equivalent invocation parameters, without
collapsing distinct invocations/arguments. This is an identity requirement, not
a requirement to support several argument bindings for the same task in one
plan. Retain the existing execution model: alias selection deduplicates canonical
tasks, while separate calls preserve their ordinary argument-sensitive execution/
cache behavior. Users needing simultaneous variants create distinct named tasks
with `extends` and task-specific `args` ([§17.10](017.00-review-findings-and-prerequisites.md#1710-canonical-task-identity-versus-invocation-identity)); aliases do not carry argument
overrides or create separate invocations.
Validate alias cycles and execution
cycles after canonicalization. Aliases neither add project-graph edges nor change
upstream-project selection. Task namespacing does not resolve conflicting project
names or other project-wide fields; those retain [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)'s explicit conflict rules.

If a plugin is disabled or a target is removed, surviving aliases must fail
actionably. Do not silently turn a partial qualified override into a valid task
with missing inference; validate its surviving final definition and binding.
Discarded aliases do not cause final target-existence failures.

An explicit unqualified task occupies its own name and suppresses any automatic
alias at that name. It does not implicitly inherit from the plugin task that
would otherwise receive the alias. A partial unqualified declaration must be
valid as its own task or use explicit `extends`; if invalid, diagnose it with
guidance to override the qualified inferred task or declare the intended
extension. An explicit alias remains non-customizable. To customize the same
underlying task for all aliases, override its qualified entry; to derive a
distinct customized task, use `extends`.

Runnable does not mean that `exec` must be present. Current long-form tasks allow
commandless aggregation/no-op definitions; preserve that behavior. An unqualified
task without `exec` does not acquire an inferred command, but omission alone is
not an error. Validate its actual dependencies, inheritance and other applicable
constraints. Diagnostics must not suggest `extends` is mandatory for every
commandless task. A qualified override's contributor/target binding is a separate
validation concern, not something inferred from command presence.

Resolve task declarations in this fixed order:

1. Compose inferred and explicit task declarations, including collection
   replacements, preserving field presence and ordered operations. Determine
   surviving names and declaration-local task kinds (`base`, normal or alias).
2. Generate automatic aliases from eligible surviving plugin declarations and
   explicit name occupancy, not from successful inheritance resolution. Exclude
   base templates and never generate aliases from other aliases. Diagnose
   unresolved competing contributors without choosing by traversal/plugin order.
3. Resolve alias chains to canonical task names. Reject missing targets and
   alias cycles; retain requested names for presentation, not execution identity.
4. Resolve task inheritance, treating an alias in `extends` as a lookup of its
   canonical target's configuration. Preserve original operations and binding
   context while replaying layers. The extending task is a distinct definition;
   it neither becomes an alias nor modifies the base task for other aliases.
5. Finalize applicable settings/defaults and runnable-target validation; lower
   root-based references and canonicalize task dependency names before building
   executable task-graph nodes. Alias targets must ultimately be runnable, not
   base templates. Aliases themselves never become executable nodes.

Check inheritance cycles after alias-aware target lookup, including indirect
cycles hidden by aliases. For example, an explicit qualified `native::build`
extending `build` fails if `build` aliases that same qualified task. In contrast,
`release: {extends: build}` may inherit through `build`'s alias to
`native::build`, producing a distinct `release` task. Explicit upstream references
use the resolved project graph to find upstream projects, then resolve aliases
within each target project; plugin-origin references retain their host binding.

Retain a per-project alias index outside the executable task map. Exact alias
selection resolves through that index to canonical runnable tasks before planning;
removing alias nodes must not make `build` unselectable. For explicit `^build`,
first resolve the project's surviving project dependencies, then look up `build`
independently in each upstream project's alias/task index: different projects may
bind that name to different canonical tasks. Lower those lookups before handing
dependencies to ordinary task-graph construction. Preserve today's upstream rule
that a project without the requested task contributes no edge; an existing alias
with an invalid target remains an error. Apply the same rules to `with`.

Current `omni_execution_plan::DefaultTaskFilter` matches task globs directly
against executable node names, and `omni_core::add_upstream` looks for a literal
task-map key. Neither implements alias lookup. Task patterns match all public
runnable names in each selected project: canonical task names and explicit or
automatic aliases. Resolve matching names to canonical targets, then deduplicate
equivalent invocations; never turn aliases into duplicate executable nodes. For
`build` and `compile` both aliasing `native::build`, `b*` selects through `build`,
`native::*` selects the qualified name, and `*` runs the underlying task once for
equivalent invocation parameters. Project, metadata and affected-file filters
apply to the canonical task; an alias has no separate settings and cannot bypass
those filters. Keep requested/matched names only as presentation metadata.

Configuration references and positional CLI task selectors identify exact tasks
or aliases using the shared reference grammar; wildcard characters in an exact
local name are literal. Request pattern selection explicitly with a repeatable,
value-taking `--task-pattern` flag, not a global mode switch. Exact selectors,
patterns or both may be supplied; a pattern-only request requires no positional
task name. Combine their matches as a union, then deduplicate equivalent canonical
invocations. MCP exposes separate exact-task and task-pattern fields with the
same semantics. For example:

```sh
omni run build                         # exact name or alias
omni run 'test*'                       # exact task literally named test*
omni run --task-pattern 'test*'        # matching public names only
omni run build --task-pattern 'test*'  # union of exact and pattern selection
```

Integrate these as two selection inputs to the existing task-filter/execution-
plan pipeline, not a separate filtering system. Their union selects canonical
task targets; existing project, directory, metadata and affected-file filters
continue to narrow that selection. Extend `DefaultTaskFilter` and its shared
CLI/MCP request plumbing rather than adding a parallel plugin-only planner.

Track exact-selector existence per requested selector within the project/directory
selection scope, before metadata and affected-file narrowing. An unqualified exact
selector must resolve to a runnable task or alias in at least one project in that
scope, not in every project; projects without that task contribute no selection.
An explicit-project selector must resolve within its named project in that scope.
Validate every exact selector independently, including in mixed exact/pattern
requests: another successful exact selector or pattern cannot conceal a missing
target. Metadata or affected-file filters removing all resolved matches is not a
missing-task error; retain ordinary empty-selection behavior. Alias resolution and
canonicalization precede canonical-task filtering, so aliases cannot bypass these
rules. Keep this request-level existence tracking in the existing selection
pipeline rather than attempting to infer missing selectors from per-node boolean
filter results. Apply the same semantics in CLI and MCP.

Patterns use the shared glob model over canonically rendered public task names;
they are not passed through the exact-reference parser as a second decoding step.
Keep reference escaping, glob escaping and shell/JSON quoting separate, with
fixtures for literal wildcard names, backslashes and escaped delimiters. Shell
quoting alone does not turn an explicit pattern into an exact selector. This
decision concerns task selection, not a change to project/directory filters.

This intentionally changes today's pattern-based task selection before v1:
positional `build*`/`*` become exact references, and existing bulk selections move
to `--task-pattern 'build*'` / `--task-pattern '*'`. Update CLI argument validation
to permit pattern-only calls, MCP schemas, help, examples and migration notes.
Missing exact targets receive actionable diagnostics, including a pattern hint
where appropriate; never silently retry a missing exact reference as a glob.
Define/test no-selector defaults separately, preserving existing behavior unless
an additional change is explicitly documented.

Migrate internal request constructors along with public selectors. In particular,
`HybridTaskExecutionCacheStore::plan_task_set` currently passes `"*"` through
`Call::new_tasks` to mean all tasks for cache stats/pruning. After exact-task
selection changes, that call would request a literal-star task instead. Represent
its intentional glob as an explicit pattern request, including the no-task-filter
case. The same migration applies to the cache prune/staleness planning branch
and `ProjectHasher::hash`, whose empty filter currently becomes `"**"`.
Audit other generated selectors. `omni run` continues to require at
least one exact or pattern input; pattern-only support does not introduce an
implicit run-all default. Preserve other surfaces' existing defaults explicitly.

The distinction between overriding a qualified inferred task, defining an alias
and creating a task via `extends` must remain visible in diagnostics and inspection.

#### Qualified reference syntax and escaping

Only unescaped separators carry syntax: `#` separates an explicit project from
its task reference, `::` separates an activation scope from its local task name,
and a leading unescaped `^` selects upstream-task lookup. Use backslash escaping
for literal component characters: `\#` for a literal hash, `\:` for a literal
colon, `\\` for a literal backslash, and `\^` for a literal caret. Preserve
ordinary single-colon names such as `lint:fix`; when a component contains `::`,
the canonical formatter escapes both colons as `\:\:`. Escape literal hashes
and backslashes, and a leading caret where it would otherwise select upstream
lookup. Unsupported escape sequences, dangling backslashes and extra unescaped
separators are errors, never substring matches or silently discarded suffixes.

Sharing a parser does not make every reference kind valid on every surface.
After parsing a textual reference once, validate its kind against the following
initial surface restrictions; raw plugin/object components retain [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)'s binding
rules rather than being reparsed as shorthand.

| Surface | Allowed reference kinds |
| --- | --- |
| Handwritten task declaration keys | Same-project unqualified or activation-qualified task identities; no project or upstream selector |
| Task `extends` and alias targets | Same-project unqualified or activation-qualified identities, including permitted alias lookup; no explicit-project, root or upstream reference |
| Task `dependencies` / `with` | Own, upstream and explicit-project references; root references additionally in plugin/host intermediate data under [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics) |
| Exact CLI/MCP task selectors | Unqualified or activation-qualified task identities, optionally prefixed with an explicit project; no upstream or root reference |
| `--task-pattern` / MCP task-pattern fields | Glob patterns over canonical public task names, not exact-reference parsing |

Task inheritance remains intra-project, including inheritance through an alias.
Aliases likewise name tasks within their own project initially; cross-project
orchestration uses `dependencies`/`with`, not cross-project aliases or inheritance.
For example, reject `alias: other-project#build`, `extends: ^build` and the exact
CLI selector `^build` with surface-specific diagnostics. A literally named
`^build` remains accessible through its escaped exact reference `\^build`.
These restrictions do not permit plugin output to select another activation or
public aliases; inferred references remain activation-bound under [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics).

Examples below are task-reference strings; YAML uses single quotes so its string
parser preserves backslashes:

```yaml
tasks:
  build:
    alias: 'native::build\:\:debug'
  verify:
    alias: 'native::check\#fast'
```

The first alias targets activation `native`'s local task `build::debug`; the
second targets its local task `check#fast`. A reference
`app#native::check\#fast` adds project `app` without changing that local name.
An unqualified literal local task name `native::build` is written
`native\:\:build`, distinct from scoped `native::build`. Apply the same literal
escaping to reference-bearing task declaration keys, `extends`, aliases,
dependency/`with` shorthand and CLI/MCP string selectors. Shell arguments need
shell quoting in addition to this grammar; JSON/YAML double-quoted strings need
their normal backslash escaping. These are transport quoting layers, not repeated
task-name decoding.

Plugin output and captured ecosystem task names are raw local names, not
reference syntax: plugins never preescape or qualify them. Omni carries those
raw names with their binding and renders escaped references automatically,
including generated unqualified aliases. Do not rename ecosystem scripts or
rewrite the actual command invocation. Typed/object component values remain raw
data and must not be reparsed/unescaped as reference strings; preserve explicit
scope/name distinctions in structured representations. Parse textual references
once, using escape-aware separator recognition before component decoding, and
format them canonically from structured identity. Escaping must be injective:
`build::debug`, `build\:\:debug` and `build#debug` remain distinct local names.

Current task dependency parsing in `omni_configurations` and `omni_cli_core`
uses duplicated regexes without escape handling; the configuration regex is
unanchored and can accept a substring rather than the whole reference. There
is no existing `#` autoescape mechanism to rely on. Replace those textual paths
with one shared, full-input, escape-aware parser/formatter. Audit task-id string
construction, selection, inspection, serialization and cache CLI handling,
including its current `task_name.split('#')` logic. Ordinary graph/execution
consumers should receive canonical structured identities, not learn escape rules.
Document intentional pre-v1 corrections to previously ambiguous/partially parsed
references, without silently reinterpreting legacy unqualified `::` names as a
different task.

**Existing `::` names.** An unescaped `::` in a declaration key is always the
qualified form (a pre-v1 correction), and the escaped `frontend\:\:build` is always the
literal name; that is how authors choose either meaning. A legacy key such as
`frontend::build` therefore becomes a qualified override of activation `frontend`'s
`build` when `frontend` is enabled. To avoid a silent change, emit a mandatory
migration notice (RFC 0023) naming the key, its new qualified meaning and the escaped
literal spelling, and instructing authors to migrate selectors, references and scripts
as well as the declaration (an old `frontend::build` selector keeps selecting the
inferred qualified task after the declaration is escaped). A qualified key whose activation is configured (enabled or disabled) but has no such
inferred local task is a missing-binding error with the same remediation, so a disabled
activation never turns a partial override into a valid commandless literal task. Only
keys whose prefix matches no configured activation remain literal names, with a notice
that explains the literal interpretation, that the exact selector for it is the escaped
`frontend\:\:build` (the unescaped selector refers to a qualified task), and that if the
activation was removed or never configured, a partial override has no inferred binding and
now exists only as a literal task (possibly commandless, and selectable by patterns). Fixtures: a
successful qualified override of an inferred task; a legacy `frontend::build` alongside
inferring activation `frontend` producing the notice; the escaped literal coexisting
with the inferred task; the old selector after escaping; a `frontend::build` key with
`frontend` disabled (missing-binding error); and keys with an unknown prefix and with a
removed activation (literal task, notice content, escaped selector).

#### Collection operator names are not task-name escapes

`DictConfig` currently recognizes object-valued `merge`/`replace` keys as
collection operators before a field-level collection validator receives the
decoded value. Reference escaping does not disambiguate those dictionary keys.
For a task literally named `replace` or `merge`, use an explicit outer `merge`
envelope so the nested key is decoded as a task name:

```yaml
tasks:
  merge:
    replace:
      alias: 'native::replace'
```

Plugin SDK serializers must use an unambiguous additive dictionary envelope
when raw local names collide with operator keys; the host still scopes those
raw names itself. Do not accidentally serialize a native `DictConfig::Value`
containing such a name into a different operator on cache/wire round trips.
The enclosing serialization path must preserve additive versus destructive
operation semantics and entries, without changing `DictConfig` or relying on a post-decode validator
to recover discarded shape information. Add native/Wasm/cache parity fixtures
for operator-named tasks and sibling entries. This is collection framing, not
lossy renaming or an additional task-reference escape sequence.

Required fixtures include multi-plugin roots, unique/ambiguous automatic aliases,
explicit alias selection, direct qualified overrides shared by multiple aliases,
normal/alias and alias/normal atomic replacement, alias/alias target replacement,
discarded lower task settings, qualified redirection, malformed mixed declarations,
canonical execution/cache deduplication, argument-sensitive separate calls, preserved
plugin-local own/upstream bindings, activation-id changes, disabled contributors,
removed targets, alias targets used by `extends`, and alias/inheritance/execution
cycles (including inheritance self-cycles hidden by automatic aliases). Test raw
names containing `::`, `#`, backslashes, literal escape-looking text and leading
carets; parse/format round trips, collisions, full-input rejection, single-colon
compatibility, malformed escapes, scoped/cross-project/upstream references,
escaped declaration keys, plugin autoescaping and CLI/MCP/serde consistency.
Cover exact alias selection, project-specific upstream aliases, upstream missing
tasks, commandless tasks and operator-named tasks with unambiguous envelopes.
Cover patterns matching canonical names and aliases, overlapping alias matches
deduplicating to one canonical target, distinct named `extends`/`args` variants, and project/
metadata/affected filters applied consistently through every public name.
Test exact-only, pattern-only and mixed requests, repeatable pattern flags,
literal wildcard exact names, no fallback to glob matching, CLI/MCP parity and
migration diagnostics for formerly positional patterns.
Test the allowed-reference matrix at each input surface, including rejected
cross-project alias/inheritance and upstream CLI selectors, escaped literal
lookalikes, and raw component handling. Cover exact names present in only some
selected projects, explicit-project targets outside the project/directory scope,
all matches removed by metadata/affected filters, and individually missing exact
selectors alongside successful exact/pattern selectors. Verify request-level
existence diagnostics and CLI/MCP parity without changing empty-selection behavior.
