## 6.1 (continued): Facts and queries

#### Snapshot access, not whole-workspace copies

Requests carry assigned roots and bounded relevant session state, not an
automatically serialized copy of every root's state/configuration. Keep the
complete approved frozen snapshot in host memory and expose defined read-only
views through bounded bulk queries. Native handlers borrow the logical query
service directly; Wasm handlers use versioned host imports with opaque handles
valid only for the invocation/stage/activation that received them. Handles cannot
grant access to mutable host objects, another plugin's private state or a later
snapshot, and their transient values are not semantic cache identities.

During dependency-ordered inference, expose bounded fact-query views for declared
producer bindings only after those producers finish validation ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)). The view
is frozen for the consumer's assigned-root batches and excludes producer project/
task fragments and private state. Published facts from declined producer roots
remain subject to the supporting-fact rules above; their presence does not imply
project acceptance or final target validity. Completing the inference phase then
makes the approved shared fact/catalog snapshot available for dependency resolution.

After successful inference, build host-owned indexes over published typed facts
and the approved root catalog (including explicit-only runnable roots where
applicable). The shared fact schema/query vocabulary must be specified and
versioned before implementing cross-plugin queries; opaque plugin session bytes
are not automatically published facts. Plugins retain ecosystem interpretation:
for example, a bulk query for a package identity returns matching approved root
facts, not an unconditional dependency edge. Return ambiguous matches explicitly
in stable order; a same-name external package must not be assumed local.

Initially use a small omni-defined fact vocabulary covering ecosystem package
identity, workspace membership and dependency metadata. Give each fact type a
namespaced identifier; its fields, meaning, validation and query behavior are
versioned with the negotiated `project_discovery` API, not an independent per-fact
version domain. Native and user-authored plugins may publish and consume the supported
types; the vocabulary does not restrict which ecosystems they may infer. Plugin
authors do not initially register custom fact schemas or attach arbitrary opaque
documents to a supported type to bypass its shape. Private ecosystem-specific
data remains in the plugin's state unless represented by a supported fact.

Negotiate required fact/query features as part of the discovery capability.
The host validates producer/consumer compatibility before hooks, including bound
inference dependencies, rather than discovering incompatible fact formats after
executing a producer. Different negotiated discovery API versions interoperate
only through explicitly defined, tested compatibility mappings ([§14.2](014.00-versioning-compatibility-and-migrations.md#142-negotiation)); sharing
a fact identifier or decoding the same fields is not proof of compatibility.
New optional fact/query features require explicit negotiation. Plugin package
versions and artifact pins are not substitutes for this contract. Example fact
envelopes below refer to the discovery API's version, not a separately negotiated
package-identity/membership/dependency-fact version.

Use a shared `package_identity` fact with a `package_system` discriminator, not
separate system-specific fact types that repeat the same distinction. Illustrative
payload (the common namespace/version envelope is abbreviated):

```yaml
type: package_identity
package_system: npm
name: "@company/shared"
project_root: packages/shared
version: "1.2.0" # optional; omit when unavailable
```

`package_system` identifies the package naming/resolution model: initially `npm`
for npm-format packages regardless of npm/Yarn/pnpm/Bun manager choice, and `cargo`
for Cargo packages. It is not a plugin activation, programming language, registry
or selected package-manager executable. Encode this distinction once in the
shared fact, not redundantly as both a system-specific type and a field. Specify
additional supported system identifiers through the versioned contract rather
than accepting arbitrary unnegotiated semantics.

`name` is the ecosystem package name, independent of final omni naming;
`project_root` is the validated workspace-relative root the identity describes,
not a guarantee of a runnable project. Include `version` only when known from
authorized, tracked inputs; never fabricate one to satisfy the schema. Keep
publication ownership/provenance distinct from the described root, including
authorized supporting facts about explicit-only/replacement roots. Package names
are not globally unique, even within one system. A matching system/name/version
alone is not proof of a local dependency; adapters must use actual resolution
evidence. Exact name/version normalization and matching rules remain part of the
system/adapter specifications, not generic case folding or host package-manager
execution.

Publish workspace membership as one concrete relationship fact per workspace/
member pair, not one fact containing an entire member list or unresolved manifest
patterns. Illustrative payload (the common namespace/version envelope is
abbreviated):

```yaml
type: workspace_membership
package_system: cargo
workspace_root: .
member_root: crates/core
```

Both roots are validated workspace-relative locations; `.` denotes the workspace
root. The producer resolves ecosystem membership patterns using authorized,
tracked inputs and membership observations. Queries may select members of a
workspace or workspaces containing a member, with bounded results/paging over
the frozen snapshot. Fact ownership/provenance remains with the assigned publishing
root/activation; membership is not authority to write the member's state.

Neither endpoint automatically becomes a runnable omni project, and membership
alone creates no project dependency edge. Selection, exclusions and containment
remain host-authoritative: a membership fact cannot enroll a root outside the
approved project selection or revive declined/skipped inference. Supporting facts
from aggregate-only declined roots follow the same rules. Concrete relationship
facts avoid forcing consumers to copy or reparse an entire workspace member list;
the host still bounds the total number/size of emitted relationships and query
work. Complete field validation and query payloads remain specification work.

Publish package dependencies as declaration metadata plus explicit resolution
information, not merely names or preselected project edges. Illustrative payload
(the common namespace/version envelope is abbreviated):

```yaml
type: package_dependency
package_system: npm
source_root: packages/web
dependency_name: "@company/shared"
requested:
  version: "^1.2.0"
  source:
    kind: workspace
resolution:
  kind: workspace
  project_root: packages/shared
```

`source_root` identifies the workspace-relative package root whose declaration is
described; publication ownership/provenance remains separately attributed to the
assigned publishing root/activation. Preserve the dependency's declared name and
request rather than substituting the final omni name or inventing a universal
version requirement. Use structured request fields, not a raw ecosystem expression
or serialized manifest document that consumers must reparse. Represent a known
version requirement separately from a typed source descriptor, allowing both when
the ecosystem permits them. For example, Cargo's
`shared = { version = "1.2", path = "../shared" }` yields conceptually:

```yaml
requested:
  version: "1.2"
  source:
    kind: path
    path: ../shared
```

Define supported source variants such as registry, path, workspace and Git through
the omni-owned versioned schema, with explicit payload fields and ecosystem-
specific valid combinations. The sketches do not promise that every source form
is supported by the initial adapters. Preserve meaningful request information;
do not fabricate a version or collapse a combined version/path declaration into
just one component. Unsupported forms follow the adapter's documented error/
degraded-interpretation policy, not lossy conversion into a supported form.

Request descriptors are bounded validated data, never instructions for omni to
fetch, install, execute or resolve modules. In particular, a declared relative
path retains its source-declaration meaning; it is not the validated workspace-
relative root carried by a resolved workspace target. Keep path-base semantics
and any required alias/target-package distinctions explicit in the concrete
schema/adapter specifications. Do not accept arbitrary opaque document payloads
as substitutes for typed source variants. Complete variant fields and validation
rules remain specification work; the structured-request policy is resolved.

Resolution explicitly distinguishes `workspace`, `external` and `unresolved`.
Workspace resolution carries a validated concrete target root established from
authorized tracked resolution evidence; a matching package name alone is not
evidence. External resolution cannot silently select a same-named workspace
package. Unresolved means no confident target was established, not permission
to guess local or classify it as external. Concrete variant payloads and evidence
requirements remain specification work; enforce mutually consistent shapes at
native/wire/cache boundaries. Facts may retain external and unresolved declarations
without turning them into project edges. Any resulting error or documented
degraded interpretation follows the adapter's specified correctness policy.

A dependency fact describes ecosystem intent/resolution, not unconditional omni
project scheduling. Adapters separately map supported relationships to project
edges under their dependency-kind/cycle rules; surviving workspace targets still
require final runnable-project validation after explicit composition. Declined
roots publishing supporting dependency facts acquire no edge-contribution or
resolution eligibility from those facts.

Do not require shared usage, optionality or condition fields in the initial
`package_dependency` contract. Adapters retain ecosystem dependency categories
and conditions in their own parsed/state representation to decide which
relationships contribute omni edges, including avoiding invalid project cycles.
An emitted omni project edge uses the ordinary dependency semantics regardless
of whether its ecosystem origin was build-time or runtime. Preserve adapter
correctness rules and fixtures; simplifying shared facts does not authorize
adding every ecosystem dependency to the graph. Consumers cannot infer that a
published dependency fact is an adapter-approved scheduling edge or reconstruct
omitted classification from its presence. Shared classification fields are
deferred until a concrete consumer needs them, then require a versioned contract
extension rather than opaque extra fields. They are not an initial implementation
prerequisite.

Adding a shared fact type requires extending the supported versioned contract,
with producer/consumer negotiation and host validation/query support. Author-
defined namespaced schemas are deferred, not implicitly available through the
namespaced identifier syntax. Keep identifiers/versioning extensible without
implementing a general schema-registration/query language now. Package-identity,
workspace-membership and package-dependency field roles follow the shared shapes
above; complete validation/query definitions and resolution-variant payloads
remain prerequisites. Shared dependency classification is deferred. A
published dependency descriptor is metadata, not an unconditional omni
project edge or cross-plugin task reference.

For explicit-only or `inference.mode: replace` roots, another root's inference
may read the target's ecosystem manifest as an authorized, tracked supporting
input to establish dependency identity. This does not schedule the target's
skipped inference, contribute its tasks/configuration or grant writes to its
root state. The reading invocation owns the dependency evidence and its input
attribution. Such reads occur only during `infer_roots`, under the existing
declared scopes, budgets and pass-consistency checks; dependency-resolution hooks
still have no file-content service. Explicit configuration remains authoritative
for the target's omni name and tasks. Missing or ambiguous ecosystem identity
must not be guessed from directory names or final omni names. Cover replacement
roots with differing ecosystem/omni names, denied supporting reads and edits that
invalidate dependent inference without invoking the skipped root.

Batch ownership and lookup scope are distinct. A batch assigned `web` and `api`
may query published facts for `shared` in another batch, then emit edges only
for `web` and `api`. The host need not send all unrelated project/task fields.
Bulk queries avoid a host call per lookup; bound query count, scanned/indexed
work, returned bytes and aggregate host memory/CPU as well as wire payloads.
Large results need bounded paging over the same frozen snapshot, not silent
truncation that changes the graph. Snapshot access has its own stage/data
authorization rules and does not implicitly grant filesystem read permissions.
Observation similarly uses bounded frozen views rather than requiring one
unbounded final-project payload.

The default cross-activation fact/catalog visibility and the workspace's means
of granting it are not yet specified. This is a security-policy decision, not
just a query-schema detail: see [D1](018.00-readiness-and-open-decisions.md#181-open-decision-checklist).
Do not interpret “published,” a bound dependency or possession of an index handle
as an unrestricted grant while that policy is unresolved. Facts may describe
supporting roots outside the consumer's selected runnable roots, so selection
alone cannot be assumed to define safe visibility. Denied access is an error,
not an empty query; cache reuse must validate the eventually chosen policy.

Initially key query-dependent cached hooks by the relevant frozen snapshot's
semantic fingerprint, including catalog changes and published-fact deletions.
This is conservative but correct. A later optimization may track query results,
including negative/ambiguous matches and membership changes, only with complete
invalidation guarantees. Validate cached query context/authorization on reuse.
Do not let the host-call sequence or batch partition alter normalized results.
Benchmark lookup/index costs against serialization savings under [§8](008.00-performance-and-shared-safeguards.md#8-performance-is-a-contract)'s batch
sweeps. Instance-local snapshot caching is optional and reconstructible; a
plugin cannot require the same runtime instance for subsequent lookups/hooks.

Observation has no state writes. Capability handlers declare a supported-hook
set; typed methods have identity/no-op defaults for omitted hooks. SDK/native
registration validation rejects declarations without implementations and
implementations without declarations. The host never calls an omitted hook.
