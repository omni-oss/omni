### 8.3 Fine-grained execution-cache integration

The inference cache avoids rerunning discovery hooks; the task execution cache
avoids rerunning selected commands and restores their prior results/outputs.
Sharing storage does not connect their keys automatically. Integrate inferred
configuration into task execution identity explicitly, without representing a
logical config id as a physical file input.

Task-cache policy may be inferred by the plugin, including inputs/outputs and
enablement where supported by its adapter contract. Built-ins emit no
`cache.enabled` value ([§4.3](004.01-native-ecosystem-adapters.md#43-initial-native-ecosystem-plugins)); effective enablement follows
[§7.1](007.00-project-modes-and-apply.md#standard-host-managed-defaults)'s tier
order, ending in the host fallback `false` for inferred tasks. Presence-aware
composition must preserve origin tiers until extraction. This policy is independent
of reuse of discovery hook results and does not create a separate inferred-task
cache system.

`cache.enabled: false` disables both execution-cache lookup/replay and persistence,
not just writing new entries. Apply the finalized origin-aware policy **before**
local/remote lookups and recheck eligibility at replay; do not restore an older
entry after the workspace/plugin disables caching. Persistent tasks likewise
remain ineligible under ordinary execution policy. Existing `--no-cache` write-only
flag semantics and force options are separate and are not silently changed here.

This needs a concrete correction in current code: `CacheManager::get_cached_results`
passes every available `TaskExecutionInfoExt::execution_info()` to the store, that
extension does not test `cache_enabled`, and `BatchExecutor` accepts returned hits
without that check. The write path already tests enablement. Filter at the
cache-lookup boundary rather than globally deleting task execution information,
which project hashing and cache-maintenance collection also consume. Test a
pre-existing local/remote entry with unchanged command/inputs after disablement:
the selected runnable task must execute, no entry may be restored or persisted,
and unrelated cache-enabled tasks still reuse their entries.

Compute a versioned **per-task effective semantic fingerprint**, after project
composition, task inheritance/lowering and final dependency resolution. Carry
it through project-data extraction, `CacheInfo`, task execution information and
the final digest construction. Audit and reuse fields already hashed there
(such as commands, arguments and dependency digests), rather than assuming
inferred commands are currently invisible or replacing existing identity inputs.
Add the missing effective semantics and ensure the combined key covers them.

#### Cache-enabled tasks and uncached dependencies

A cache-enabled task is reuse-eligible only if every **execution dependency** it
reuses through is itself cache-eligible. Current `BatchExecutor` emits
`DefaultHash::default()` for completed uncached tasks and the next task context
forwards that sentinel as a dependency digest, so the all-zero value cannot prove
freshness. It must never enter a task-cache key. This rule replaces dependency
fingerprinting for uncached work; computing real digests for uncached tasks is
not part of this RFC and would be a later explicit opt-in.

- **Implicit conflict:** if either side's enablement comes from a non-explicit source
  (plugin output, activation `defaults`, host fallback), the dependent runs as
  cache-ineligible: no lookup, replay or persistence. Report one concise
  **informational** note per run/plan, not a warning per edge. Detailed per-task
  chains, deciding sources and the demotion cause belong in dry-run/inspection
  output and tracing.
- **Explicit conflict is an error:** if the dependent's effective `cache.enabled:
  true` and the dependency's effective `false` are each decided by an authored
  explicit authored source (§7.1: authored/applied task or authored project), fail planning
  with both task names and file provenance. Evaluate this on executable dependency
  edges of the planned graph, so unrelated runs are not blocked; validation/
  inspection should still be able to report every such contradiction. Activation
  `defaults` and plugin tiers are not explicit for this rule.
- **Propagation:** demotion follows execution-dependency edges (A → B → C).
  Commandless/skipped aggregate nodes are transparent: they are eligible exactly
  when all their own dependencies are. A persistent dependency is uncached.
  `with` co-scheduling is not an execution dependency.
- **Flags:** write-only `--no-cache` keeps its existing semantics but must not feed
  the zero sentinel into any persisted key; nothing is written under it.

Record a typed **cache-eligibility status** on each task's execution result (and
dry-run/inspection output), not only in logs. Variants: `eligible`;
`disabled{deciding_source?}`; `persistent`; `no_command`; `write_only_no_cache`; and
`demoted{direct_dependency, root_cause}` naming the adjacent dependency and the
originating uncached task rather than a full chain (bounded for deep graphs).
`deciding_source` is optional and names what supplied the effective value: an
authored task/applied or project setting, a plugin task/project opinion, activation
`defaults`, or the host fallback/built-in default. It need not be a configuration
tier: it is absent for causes with no configured value (`persistent`, `no_command`,
the `--no-cache` flag), and for `demoted` the cause is the dependency, not a value.
Only the authored sources count as explicit for the contradiction error above.
Derive the aggregated informational note, CLI/JSON output and MCP inspection from
this one status; per-edge detail belongs to inspection/tracing. It is derived,
non-persisted metadata: it is not a cache-key input, is not stored in cache
artifacts, and a replayed result recomputes it from the current graph. Report
task names and tiers only, with ordinary redaction of paths/values.

This applies to handwritten and inferred tasks alike (a pre-v1 correction with a
regression note) and needs no cache storage or remote-format change.

Propagate the contribution to every collector input constructor, not just the
normal executor. `ProjectHasher::hash` constructs `ProjectTaskInfo` directly;
`HybridTaskExecutionCacheStore` constructs it for task lookup and recomputes fresh
digests for stale pruning. These paths must agree on the same canonical task and
semantic contribution or workspace hashes/cache staleness can contradict ordinary
execution. Include project/workspace hash and cache stats/prune regression fixtures.
`CacheManager::cache_results` also constructs collector inputs directly in its
dry-run branch; a display-only run must not accidentally calculate a different
notion of current semantic identity.

Provide a named, versioned digest-contribution slot (for example,
`effective-task-config/v1`), not a virtual path or synthetic file input. Omni
computes the contribution from the final effective semantics; a plugin-emitted
signature is not authoritative after explicit overrides. Use omni's existing
content hasher over an explicitly stable canonical encoding, not Rust's standard
`Hash`/`DefaultHasher` contract. Compute once per finalized task; prefer streaming
fixed-order, type/length-framed fields without allocating an intermediate JSON
string. Canonicalize unordered maps and preserve order-sensitive lists. Cover
encoding/version stability with golden tests and benchmark the actual path.

Choose the finest granularity that can be proven correct: only the task's
execution-relevant effective fields, inherited settings actually consumed by
that task and resolved dependency semantics participate, not the entire project
or plugin output. Include literal/expandable interpretation modes where they
change execution. Exclude provenance, plugin timings, notices, redaction policy
and display-only settings; metadata used in command/execution expressions is
not display-only. Preserve ordinary declared file/environment inputs and
dependency-result hashing, which cover runtime inputs beyond task definitions.
Version and test the semantic projection and its canonical encoding; use
conservative invalidation where a dependency cannot safely be narrowed.

The audit must also distinguish definition semantics from runtime context.
`omni_collector` currently hashes raw command configuration, not the command after
Tera/environment resolution. A fixed expression can consume changing metadata,
environment or platform values while its raw text stays unchanged. Ensure every
execution-affecting context value is covered by effective semantic projection or
ordinary runtime inputs; the new digest must not justify dropping existing inputs
or assume a raw command hash proves equivalence. Cover literal command operands
and single-pass substitution under [§6.3](006.03-data-boundary-and-literal-values.md#literal-command-operands).

Task semantic identity cannot make an unrepeatable side effect cacheable, nor
restore outputs that ordinary replay refuses to overwrite. Inferred tasks without
a higher-tier enablement opinion are uncached; workspace configuration or an
opinionated plugin can opt them in. Discovery does not certify that any
script is safe to skip; adapter input/output specifications remain release
prerequisites.
The current cache store recollects digests after execution. A mutating task with
complete inputs may therefore be keyed by its post-state rather than its incoming
state; safe reuse needs an explicit idempotence/effect argument and fixtures.
Do not assert that adding source inputs can never prevent an unsafe hit, or
silently redesign task caching around pre-execution snapshots in this RFC.

Plugin artifact/build, options and observed discovery inputs invalidate
inference as appropriate, but do not independently invalidate task execution
when the resulting task semantics and ordinary execution inputs are unchanged.
For example, a manifest edit affecting only a sibling task should not change
this task's added fingerprint. Existing explicit config-file hashing can still
cause broader invalidation; this change does not silently remove those inputs
or promise fine-grained explicit-file invalidation without a separate design.

The added semantic identity remains mandatory with `cache.key.defaults: false`:
that switch controls default file inputs, not permission to reuse results after
the task definition changes. Apply this origin-independently to explicit and
inferred effective tasks; disabling caching entirely uses `cache.enabled: false`,
not `cache.key.defaults: false`. Cache lookup happens only after successful current
inference/composition, so an old task result cannot conceal a failed discovery
stage. A miss follows normal scheduling/execution; no separate plugin executor
or unconditional rerun is introduced.

Tests must demonstrate that changed effective inferred semantics miss the task
cache, unrelated sibling contributions do not change the added fingerprint,
plugin updates producing identical semantics retain the same added fingerprint,
explicit overrides mask irrelevant inferred changes, inherited execution changes
invalidate affected tasks, presentation-only changes do not affect semantic
identity, and disabling default file inputs cannot disable semantic invalidation.
