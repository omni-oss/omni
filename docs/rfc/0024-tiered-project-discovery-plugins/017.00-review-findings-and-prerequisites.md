## 17. Resolved review findings and remaining specification prerequisites

The preceding sections record the agreed architecture. The items below track
gaps found during review; their status paragraphs distinguish resolved policy
decisions from remaining specification prerequisites. The original review's
architectural choices are resolved; subsequent inference-dependency refinements
have the explicit remaining specifications listed in [§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings). Complete prerequisites before
implementing the affected contract; they do not require executable scaffolding
to investigate. The already agreed adapter specifications, calibrated limits,
Wasm engine/ABI design and semantic-digest field audit remain prerequisites to
their affected components, not all foundation work. The fresh code-grounded
assessment and the only active decision checklist are in
[§18](018.00-readiness-and-open-decisions.md#18-code-grounded-readiness-and-open-decisions).
Historical options below are rationale, not requests to decide them again.

### 17.1 Inferred collection operations versus conflict detection

**Status: resolved.** Adopt option 1 using `CollectionConfigValidator` on enclosing
configuration types and field-level deserialization drivers ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)), leaving
`ListConfig`/`DictConfig` unchanged. Non-additive serialized plugin/cache operations
fail during deserialization; direct typed native output must enforce the same
policy at its boundary. The context/options below retain the review
rationale. The initial list profile accepts plain lists and `append` only ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts));
field-specific duplicate handling is defined in [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts). Preserve raw operations
until composition finishes; normalize resolved edges and cache environment names
without deduplicating meaningful repetitions or command arguments. The complete
field/operator inventory and conformance fixtures remain specification work.

**Context/problem:** [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts) promises disjoint composition and no implicit winner,
but also permits shared collection semantics in stable plugin-id order. Today's
`ListConfig` supports positional `merge` and destructive `replace`; `DictConfig`
supports `replace`. Those are not simply additive contributions. If A emits a
`build` task and B emits `tasks: {replace: {test: ...}}`, ordinary layer replay
can erase A's disjoint task without a conflict. Changing aliases can change
which contribution survives. Identical ordered-list values also need a defined
coalescing rule: deduplication is not correct for every execution-sensitive list.

**Options:**

1. Restrict plugin output to partial values/additive collections; reserve
   destructive/positional operations for explicit layers.
2. Allow plugin operations, but model overlapping/destructive effects as
   conflicts rather than silently applying ordinary last-writer behavior.
3. Let sorted plugin ids determine all operation effects, accepting erasure.

**Decision:** option 1 for the initial protocol, with explicit field-level
rules for additive lists and duplicate values. Keep the full shared operator
language for handwritten layers. Plugin lists accept plain additions and `append`,
not `prepend`, `replace` or positional `merge`; preserve meaningful internal order/
repetitions and normalize dependency edges after target resolution ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)).
Broader plugin-side operations would require a
future contract change, not an implicit exception to the validator. In particular,
test explicit masking at leaf/subtree boundaries, equal text with different
interpretation modes, positional list operations and alias changes. Conflict
markers must survive until the explicit operation that actually resolves them;
an unrelated explicit edit must not hide a conflict.
Add plain-list/`append` equivalence, rejected plugin `prepend` even when later
discarded, stable contributor ordering, retained meaningful repetitions and
dependency-edge deduplication fixtures across native/Wasm/cache boundaries.
Cover duplicate environment names within/across contributors and explicit layers,
one effective hash input per name, overlapping file patterns, distinct dependency/
`with` relationships, repeated argv entries, and positional explicit operations
whose addressed entries would change if normalization happened too early.
Explicit `prepend` and dictionary `merge` envelopes remain valid and need
regression coverage.

### 17.2 Frozen facts do not imply frozen filesystem inputs

**Status: resolved.** Capture/revalidate inputs and reject detected concurrent
changes by default. Implement and test bounded automatic restarts for future use,
but leave them disabled by default (zero retries).

**Context/problem:** [§6](006.00-hooks-and-lifecycle.md#6-discovery-and-the-host-contract)
and [§8](008.00-performance-and-shared-safeguards.md#8-performance-is-a-contract) freeze host state and track file dependencies, but do
not define what happens when a file changes during discovery or cache-hit
validation. For example, two batches can read different versions of a workspace
lockfile, or a manifest can change after its cached dependency record was checked.
Publishing both results can produce an internally inconsistent graph even though
each individual read was authorized. A watcher notification is not proof that
the bytes used by a hook matched the bytes validated for publication.

**Options:**

1. Accept best-effort live reads and document possible mixed-version results.
2. Use a command-local input view, memoize reads/missing paths/membership, and
   revalidate observed inputs and selection before accepting the discovery result;
   restart on detected changes with a bounded retry policy.
3. Require an actual filesystem snapshot for every discovery pass.

**Decision:** option 2's captured view/revalidation, with default rejection rather
than automatic retries. Hash the bytes actually supplied, share one read
view across plugins and cache validation, and detect changes to explicit layers,
markers and observed membership as well as content. Publish reusable entries and
user-facing hook notices only after both stage success and pass consistency
validation. A detected change discards the provisional pass and fails actionably
without stale fallback or task execution. Retain existing valid cache entries.

Include the workspace configuration and any configuration layers supplying
activation, selection, options or permission ceilings in this capture/revalidation
set. Bootstrap must retain evidence of the bytes actually loaded, not start
tracking only after those values selected descriptors and scheduled hooks. A
configuration change during the pass cannot leave an accepted graph authorized
under one view while cache publication claims another. This does not promise an
atomic filesystem snapshot or retroactive revocation after final acceptance.

Provide a host-owned bounded restart policy, disabled by default, for future use
and explicitly enabled tests. Its exact public configuration/CLI spelling is not
required now. A restart reconstructs the input view and semantic session from
scratch, revalidating cache hits; private plugin memory may be reused only under
the observational-statelessness contract. Do not carry rejected-attempt semantic
state, graph fragments or notices into the new pass. Bound attempts and total
command work/deadline so retries cannot multiply the discovery budget. Retry
only detected concurrent-input changes, not arbitrary plugin errors, permission
denials, malformed output or timeouts. Exhaustion fails with an actionable
concurrent-change diagnostic identifying bounded relevant paths.

Required tests cover default immediate rejection/no retry, enabled restart
success after one mutation, restart exhaustion under repeated mutations,
cancellation, fresh per-attempt input/session state and absence of rejected-pass
cache publication, task execution or duplicate/leaked user-facing notices. Cover
mutations during reads, cache-hit validation and pass finalization, including
creation/deletion of previously missing files and marker/membership changes.

Specify the residual race guarantee honestly:
revalidation is not a transactional filesystem snapshot and cannot prevent an
edit immediately after validation. Reject detected changes; do not claim to
detect every possible concurrent mutation.

### 17.3 Root-based references for task dependency fields

**Status: resolved.** Adopt option 2: a `ProjectRoot` task-reference variant in
both `dependencies` and `with`, lowered after composition/task inheritance to
final project names ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)). Also accept both `project#task` shorthand and
`{ project, task }` objects for explicit-project references in handwritten files.

**Context/problem:** [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics) defines root references for project dependencies, but
tasks also have `dependencies` and `with`. Today's
`TaskDependencyConfiguration::ExplicitProject` stores a project name, while
`Own` and `Upstream` do not need one. A plugin emitting `@company/shared#build`
can still break when an explicit file renames that project to `common`, despite
the RFC's root-reference guarantee. Resolution hooks currently return project
edges only and cannot repair those task fields afterward.

**Options:**

1. Initially permit only own/upstream task references in plugin output; reject
   explicit cross-project task references.
2. Add a typed root-plus-task reference for plugin task `dependencies` and
   `with`, lowering surviving references after explicit composition.
3. Permit final-name strings and narrow the rename guarantee to project edges.

**Decision:** option 2, plus equivalent explicit-project shorthand/object syntax.
Do not silently assume project-edge resolution solves task references. Preserve
the same replacement-before-target-validation rule, provenance and malformed
path checks. Fixtures must cover renames, removed target tasks, `with`, upstream
references and explicit task/collection replacement. Root-to-name lowering runs
after task extensions and before executable dependency conversion/final target
validation, as specified in [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics).

### 17.4 Published facts and the pre-composition root catalog

**Policy: resolved; shared fact/query specification required.** Use a minimal
typed, namespaced published-fact contract for cross-plugin project-edge resolution,
not opaque session-state queries or automatic cross-plugin task coordination.
Permit authorized, tracked supporting
manifest reads during another root's inference to establish dependency identity,
without running inference or contributing configuration for the replacement root
([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)). Its explicit configuration controls its tasks and omni name. The precise
shared fact schema/query vocabulary remains a prerequisite to implementation.
Vocabulary ownership is resolved: start with omni-defined, namespaced/versioned
package-identity, workspace-membership and dependency-metadata fact families.
All plugin tiers can use them; author-defined fact schemas are deferred ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)).
Fact shapes, meanings and queries are versioned with `project_discovery`, not
independently per fact or by the producer's package version. Required features
and any cross-API compatibility mappings are validated before hooks ([§14.2](014.00-versioning-compatibility-and-migrations.md#142-negotiation)).
Package identity uses one shared fact type with `package_system`, ecosystem `name`,
workspace-relative `project_root` and optional known `version`. Do not duplicate
the system distinction in separate npm/Cargo fact types or fabricate versions.
Workspace membership likewise uses a shared fact type with `package_system`,
`workspace_root` and `member_root`, one concrete relationship per fact ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)).
Forward/reverse queries are bounded; raw patterns and whole-member-list facts are
not the interchange shape. Membership does not establish project existence,
selection eligibility or a dependency edge.
Package dependencies use shared declaration metadata plus explicit workspace,
external or unresolved resolution ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)), preserving the declared name/request
and a concrete root only for an evidenced workspace target. Requests use a
version requirement plus a
typed source descriptor where applicable, not raw manifest syntax, and never
instruct the host to fetch or execute anything. Fact publication is
separate from project-edge contribution; complete variant payloads and dependency
validation/query rules still need specification. Shared usage/optional/condition
fields are deferred; adapters retain the classifications needed for their own
correct edge/cycle policy ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)).

**Context/problem:** [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle) requires a versioned shared fact vocabulary, but does
not yet define its fields, ownership or query authorization. Resolution happens
before final explicit composition. An approved candidate may be declined, a
project may be a base template, and a `replace` root emits no plugin identity
facts at all. Merely including an explicit-only root in the catalog cannot tell
a JavaScript plugin its package identity. Raw inferred facts must not be confused
with final task availability or an explicitly overridden omni project name.

**Options:**

1. Publish only host root/status facts; keep ecosystem resolution within each
   activation until a cross-plugin schema is justified.
2. Define a minimal typed, namespaced published-fact schema and query contract
   now, separating candidate approval, inferred acceptance and final runnability.
3. Publish opaque plugin-defined documents with a generic query language.

**Required specification:** option 2 implements the shared fact/catalog design
already agreed in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle). Specify producer/consumer feature negotiation, fact size/index
limits, duplicate/ambiguous identities and visibility rules. Separate ecosystem
identity from omni naming and distinguish preliminary from final facts. Catalog
membership alone grants neither a local identity match nor a runnable target.
For replacement/explicit-only roots, authorized supporting manifest reads may
supply identity during another root's inference, as agreed in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle); never run a
skipped root's inference just to populate the catalog. If those reads cannot
establish an unambiguous identity, do not invent one.
Options 1 and 3 are historical alternatives, not unresolved policy choices or
implicit fallback behavior. Automatic cross-plugin task coordination remains
separately deferred under [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics).
Declared inference dependencies may consume frozen published typed facts during
their own inference ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)), without waiting for the global resolution stage.
The declaration/binding, facts-only surface and omni-defined vocabulary ownership
are agreed; concrete fact schemas, bounded query/authorization definitions,
feature-negotiation details and variant validation remain prerequisites.
Required producers need not publish particular data: a successful empty view/query
is interpreted by the consumer's documented rules, not a host missing-dependency
failure ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)). Execution/permission/version failures never become empty success.
Raw manifests, private state and inferred/effective project configuration are not dependency-handle
outputs, and later execution grants no override priority.

### 17.5 Batch-independent results versus resource-dependent outcomes

**Status: resolved.** Adopt option 2: per-root logical limits, bounded transport
batches and deterministic splitting for attributable aggregate size overflows
([§8.1](008.00-performance-and-shared-safeguards.md#81-shared-safeguards)), with cache resource handling in [§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches). Successful normalized semantics are
batch-independent; resource/deadline outcomes need not be.

**Context/problem:** [§6](006.00-hooks-and-lifecycle.md#6-discovery-and-the-host-contract)
and [§8](008.00-performance-and-shared-safeguards.md#8-performance-is-a-contract) require batch invariance, but the proposed envelope
uses per-batch byte/deadline limits and an aggregate deadline. Two roots may
each fit an 8 MiB output limit yet fail when batched together. A cached large
batch can also be rejected under a smaller current limit even though the same
roots would fit separately. Thus successful semantic output can be invariant
while success/failure still depends on host partitioning and cache warmth.

**Options:**

1. Limit the invariance promise to successful normalized results and explicitly
   allow resource failures to depend on physical batches.
2. Define per-root logical accounting plus bounded transport batches and a
   deterministic split/retry policy for attributable size overflows.
3. Fix batch membership as part of the semantic protocol and persistent key.

**Decision:** option 2 for count/byte/state accounting, and explicitly
acknowledge option 1's unavoidable deadline limitation. Keep finite host-wide
limits and do not retry arbitrary traps/timeouts as if splitting guaranteed
success. Cache granularity is resolved: per-root logical records for root-oriented
hooks, bounded singleton records for workspace-wide hooks, with physical bulk
storage allowed ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)). Accounting policy is resolved: charge actual host/runtime
work, including unsuccessful split/retry attempts, without hypothetical execution
charges for cache hits. Apply identical logical result limits to hits and live
roots and bound aggregate accepted results. Concrete counters/defaults still
require specification/calibration; retries cannot multiply the total budget.
Test oversized single roots, combined-output overflow, cached results under
reduced limits and different partitions. Verify bounded split attempts, aggregate
charging, original stage-state reuse, failed-attempt invisibility and no automatic
splitting on unrelated errors. Distinguish size-overflow recovery from disabled-
by-default concurrent-input restart tests. Do not promise wall-time invariance.

### 17.6 Artifact digests versus mutable artifact loading

**Status: resolved.** Adopt option 2: hash and load the same bounded captured
manifest/module bytes ([§15.3](015.00-remote-source-integration.md#153-source-types-and-artifact-layout)), without reopening mutable paths for execution.

**Context/problem:** [§15](015.00-remote-source-integration.md#15-remote-source-integration) protects checkout lifetime with leases and fingerprints
local modules, but retention is not immutability. A local manifest/module can
change between fingerprinting and engine loading. Re-reading its path can execute
bytes different from the artifact digest used for trust, state and cache identity.
The same issue affects dynamically loaded bundled modules if only the entry bytes
were frozen. A GC lease does not prevent modification by another process.

**Options:**

1. Load directly from paths after hashing and accept the race.
2. Resolve a bounded immutable byte snapshot of the verified manifest/module
   closure and compile/load only those bytes.
3. Copy every local artifact into a verified content-addressed store before use.

**Decision:** option 2 as the minimum correctness/security contract;
option 3 may implement it when storage reuse is worthwhile. Verify the closure
and execute the exact captured bytes; deny later filesystem/module resolution
outside that snapshot. Treat a local edit as a new descriptor/session on the
next refresh rather than mutating a live instance's identity. Distinguish shared
checkout retention from verified module ownership. Test entry/import mutation,
symlink swaps and edits between hash verification and instantiation.

### 17.7 Candidate disposition and hook eligibility

**Status: resolved.** Adopt option 2 with explicit per-activation/root dispositions
and the host-owned transition table in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle). Resolution-only participants require
an explicit capability declaration; omitting inference does not opt into resolution.
Inference result shape is also resolved: use distinct tagged accepted/declined
alternatives with exactly one result per assigned root
([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle) and
[§12.3](012.00-rust-trait-sketches.md#123-host-owned-state)), not a boolean
and optional contribution fields. Declined results cannot contain project/edges;
accepted-empty results still require final validation. Missing/duplicate/unassigned
results fail, and state/facts/notices do not imply acceptance.
Declined inference roots may publish authorized bounded supporting facts, including
aggregate-workspace membership, without creating projects or regaining resolution
eligibility. Other eligible roots may query those facts under the ordinary frozen
snapshot visibility rules; caches preserve facts and disposition together ([§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)).

**Context/problem:** the lifecycle allows a filter or inference hook to decline
a root, and allows plugins to omit hooks, but does not define the exact resulting
schedule. If A declines a root that B accepts, A must not accidentally regain
write ownership during resolution. If every plugin declines an inferred-only
candidate, root state or dependency facts alone must not manufacture a project.
An explicit project at that root must remain usable independently.

**Options:**

1. Retain every marker candidate through all hooks and infer project existence
   from whichever output happens to be present.
2. Define explicit per-activation/root dispositions and stage eligibility,
   separately from the host's project-existence decision.

**Decision:** option 2. Specify the difference between declining a root,
returning an empty fragment, publishing supporting facts and preserving state.
Define identity transitions for omitted filter/inference hooks, which accepted
roots resolution may update, and whether observation is workspace-wide or
limited to contributed roots. Preserve other plugins' acceptance and explicit
projects; only final validated effective projects become runnable. Implement
[§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle)'s hook/disposition transition table and fixtures before finalizing request types.

### 17.8 Scoped object references and alias-aware selectors

**Status: resolved.** Object qualification, implicit cross-root binding and selector
policy are agreed. Deliberate cross-plugin task wiring is explicit-configuration-
only initially; automatic plugin-to-plugin task coordination is deferred.
Use optional `plugin` alongside `project`/`project_root` and raw `task` ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
The scoping, reference escaping and per-project alias policies are agreed ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).
Positional selectors are exact; repeatable `--task-pattern` selectors match
canonical names and aliases. Either or both may be supplied, including pattern-
only requests, followed by union and canonical deduplication ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)), within the
existing task-filter/execution-plan pipeline. Inferred task references stay within
the originating activation, independent of the target's public aliases ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).
The surface matrix in [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases) limits `extends`/aliases to same-project targets and
rejects upstream CLI/MCP selectors. Each exact selector must exist in the project/
directory selection scope before metadata/affected narrowing; one matching project
suffices for an unqualified name. Other selectors cannot mask a missing exact
target, while later filter exclusion is not a missing-task error.

Today's `TaskDependencyConfiguration` has string task components and string-only
serde. The proposed two-field `{project, task}` / `{project_root, task}` objects
cannot distinguish a literal local name `native::build` from scoped `(native,
build)` if components remain raw, as required. The agreed optional `plugin`
field supplies that distinction. Implement its strict schema and structured
identity; do not reinterpret a raw object component as shorthand.
Own/upstream and implicit cross-root references retain originating activation
context. Users wire cross-plugin task dependencies explicitly with `plugin` or
their authored public aliases; plugins cannot emit cross-activation task targets
or follow public aliases. Automatic coordination is deferred, without deferring
cross-plugin project-edge resolution through the shared fact catalog. Cover rejected
plugin attempts to select another activation, literal qualification-looking names,
valid explicit cross-plugin dependencies, direct missing
targets, upstream missing-task skips, multiple activations, changed public aliases,
explicit handwritten selection, inheritance and cache round trips.

Today's task filter consumes globs over executable names. Extend selection to
all public canonical/alias names and deduplicate their canonical targets ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)),
with project/metadata/affected filtering on the underlying tasks. Implement exact
selectors and explicit patterns as separate paths: literal wildcard selection
uses the exact path, while patterns match canonically rendered names using the
shared glob model. Preserve reference backslashes without an accidental extra
reference-decoding pass. Add scoped/literal
object/shorthand round trips, per-project upstream alias selection, missing
upstream tasks, project filters and escaped pattern fixtures. Keep aliases out
of executable node maps.

### 17.9 Task declaration-kind composition

**Status: resolved.** Normal-task pairs merge field by field; changes between
normal-task and alias declarations replace the entry atomically. Alias/alias
composition selects the higher explicit target without merging task settings
([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics) and
[§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).
Adopt consistent field-level composition for all normal short/full-form pairs
using presence-aware shorthand expansion before composition ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)). This is an
intentional pre-v1 correction, not preservation of today's mixed-form replacement.
The no-hidden-inheritance and qualified-override policies remain agreed. Current
`TaskConfiguration::merge` field-merges long/long forms but replaces the entire
task for short/long, long/short and short/short pairs. `into_long_form` additionally
introduces defaults and an implicit upstream self-task dependency. Reusing either
unchanged can contradict presence preservation or a qualified partial override.

Implement the agreed normal-task short/short, short/long, long/short and long/long
matrix with identical per-field rules; do not retain representation-based whole-
task replacement. Expand each shorthand declaration once into its command and
implicit upstream dependency, with other inheritable fields absent. Test qualified
overrides, explicit `extends`, dictionary replacement, retained command/env/cache
fields, implicit dependency addition/removal and migration examples. Preserve
operation order, declaration-local template status and original reference binding;
never use today's eager-default `into_long_form` unchanged for patch expansion.

Implement normal-task/alias transitions under [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases), including qualified inferred
entries redirected by explicit aliases. No execution/settings fields survive
normal-to-alias replacement, and alias-to-normal replacement never imports the
target's configuration. Test alias/alias target replacement, explicit extension
layers, reference redirection, cycles, missing targets and malformed mixed
declarations. Input-boundary shape validation still rejects an alias carrying
task overrides even when a later layer would replace it.
Commandless tasks remain valid under the existing model; missing `exec` is not
a substitute for checking contributor binding or actual final constraints.

### 17.10 Canonical task identity versus invocation identity

**Status: resolved.** Retain the existing execution model; multiple argument
bindings for one canonical task in a single plan are out of scope. Users may
define distinct named tasks through `extends` with different `args`.
Aliases share canonical task/configuration/cache identity; distinct execution
arguments must not be accidentally coalesced. Today's `omni_core::TaskKey` uses
only project/task, while task context and override-argument lookup are also keyed
by project/task. These structures do not represent multiple argument bindings
for one canonical task within a single execution graph.

[§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases) preserves argument distinctions across invocations already supported by
omni; it does not add argument-specific nodes for one canonical task in a plan.
Equivalent alias selections deduplicate to that canonical task. Separate command
calls retain ordinary argument-sensitive hashing/execution. Any future support
for multiple bindings in one plan needs a separate invocation-key and dependency/
result/context design, not merely reference lowering.

For simultaneous variants, explicit task inheritance already creates distinct
task definitions and identities. Assuming the inferred command consumes
`args.profile`, for example:

```yaml
tasks:
  build-debug:
    extends: native::build
    args:
      profile: debug
  build-release:
    extends: native::build
    args:
      profile: release
```

Both named tasks may be selected in one plan without becoming aliases or
overriding the underlying inferred task. Merely setting `args` does not append
command-line flags: the inherited command must consume those argument values,
or the derived task must explicitly override its command. Test distinct derived
task identities, inherited settings/reference binding, argument-sensitive cache
behavior across separate calls, and canonical deduplication through aliases.
