## 17. Resolved review findings and remaining specification prerequisites

A decision log for gaps found during review. Each entry states the problem, the
resolved decision and where the normative rule lives; the options considered are not
repeated, and none of these decisions is open. Remaining specification work (claim
schemas, adapter tables, calibrated limits, field audits) must be completed before
the affected contract is implemented and is tracked in
[§18](018.00-readiness-and-open-decisions.md#18-code-grounded-readiness-and-open-decisions).

### 17.1 Inferred collection operations versus conflict detection

**Problem.** Today's `ListConfig` (positional `merge`, destructive `replace`) and
`DictConfig` (`replace`) are not additive. If plugin A emits `build` and plugin B
emits `tasks: {replace: {test: ...}}`, layer replay can erase A's task without a
conflict, and deduplication is wrong for execution-sensitive lists.

**Decision.** Plugin output is partial values and additive collections only; the full
operator language stays for handwritten layers. `CollectionConfigValidator` on the
enclosing types and field-level deserialization drivers enforce this
([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts));
`ListConfig`/`DictConfig` are unchanged.

- Plugin lists accept plain additions and `append`; `prepend`, `replace` and positional
  `merge` are rejected during deserialization, and direct typed native output
  enforces the same policy.
- Preserve raw operations until composition finishes. Normalize resolved dependency
  edges and cache environment names afterwards, without deduplicating meaningful
  repetitions or argv entries.
- Conflict markers survive until an explicit operation actually resolves them.

**Required fixtures.** Explicit masking at leaf/subtree boundaries; equal text with
different interpretation modes; positional operations whose addressed entries would
change if normalization ran too early; alias changes; plain-list/`append`
equivalence; rejected plugin `prepend` even when later discarded; stable contributor
order; duplicate environment names and overlapping file patterns (one effective hash
input per name); distinct dependency/`with` relationships; repeated argv entries;
regression coverage for explicit `prepend` and dictionary `merge`.

### 17.2 Frozen claims do not imply frozen filesystem inputs

**Problem.** Frozen host state does not freeze the filesystem. Two batches can read
different versions of a lockfile, or a manifest can change after its cache record was
validated, producing an inconsistent graph from individually authorized reads.

**Decision.** Use a command-local captured input view and revalidate before accepting
the pass. Detected changes **reject** the pass by default; bounded automatic restart
is implemented and tested but disabled (zero retries).

- **Capture:** hash the bytes actually supplied; share one read view across plugins
  and cache validation; track explicit layers, markers and observed membership as well
  as content. The set includes the workspace configuration and any layer supplying
  activation, selection, options or permission ceilings, captured from the bytes
  actually loaded during bootstrap.
- **Publication:** reusable entries and user-facing notices are published only after
  stage success and final consistency validation. A rejected pass discards its
  provisional state, fails actionably, runs no tasks and uses no stale fallback.
  Existing valid cache entries are retained.
- **Restart (default off, exact spelling not required now):** rebuild the input view
  and semantic session from scratch and revalidate cache hits; private plugin memory
  may be reused only under observational statelessness; carry no rejected-attempt
  state, graph fragments or notices. Bound attempts and total work/deadline so retries
  cannot multiply the budget. Retry only detected concurrent-input changes, never
  plugin errors, denials, malformed output or timeouts. Exhaustion fails with a
  concurrent-change diagnostic naming bounded relevant paths.
- **Honest guarantee:** this is not a transactional snapshot. It cannot prevent an
  edit just after validation, so it rejects _detected_ changes and does not claim to
  detect every mutation.

**Required tests.** Default rejection without retry; restart success after one
mutation; exhaustion under repeated mutation; cancellation; fresh per-attempt state;
no cache publication, task execution or leaked notices from a rejected pass; mutations
during reads, cache-hit validation and finalization, including creation/deletion of
previously missing files and marker/membership changes.

### 17.3 Root-based references for task dependency fields

**Problem.** Project dependencies have root references ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)),
but task `dependencies` and `with` do not: `ExplicitProject` stores a project name, so
a plugin emitting `@company/shared#build` breaks when an explicit file renames that
project.

**Decision.** Add a `ProjectRoot` task-reference variant to `dependencies` and `with`,
lowered after composition and task inheritance to final project names. Handwritten
files also accept `project#task` shorthand and `{ project, task }` objects. Keep the
replacement-before-target-validation rule, provenance and malformed-path checks.
Lowering runs after task extensions and before executable dependency conversion and
final target validation ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).

**Required fixtures.** Renames, removed target tasks, `with`, upstream references and
explicit task/collection replacement.

### 17.4 Published claims and the pre-composition root catalog

**Problem.** Resolution runs before explicit composition. A candidate may be declined,
a root may be a base template, and a `replace` root emits no plugin identity claims,
so a root catalog alone cannot tell a JavaScript plugin its package identity.

**Decision.** A minimal typed, namespaced, versioned published-claim contract
([§6.1](006.01-claims-and-queries.md)), not opaque state queries or automatic
cross-plugin task coordination.

- omni defines the initial vocabulary (package identity, workspace membership,
  dependency metadata); all tiers use it; author-defined schemas are deferred. Shapes
  are versioned with `project_discovery`, with features validated before hooks
  ([§14.2](014.00-versioning-compatibility-and-migrations.md#142-negotiation)).
- Package identity is one shared type (`package_system`, `name`, workspace-relative
  `project_root`, optional known `version`); membership is one shared type
  (`package_system`, `workspace_root`, `member_root`), one relationship per claim.
  Membership proves neither project existence, selection eligibility nor an edge.
  Never fabricate versions or duplicate per-ecosystem claim types.
- Dependencies carry declaration metadata plus explicit workspace/external/unresolved
  resolution, a version requirement and a typed source descriptor, never raw manifest
  syntax and never an instruction to fetch or execute. Usage/optional/condition fields
  stay with adapters.
- Authorized, tracked supporting manifest reads may establish identity for a
  replacement or explicit-only root during another root's inference; never run a
  skipped root's inference to populate the catalog, and never invent an identity.
- Declared inference dependencies may consume frozen published claims
  ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)).
  An empty successful view is interpreted by the consumer's rules, not a host
  missing-dependency failure; execution, permission and version failures never become
  empty success. Raw manifests, private state and inferred/effective configuration are
  not dependency outputs.

Concrete schemas, bounded query/authorization, feature negotiation and variant
validation remain specification prerequisites ([§6.4](006.04-hook-and-claim-schemas.md#64-hook-claim-and-query-schemas-project_discovery-v0)).
Automatic cross-plugin task coordination stays deferred ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)).

### 17.5 Batch-independent results versus resource-dependent outcomes

**Problem.** Two roots can each fit an 8 MiB output limit yet fail when batched
together, and a cached large batch can fail under a smaller current limit. Semantic
output can be invariant while success still depends on partitioning and cache warmth.

**Decision.** Per-root logical limits, bounded transport batches and deterministic
splitting for attributable size overflows ([§8.1](008.00-performance-and-shared-safeguards.md#81-shared-safeguards),
[§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)).
Successful normalized semantics are batch-independent; resource and deadline outcomes
need not be, and wall-time invariance is not promised.

- Keep finite host-wide limits; do not retry traps or timeouts as if splitting would
  help; retries cannot multiply the total budget.
- Cache records are per-root for root-oriented hooks and bounded singletons for
  workspace-wide hooks, with physical bulk storage allowed.
- Charge actual host/runtime work including failed split attempts; no hypothetical
  charge for cache hits. Identical logical limits apply to hits and live roots, and
  aggregate accepted results are bounded. Concrete counters need calibration.

**Required tests.** Oversized single roots; combined-output overflow; cached results
under reduced limits; different partitions; bounded split attempts; aggregate charging;
original stage-state reuse; failed-attempt invisibility; no splitting on unrelated
errors. Keep these separate from the default-off concurrent-input restart tests.

### 17.6 Artifact digests versus mutable artifact loading

**Problem.** A local manifest or module can change between fingerprinting and engine
loading, so re-reading a path could execute bytes other than the digest used for trust,
state and cache identity. A GC lease does not prevent modification.

**Decision.** Hash and load the **same bounded captured bytes** of the manifest/module
closure ([§15.3](015.00-remote-source-integration.md#153-source-types-and-artifact-layout));
never reopen mutable paths for execution, and deny later filesystem/module resolution
outside the snapshot. A content-addressed store may implement this when reuse is
worthwhile. A local edit becomes a new descriptor/session on the next refresh. Checkout
retention is distinct from verified module ownership.

**Required tests.** Entry/import mutation, symlink swaps, and edits between hash
verification and instantiation.

### 17.7 Candidate disposition and hook eligibility

**Problem.** The lifecycle lets filter or inference hooks decline a root and lets
plugins omit hooks, but did not fix the resulting schedule. A declining plugin must not
regain write ownership in resolution, and claims or state alone must not create a
project.

**Decision.** Explicit per-activation/root dispositions with the host-owned transition
table in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle),
separate from the host's project-existence decision.

- Resolution-only participation needs an explicit capability declaration; omitting
  inference does not opt in.
- Inference returns distinct tagged accepted/declined alternatives, exactly one per
  assigned root ([§12.3](012.00-rust-trait-sketches.md#123-host-owned-state)). Declined
  results contain no project or edges; accepted-empty results still face final
  validation; missing, duplicate or unassigned results fail.
- State, claims and notices never imply acceptance. Declined roots may publish bounded
  supporting claims (including aggregate workspace membership) under ordinary frozen
  visibility, and caches keep claims and disposition together.
- Only final validated effective projects become runnable; explicit projects stay
  usable independently.

Implement the transition table and fixtures before finalizing request types.

### 17.8 Scoped object references and alias-aware selectors

**Decision.** Object qualification, implicit cross-root binding and selector policy are
agreed ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics),
[§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).

- **Scoped references.** Add optional `plugin` beside `project`/`project_root` and a raw
  `task`. Today's string-only `TaskDependencyConfiguration` cannot distinguish a
  literal local name `native::build` from scoped `(native, build)`, so implement the
  strict schema and structured identity and never reinterpret a raw component as
  shorthand.
- **Cross-plugin wiring is explicit-only initially.** Plugins cannot emit
  cross-activation task targets or follow public aliases; inferred references stay in
  the originating activation. Users wire dependencies with `plugin` or authored public
  aliases. Cross-plugin _project-edge_ resolution through claims is unaffected.
- **Selectors.** Positional selectors are exact; repeatable `--task-pattern` selectors
  match canonical names and aliases (pattern-only requests allowed), then union and
  canonical deduplication within the existing filter/plan pipeline. Exact selectors and
  patterns are separate code paths; literal wildcard names use the exact path. Preserve
  reference backslashes with no extra decoding pass. Each exact selector must exist in
  the project/directory scope before metadata/affected narrowing; later filter
  exclusion is not a missing-task error. Aliases stay out of executable node maps.

**Required fixtures.** Rejected selection of another activation; literal
qualification-looking names; valid explicit cross-plugin dependencies; missing direct
targets and upstream skips; multiple activations; changed aliases; inheritance and
cache round trips; scoped/literal object and shorthand round trips; per-project
upstream alias selection; project filters; escaped patterns.

### 17.9 Task declaration-kind composition

**Problem.** Today `TaskConfiguration::merge` field-merges long/long forms but replaces
the whole task for short/long, long/short and short/short pairs, and `into_long_form`
adds defaults and an implicit upstream self-dependency. Reusing either contradicts
presence preservation and qualified partial overrides.

**Decision (intentional pre-v1 correction).**

- Normal-task pairs (short/short, short/long, long/short, long/long) merge field by
  field with identical per-field rules. Expand each shorthand once into its command and
  implicit upstream dependency, with every other inheritable field absent; never use
  `into_long_form` unchanged for patch expansion.
- Changing between a normal task and an alias replaces the entry atomically; no
  execution or settings fields survive normal-to-alias, and alias-to-normal never
  imports the target's configuration. Alias/alias selects the higher explicit target
  without merging settings ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics),
  [§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).
- Preserve operation order, declaration-local template status and original reference
  binding. Input-boundary validation still rejects an alias carrying task overrides.
- Commandless tasks remain valid; a missing `exec` does not substitute for checking
  contributor binding or final constraints.

**Required tests.** Qualified overrides; explicit `extends`; dictionary replacement;
retained command/env/cache fields; implicit dependency addition/removal; alias/alias
replacement; extension layers; reference redirection; cycles; missing targets;
malformed mixed declarations; migration examples.

### 17.10 Canonical task identity versus invocation identity

**Decision.** Keep the existing execution model: one canonical task has one argument
binding per plan. `omni_core::TaskKey` is project/task only, and task context and
override-argument lookup are keyed the same way, so multiple bindings would need a
separate invocation-key, dependency, result and context design.

- Aliases share canonical task, configuration and cache identity; equivalent alias
  selections deduplicate. Separate command calls keep ordinary argument-sensitive
  hashing ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)).
- For simultaneous variants, define distinct named tasks with `extends`:

```yaml
tasks:
    build-debug:
        extends: native::build
        args:
            profile: debug
    build-release:
        extends: native::build
        args:
            profile: release
```

Both can run in one plan without becoming aliases. Setting `args` does not append
flags: the inherited command must consume them, or the derived task overrides its
command.

**Required tests.** Distinct derived identities; inherited settings and reference
binding; argument-sensitive caching across calls; alias deduplication.
