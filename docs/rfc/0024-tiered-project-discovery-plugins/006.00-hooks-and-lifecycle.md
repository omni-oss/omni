## 6. Discovery and the host contract

### 6.1 Hook namespaces and lifecycle

Plugins are **observationally stateless but not sessionless**. Omni owns a
per-plugin, per-capability, per-discovery **session state** that plugins populate
and receive back in later hooks. That state and the invocation's explicit inputs
are the authority for semantic progress, so hooks can be interrupted, retried,
cached and scheduled freely while still accumulating context across a pass.

Private mutable globals, memoization and runtime-local caches are implementation
details and are allowed if their presence, absence or prior contents cannot
change normalized contributions, state updates, notices or validation outcomes
for equivalent authorized inputs. They may change performance within host
budgets, not observable discovery semantics. The host may reuse, recycle or
discard an instance; no plugin may require a particular instance's memory to
survive between hooks. Fresh instantiation is not a contract requirement.
Private caches cannot bypass tracked input reads/dependency attribution, stage
permissions or limits, and must be safe under the advertised concurrency model.
Scope private data to activation/session identity wherever reuse across bindings
would affect correctness or confidentiality. Isolation of plugin activations
remains required; this permission does not expose host globals or another
plugin's memory. Determinism is a conformance obligation, not a claim that Wasm
confinement itself proves arbitrary plugin code deterministic.

Document this as an explicit plugin-author responsibility in SDK guides and
examples: keep semantic cross-hook progress in returned session state, treat
private globals as discardable optimizations, and test fresh/reused instances,
retries, cached/skipped hooks and reordered batches. A plugin whose correctness
depends on hidden invocation history violates the contract even when its runtime
permissions are otherwise valid. Provide conformance fixtures for those cases;
the host need not prohibit all internal mutation to enforce the public API.

The contract is a set of **stage hooks**. Every hook is **namespaced by
capability**, so adding a new capability later cannot collide with discovery
hooks or with hooks from another capability. A hook name has the shape
`<capability>.<stage>` (for example `project_discovery.infer_roots`). Plugins
register separate typed capability handlers. Each capability owns a fixed
namespace, version and hook vocabulary; there is no single `capability_id()`
method on a multi-capability plugin. The host invokes only explicitly supported
hooks of negotiated capabilities. Unsupported required capabilities fail;
explicitly optional ones follow [§5](005.00-activation-identity-and-delivery.md#5-activation-identity-and-delivery)'s skip policy.

The initial capability is `project_discovery`. Its stages (plugins implement
only those they need) are:

1. **`project_discovery.on_workspace`** — receive workspace options and static
   discovery scopes. May return a small, serializable workspace state seed.
   No file-content access.
2. **`project_discovery.filter_candidates`** — receive candidate roots and a
   bounded file index; may decline roots or select additional input paths for
   inference within already declared/authorized scopes, never widen those scopes.
   Runs before any heavy parsing.
3. **`project_discovery.infer_roots`** — batched per plugin over multiple
   roots; returns project fragments, local dependency references, and an
   updated session state. This is the only hook that may parse declared input
   files.
4. **`project_discovery.resolve_dependencies`** — runs after all plugins'
   `infer_roots` complete; receives the accumulated session state, frozen
   inference facts and the host-approved root catalog (including explicit-only
   projects), allowing cross-root and cross-plugin resolution without guessing
   final omni names.
5. **`project_discovery.observe`** — optionally inspect the frozen, composed
   project/dependency snapshot and return notices or inspection metadata only.
   It cannot change roots, fields or edges. All fragment edits finish before
   dependency resolution; there is no mutating post-resolution finalizer.

Future capabilities (for example `generator_contribution` or
`tool_contribution`) would define their own namespace and stages; the host
schedules each capability's stages independently and never assumes a flat
global hook list. Session state is also partitioned by capability namespace,
so one capability's state cannot be read by another.

The host may:

- batch many roots into one `infer_roots` call instead of one call per
  directory;
- run independent plugins concurrently;
- skip omitted hooks and optional capabilities rejected during negotiation;
  unknown hooks and unsupported required capabilities remain activation errors;
- cache and reuse session state fragments keyed by inputs;
- interrupt and retry a hook against the original session snapshot, regardless
  of whether its private runtime memory was preserved or discarded. Cancellation
  still requires actual runtime interruption/resource cleanup.

Plugins may rely on stage order and their declared inference dependencies ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)),
not incidental registration, completion or batch order, and cannot assume they
are the only plugin. They must tolerate re-invocation and must not depend on
wall-clock or randomness.

#### Dependency-ordered inference

Within `infer_roots`, schedule producer activations before their bound consumers.
A required producer finishes all its assigned inference work and its output is
validated before the consumer's inference begins. Consumers receive a frozen view
of declared producers' published typed facts through dependency handles ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)),
not private state, raw manifests or inferred/effective configuration. Concrete
fact schemas and query payloads remain specification prerequisites. Do not expose
partially completed producer batches or mutable live outputs. This permits
inference to use declared predecessor facts without
adding a fixed lifecycle stage for every integration. It does not grant filtering
hooks cross-plugin inference access or relax root eligibility and read permissions.

Validated predecessor output is provisional within the private inference stage/
pass, not externally committed reusable data. The whole inference stage still
commits atomically only after every required invocation succeeds; a producer or
consumer failure cannot publish a partial graph, reusable entries or notices.
Retries use unchanged declared-producer views along with their incoming state
and captured input view. Cache identity/validation must include the semantic
producer-fact view consumed by dependent inference; registration/completion order is
not an input identity. Later `resolve_dependencies` still runs after the complete
inference phase against the approved frozen shared snapshot.

#### Candidate disposition and hook eligibility

Track participation per activation/capability/root, independently of whether
another plugin or an explicit file produces a project at the same root. Filtering
and inference results explicitly identify kept/declined and accepted/declined
roots respectively; an empty fragment is not a decline. Do not derive acceptance
from arbitrary state bytes, notices or supporting facts. Validate dispositions
against assigned roots and reject contradictory/duplicate results.

Use distinct tagged `accepted` and `declined` inference result shapes, not an
acceptance boolean alongside independently optional project/edge fields. Require
exactly one result for every root assigned to a scheduled inference invocation;
missing, duplicate and unassigned-root results are errors. An accepted result may
carry an empty fragment, subject to final composition and validation. A declined
result has no project-fragment or dependency-edge payload: reject such fields at
the input boundary, rather than ignoring them because the root declined. State,
supporting facts and notices follow their separate stage-specific rules and do
not imply acceptance. Native typed results represent the same alternatives
without requiring serialization; external/cache decoding enforces the tagged
shape and the host validates complete assigned-root coverage. Omitting the hook
is distinct from omitting a result in a scheduled hook.

| Per-activation/root outcome | Subsequent scheduling / project effect |
| --- | --- |
| Filter declines | No inference or resolution for this activation/root |
| Filter omitted | Keep eligible host-approved candidates |
| Inference accepts | Eligible for this activation's registered resolution hook |
| Inference declines | No resolution for this activation/root; cannot smuggle project fragments/edges through the decline |
| Inference omitted | No implicit inference acceptance or resolution eligibility |
| All inference participants decline; no explicit project | No project is created |
| Explicit project exists | Its runnable status follows explicit composition/base rules independently of plugin declines |

Accepted empty contributions still require final composition/defaults/validation
to produce a runnable project; acceptance alone is not sufficient. Supporting
facts and state have their own typed stage rules and never manufacture a project.
One activation's acceptance cannot revive another activation's declined root,
and declining does not suppress another plugin's accepted contribution. Cached
results restore the same dispositions and scheduling consequences as live results.

A root declined during inference may still publish authorized, bounded supporting
facts, separately from its absent project/edge contribution. For example, an
aggregate Cargo workspace manifest may supply workspace-membership facts without
becoming a runnable project. The facts remain owned by the publishing activation/
assigned root and subject to typed-schema validation, tracked-input attribution,
visibility, resource limits and stage/pass transactions. Other eligible roots may
query them through the frozen fact service under its normal authorization rules.
Publishing facts does not reactivate the declined root for resolution or create
tasks, project configuration or dependency edges. A fact naming a root is not proof
that the root is a valid dependency target; surviving targets still require final
runnable-project validation. Cached results restore both the decline and permitted
facts with the same visibility and invalidation rules. This applies only to an
actually scheduled inference result: filter-declined, replacement or otherwise
skipped roots do not run inference merely to publish facts.

Allow resolution-only participation only through an explicit versioned capability
declaration validated against its supported hooks. Omission of `infer_roots` is
not that declaration. The host assigns resolution-only source roots from approved
projects established explicitly or by accepted inference, narrowed by the
activation's declared selection and applicable project allowlist; it cannot create
projects or acquire write ownership merely by querying the catalog. Root-local
replacement/base exclusions still apply: this is not a bypass for skipped
inference. An optional filter may narrow this participation, and a decline remains
binding for the pass. Exact declaration spelling and payloads belong to the
versioned contract specification before implementation.

Observation remains read-only over its authorized frozen views; observing a root
does not reactivate declined participation or grant contribution/state writes.
Test mixed-plugin acceptance/decline at one root, all-declined candidates,
accepted-empty results, explicit/base/replacement roots, omitted hooks, explicitly
declared resolution-only participation, invalid disposition output and cache
restoration. The host owns this transition table, not plugin invocation history.
Test accepted/declined wire and native result parity, accepted-empty fragments,
missing/duplicate/unassigned results, rejected declined project/edge payloads and
cached restoration of the same outcomes without implicit acceptance from state,
facts or notices.
Cover aggregate-only declined roots publishing membership facts, authorized
queries from accepted roots, denied fact visibility, tracked-input invalidation
and live/cache parity. Verify no project creation, resolution reactivation or
dependency-target validity is inferred from supporting-fact presence.

#### Session partitions and stage transactions

Session state has two partitions: **workspace state**, written only by the
singleton `on_workspace` hook, and **root state**, keyed by stable candidate
root. Later hooks receive workspace state read-only. Root-oriented stages may
replace state only for their assigned roots; cross-root knowledge is supplied
through immutable stage snapshots, not shared writes.

For each activation, invocations within a stage read the same committed
stage-start state snapshot. Inference consumers additionally receive the same
frozen validated view of their declared predecessor outputs ([§5.1](005.00-activation-identity-and-delivery.md#51-declared-inference-dependencies-and-consumer-bindings)); those views
are not writes to another activation's state or externally committed stage data.
For each activation/capability, omni assigns each root to at most one invocation
in that stage. Different plugins may evaluate the same root in isolated state
partitions. Batches may run in parallel, but cannot overwrite another batch's
root state. Cross-root
dependency resolution has query access to the frozen inference snapshot and emits
only results for assigned source roots. A result for a root must be independent
of its batch neighbors and invocation order.

Omni validates all invocations before atomically committing that stage's state,
contributions and notices. A failed or cancelled stage commits nothing; retries
start from its original snapshot. There is no last-writer-wins merge and no
plugin-defined state reducer. Workspace data discovered during inference can
be represented as root-owned facts and queried in the next stage's snapshot,
without introducing a mutable workspace accumulator.
