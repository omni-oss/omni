## 10. Implementation and rollout

1. **Contract and composition first:** typed layers, inference controls,
   virtual identities, conflict handling, provenance, final-name dependency
   resolution, hook stage definitions, session-state serialization and
   zero-plugin regression tests. No runtime dependency needed.
2. **Native pilots:** opt-in `@omni/javascript` and `@omni/rust` handlers behind
   the same protocol and hook stages, host-owned candidate scan and input
   tracking. Specify package-manager detection and ecosystem inference rules
   in separate adapter documentation; initial scope is [§4.3](004.01-native-ecosystem-adapters.md#43-initial-native-ecosystem-plugins).
3. **Wasm:** versioned SDK/fixtures, pinned source loading, sandbox, resource
   enforcement and cache invalidation. No external runtime ships without its
   cancellation and containment tests.
4. **Deferred JavaScript:** future work using the same contract and conformance
   suite, only after a separate isolation and runtime assessment. It does not
   gate this proposal's acceptance or initial stable delivery.
5. **Stabilize:** publish baseline measurements and freeze protocol/capability
   1.0 no later than omni 1.0, with [§14](014.00-versioning-compatibility-and-migrations.md#14-versioning-compatibility-and-migrations)'s compatibility/migration tests and
   tooling. Retain explicit activation for every tier after stabilization.

This is a delivery sequence, not permission to freeze contract types before
their payload/validation specifications. The current source-grounded gates and
active decisions are collected in [§18](018.00-readiness-and-open-decisions.md#18-code-grounded-readiness-and-open-decisions).

Do not select a Wasm or JavaScript engine solely in this proposal. Evaluate
binary size, cold start, target-platform support, deterministic imports, license
and enforceable interruption before committing dependencies. Missing-runtime
builds reject activation clearly rather than invoking a system interpreter.

**Open implementation decision:** choose between a core-Wasm SDK-managed message
ABI and the Wasm Component Model using prototype evidence, not a preference fixed
by this RFC. Evaluate both against equivalent discovery workloads: binary size,
cold/warm startup, request/result transfer, tracked-read and fact-query host calls,
allocations/peak memory, cancellation latency, metering/limits, supported platforms,
authoring/binding tooling and maintenance/security complexity. Document the measured
tradeoffs and selection before finalizing the external runtime ABI/engine. Neither
choice relaxes permissions, stage ownership, captured-byte identity, budgets or
contract compatibility. The runtime-neutral capability contract and native work
do not wait on this choice; JavaScript runtime assessment remains separately deferred.

Keep the Wasm execution foundation as flexible/reusable as practical so future
Wasm-backed generators and tools can share it. Separate engine/module compilation,
instance ownership, guest-memory/binding mechanics, cancellation, metering and
resource-limit enforcement from discovery-specific requests, session partitions,
tracked-input attribution, fact queries and scheduling. Prototype evaluation must
consider this reuse as well as discovery performance, without selecting an ABI
solely for hypothetical consumers or building their functionality in this RFC.

Reuse runtime mechanics, not discovery authority or generator/tool semantics.
Future consumers provide explicit versioned host interfaces, permission profiles,
lifecycle and budgets; no discovery instance acquires filesystem writes, process
execution or other authority merely because the engine can serve another subsystem.
Default-deny imports and consumer-specific bindings remain mandatory. This is not
generator/tool injection through discovery or a new task executor; those future
integrations need their own contracts and tests.

Required tests include:

- Native and Wasm contract fixtures produce identical normalized semantic output,
  logical contribution provenance and validation outcomes for equivalent
  implementations. Actual runtime/artifact identities remain accurate and may
  differ; do not erase them to make cross-tier fixtures compare equal. Any later
  JavaScript runtime must pass the same suite before shipping.
- Hook ordering and batching do not change normalized results.
- Fresh/reused instances, retries after interruption and cached/skipped hooks
  preserve normalized results and tracked dependencies. Transparent private
  caches cannot hide input changes or leak data between activations/sessions.
- Session state round-trips and cache invalidation work across hook
  re-invocation.
- Parallel batches cannot lose state updates or write another batch's roots;
  failed stages and retries publish neither partial state nor duplicate notices.
- Required/optional capability negotiation and registered-hook validation reject
  misspelled names and inconsistent exports. Multi-capability registrations keep
  state and dispatch isolated.
- Post-resolution observation cannot mutate projects/edges; dependency-hook
  caches invalidate when their frozen cross-root snapshot changes.
- No enabled plugins preserves existing discovery selection except for [§6.2](006.02-discovery-pipeline-and-lockfiles.md#62-pipeline)'s
  duplicate-explicit-file validation, and preserves extension ordering/path
  resolution, cache-exclusion and ignore behavior; disabled sources are never
  fetched or instantiated. Explicit inheritance follows [§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)'s intentional
  presence/default correction, with old/new fixtures and migration examples.
- Inferred-only, extend, replace, missing-name, base-template and explicit
  extension cases, including absence versus default-valued fields.
- Multiple selected explicit project files at one canonical root fail with all
  conflicting paths before hooks, with and without enabled plugins. Cover
  `yml`/`yaml` aliases, conflicting inference controls and reordered discovery;
  multiple ecosystem markers and separate explicit base-file references remain
  valid under their ordinary rules.
- Real/virtual configuration locations round-trip through inspection APIs and
  serialization. Virtual projects remain runnable/selectable by name/root;
  filesystem/hash consumers never receive logical virtual identities as files.
  Adding/removing an explicit override preserves root identity and correct
  discovery status without manufacturing a physical config file.
- Inferred project/task environment values containing `${VAR}` or `$(...)`
  stay literal without spawning processes during loading. Cover indirect values
  such as project names, explicit overrides (including equal-text overrides),
  task inheritance, substituted literal data and inference-cache round trips.
  Handwritten values retain existing expansion behavior.
- Explicit renaming preserves surviving root-based dependency edges. Explicit
  dependency replacement removes edges from both inference and resolution
  hooks before target validation; discarded missing/excluded targets do not
  fail loading. Surviving unresolved/excluded targets and cycles receive graph
  diagnostics, while malformed/escaping references fail even if later removed.
- Lockfile markers do not manufacture aggregate-root projects or bypass project
  selection. Tests cover shared workspace locks, manifest/lock mismatches,
   missing/changed locks, external same-name packages and unsupported formats,
   without executing package managers to parse them.
  Relevant unreadable/malformed/unsupported locks fail without stale facts or
  manifest-only fallback; absent locks may succeed with sufficient tracked
  manifest evidence. Irrelevant locks are not parsed solely due to their presence.
  Relevant manifest/lock contradictions fail with dependency/file provenance;
  fixtures distinguish genuine target contradictions from harmless representational
  differences, without full-install validation, source precedence guesses, automatic
  lock regeneration or concurrent-change restart treatment.
- Conflicts are deterministic under reordered scheduling; explicit replacements
  and allowlists resolve only the intended contributions.
- Ordered raw-layer replay preserves list/dictionary operations, including a
  base replacement followed by child append/prepend, multiple bases and diamond
  inheritance. Extending an inferred project's explicit file never imports that
  root's inference or effective defaults; explicit tasks can extend surviving
  inferred tasks after project composition.
- Cache invalidation covers edits, new/deleted/missing inputs, directory
  membership, local bundle changes, options, host upgrades and activation.
- Infinite loops, allocation/output/read floods, path traversal, symlink escape,
  forbidden imports and denied host operations fail within the external budget.
- Discovery permission schemas/validation accept only the supported read-only
  profile and fail-closed rule settings. Test layered ceilings (including empty
  scope sets), stage-restricted imports, module initialization, filtered index
  queries and negative reads. Wasm cannot bypass the input service through WASI
  or unknown imports; concurrent symlink changes cannot escape host containment.
- Performance fixtures cover no plugins, unmatched markers, 1,000 projects,
  many enabled plugins, cold/warm caches and long-lived MCP invalidation.
