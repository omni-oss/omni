### 6.3 Data boundary

Define a versioned, serializable contract in a small shared crate. Native plugins
use the same logical request/response as external ones without requiring an
unnecessary serialization round trip.

Requests contain stage-appropriate root ids, bounded index/state views and
options. Only inference receives the tracked file-content service; other stages
receive the restricted views described in [§6.1](006.00-hooks-and-lifecycle.md#61-hook-namespaces-and-lifecycle). Responses contain project
fragments keyed by root, local dependency references, provenance, structured
non-fatal notices, and stage-appropriate state replacements. Represent local
dependencies by stable workspace-relative roots where possible, not guessed
final omni names: explicit configuration may rename a project. Non-local package
dependencies must not become spurious omni project edges.

Host-managed configuration fields (`file`, `dir`, project `base`, inference
controls and activation/security policy) cannot be emitted by plugins. Plugin
output cannot introduce project-level `extends` paths; ecosystem inheritance
must be handled through declared, tracked input reads. Unknown fields and invalid paths fail
validation. A plugin may decline a candidate, but cannot return arbitrary roots
that were never in its host-approved candidate set.

Task-level `extends` is distinct from project-file inclusion: it references
tasks in the composed task set, not files. If contributed, it follows the same
post-composition task-extension resolution and validation as explicit tasks.

The file service validates canonical containment, records successful and missing
reads, and applies byte/read limits before allocation. Reads must match declared
input scopes. Additional inputs discovered from a manifest are allowed only
within those scopes and are tracked. No raw host filesystem handle, environment,
wall clock, randomness, network or subprocess service is exposed.

#### Literal inferred values and downstream interpretation

Plugin-origin project/task environment values are literal data: neither
`${VAR}` references nor `$(command ...)` substitutions are expanded by omni.
This applies across native and external tiers, including restored cache results.
The sandbox boundary must survive lowering into ordinary project configuration;
denying subprocess imports is insufficient if host configuration processing can
execute emitted strings later.

Preserve a semantic literal/expandable distinction per winning value through
layer composition, task inheritance, extraction and inference-cache round trips,
not merely display provenance. An explicit file/base override uses existing
handwritten expansion semantics, even if its text equals the inferred value;
an inherited inferred value remains literal. Plugin output cannot mark a value
as handwritten or opt into expansion. Equal-value coalescing must not erase this
distinction. Include interpretation mode in effective semantic identity where
it affects execution.

Audit indirect expansion paths as well: inferred project names and other
metadata copied into host environment maps must remain data, not executable
expansion source. Substituting literal inferred data into an explicitly authored
expression must not recursively reinterpret that data as expansion syntax.
Refactor the current command-enabled project/environment loading paths rather
than passing merged inferred strings through them unchanged.

Task `exec`/`retry_exec` fields remain command definitions, interpreted only by
the normal task execution pipeline after selection. Literal handling of an
environment value does not prevent a deliberately selected command from using
that value; it prevents omni from executing or expanding it during loading.

Session state is owned by omni: it is serializable, size-bounded and versioned.
Hook cache keys include incoming state fingerprints; cache entries contain both
outputs and state replacements with their tracked input dependencies. State may
contain parsed facts derived from tracked inputs, but never bypass input
tracking. Live partition keys include workspace/session, plugin activation id,
artifact identity, capability/version and (for root state) root id. Native
handlers may use typed in-memory state without serialization on every call;
external adapters and persistent caches use the versioned serialized form.

An invocation/session nonce separates live ownership but is not a persistent
cache-key input. Persistent reuse uses the stable workspace scope and semantic
inputs in [§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches); otherwise every new command would defeat warm-cache reuse.

Virtual projects need a stable logical configuration identity distinct from a
physical filename. Preserve root and plugin/artifact provenance rather than
pretending a `project.omni.yaml` exists. Keep this effective-project identity
separate from explicit-file extension graph ids ([§7.2](007.01-layer-order-and-merge-semantics.md#72-layer-order-and-merge-semantics)); update discovery,
config inspection and cache consumers accordingly. Merely accepting the existing
`Virtual` enum variant is insufficient.

Make downstream consumers that interpret configuration locations explicitly
aware of **real versus virtual configuration locations**, using a tagged
representation rather than an undifferentiated filesystem path. Do not propagate
this distinction into consumers that only need effective projects/tasks or real
project directories. Reuse `DiscoveredPath::Virtual { dir }` as
the discovery seam: its `dir` is the real project root, not a required physical
configuration file. A virtual configuration identity need not exist on disk.
Do not create placeholder files or disguise virtual identities as ordinary
`project.omni.*` filenames. Effective root identity remains stable when a root
changes from inferred-only to inference plus an explicit file.

Audit discovery/runnable classification (`ProjectConfigEntry::is_discovered`),
project extraction, graph adapters, CLI/MCP list/config responses and selectors,
diagnostics, serialization and cache input collection for physical-file
assumptions. Change only the consumers/boundaries that actually depend on config
locations; graph/planner/executor code consuming ordinary effective tasks need
not become virtual-path-aware. Match real locations
before invoking filesystem APIs; virtual identities cannot be read, canonicalized
or included in file-hashing globs as though they were files. Classification must
use discovered root/status, not membership of `config.file` in physical paths.
Keep explicit-only extension targets and `base` templates non-runnable under
the existing classification rules.

Inspection exposes the real root, tagged configuration location/identity,
optional explicit file and contributor provenance. It must work for real,
virtual and explicitly extended inferred projects without fabricating file
locations. Existing file-path selection retains physical-file meaning; offer
root-based selection for effective inferred projects without requiring a fake
filename. Exact API field/selector spelling is deferred, but their distinction
and schemas must be explicit. Execution-cache integration uses [§8.3](008.02-execution-cache-semantic-identity.md#83-fine-grained-execution-cache-integration)'s semantic
fingerprint for inferred configuration and real files only for physical inputs.
