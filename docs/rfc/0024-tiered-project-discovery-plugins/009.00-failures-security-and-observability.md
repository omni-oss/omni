## 9. Failures, security and observability

Enabled-plugin failures are fatal by default: timeout, resource exhaustion,
unsupported required protocol/capability, invalid output and inference errors must not quietly
produce an incomplete graph. Commit no partial response from a failed batch;
do not silently reuse stale output. No automatic “disable the slow plugin and
continue” policy: command meaning must not depend on machine speed.

Replacement roots remain usable without executing their inference, but cannot
magically recover a command that still needs other roots from a failing plugin.
Users can explicitly disable a plugin and provide handwritten configurations.

Use RFC 0021 diagnostics for fatal failures and RFC 0023 notices for successful
but degraded interpretation (for example, an ecosystem feature deliberately not
inferred). Present bounded, sanitized plugin text; provenance never exempts
output from RFC 0022 redaction. Developer timings, cache reasons and host-call
counts go to tracing, not routine terminal noise. Hook notices are returned or
buffered transactionally alongside contributions and state, never published
immediately through a reporter. Failed attempts publish nothing; cached or
retried successful results are committed once per stage in deterministic order
within the private pass. User-facing publication waits for successful final
input-consistency validation ([§8.2](008.01-inference-cache-and-storage.md#82-shared-storage-separate-task-and-inference-caches)); a rejected pass leaks no hook notices.
Immediate developer tracing is allowed and carries invocation/attempt ids.

Propose CLI and MCP inspection operations for:

- Available/enabled plugins, runtime, canonical identity, artifact digest,
  declared scopes and effective limits.
- Effective project configuration with field-level plugin/file provenance,
  skipped/replaced contributors and merge decisions.
- Discovery cost breakdown and inference-cache status.

Exact command names are an implementation detail; both surfaces must expose
structured results rather than requiring users to parse logs. Inference never
writes `project.omni.yaml` automatically. A future explicit export command can
materialize configuration for migration or debugging.

Sandboxing is mandatory for external discovery plugins regardless of the
existing experimental generator-capabilities switch. It must not inherit that
switch's unconfined fallback. Direct input/module access stays within approved
workspace scopes or captured artifact modules; separately authorized claim,
catalog and root-limited observation views have the explicit information-sharing
grants in §6.1/§6.4. Those views do not imply filesystem authority, and filesystem
denial is not a claim that composed configuration is secret from an authorized
observer at the same accepted root. Ecosystem inputs and plugin
output are untrusted data, not implicitly executable configuration. Explicitly
authored omni configuration retains its existing interpretation semantics;
plugin activation never upgrades inferred strings to that trust level ([§6.3](006.03-data-boundary-and-literal-values.md#63-data-boundary)).

### 9.1 Projection control-plane protection

Add `plugin.omni.{ext}` across supported formats to the shared control-plane
manifest names protected by projection guardrails. Use the existing explicit
`allow_omni_config` override and apply the same checks to individual destinations
and directory-copy contents; do not create a separate plugin-only bypass.

Do not automatically protect all discovery markers/inputs, such as
`package.json`, `Cargo.toml` or lockfiles, merely because an enabled plugin reads
them. These remain ordinary project files that users may intentionally project;
broad input globs must not silently become broad write restrictions. Existing
independent protections still apply. Document that projecting such files can
change inferred configuration on the next discovery, with ordinary tracked-input
invalidation rather than implicit plugin execution during projection.

Include `omni_constants` and `omni_projections` in the implementation audit.
Test protected plugin manifests with/without the explicit override, directory
copies containing them, and otherwise permitted ecosystem-input projections
whose changes invalidate subsequent inference without gaining automatic
control-plane protection.
