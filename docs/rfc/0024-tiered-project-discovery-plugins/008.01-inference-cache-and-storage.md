### 8.2 Shared storage, separate task and inference caches

Extract a small shared local cache-storage layer from the current task cache,
with both task execution and plugin inference as real consumers. Reuse storage
mechanics, not task execution semantics. `TaskExecutionCacheStore` accepts task
execution information, `CachedTaskExecution` carries commands/exit codes/logs
and output files, and `HybridTaskExecutionCacheStore` invokes collection and
execution-plan machinery. Discovery must not invent synthetic tasks or require
a loaded task graph just to access its cache.

The shared layer owns namespaced keys, bounded reads, atomic publication,
integrity/version-envelope checks and publication/pruning coordination. It knows
nothing about projects, hook stages, dependency graphs or execution outcomes.
Task caching retains task digests, archive restoration, output/log handling,
success/failure replacement policy and existing remote transport. Inference
caching retains hook identity, contributions/state/notices, observed dependency
records, snapshot validation and transactional stage publication. Do not build
a universal hashing/scheduling/invalidation framework as part of this extraction.
The low-level layer may initially be a module or a small dedicated crate; keep
it dependency-neutral so discovery can use it before project/task graph loading.

Discovery inputs use existing rooted paths and shared include/exclude glob
semantics: `@project/...` resolves against the assigned candidate root and
`@workspace/...` against the workspace root. Declarations bound permitted reads;
successful/missing reads and authorized directory membership actually observed
by a hook determine its file dependencies. These are inference-cache inputs,
not automatic additions to project/task `cache.key.files`. Plugins may separately
contribute task-cache input configuration. Share immutable input reads across
batches through the host cache without losing root/hook dependency attribution.

Because dependencies are learned during execution, inference lookup has two
steps. First compute a stable lookup identity from host/plugin artifact/build,
activation id, negotiated protocol/capability/hook versions, options, effective
permission scopes, semantic request and incoming state/snapshots. Find candidate
entries through a bounded dependency index, then verify each candidate's prior
observed dependency record against current files, missing paths and membership.
Only a matching record permits reuse; otherwise execute the hook and capture a
new record. Validate cached output against current contracts, permissions and
resource limits before restoring state/contributions. A cache hit cannot bypass
reduced permissions. No stale result is substituted for a failed invocation.

Observed-input validation must use the actual bounded captured content (or a
proven immutable identity), not just matching size/mtime. The existing task
directory hasher's metadata-stamp optimization is not an input-consistency proof
and cannot be reused unchanged to validate inference records or a pass. Same-size
edits with preserved timestamps, symlink swaps, missing-file creation and directory
membership changes still have to invalidate the corresponding evidence. Keep
read/validation costs in actual host accounting; a cache hit avoids plugin work,
not the cost of proving its recorded inputs still match.

For root-oriented hooks, use one logical persistent record per activation/
capability/hook/root, not one record for an invocation batch or the whole plugin.
Each record contains that root's stage-appropriate outcome, contributions,
published claims, state update and notices together with the dependency evidence
needed to validate reuse. Scope stable lookup identity and incoming root-state
inputs to the logical root request while retaining required workspace state and
frozen claim/catalog context. Physical batch membership, neighbor identities and
transport partitioning are not semantic lookup inputs. Singleton/workspace-wide
hooks use their own bounded logical invocation records rather than invented
root records.

These hook records store the original validated plugin output and its stage
effects, before host-managed `apply` or explicit composition. Decode that output
with the additive contribution validator. Application-file layers/ordered plans
use their ordinary validator and distinct interpretation identity; an applied
`replace` is not forbidden plugin output merely because a host cache stores the
plan. Any optional cache of composed results must key all application/explicit
inputs and preserve operations, binding and trust metadata. It cannot be mistaken
for a reusable raw hook result or decoded under the wrong collection profile.

Validate/reuse root records independently, then batch only the roots requiring
live work. Restored roots still contribute their outcomes/claims/state to the
private stage snapshot and undergo the same full stage/pass acceptance. A changed
root need not force unrelated roots to rerun merely because they previously
shared a batch. Shared observed inputs or query snapshots may conservatively
invalidate multiple root records when narrower attribution cannot be proved
correct; never drop dependency evidence to claim fine-grained reuse. Preserve
stage-start state semantics and declared-producer claim views for both hits and
live roots.

Use bounded bulk lookup/read/write operations. Physical storage may group records
or share immutable dependency evidence, but grouping must not redefine logical
identity or require unchanged batch composition for reuse. Per-root granularity
does not permit early publication: new records and their index references remain
provisional until successful stage and final pass validation.

Account for actual work while enforcing identical logical result limits for live
and cached results. Each restored root must satisfy the same current contribution,
state, count and size limits as a live root. Total accepted project/task/claim counts
remain bounded across hits and live results; cache reuse cannot evade them.
Charge cache I/O, decoding, validation, queries and memory to their applicable
host-wide budgets. A cache hit incurs no hypothetical plugin fuel or execution
time for a hook that did not run, but actual loading/validation time remains
subject to the applicable host/command deadlines and cancellation rules.

Charge all actual split/retry work, including unsuccessful attempts and repeated
reads/decodes/validation, to unchanged aggregate budgets. Attempts never reset or
multiply those budgets, and failed attempt allocations must be released/accounted
for rather than hidden by a successful retry. Separate logical accepted-result
counts from attempted-work accounting: a discarded attempt does not become a
second accepted result, but its work is not free. Calibrate numeric defaults and
measurement mechanisms through benchmarks instead of estimating a cache hit's
cost as though the plugin executed.

Validate cached contributions against current per-root logical limits and bound
cache decoding/materialization separately from physical hook-batch transport.
An aggregate cached batch exceeding a current transport cap must not falsely
label each constituent root oversized: safely repartition its validated records
where supported, or treat it as a miss and schedule bounded batches. Logical
entry granularity follows the per-root/singleton rules above; concrete physical
storage layout and concrete accounting mechanisms still need specification before cache
implementation. Batching remains host-owned, not semantic plugin behavior.
Cache hits and split attempts cannot bypass aggregate budgets.

Stage success gates publication of reusable inference entries/index references
as well as live state/contributions/notices. Private staging or unreachable
content blobs may exist earlier, but failed/cancelled stages expose no reusable
partial results; orphan cleanup is safe. A successful cache hit still follows
stage transaction and notice deduplication rules. Corrupt/incompatible cache
data is treated as a miss with bounded diagnostics, never trusted as valid output.
Recoverable cache-write failures must not publish an incomplete index entry.

Inference-cache persistence is best-effort after successful discovery validation.
Recoverable write failures, such as a full disk or read-only cache directory,
do not invalidate an otherwise accepted discovery result or prevent ordinary
task execution. Report a bounded sanitized cache-write warning and inspection
status; a later command may need to rerun inference. Publish no incomplete record
or index reference, preserve existing valid entries and safely reclaim unreachable
staging data. Diagnostics remain subject to pass acceptance and ordinary redaction/
deduplication rules; failed discovery attempts cannot leak provisional hook notices.

This recovery applies only to inference-cache persistence, not plugin execution
or input validation. Invalid output, exhausted discovery budgets, denied plugin
operations and inconsistent inputs remain failures and cannot be downgraded to
cache warnings or successful empty results. Failure to persist never permits
stale-output fallback. Existing task-execution-cache failure policies and remote
transport behavior are unchanged.

Stage success is necessary but not sufficient for external publication: keep
new entries/index references and user-facing hook notices provisional until the
pass's input-consistency check succeeds ([§17.2](017.00-review-findings-and-prerequisites.md#172-frozen-claims-do-not-imply-frozen-filesystem-inputs)). Rejecting/restarting a pass
discards its provisional graph/state/notices and exposes no new reusable entries
from that pass. Existing valid cache entries need not be deleted; each new pass
must validate them against its own captured input view. Stage commits remain
atomic within the private pass and cannot leak rejected-attempt notices.

Use distinct task/inference namespaces. Scope mutable inference indexes to the
canonical physical workspace/worktree, even when worktrees share a cache
directory; content sharing must not mix selection, permissions or observed
dependency state. Lookup/index operations and multi-entry publication must be
bounded and batched where useful so cache overhead does not erase hook savings.

Initially inference caching is local only. Reusing storage primitives must not
implicitly upload parsed workspace data/state or accept remote inference entries.
Remote inference caching needs a separate trust/privacy design. Migrate task
storage onto the extracted primitives incrementally, preserving task formats,
remote-cache protocol and existing behavior; add inference storage on the same
primitives rather than postponing the task consumer indefinitely. Test both
consumers, concurrent publish/prune, corruption/recovery, physical worktree
isolation, dynamic dependency invalidation and failed-stage invisibility.

Behavior preservation here concerns the storage extraction and existing task-cache
failure/transport policies, not preservation of an enablement bug. §8.3's explicit
lookup/replay eligibility correction applies to handwritten and inferred tasks
alike, with a pre-v1 regression note. §8.3's uncached-dependency eligibility rule is likewise separate; storage extraction
cannot quietly bypass it.
