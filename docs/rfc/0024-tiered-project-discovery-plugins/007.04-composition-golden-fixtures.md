### 7.5 Composition golden fixtures

These cases specify inputs and exact semantic outcomes for the future layer/host
conformance suite. They are documentation fixtures, **not executable tests of an
implemented plugin pipeline**. Translate each stable `Cxx` id to native, wire and
inference-cache test cases when the affected contract exists. Do not update an
expected result merely to match current eager-default/flattened behavior.

#### Fixture conventions

- Each case is independent. Unless overridden: selected root `packages/web`, final
  name `web`, activation `frontend`, inferred normal task `build` with a literal
  command, no dependencies or explicit cache enablement. Plugins are synthetic
  fixture handlers, not promises of built-in adapter output.
- YAML fragments below identify ordinary project/task/default layers; labels such
  as `applied` and `expected` are fixture notation, not new config fields. Direct
  plugin lists have additive meaning; authored plain lists retain ordinary replace
  semantics. Inferred task keys are raw local names, authored keys use §7.4 syntax.
- `—` in tables means no value, not YAML `null`, deletion or an explicit default.
  Missing optional fields remain absent until their applicable finalization.
- Expected file lists describe contributed configuration patterns, before ordinary
  default physical config-file inputs. Resolve `@project` against the real root;
  retain original operations and declaration origins separately for inspection.
- All successful results must be invariant under permitted batching, cache hits,
  source-loading order and unrelated scheduling. All failures publish no new
  reusable entries/notices and execute no tasks. Input-shape errors happen before
  composition; missing targets/cycles are checked on surviving references.

#### C01 — Cache enablement tier matrix

For `frontend::build`, resolve the first tier supplying a value in this order:
authored task → authored project → plugin task → plugin project → activation
`defaults` → inferred-task host fallback. Authored means explicit or applied, in
ordinary layer order within the tier. Each row is a separate case.

| Authored task | Authored project | Plugin task | Plugin project | Defaults | Effective | Deciding tier |
| --- | --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | false | host inferred-task fallback |
| — | — | — | — | true | true | activation defaults |
| — | — | false | — | true | false | plugin task |
| — | — | true | — | false | true | plugin task |
| — | — | — | false | true | false | plugin project |
| — | — | true | false | false | true | plugin task |
| — | false | true | true | true | false | authored project |
| false | true | true | true | true | false | authored task |
| true | false | false | false | false | true | authored task |

Also check applied task `true` then explicit qualified-task `false` → `false`, and
applied project `true` then explicit project `false` → `false`, by ordinary same-tier
layer order. An applied task value still beats an explicit project value: task and
project tiers are deliberately distinct. An ordinary explicit unqualified task
with no values at any tier gets the existing handwritten fallback `true` instead.
Inspection records the actual winning value/tier, not just the resulting boolean.

#### C02 — Baseline input append, replacement and later operations

```yaml
# activation defaults.tasks
cache:
  key:
    files: ["@workspace/pnpm-lock.yaml"]
    env: [NODE_ENV, NODE_ENV]
---
# plugin's raw local build task
cache:
  key:
    files: ["@project/package.json"]
    env: [NODE_ENV, API_MODE]
---
# applied build task
cache:
  key:
    files: {replace: ["@project/src/**"]}
---
# explicit task frontend::build
cache:
  key:
    files: {append: ["@project/schema.json"]}
```

**Expected:** files `[@project/src/**, @project/schema.json]`; effective environment
names `[NODE_ENV, API_MODE]` (one hash input per name). The applied replacement
removes both the default lockfile and inferred manifest contribution; no hidden
manifest-input bypass restores either. With the applied layer omitted, files are
`[@workspace/pnpm-lock.yaml, @project/package.json, @project/schema.json]`.
Plain `defaults` lists and explicit `append` in `defaults` have identical results.
Variants: explicit omission keeps the applied replacement; explicit `prepend`
puts its entries before `src/**`; explicit `replace: []` leaves no contributed
file inputs. None of these operations disables mandatory semantic task identity.

#### C03 — Strict defaults surface

Each input is under `defaults.tasks.cache` and is independently invalid:

| Input | Expected |
| --- | --- |
| `output: {files: ["@project/dist/**"]}` | Reject unsupported defaults field |
| `key: {defaults: false}` | Reject unsupported defaults field |
| `key: {files: {prepend: ["@project/src/**"]}}` | Reject forbidden defaults operator |
| `key: {env: {replace: [MODE]}}` | Reject forbidden defaults operator |
| `key: {files: ["src/**"]}` | Reject missing explicit project/workspace root |

Task-name entries under `defaults.tasks`, unknown fields and mixed operator
envelopes are also invalid. The same per-task settings remain valid in a supported
`apply`/explicit task patch with its ordinary collection profile.

#### C04 — Application subtraction is activation-local

Synthetic `frontend` emits project roots `[packages/a, packages/b]` as dependencies;
`native` emits `[packages/b, packages/c]`. Both supply the same project name `web`.
The final target names are `a`, `b`, `c`, `d` at roots `packages/a` through
`packages/d`. An application file selected only by `frontend` uses authored
`dependencies: {replace: [d]}`: this is a **name reference**, not handwritten root
syntax. All four targets have final runnable projects.

**Expected:** combined surviving root edges `[packages/d, packages/b, packages/c]`
in stable contributor order (`frontend`, then `native`), with no edge to `packages/a`.
Reversing execution order does not change this. An explicit project
`dependencies: {replace: []}` then removes all combined edges. No task dependency
is manufactured by any of these project relationships.

#### C05 — Conditional applied wiring, not optional direct references

Plugin tasks: `test` and `prepare`; plugin `test.dependencies` contains own
`prepare`. No inferred `build` or `lint` exists. The applied file is:

```yaml
tasks:
  test:
    dependencies: {replace: [build]}
  lint:
    cache: {enabled: true}
```

**Expected:** the `lint` source patch is silently skipped with inspection/debug
reason. The absent inferred own target `build` is omitted from the `test` rule;
the retained empty `replace` clears `prepare`, leaving no dependency. A later
explicit unqualified `build` declaration cannot retroactively bind that rule.
The same applies to `with`. In contrast, surviving direct plugin output naming
missing own `build`, or an applied qualified `native::build` with no target,
fails target validation. No public-name fallback is attempted.

#### C06 — Fallbacks do not become inheritable values

The activation has baseline file `@workspace/pnpm-lock.yaml`, inferred `build`
adds `@project/package.json`, and its `defaults.tasks.cache.enabled` is `false`.

```yaml
# explicit project tasks
tasks:
  compile: {alias: "frontend::build"}
  release: {extends: "frontend::build"}
```

**Expected:** `build` (automatic alias) and `compile` both select canonical
`frontend::build`, whose caching is `false` from the activation fallback.
`release` is a distinct explicit task with handwritten fallback `true`; it inherits
both file patterns once and the command, but not the activation's fallback value.
Variants: a real plugin `cache.enabled: false` is inherited by `release` as a
plugin-origin value; an applied task `cache.enabled: false` is inherited as an
authored-task value. Both variants disable `release`. Changing the requested alias
never changes the canonical task's cache policy or semantic identity.

#### C07 — Task inheritance replays original operations

```yaml
# explicit project base file
tasks:
  release:
    extends: seed
    cache:
      key:
        env: {replace: [BASE]}
---
# concrete project file extending that base
name: web
tasks:
  seed:
    base: true
    cache:
      key:
        env: [SEED]
  release:
    cache:
      key:
        env: {append: [CHILD]}
```

**Expected:** executable `release.cache.key.env = [BASE, CHILD]`; `seed` is an
extension-only template. Flattening the project layers into a final append and
then inheriting `seed` would wrongly yield `[SEED, BASE, CHILD]`. Both commandless
tasks are valid; missing `exec` is not an error. Repeat with no enabled plugins
to verify the same corrected explicit pipeline.

#### C08 — Qualified overrides and canonical alias identity

Plugin `build` has a literal runner command and outputs `@project/dist/**`.

```yaml
tasks:
  "frontend::build": {exec: "node build.mjs"}
  compile: {alias: "frontend::build"}
```

**Expected:** qualified partial override preserves outputs and other omitted
settings; `build` and `compile` alias that modified canonical task. Selecting
`build`, `compile` and `frontend::build` produces one executable node and one
execution/cache identity. Alias names have no independent override fields.

#### C09 — Explicit name occupancy does not import inference

```yaml
tasks:
  build: {description: "aggregate"}
```

**Expected:** explicit commandless `build` suppresses the automatic alias but does
not inherit `frontend::build`'s command or input policy. Both are valid distinct
canonical tasks; explicit `build` gets handwritten caching fallback `true`, while
the inference task keeps its inferred-task policy. `extends: frontend::build`
would be an explicit request to inherit, not an alias or automatic behavior.

#### C10 — Declaration-kind changes replace atomically

Two activations contribute `build`; explicit configuration chooses the public alias
and redirects a qualified task:

```yaml
tasks:
  build: {alias: "native::build"}
  "frontend::build": {alias: "native::build"}
```

**Expected:** only `native::build` is the canonical target of these names;
the old frontend command/env/cache/dependency settings do not survive the
normal-to-alias transition. A later explicit normal task replacing the qualified
alias starts fresh, without importing the native target's configuration. Alias
to alias replaces the target wholly, not fieldwise. No missing activation binding
can be manufactured by any of these transitions.

#### C11 — Normal short/full tasks compose fieldwise

An explicit base declares `build` with long-form `exec: echo old`, environment
`MODE: production`, and `cache.output.logs: false`. The concrete layer supplies
short-form `build: echo new`.

**Expected:** command is `echo new`, environment and `logs: false` survive, and
shorthand contributes exactly one upstream-self reference to the originally
declared `build`. Extending it into `release` must not regenerate that reference
as `^release`. A long-form command-only override has the same field preservation
but contributes no shorthand dependency. A later `dependencies: {replace: []}`
removes the shorthand edge before target validation. Cover short/short,
short/full, full/short and full/full, rather than keeping representation-based
whole-task replacement.

#### C12 — Cross-plugin conflicts require a relevant explicit resolution

`frontend` and `native` contribute project descriptions `web frontend` and
`web native`. They also contribute scoped, nonconflicting task sets.

**Expected:** without an explicit description, deterministic conflict diagnostics
identify both activations, the root and `description`. Setting explicit
`description: web` resolves that conflict. An unrelated explicit command override
does not. Reversing activation execution/loading order does not pick a winner.
Separate roots with duplicate final project names still fail independently.

#### C13 — Project extension imports only authored layers

Root A has inferred task `only-a` and an explicit project file containing
`env.vars.EXPLICIT: "yes"`. Root B extends that file, declares its own final name,
and independently has inferred task `only-b`.

**Expected:** B inherits the authored environment value and `only-b`, not
`only-a`, A's inference controls or A's effective defaults. A remains independently
selectable if discovered/runnable. Merely reaching A's file through `extends`
does not select A as a project if it was not discovered. Diamond/multiple-base
variants must use the existing raw traversal order and visit a shared ancestor
once, not import a flattened effective project.

#### C14 — Compose dependencies before existence checks and naming

Plugin source `packages/web` contributes an edge to nonexistent but well-formed
`packages/unused` and to accepted `packages/shared`. Explicit configuration names
the latter `common`.

**Expected:** a surviving edge to `packages/unused` fails with contributor
provenance. Explicit `dependencies: {replace: [common]}` removes both inferred
references first and resolves only the surviving authored target. No error is
raised for the discarded missing root. A malformed `../outside` root still fails
at the output boundary even with the same replacement. Root-plus-task references
in `dependencies` and `with` use the same structural-before/existence-after rule.

#### C15 — Binding survives renames and public aliases

Plugin `frontend` contributes a root-based task reference from `web` to the raw
local task `build::debug` at `packages/shared`. The target project is explicitly
renamed `common`; another activation owns that project's public `build` alias.

**Expected:** the reference lowers to `common` + activation `frontend` + raw local
name `build::debug`, rendered `common#frontend::build\:\:debug`. No public alias
redirects it. Missing frontend targets fail, even if another activation has the
same local task. Upstream missing tasks instead contribute no edge under their
separate skip rule. Task references alone add no project edge.

#### C16 — Literal inferred values stay literal after inheritance

Plugin `frontend::build.env.vars.VALUE` contains `${HOME}`. Set the fixture's
ordinary environment `HOME=/fixture/home`. A derived explicit `release` inherits
the field without overriding it.

**Expected:** both effective values retain literal interpretation; environment
loading does not expand them or execute substitutions. If `release` instead
explicitly sets the identical text `${HOME}`, its winning value has handwritten
interpretation, resolves to `/fixture/home`, and the corresponding semantic identity changes. Repeating the
case with `$(...)` must never spawn a process for inherited plugin data. Literal
command operands containing `$VAR`, `{{name}}` or `{#comment#}` likewise reach the
program unchanged, even through native/wire/cache round trips and display.

Mixed-path variant: an inferred `args.raw` is the literal text `$HOME`, and an
authored argv expression interpolates `{{ args.raw }}`. **Expected:** the selected
program receives `$HOME`, not `/fixture/home`. Deliberately authored `$HOME` source
retains ordinary environment expansion; inherited data is not reclassified as
that source. Cover metadata and task-argument overrides as well as direct env
values, including Tera filters/comparisons that must still see the original data.

#### C17 — Normalize duplicates only after positional operations

Plugin `build.cache.key.env` contributes `[A, A]`; explicit configuration applies
`merge: [B]` to that field.

**Expected:** positional replay produces `[B, A]` before final normalization, so
the effective names are `[B, A]`. Early deduplication would wrongly lose `A`.
Equivalent dependency edges deduplicate only after resolution/canonicalization;
dependency and `with` relationships remain distinct. File-pattern repetitions
and repeated argv operands (e.g. `[tool, --flag, --flag]`) are preserved; one file
matched by several patterns is still one collected file.

#### C18 — Malformed declarations cannot be repaired by later replacement

Each case is independent; even a later `tasks: {replace: {}}` cannot hide it.

| Input | Expected |
| --- | --- |
| Plugin list `prepend`, `replace` or positional `merge` | Boundary rejection under additive profile |
| `tasks: {merge: {build: {}}, hidden: {alias: build, exec: echo}}` | Reject mixed operator envelope before decoder can discard `hidden` |
| `dependencies: {append: [], replace: malformed}` | Reject extra operator-envelope field |
| `{alias: "frontend::build", cache: {enabled: true}}` | Reject alias/task mixed declaration |
| Task literally named `replace` inside `tasks: {merge: {replace: {exec: echo}}}` | Valid authored declaration; name is not an operator at that nested entry level |

SDK/cache serializers must preserve the last case without creating a destructive
task-dictionary replacement, and preserve plain-list versus append contribution
meaning for the chosen profile.

#### C19 — Defaults invalidate composition, not unchanged hook work

Run two passes with identical plugin/options/observed inputs. Only activation
`defaults.tasks.cache.enabled` changes from `false` to `true`.

**Expected:** raw hook cache records remain reusable. Composition and inspection
refresh; an inferred task with no higher-tier opinion changes enablement. If the
plugin explicitly emitted `false` for that task, the defaults change is masked:
its effective semantics and added semantic digest remain unchanged. Repeat with
baseline inputs replaced by an authored `replace`: changed masked defaults must
not independently invalidate that task's semantic contribution. Ordinary physical
config-file/runtime inputs can still affect its full execution key separately.

#### C20 — Alias and inheritance failures validate surviving graphs

| Declarations | Expected |
| --- | --- |
| Two inferred `build` contributors, no explicit unqualified occupant | Ambiguous automatic alias error listing both qualified candidates |
| Explicit `build` aliases `frontend::build`; qualified frontend task extends `build` | Alias-aware inheritance self-cycle error |
| Aliases `a → b → a` | Alias cycle error; no executable alias nodes |
| Surviving alias to disabled/removed task | Missing-target error; no reinterpretation as a commandless task |
| Bad lower alias replaced by a valid normal declaration | Discarded target is not resolved, but original declaration shape must be valid |

#### C21 — Preserve each glob side; exclusions still win

```yaml
# authored base task cache
key:
  files:
    include: ["@project/src/**"]
    exclude: ["@project/src/generated/**"]
---
# authored child task cache, exclude side omitted
key:
  files:
    include: {append: ["@project/package.json"]}
```

**Expected:** includes `[@project/src/**, @project/package.json]`, excludes
`[@project/src/generated/**]`. Today's shared glob type fills the missing exclude
with an empty replacing value; do not preserve that loss in the new layer pipeline.
An explicit child `exclude: []` clears the exclude side; `include: []` clears only
the include side; `files: {exclude: {append: ["@project/tmp/**"]}}` retains the
base includes and appends the new exclude. Repeat without plugins.

For an inferred task, let activation defaults include `@project/package.json` and
the plugin append the same path to `key.files.exclude`. **Expected:** the baseline
include entry is retained, but the manifest is not a matched task-cache input
because exclusions win. Additive means pattern-entry accumulation, not guaranteed
file inclusion. Discovery reads of that manifest remain independently tracked for
inference invalidation. No implicit task-cache input bypass undoes a valid exclude.

#### C22 — Applied project settings are shared, defaults are activation-local

At one root, both `frontend` and `native` infer `build`, with no project cache
opinions. Explicit `build: {alias: "frontend::build"}` resolves the public-name
collision. `frontend` has `defaults.tasks.cache.enabled: true`; `native` has no
default and supplies task `cache.enabled: false`.

**Expected:** frontend build is enabled for caching; native build is disabled.
Now select an `apply` file only for frontend containing **project-level**
`cache: {enabled: true}`. That authored project-field contribution combines into
the shared effective project, and its tier beats native's plugin task opinion:
both tasks become cache-enabled. A named applied `tasks.build.cache.enabled`
instead targets only frontend's inferred task and leaves native unchanged.
Configuration inspection must distinguish these cases, not silently scope a
shared project setting by the file's originating activation.

#### C23 — Optional values and explicit empty operations are different

An inferred task has cache-file include `@project/package.json`, exclude
`@project/generated/**`, and plugin cache enablement `false`.

| Authored task patch | Expected |
| --- | --- |
| `cache: {}` | No task opinion invented; plugin enablement and both glob sides survive |
| `cache: {enabled: null}` | Existing optional-field null behavior supplies no replacement; plugin `false` survives, not deletion or `true` |
| `cache: {key: {files: {include: []}}}` | Include cleared, exclude retained; enablement unchanged |
| `cache: {key: {files: {exclude: []}}}` | Exclude cleared, include retained; enablement unchanged |
| `cache: {key: {files: {include: {append: []}}}}` | Explicit identity operation; no side cleared |

Retain these distinctions through task inheritance, project-to-task settings and
native/wire/cache round trips. Defaults are not deserialized into omitted fields.

#### C24 — Disabling caching prevents reads as well as writes

Seed a matching successful local or remote entry for `frontend::build`. Keep its
command and declared inputs unchanged but finalize `cache.enabled: false` through
the winning tier. Use a controllable store/digest fixture so incidental physical
config-file invalidation cannot conceal missing eligibility checks.

**Expected:** no artifact lookup/download/replay for that task, its ordinary
command executes, and no new execution-cache entry is persisted. A mock store
returning an unsolicited hit must not make the executor replay it. Unrelated
cache-enabled tasks still hit normally; persistent tasks remain cache-ineligible.
Run the same case for an explicit task. `--no-cache` keeps its existing distinct
write-only behavior; do not use that flag as a substitute for testing enablement.

#### C25 — Cached tasks with uncached dependencies

Uncached A executes before cache-enabled B, with B depending on A and no file
pattern of its own covering A's inputs. Seed B's prior cache entry, then change A's
tracked input.

| Case | Expected |
| --- | --- |
| A uncached by host fallback/plugin/`defaults`; B enabled by any tier | B is cache-ineligible: no lookup/replay/persist, so the stale entry is never used. One informational note per run; detail only in inspection/tracing |
| A explicitly `cache.enabled: false` and B explicitly `true` (authored/applied task or project tiers) | Planning error naming both tasks and provenance; unrelated runs not containing the edge still plan |
| A → B → C, with only A uncached | B and C are both ineligible |
| Commandless aggregate between cached tasks | Transparent: eligible only if its dependencies are |
| Persistent dependency | Treated as uncached |
| `with` co-scheduled uncached task | No effect; not an execution dependency |
| Write-only `--no-cache` | Zero sentinel never appears in a persisted key |
| Any demoted B | Result status is `demoted{direct_dependency, root_cause}`; deciding source of the uncached cause is inspectable; status is absent from the cache key and artifacts |
| A cached too | Ordinary behavior; a change to A's declared input changes B's key |

#### C26 — Application-file origins and effective project roots stay separate

The workspace configuration selects `./configs/javascript.omni.yaml`. That file
extends `./base/common.omni.yaml`, which patches an existing local `build` task:

```yaml
tasks:
  build:
    cache:
      key:
        files:
          append: ["@project/src/**", "@workspace/shared/**"]
```

**Expected:** the file reference resolves first to workspace file
`configs/javascript.omni.yaml`, then its nested `extends` resolves to
`configs/base/common.omni.yaml`, using each declaration's file origin. Applied at
root `packages/web`, the patterns refer to that project's `src/**` and workspace
`shared/**`, not either configuration directory. Reusing the same raw file plan at
`packages/api` points `@project` at `packages/api`, without changing either project
directory or reading inference from the configuration directories. Track both
config-file contents/closure and the effective root in the composition identity;
never cache a path-resolved applied plan under just its filename.

#### Promotion into executable tests

Record source layers, host identities and expected deciding sources separately from
the final effective projection. Every positive fixture needs layer inspection and
execution-graph assertions; failures need phase, field/root and bounded provenance
assertions, not brittle full error strings. Exercise cache-hit/live equivalence,
fresh/reused instances, and alias/exact/pattern selection through normal,
ignored-dependency and dependent planning paths where applicable. Keep this
specification and executable golden files synchronized once those tests exist.
