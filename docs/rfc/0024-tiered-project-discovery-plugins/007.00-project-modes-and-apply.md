## 7. Explicit configuration and composition

### 7.1 Project modes

No explicit file: the merged inferred layer is the project. An explicit file
defaults to `extend` and can control participation:

```yaml
# packages/web/project.omni.yaml
inference:
  mode: extend
  plugins: [frontend] # optional allowlist of already enabled workspace ids
name: web
tasks:
  "frontend::build": # qualified inferred task; see §7.4
    exec: pnpm run build:production
```

```yaml
# Fully handwritten: none of this root's inferred fields survive.
inference:
  mode: replace
name: web
tasks:
  build:
    exec: ./build.sh
```

`replace` bypasses all inference for this root, including plugin conflicts and
invalid inferred output. Explicit `extends` continues to work: it replaces
*inference*, not ordinary explicit inheritance. The `plugins` allowlist only
narrows activation and is invalid with `replace`; it cannot enable anything.
These controls belong to the concrete discovered file and are not inherited
from project bases. Explicit `base: true` continues to exclude a template from
the runnable project set, including when an ecosystem marker shares its root.

#### Standard host-managed `apply`

Make `apply` a standard host-managed `project_discovery` feature for native and
external plugins, not a built-in-specific settings language. Workspace-selected
application files are declared alongside activation `options`, illustratively:

```yaml
plugins:
  - source: builtin
    name: "@omni/javascript"
    apply:
      - ./configs/javascript-defaults.omni.yaml
```

Plugins provide inferred configuration, not shipped configuration-file defaults.
`apply` defaults to an empty list and contains only files explicitly selected by
workspace configuration, in application order. There is no automatic plugin-
bundled file list, inherited default-file list or separate default-file toggle.
The example's defaults file is workspace-authored configuration, not a file
distributed or selected by the plugin artifact.

Reuse explicit-file extension-graph traversal, path-origin tracking, raw-layer
replay and cycle validation for application files; never import inference from
their directories or flatten away collection operations. Track their contents
and extension closures in the discovery pass/cache dependencies. Apply these
layers to the originating activation's inference before combining activations,
and before ordinary explicit project bases/concrete fields.
Root-local replacement/base/allowlist exclusions cannot be bypassed by application.

Resolve workspace-authored `apply` file references relative to the configuration
file that declares them, not separately against every inferred project root.
Within an applied file's extension closure, resolve each `extends` using the
existing per-file path-origin and explicit-configuration loading rules. No plugin
artifact-relative default-file loading or plugin-authored automatic `apply` list
is introduced. Plugin code still cannot request arbitrary host configuration
loading through its output.

File-reference origins are distinct from project-relative settings inside the
layers. `@project/...` input/output settings continue to resolve against the real
inferred project root, and `@workspace/...` against the workspace root, not the
directory containing the defaults file. Applying a shared file never changes
the project's real `dir` or fabricates a project at the defaults file's directory.
Preserve both declaration/file origin and effective project-root context through
loading, replay, inspection and cache tracking.

Applied task keys refer to the originating activation's scoped inferred tasks,
not public aliases: local `build` customizes `frontend::build` when bound to
activation `frontend`. Only tasks established by that activation's inference are
eligible; application does not manufacture missing tasks or modify another
activation's tasks. Silently skip unmatched task patches by default, exposing the
reason in configuration inspection/debug tracing rather than routine warnings.
Malformed configuration still fails. Normal explicit project configuration runs
later and retains its ordinary ability to define new tasks.

Use this shared configuration syntax for inferred task inputs, outputs, cache
settings and other supported patches, avoiding a duplicate inline task-settings
language in plugin options. Keep options for ecosystem-specific inference choices.
Application task-wiring rules retain the agreed missing-inferred-script handling;
ordinary explicit references and surviving emitted direct references remain strict.

Evaluate this exception against the originating activation's inferred task set
at the root, before application and later explicit layers: ignore an unmatched
source task patch, and omit an unqualified own-task dependency rule whose target
was not inferred there. For JavaScript this includes absent or selection-filtered
scripts; for Cargo it uses the actual inferred task set. Apply the same rule to
`dependencies` and `with`, preserving the surrounding collection operation even
when all of its entries are omitted (an empty `replace` still replaces). Never
resolve an absent local target through an explicit task, a public alias or another
activation. This exception does not soften task `extends`, alias targets,
cross-project direct references or explicitly qualified targets. Once a reference
is retained, later removal of its target is a normal surviving-reference error
unless later composition also removes that reference. No ordinary explicit-file
or direct plugin-output reference acquires this conditional behavior.

Bind unqualified task references inside applied patches to the originating
activation, not to public unqualified tasks/aliases. With activation `frontend`,
an applied `test` dependency on `build` selects `frontend::build`; `^build` selects
that activation's upstream `build` tasks. Preserve this context through task
inheritance, per-file extension replay, project/task settings and cache restoration.
The same originating-activation default applies to unqualified task components in
cross-project references; object components remain raw and are not reparsed.
Changing a public alias or consumer activation id must not silently redirect
these local bindings.

Workspace-authored application files may deliberately select another activation
using explicit qualification (or the object `plugin` field), under the ordinary
reference-surface restrictions. This is explicit configuration wiring, not new
authority for plugin-emitted references. Such qualified cross-plugin targets are
strict: missing targets fail rather than being ignored as absent inferred scripts.
Existing-inferred-task eligibility still constrains the source patch; qualification
does not let the application define or modify another activation's task. Local
task-wiring rules retain missing-inferred-script handling, upstream missing tasks
retain their ordinary skip rule, and surviving direct references validate normally
after later explicit composition. No implicit public-alias fallback is introduced.

Applied files use standard collection validation and supported operation semantics,
including subtractive effects such as list/dictionary `replace`; they are not
decoded with the additive-only validator for plugin-emitted contributions. This
uses the workspace-selected files' ordinary supported field semantics. Reuse the ordinary configuration
language, not a second additive-only dialect for application files. This does not
relax the additive-only boundary on direct plugin output.

Replay operations at the applied layer's position. An inferred list `[a, b]`,
applied `replace: [c]`, then explicit `append: [d]` yields `[c, d]`. If the explicit
layer omits the field it retains `[c]`; explicit `prepend: [d]` yields `[d, c]`,
and explicit `replace: [d]` yields `[d]`. Earlier replacement discards accumulated
values, not later layers, and does not lock the field. Preserve original operations
through application-file extension traversal and subsequent project/task inheritance
rather than flattening replacement into a plain list. Task patches remain scoped
to the originating activation's eligible inferred tasks; unmatched-task filtering
does not convert collection operators into another operation or waive malformed
configuration validation. For shared project fields, these examples describe the
originating activation's accumulated value; later combination with other
activations still follows the conflict/additive rules below.

The host loads/interprets workspace-selected application files, not the guest
runtime. Their authored values retain handwritten interpretation semantics;
inherited inferred values retain plugin-origin restrictions, including literal
environment values ([§6.3](006.03-data-boundary-and-literal-values.md#63-data-boundary)). Applying a file or traversing its extension closure
cannot relabel unchanged inferred values as trusted handwritten expansion source.

Compose application layers within each activation first, in its declared `apply`
list order with each file's existing extension traversal order preserved. A
subtractive operation acts on that activation's accumulated contribution, never
as an instruction to erase another activation's values. Then combine the resulting
activation contributions under [§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts): disjoint values compose, compatible identical
values coalesce and conflicting shared fields require later explicit resolution.
Neither activation execution order nor the order in which their application files
finish loading selects a winner. For example, a workspace-selected file applied
to JavaScript inference may replace that contribution's project dependencies,
without erasing project dependencies contributed by Rust.
An ordinary explicit project/base layer, applied after combination, retains its
existing authority to replace the combined collection globally.

Keep original application/task layer plans and binding/trust metadata wherever
later task inheritance or project-to-task settings require operation replay.
Per-activation composition is not permission to turn an operation-bearing task
patch into a flattened reusable inheritance base. Direct plugin-output validation
still happens before application, so applied replacement cannot repair malformed
or forbidden emitted output.
