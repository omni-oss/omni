### 6.4 Hook, claim and query schemas (`project_discovery` v0)

This section specifies the draft logical contract for `project_discovery` API `0.x`. It defines
shapes, validation and invariants; it is encoding-neutral. The wire encoding and
binding mechanism belong to the Wasm ABI decision (§10); native handlers use the same
typed values without serialization. YAML below is notation, not a promised transport.
Defaults for numeric limits are calibrated under [§8.4](008.03-tier-specific-enforcement.md#84-tier-specific-enforcement);
here limits are named, finite and host-owned. Fixed-schema records reject unknown
fields; typed dictionaries (options, metadata, argument maps and task names) allow
their declared key/value domain rather than treating user keys as record fields.
All decoded maps reject duplicate keys and all values obey their bounds at the
boundary ([§6.3](006.03-data-boundary-and-literal-values.md#63-data-boundary)).
Check duplicates before conversion to a generic JSON/map value can discard them;
do not inspect arbitrary opaque `StateValue.bytes` as if they were host records.
This is a `0.x` experimental contract (§14): shapes may change between minors until
the stabilization release.

#### Common types

| Type | Definition |
| --- | --- |
| `WorkspacePath` | A normalized Linux-style path ([Path normalization](#path-normalization)): UTF-8, `/`-separated, relative to the workspace root, never absolute, and bounded by `max_path_bytes`. Compared byte-for-byte. Validated for containment; never a filesystem handle |
| `ProjectRootId` | A normalized `WorkspacePath` identifying a root. Eligibility is a separate host-validated property: an assigned source must be eligible for that activation/stage; a described claim root or unresolved edge target does not acquire that property just by having an id |
| `DeclaredRelativePath` | Normalized Linux-style relative path metadata, interpreted against an explicit declaration base. Redundant separators and `.` segments are removed, but `..` segments are retained without cancelling adjacent components or resolving symlinks. `.` denotes the declaration base; not a workspace-root identity |
| `ArtifactRelativePath` | Normalized `/`-separated entry/module/provenance path within an acquired artifact directory, not within the workspace. No parent traversal or absolute/native prefix; validate containment separately during byte capture |
| `InputPath` | A concrete rooted `@project/...` or `@workspace/...` input address, with a normalized relative suffix; `@project` uses the assigned source root. Resolve and authorize it before access; store tracked evidence using normalized `WorkspacePath` identities |
| `PathPattern` | An existing rooted include/exclude glob expression, not a concrete file identity. Preserve glob syntax and escaping; do not canonicalize it as a path or expand it during decoding |
| `LocalTaskName` | Raw ecosystem task name: non-empty UTF-8 without NUL, at most `max_task_name_bytes`. Not reference syntax and never pre-escaped or qualified ([§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases)) |
| `StateValue` | `{version: u32, bytes: bytes}`, at most `max_state_bytes`. Opaque to the host; never a claim |
| `StateUpdate` | One-key tagged object: `{keep: {}}`, `{replace: StateValue}` or `{clear: {}}`. Omission means `keep`; decoding never confuses omitted state with `clear` |
| `Notice` | `{code: snake_case string (≤64), severity: info\|warning, message: string (≤max_notice_bytes), path?: WorkspacePath}`. Failures are errors, not notices. At most `max_notices_per_response`; sanitized and redacted by the host |
| `Cursor` | Opaque host-issued paging token bound to the issuing activation, stage, API, snapshot, authorization and normalized query. Invocation-local, never a persistent cache identity |

Record field aliases such as task `if`/`enabled` or `command`/`exec` refer to one
field: supplying both aliases is a duplicate-field error, not two operations.
Command/claim map values do not become executable or trusted merely because a
schema permits their keys.

#### Path normalization

Every new discovery path value stored or exchanged uses normalized Linux-style
`/` separators on every platform. This includes project-root identities, path-valued
claim fields, host state-partition keys, provenance locations, inference-cache
records/indexes, tracked inputs and discovery inspection. It does not make every
string in an opaque `StateValue`, a command operand, URL or task-reference grammar
into a path, nor change existing task-cache formats or remote transport.

Use distinct validated types for concrete workspace identities, declaration-relative
metadata and glob expressions. Native absolute `Path`/`PathBuf` values remain
implementation details of OS access, containment and source acquisition; never use
their platform-specific rendering as a discovery identity. Shared constructors
convert OS paths to workspace-relative identities; typed parsers validate already
normalized protocol/cache paths without accessing the filesystem or proving target
existence. Neither path parsing nor Linux-style normalization grants I/O authority.

A normalized concrete `WorkspacePath`:

- uses `/` as the only separator; on Windows, `\` separators are converted at the OS
  boundary and drive letters, UNC prefixes and verbatim (`\\?\`) prefixes are removed
  after the path is proven to lie inside the workspace;
- is relative to the workspace root: no leading `/`, no drive or scheme, and the root
  itself is exactly `.`;
- has no empty segments (`a//b`), no `.` segments (`./a`), no `..` segments, no
  trailing `/`, and no NUL;
- contains no `\` byte in any segment. A file or directory whose name contains a
  backslash cannot be a root or a stored path, and fails with an actionable diagnostic
  rather than being silently rewritten. Reject an unsupported name when it is
  selected/described/accessed, not merely because an unrelated ignored file exists;
- takes its casing from the directory walk (the filesystem's actual names), never from
  user text or case folding, and is compared byte-for-byte. Two paths differing only by
  case are distinct values; a case-insensitive filesystem that yields both is an error
  to report, not to merge.

Normalization is idempotent. Wire, native and inference-cache boundaries reject
non-normalized concrete identities rather than repairing them. An edge target can
be a well-formed identity before it exists; target existence is checked only after
composition. Directory walks establish actual casing for existing selected roots;
a guessed path's spelling is not evidence of target identity on a case-insensitive OS.

Containment is a separate access-time obligation ([§12.4](012.00-rust-trait-sketches.md#124-host-services-plugin-side-view)).
Do not resolve symlinks once and assume later reads remain safe. Recorded identities
and captured-input evidence must agree with the containment-safe reader and final
pass revalidation. An authored `../shared` declaration stays relative metadata
until an authorized resolver establishes a concrete workspace target.

`DeclaredRelativePath` uses `/` separators and has no drive/prefix, leading slash,
NUL or backslash. Preserve parent components: `a/../b` stays `a/../b`, not `b`,
because cancellation could change symlink-dependent meaning. It never instructs
the host to read or fetch anything. Unsupported absolute/external path declarations
follow the adapter's documented source-form policy rather than being stripped into
fake workspace-relative paths. Path patterns keep the shared glob model, including
meaningful escaping and literal `!`; never globally replace every backslash in a
glob or a task reference. Runtime filesystem access converts normalized identities
to native paths at its boundary, not throughout composition.

`invocation_id` and attempt ids appear in tracing only. They are not semantic
inputs, are never cache-key inputs and cannot influence normalized output.

#### Envelope

Every hook call carries a host-built envelope; a plugin never chooses these values.

```yaml
envelope:
  protocol: "0.1.0"           # negotiated envelope version
  capability: {name: project_discovery, api: "0.1.0"}
  hook: infer_roots           # validated against the declared hook set
  invocation_id: "…"          # tracing only
  options: {…}                # activation options, schema-validated by the host
  negotiated_features: []
  limits: {…}                 # effective finite limits for this invocation
  workspace_state: StateValue?   # absent initially; read-only after on_workspace
```

A response is `{ok: <hook result>}` or `{error: ProjectDiscoveryCapabilityError}`; any other shape,
including a result for a different hook than requested, fails validation. Output
for roots not assigned to the invocation is rejected, never ignored.

#### Hook requests and results

Per-root requests carry only assigned roots and bounded relevant state, not the whole
workspace ([§6.1](006.01-claims-and-queries.md#snapshot-access-not-whole-workspace-copies)).
`results` are a list with one entry per `root`, not a mapping that could discard
duplicate keys before validation. Their order is not significant. Every scheduled root-oriented invocation requires **exactly one result
per assigned root**; missing, duplicate and unassigned results fail the stage.

| Hook | Request (beyond envelope) | Result |
| --- | --- | --- |
| `on_workspace` | `scopes` (static declared input scopes), `markers` | `{workspace_state?: StateUpdate, notices?: [Notice]}`. Initial `keep`/`clear` leave no seed; `replace` supplies it. No later hook writes workspace state |
| `filter_candidates` | `roots: [{root, markers: [WorkspacePath], state?: StateValue}]`, authorized bounded index-query handle | `results: [{root, disposition: kept\|declined, extra_inputs?: [InputPath], state?: StateUpdate, notices?: [Notice]}]`. `extra_inputs` narrow/select declared scopes; they never widen scopes or become untracked reads |
| `infer_roots` | `roots: [{root, markers: [WorkspacePath], state?: StateValue}]`, `bindings: {slot → claim handle}` | `results: [{root, outcome: InferenceOutcome, state?: StateUpdate, claims?: [Claim], notices?: [Notice]}]`; tagged outcome below |
| `resolve_dependencies` | `roots: [{root, state?: StateValue}]`, claim/catalog query handles ([queries](#claim-and-catalog-queries)) | `results: [{root, dependencies?: [RootRef], state?: StateUpdate, notices?: [Notice]}]`; omitted dependencies mean no new edges, not removal of inferred edges |
| `observe` | bounded final-project and authorized claim/catalog handles, restricted to its accepted roots that survive as final runnable projects | `{notices?: [Notice], inspection?: [{root?: ProjectRootId, key, value}]}`. No state, projects or edges; scalar inspection entries use host byte/count budgets |

```yaml
# InferenceOutcome is exactly ONE of these tagged objects:
accepted: {project: ProjectContribution}
# OR:
declined: {}
```

`state` defaults to `{keep: {}}`; `claims` and `notices` default to empty lists.
Omitted inference `project` is invalid for `accepted`; `{accepted: {project: {}}}`
is the explicit accepted-empty case. `outcome: accepted`, `outcome: false`, a
separate sibling `project`, both outcome keys, and any declined payload fields
are invalid. These rules apply identically to native types, wire and cache data.

Normative rules:

- A `declined` outcome has no `project`; its presence is a boundary error, not ignored.
  An `accepted` outcome may carry an empty `project`, which still undergoes final
  composition and validation. State, claims and notices never imply acceptance.
- A hook is scheduled only if declared and registered; omitting `infer_roots` is not
  acceptance ([§6.1](006.00-hooks-and-lifecycle.md#candidate-disposition-and-hook-eligibility)).
- A declined root may still publish bounded supporting claims; they grant no project,
  resolution eligibility or edge.
- Concrete input/root identities receive structural/containment validation, and
  input access receives the separate access-time check. Declaration-relative
  descriptors and glob expressions use their own typed validation, not a false
  assertion that `../shared` is a normalized workspace identity. All payloads are
  counted against limits before expansion into host structures.
- Results for a root must not depend on its batch neighbors or invocation order.

#### Tracked reads and expected absence

Only `infer_roots` receives the following logical service; native handlers borrow
bounded captured bytes and external adapters transfer them under the same limits.

```yaml
inputs.read:
  root: packages/web             # must be assigned to this invocation
  path: "@workspace/pnpm-lock.yaml"
result:                         # exactly one successful alternative
  found: {path: pnpm-lock.yaml, bytes: <captured bytes>}
# OR: result: {missing: {path: pnpm-lock.yaml}}
```

Authorize the concrete address before reporting existence. `missing` is a tracked
successful observation, not an error to make every absent lockfile fatal; an
adapter decides whether its supported inference needs that file. Record both
positive and negative observations in the owning root's evidence, even when the
host shares byte/miss storage. Creation, deletion or content changes invalidate
reuse and participate in final pass revalidation. A missing record names the
normalized requested address without pretending an existing filesystem object
was canonicalized.

Permission denial, non-regular/unsupported input kinds, allocation/byte budgets,
unreadable files and other I/O failures are typed host failures, never `missing`.
Containment-safe access must not block indefinitely on a FIFO/device. Account for
all attempted reads, including misses and failed attempts, before allocation or
deduplication can hide their work. A guest cannot downgrade a fatal host failure
to an empty/declined successful root result. Expected absence remains the explicit
exception, not an automatic manifest-only recovery from malformed/unreadable inputs.

#### `ProjectContribution`

A contribution is a restricted subset of project configuration, decoded with the
additive collection validator ([§7.3](007.02-multiple-plugins-and-conflicts.md#73-multiple-plugins-and-conflicts)):
plain lists and `append` only for lists; plain mappings and `merge` for mappings;
`prepend`, `replace` and positional `merge` are rejected.
These restrictions concern operation-bearing configuration collections, not argv
or fixed record lists. Strictly check an operator envelope before shared decoding
can drop its sibling fields. Reuse the presence-aware configuration field types
from `omni_configurations`, not a separate merge language invented by this table.

```yaml
project:
  name: "@company/shared"        # optional here; final composition must supply a name
  description: "…"
  meta: {…}
  env: {vars: {KEY: "literal value"}}   # always literal; never expanded
  cache:                          # project-level task-cache fields (§7.1 tiers)
    enabled?: bool
    key: {defaults?: bool, files: [..], env: [..]}
    output: {files: [..], logs?: bool}
  dependencies: [RootRef]         # project edges
  output_logs: failed             # ordinary display-only output-log configuration
  tasks:
    <LocalTaskName>: TaskContribution
```

Initial project field inventory: `name`, `description`, `meta`, `env`, `cache`,
`dependencies`, `output_logs`, `tasks`. Reuse each ordinary field's schema and
layer presence semantics, with literal inferred environment values, typed root
references and the additive collection validator. Omitted `name` is not filled
by a generic host basename rule; an adapter may supply a justified name, otherwise
later explicit layers must supply it before final validation.

`CacheContribution` reuses ordinary `CacheConfiguration` layer fields:
`enabled?`, `key.defaults?`, `key.files`, `key.env`, `output.files`, `output.logs?`.
File fields use existing rooted include/exclude `MergeGlobConfig` forms with
`PathPattern` entries and the selected additive list validators; they are not
concrete `WorkspacePath` lists. This plugin-output inventory is distinct from
the narrower activation `defaults` surface, which permits only `enabled`,
`key.files` and `key.env`. All omitted cache subfields remain absent until
project/task settings and the origin-aware enablement tiers have been resolved.

Excluded: `file`, `dir`, project `base`, project-file `extends`, `inference`,
`redact` and activation/security policy. Redaction is host/workspace policy, not
guest authority to weaken it. `output_logs` is ordinary display behavior, not a
security grant, and is not excluded merely because it is display-only. Aliases are
host-managed; workspace-authored aliases remain available under
[§7.4](007.03-task-scoping-aliases-and-selectors.md#74-host-owned-task-scoping-and-aliases).

```yaml
TaskContribution:
  base?: bool                    # declaration-local task template, not project base
  exec?: Command
  retry_exec?: Command
  args?: {key: json value}
  dependencies?: [TaskRef]
  with?: [TaskRef]
  description?: string
  enabled?: bool | expression    # ordinary `if` alias; evaluated for selected execution
  interactive?: bool
  persistent?: bool
  extends?: [LocalTaskName]       # same activation, post-composition resolution
  env?: {vars: {KEY: "literal"}}
  cache?: CacheContribution      # same fields as project.cache, with presence preserved
  meta?: {…}
  output_logs?: OutputLogsConfiguration
  max_retries?: u8
  retry_interval?: duration string
```

The ordinary task `enabled`/`if` execution condition is distinct from
`cache.enabled`, and does not run during discovery. Task-level `base` and `extends`
retain the ordinary declaration-local/template and same-activation inheritance
rules; templates get neither executable nodes nor automatic aliases. The previous
draft's exclusion of conditions, task templates and output-log settings was not
an agreed policy and is removed. Task `redact`, aliases and host/security fields
remain excluded. Plugin-origin `env.vars` and string data used by expressions
retain their literal interpretation through composition and inheritance; command
expressions themselves retain their normal selected-execution semantics
([§6.3](006.03-data-boundary-and-literal-values.md#literal-command-operands)).

`Command` logically supports a shell-style command expression or an argv plan.
In the illustrative `{argv: [Operand]}` plan, `Operand` is `{literal: string}` (carried
unchanged, never templated or env-expanded) or `{expr: string}` (an authored-style
expression, rarely needed by adapters). The exact spelling and the lowering into
`CommandConfig` are pending the literal-operand specification; adapters use only
`literal` operands for ecosystem-derived values.

```yaml
RootRef: {project_root: WorkspacePath}

TaskRef:                          # never selects another activation or a public alias
  - {kind: own, task: LocalTaskName}
  - {kind: upstream, task: LocalTaskName}
  - {kind: project_root, project_root: WorkspacePath, task: LocalTaskName}
```

`TaskRef` has no `plugin` field in plugin output; the host binds every reference to the
emitting activation ([§7.2](007.01-layer-order-and-merge-semantics.md#task-dependency-references-and-explicit-project-syntax)).

#### Claims

A **claim** is a typed, evidence-derived assertion published about a root. Plugins
publish only supported omni-defined types; unknown types and arbitrary payloads are
rejected. Common rules:

The `type` enum is scoped to the negotiated `project_discovery` capability; the
short identifiers below do not create an unnamespaced global claim registry or
independent claim-version domains. Cache interpretation includes capability/API
and any defined compatibility mapping.

- The host records the publisher (activation and assigned root) and the tracked
  inputs it read; plugins do not set or forge them.
- Described roots are `WorkspacePath`s that need not be candidate roots (a claim
  about an explicit-only or replacement root is allowed), but are never proof of a
  runnable project or a valid dependency target.
- Exact duplicates from one publisher coalesce. Distinct payloads with the same key
  are kept as distinct claims unless a rule below says they conflict.
- Publishing is bounded by `max_claims_per_root`, `max_claim_bytes` and an aggregate
  claim count; cached and live claims face identical limits.

Bound supplied entry counts/decoded bytes **before** coalescing duplicates as well
as logical published claims afterward. A flood of equal claims is not free host
work. Charge actual parsing/validation/memory; do not invent plugin execution
charges on a cache hit whose canonical records already contain coalesced claims.

```yaml
# package_identity
type: package_identity
package_system: npm | cargo      # versioned enum; unknown values are rejected
name: string                     # ≤ max_package_name_bytes; ecosystem name, not an omni name
project_root: WorkspacePath
version?: string                 # only if known from tracked inputs; ≤ max_version_bytes
```

Here and below, publisher means the host-attributed `(activation, assigned root)`
pair, not the described root or a consumer's slot alias. Conflict rule: one
publisher cannot publish two `package_identity` claims with the
same `(package_system, project_root)` and different `name` or `version`. The same
`(package_system, name)` at different roots is valid and returned as an ambiguous match.

```yaml
# workspace_membership — one relationship per claim
type: workspace_membership
package_system: npm | cargo
workspace_root: WorkspacePath    # '.' for the workspace root
member_root: WorkspacePath       # may equal workspace_root (root package)
```

Key: the full triple. Membership never creates a project, edge or write authority.

```yaml
# package_dependency — declaration plus explicit resolution
type: package_dependency
package_system: npm | cargo
source_root: WorkspacePath
dependency_name: string
requested:
  package_name?: string          # actual target package when declaration uses an alias
  version?: string               # ecosystem requirement text, never parsed by the host
  source?: SourceDescriptor
resolution:                      # tagged; consistency enforced at every boundary
  - {kind: workspace, project_root: WorkspacePath}
  - {kind: external}
  - {kind: unresolved, reason?: string}   # reason ≤ max_notice_bytes
```

```yaml
SourceDescriptor:
  - {kind: registry, registry?: string}
  - {kind: path, base: WorkspacePath, path: DeclaredRelativePath}
  - {kind: workspace}
  - {kind: git, url: string, rev?: string, branch?: string, tag?: string, subdir?: DeclaredRelativePath}
```

Validity: `requested` may have `version`, `source` or both (a Cargo `version` plus
`path` stays both). At most one of `rev`/`branch`/`tag`. `resolution.kind: workspace`
requires `project_root` established from tracked evidence; `external` and
`unresolved` carry none. A name match alone is never evidence. Which `package_system`
accepts which `source.kind` is a per-system table in the adapter specification; the
host rejects combinations a system does not declare. Descriptors never cause a fetch
or execution. No usage/optional/condition fields exist in v0; adapters keep that
classification privately ([§6.1](006.01-claims-and-queries.md)).

For `kind: path`, `base` is the workspace-relative directory of the manifest that
declared the path, not necessarily the package's `source_root` or the assigned
publishing root. For example, workspace-inherited Cargo metadata can have a
different declaration base. The producer supplies it from tracked declaration
evidence; the host validates containment/shape but does not resolve it through I/O
at claim decoding. `path: ../shared` is retained as relative metadata, never copied
into `resolution.project_root`. Resolve a concrete target separately using authorized
evidence. A Git `subdir` is repository-relative metadata, not a local workspace path.

#### Claim and catalog queries

Queries are bounded host calls over a frozen snapshot, authorized by the consumer's
bindings and declared claim types ([§6.1](006.01-claims-and-queries.md#claim-visibility-and-grants)).

```yaml
claims.query:                    # bulk: up to max_queries_per_call
  queries:
    - type: package_identity
      scope: {kind: slot, slot: javascript} # alternatives: {kind: self}, {kind: all}
      where: {name: "@company/shared"}   # exact-match selectors only
      page: {limit: ≤max_page_size, cursor?: Cursor}
result:
  results:                       # same order as queries
    - items:
        - publisher:
            view: {kind: slot, slot: javascript} # or {kind: self}
            root: packages/shared               # assigned publishing root
          claim: Claim
      next?: Cursor
```

| Claim type | Allowed `where` selectors (all optional, exact match, ANDed) |
| --- | --- |
| `package_identity` | `package_system`, `name`, `project_root` |
| `workspace_membership` | `package_system`, `workspace_root`, `member_root` |
| `package_dependency` | `package_system`, `source_root`, `dependency_name`, `resolution.kind`, `resolution.project_root` |

- Omitted `scope` means `{kind: all}`: the union of permitted self/bound producer
  views for this type and stage, not all enabled activations. For a slot, the type
  must be in consumer `consumes` ∩ producer `publishes`. Self reads require a
  supported type the activation declared in `publishes`, not a redundant `consumes`
  declaration. Unsupported types/selectors or malformed combinations are
  `invalid_query`; a supported but undeclared type or unbound slot is
  `claim_access_denied`. Either error fails the entire bulk call without partial
  results. Denial never becomes an empty result.
- If `all` yields no authorized view for the requested type, deny the query;
  declarations/bindings cannot be inferred from an empty data set. If at least one
  declared authorized view exists but contains no matching claims, return a
  successful empty page. Validate authorization and the whole bulk request before
  serving pages so a denied later query cannot leak earlier partial results.
- A well-formed exact selector for an absent root/name returns no match, not a
  target-existence error. That is distinct from an explicit request outside an
  authorized stage/root view, which is denied. Limits/denials cannot be swallowed
  by returning successful empty output from the hook.
- Self views during inference contain only stage-start committed data, never
  current sibling-batch publications. They cannot create an order-sensitive
  intra-activation producer loop. Resolution sees the complete validated inference
  snapshot; predecessor handles during inference see only bound completed producers.
  Own private state remains limited to the workspace seed and assigned-root state
  partitions, not an arbitrary cross-root state-query service.
- Returned ownership is `(producer activation, assigned publishing root)`;
  `publisher.view` names that producer via `self` or a bound slot, not a host id
  the guest must discover. Multiple slots bound to the same producer do not duplicate
  a claim in an `all` query: render via `self` if applicable, otherwise the smallest
  authorized slot name in UTF-8 byte order. An explicitly slot-scoped query uses that
  slot. Distinct publishing roots remain distinguishable, even for equal payloads.
- Order by the type's typed payload tuple, followed by view (`self` before slots,
  slots in UTF-8 byte order), then publishing root. Tuple field order is specified
  below, not serializer field order, hash-map iteration or producer completion order.
  Exact duplicates with the same owner occur once; conflicting package identities
  from one owner fail inference rather than selecting a page/order winner.
- Cursor validation binds activation, stage, negotiated API/mapping, frozen snapshot
  identity, effective grant set, normalized type/scope/selectors, page limit and next
  position. A stale/foreign cursor, changed query or changed limit is `invalid_cursor`.
  The host enforces bounded token sizes and cursor resources; guests cannot forge a
  new scope or position. A new invocation receives fresh handles/cursors, even if
  its semantic snapshot is equivalent. Persistent cache dependencies use the
  authorized semantic view fingerprint, never token bytes.
  Plugins must not embed handle/cursor/invocation tokens in semantic output or
  returned state; treat them only as invocation-local query continuations. Private
  memory reuse never makes an expired token valid in a later invocation.
- Each page has `1 <= limit <= max_page_size`; zero is `invalid_query`. The host
  may pack fewer than `limit` whole items to fit the page-byte cap, but a non-final
  page must make progress and return `next`. One item that cannot fit is a typed
  size-limit error, not an endless empty page or partial claim. Return `next` iff
  further authorized results remain, never a silent prefix or a total count over
  denied data. Exhausting aggregate query-work/returned-byte budgets is an error,
  not successful truncation. Native handlers use the same rules.

Payload sort tuples (lexicographic, strings by UTF-8 bytes, absent optional values
before present ones; no case folding or ecosystem version ordering):

| Type | Tuple |
| --- | --- |
| `package_identity` | `(package_system, project_root, name, version?)` |
| `workspace_membership` | `(package_system, workspace_root, member_root)` |
| `package_dependency` | `(package_system, source_root, dependency_name, requested, resolution)` |

Nested request order is `(package_name?, version?, source?)`; source variants sort
as `registry`, `path`, `workspace`, `git`, followed by their listed field order
(`registry?`; `base, path`; no fields; `url, rev?, branch?, tag?, subdir?`).
Resolution variants sort as `workspace`, `external`, `unresolved`, followed by
`project_root`, no fields, or `reason?` respectively. These are deterministic query
ordering rules, not a selection-precedence or resolution-evidence rule.

```yaml
catalog.roots:                   # roots and selection status only; no ecosystem data
  page: {limit, cursor?}
result:
  items:
    - root: ProjectRootId
      explicit: none | project | base      # explicit file kind at this root
      inference_mode: extend | replace
      approved_candidate: bool             # host-approved marker candidate
      accepted_by_self: bool               # true or false; never a visibility grant
  next?: Cursor
```

`resolution.project_root` is a selector only for workspace resolution; an explicit
contradictory `resolution.kind: external|unresolved` is `invalid_query`. Dotted
selector names are the fixed vocabulary above, not an arbitrary JSON-path language.

The resolution catalog is a frozen host view of selected candidate and explicit
roots, not just the caller's accepted roots. It can include declined/aggregate,
replacement and base roots with their actual status; `accepted_by_self` is false
where appropriate. Neither a catalog row nor another activation's acceptance
grants source participation or proves final runnability. Final target validation
still follows explicit composition. Return roots in normalized UTF-8 byte order;
the same cursor rules apply. This metadata catalog contains no package claims,
other activation state, inferred fragments or effective configuration.
`approved_candidate` means at least one selected enabled-plugin marker at that
root, not marker ownership for every activation. An explicit-only catalog row can
have `approved_candidate: false` and still be a valid explicit project. Use the
root's status and the activation's admission rules, not that boolean alone.

Observation uses a separate bounded final-project view, including final fields,
tasks and edges for this activation's accepted roots that survive as runnable
projects. Its catalog/claim views are narrowed to the same subjects: identity
`project_root`, membership `member_root`, dependency `source_root`. References to
other roots in a visible relationship do not expose those projects' configuration
or grant expansion of the view. An unqualified page lists only authorized subjects;
an explicit subject outside that view is denied. Resolution-only participants
have no accepted inference roots and thus no nonempty observation view initially.

Observation is a distinct declared-hook information-sharing surface: its agreed
root-limited **composed** view can contain authored settings and other contributors'
final fields at those roots. Claim bindings alone neither grant nor constrain that
separate view. Do not describe observation as sandboxed to the plugin's filesystem
read scope or only its own contributed fields. It exposes configuration, not the
process environment, loaded dotenv values, rendered commands, invocation arguments,
credentials from host services or another plugin's private state. It must not call
the command-enabled environment/task-context extraction paths to construct its
snapshot. Read-only observation is not permission to execute authored expressions.

#### Errors

`ProjectDiscoveryCapabilityError` has `kind`, bounded `message`, optional typed
`root`/`path`, and kind-specific detail. The
host maps it into the shared diagnostic envelope with activation, hook and root
provenance. Plugins return these kinds; the host emits the others itself.

| Kind | Origin | Meaning |
| --- | --- | --- |
| `malformed_input` | plugin | A tracked input is syntactically invalid |
| `unsupported_input` | plugin | A relevant input format or version is unsupported |
| `contradictory_evidence` | plugin | Supported evidence disagrees about a relevant resolution |
| `ambiguous_evidence` | plugin | Evidence needed for correctness is ambiguous with no policy to choose |
| `internal` | plugin | An unexpected plugin failure |
| `claim_access_denied`, `read_denied`, `invalid_cursor` | host | Authorization or paging failures |
| `input_unavailable` | host | Unreadable/non-regular input or other I/O failure; never an expected missing observation |
| `invalid_query` | host | Malformed type/scope/selectors, unsupported query vocabulary or invalid page arguments |
| `limit_exceeded` | host | A finite budget was exhausted (reports which limit) |
| `invalid_output` | host | The response violated this schema, coverage or ownership rules |
| `timeout`, `cancelled` | host | Deadline or cancellation |

Host limit details include a machine-readable limit id, scope (root, transport,
activation or command), unit and configured/observed values with checked counters;
the host owns those facts. Distinguish an attributable **aggregate transport-size
overflow** from logical root limits, guest memory/fuel failure, timeouts and
malformed output. Only that trusted transport-overflow classification may trigger
§8.1's deterministic split. A plugin-provided message/kind cannot request a retry,
expand budgets or forge a host provenance classification.

Failures abort the attempt/stage and never become empty success. The existing
host-controlled aggregate-size splitting and default-off whole-pass input-change
restarts remain the only defined recoveries; they preserve aggregate work/deadline
accounting and publish nothing from failed attempts. Cache corruption/misses and
best-effort inference-cache writes have their separate §8.2 policy; do not confuse
them with plugin/input failure recovery. Diagnostics redact path/data details
without dropping the machine-readable classification used by host scheduling.

#### Resolution-only participation

A plugin that only implements `resolve_dependencies` declares participation
explicitly in its capability entry; omitting `infer_roots` does not imply it.

```yaml
capabilities:
  - name: project_discovery
    api: ">=0.1.0, <0.2.0"
    hooks: [resolve_dependencies]
    participation:
      mode: resolution_only
      roots: all_approved             # or marked; explicit selection, not a read grant
```

Validated at load: `mode: resolution_only` requires `resolve_dependencies` and
forbids `infer_roots`; `roots` is required in that mode. Ordinary inference mode
remains the default and grants resolution only after that activation's acceptance.
Omitted hooks, static markers or queries are not an alternate participation mode.
Initialization/filter/observation hooks may still be declared, subject to their
ordinary permissions; observation of resolution-only roots stays empty as above.

Admission and filtering follow one timing model:

1. Before any inference, form the preliminary host root set from selected explicit
   files and selected marker candidates in the shared walk. For `marked`, intersect
   with **this activation's selected marker hits**; an adjacent ignored/excluded
   marker does not count. For `all_approved`, use the preliminary set without
   requiring a marker from this activation. Neither mode enrolls arbitrary paths.
2. Apply root-local `base`, `replace` and plugin-allowlist exclusions before invoking
   this activation's optional filter. It receives these preliminary roots and the
   authorized index, without file-content or producer-inference access. A declined
   result is binding for the pass; an omitted filter keeps the remaining set.
   Filter state belongs only to that activation/root and creates no project.
3. After the complete inference phase, intersect the kept preliminary set with
   roots established explicitly or accepted by at least one inference activation.
   An all-declined root without an explicit project drops out, even if claims or
   filter state exist. Preserve the exclusions and original filter dispositions;
   do not invoke a new post-inference filter or revive a declined root.
4. Assign the resulting source roots to resolution batches. The hook may update
   only its own state and emit edges from those sources. It cannot create projects,
   alter another activation's state, read manifests during resolution or bypass
   final runnable-source/target validation after composition.

Claim-query grants still require bound producers and declared types in either
mode. `all_approved` is source selection, not workspace-wide claim authority.

#### Example exchange (illustrative)

An aggregate Cargo workspace root declines and publishes membership claims; its member
is accepted.

```yaml
# infer_roots request (@omni/rust), assigned roots: ".", "crates/core"
# response; omitted state means keep, omitted notices means []
ok:
  results:
    - root: "."
      outcome: {declined: {}}
      claims:
        - {type: workspace_membership, package_system: cargo, workspace_root: ".", member_root: crates/core}
    - root: crates/core
      outcome:
        accepted:
          project:
            name: core
            tasks:
              build:
                exec: {argv: [{literal: cargo}, {literal: build}, {literal: --manifest-path}, {literal: Cargo.toml}, {literal: --package}, {literal: core}]}
      claims:
        - {type: package_identity, package_system: cargo, name: core, project_root: crates/core, version: "0.3.0"}
```

#### Contract conformance cases

These are schema/view expectations for future native, wire and cache tests, not
claims that a runtime validator exists today. Every rejected pass publishes no
new reusable records/notices and executes no tasks.

| Case | Input or operation | Expected |
| --- | --- | --- |
| H01 | One assigned root `p`, `{root: p, outcome: {accepted: {project: {}}}}` | Structurally valid; final project composition still must succeed |
| H02 | `{root: p, outcome: {declined: {}}, claims: [valid supporting claim]}` | Valid decline; no project or resolution eligibility |
| H03 | Declined payload contains `project`, or a sibling top-level `project`, or both outcome tags | `invalid_output`, even if explicit layers would replace it |
| H04 | Assigned `[p, q]`, results contain `[p]`, `[p, p]` or `[p, q, other]` | `invalid_output`; no map overwrite or implicit default result |
| H05 | Normalized `ProjectRootId` strings `p/q`, `.`; decoded `p\\q`, `p/../q`, `./p`, `/p`, `p//q`, `p/` | First two valid, remaining strings rejected, never silently repaired |
| H06 | OS path `C:\\repo\\p\\q` under workspace `C:\\repo` versus `/repo/p/q` under `/repo` | Constructors yield `p/q` after verified containment, not native prefixes |
| H07 | Path descriptor `{base: packages/web, path: ../shared}` | Valid relative metadata, not automatic root `packages/shared` or permission to read it |
| H08 | Task `base: true`, condition `enabled: false` or ordinary `output_logs` | Structurally permitted normal fields; no alias for a template, no discovery-time condition execution |
| H09 | Inference consumer queries current sibling-batch claims through `self` | No current-stage data is exposed; reordering batches cannot change the view |
| H10 | Consumer type not declared, unbound slot or forbidden observation subject | `claim_access_denied`, never `items: []` |
| H11 | Unknown selector, zero page limit, malformed scope or selector kind | `invalid_query` |
| H12 | Query page token reused with another activation, snapshot, predicate or page limit | `invalid_cursor`; no partial result |
| H13 | Two bound slots select one producer; two publishing roots emit equal claims | `all` returns one row per actual owner/payload, with deterministic slot rendering; no per-slot duplication |
| H14 | Two roots have equal package-system/name/version | Stable multiple matches, no guessed local edge |
| H15 | A resolution-only `all_approved` root is filter-declined or `replace` | No resolution assignment, even if another activation accepts it |
| H16 | A kept resolution-only candidate has no explicit project and all inference declines | Drops from resolution; supporting claims/state cannot restore it |
| H17 | A selected explicit-only root has no activation marker | Eligible under `all_approved`, not under `marked`, subject to exclusions |
| H18 | Observation asks for the final config of a root the activation did not accept | Denied; visible edge references are not a wider config grant |
| H19 | Authorized `inputs.read` of an absent optional lockfile, then the file is created | Tracked `missing` success initially; dependent cache reuse invalidated after creation |
| H20 | Same address is denied, unreadable, a FIFO/device or over a byte/read budget | Typed host failure, never `missing` or manifest-only success |
| H21 | Supported type in `all` has no authorized view versus a declared authorized view with zero rows | First is `claim_access_denied`; second is successful empty output |
| H22 | Host reports aggregate transport overflow versus guest reports `limit_exceeded` in a message | Only trusted host classification can permit bounded size splitting; neither attempt publishes partial data |
| H23 | Arbitrary valid argument/metadata key versus unknown fixed-record field or duplicate `if`/`enabled` aliases | Dynamic key valid under its type/bounds; unknown/duplicate field rejected before generic-map conversion |
| H24 | Page-byte cap packs fewer than requested items, then one item exceeds the cap by itself | First page returns a progressing cursor; oversized single item errors, never an endless empty page |

#### Remaining schema work

Numeric defaults/counter definitions for every named limit; per-`package_system`
tables of valid source kinds, renamed-package rules and version/name grammars;
bounded index/final-project query payloads behind the scoped handles; the final
`Command` operand spelling; wire encoding (D3); and executable validators/
fixtures for every shape above. Fixed record-list and operation-bearing field
schemas must be emitted from the same field inventory. The cases above and
[§7.5's composition fixtures](007.04-composition-golden-fixtures.md#75-composition-golden-fixtures)
are test specifications, not passing implementation tests or a frozen SDK.
